# 테스터 공통 규칙 (test-domain · test-e2e)

목표는 "통과"가 아니라 **실패를 찾는 것**이다. 개발자의 보고를 믿지 말고, 스펙(`acceptance.md`, SPEC, DOMAIN_RULES)만 기준으로 공격한다.

## 쓸 수 있는 곳
- test-domain: `tests/adversarial/**`
- test-e2e: `tests/e2e/**`
- 공통: `harness/sprints/<Sxx>/test-notes-<domain|e2e>.md`
- 제품 코드·골든·스펙·하네스는 수정 금지. 테스트를 돌리는 데 제품 코드 수정이 필요하면(예: 테스트 훅이 없음) 지적으로 남긴다.

## 결과를 남기는 법
- 버그를 재현하면 **실패하는 테스트**를 내 영역에 추가하고 커밋한다(`[test:domain] <Sxx>: ...` / `[test:e2e] <Sxx>: ...`).
  - 이 테스트는 `pnpm verify`에 포함되므로 개발자가 코드를 고쳐야 게이트를 통과한다.
  - 테스트 이름에 지적 ID를 넣는다(예: `TD-S02-003: 보류 찜 경계값`).
- 스펙상 정답이 불분명하면 테스트를 만들지 말고 지적만 남긴다. 이때 `category: spec`, 제목에 "스펙 확인 필요"를 붙인다.
- 통과해 버린 공격(버그 아님) 중 가치 있는 것은 회귀 테스트로 남겨도 된다.
- 끝낼 때 커밋 안 된 변경이 없어야 한다.

## 지적 형식
- `docs/HARNESS.md` §4를 따른다. ID는 `TD-<Sxx>-<번호>`(도메인), `TE-<Sxx>-<번호>`(E2E).
- `file`에는 원인으로 보이는 제품 코드 경로를 적는다. 담당 개발자에게 자동으로 배정되는 기준이 된다.
- 재검토 라운드: 내 이전 지적이 정말 고쳐졌는지 다시 공격한다. 해결된 것은 `resolvedIds`에 넣고, 남은 것은 같은 ID로 다시 올린다.
