# SMS3 수용 기준 — 문자·입금 알림 자동 받기

- 스프린트: SMS3 · spec ID: **ORD-13**(새 — 받는 약속 C-01~C-07), **PAY-02**(새), ORD-08(넣는 `sms` 이벤트), PAY-01(입금 확인), DAT-06
- 규칙: DOMAIN_RULES **R-26** 문자 읽기(골든 `tests/golden/parser/sms-text.yaml`), DEPOSIT_RULES **DP-9** 은행 알림 읽기(골든 `tests/golden/deposit/notice.json`)·DP-1 원천 `PHONE`·DP-5 "먼저 보는 것"·DP-8 낱말·DP-INV-6~8
- 결정: **D-SMS3-01~D-SMS3-14**, **D-DEP2-01~D-DEP2-07** (`docs/DECISIONS.md` "문자·입금 알림 자동 받기 (SMS3 자율 결정)"), D-036(단순하게), D-APP-22·D-APP-23(읽기는 서버)
- BASE = `harness/sprints/SMS3/BASE`(3b403c44)
- 개발 영역 순서: **core → device → server → web**. 테스트: **domain**(`tests/adversarial/sms3/**`), **e2e**(`tests/e2e/sms3/**`). 사용성 검토 있음.
- 태그: `[core]` dev-core(`packages/core`), `[device]` dev-device(`packages/mobile-*` — 앱 알림 읽기 네이티브 모듈), `[server]` dev-server(`apps/server`), `[web]` dev-web(`apps/web`·`apps/mobile` 화면), `[domain]` test-domain, `[e2e]` test-e2e, `[ux]` 사용성 검토.
- 판정 엔진 규칙(R-1~R-25)·엔진 골든은 바꾸지 않는다. 넣는 것은 지금의 `sms` 이벤트, 적는 것은 지금의 `settlement.payment`.

## 골든 상태 (스프린트 시작 때)

- `parser/sms-text.yaml`(suite `sms-text`, 사례 129)은 코어 러너가 suite를 알기 전까지 **읽기 오류**다 — 허용 목록으로 가리지 않는다(README "러너가 읽는 범위"). dev-core가 러너에 suite를 더하면 사라진다.
- `deposit/notice.json`(kind `notice`, 사례 30 — G-DEP-201~230)은 서버 입금 골든 시험이 모르는 `kind`라 실패한다. dev-server가 `readBankNotice`와 시험의 `notice` 분기·파일/사례 합계 고정값을 더하면 사라진다.

## 범위 밖

- 문자 답장 보내기, 카카오톡 등 메신저 알림, 아이폰 은행 앱 알림(아이폰은 다른 앱 알림을 읽을 수 없다), 문자 본문으로 옵션·수량 읽기(D-036), 연습 도구 `/_try/sms-test`(SMS2)와 잇기, 은행 알림으로 자동 환불·되돌리기, 은행 표 밖 은행의 자동 확인, 안드로이드 문자 수신 권한(READ_SMS).
- 실제 휴대폰·실제 은행 알림 확인은 HG-SMS3(사용자 확인 필요 표) — 이번엔 가짜 알림·가짜 요청으로 시험한다.

## 수용 기준

### 문자 읽기 R-26 (core)

**AC-SMS3-01** [core] 골든 그대로
- Given 골든 `parser/sms-text.yaml`의 문서 6개·사례 129개
- When 코어 러너(`pnpm golden`)가 suite `sms-text`를 코어 `parseSmsText({ from, text }, { parseMode, multiNumber, maxNumber })`로 돌린다(`from`을 적지 않은 사례는 `"010-1234-5678"`)
- Then 모두 통과, `out`에 없는 키는 결과에도 없다(README `sms-text` 줄). 러너는 `sms-text`가 아닌 suite에 `from` 키가 있으면 읽기 오류다
- 확인: 골든

**AC-SMS3-02** [core] 예외 없음·결정성
- When 임의 글(제어 문자·서로게이트 짝 잃은 글·10만 자·이모지 연속)과 임의 `from`(숫자만 40자리·`+82`만·`null`)을 넣는다
- Then 예외 없이 다섯 모양 중 하나, 같은 입력은 같은 결과, `memo`는 늘 한글 음절 2~10자이고 숫자를 담지 않는다
- 확인: 단위 + [domain] 속성 시험

### 은행 알림 읽기 DP-9 1~7 (server)

**AC-SMS3-03** [server] 골든 그대로
- Given `deposit/notice.json` 사례 30(G-DEP-201~230)
- When 서버 입금 골든 시험이 `readBankNotice(in)`을 돌린다(TZ를 바꿔도)
- Then 모두 `out`과 깊은 같음. 그 시험의 파일 수·사례 수 합계 고정값에 `notice` 30이 더해진다
- 확인: 단위(골든)

**AC-SMS3-04** [server] 예외 없음
- When 본문 1,000자 임의 글, `title`·`from` `null`, 금액 모양 수천 개
- Then 예외 없이 결과 하나, 입금·입금 취소의 `amount`는 1~100,000,000 정수
- 확인: 단위 + [domain] 속성 시험

### 받는 입구 C-02·C-04 (server)

**AC-SMS3-05** [server] 받기 토큰
- Given 판매자 A가 설정에서 토큰 t1을 만들었다
- When `POST /api/inbox/messages`를 머리글 없이 / `Bearer 엉터리` / 판매자 B의 토큰으로 / t1으로 보낸다
- Then 앞 둘은 401 `TOKEN_INVALID`, B의 토큰은 B의 것으로만 처리(A의 방송·입금에 아무것도 없음), t1은 200. 토큰을 다시 만들어 t2가 되면 t1은 401. "끄기" 뒤엔 t2도 401
- And DB에는 토큰 원문이 없다(해시만). t1로 다른 API(`/api/broadcasts` 등)를 부르면 401
- 확인: 단위

**AC-SMS3-06** [server] 요청 모양
- When `messages` 21건 / `channel: "MMS"` / `id` 65자 / `device` 31자 / `text`가 숫자 / 본문에 모르는 키
- Then 400 `BAD_REQUEST`, 그 요청의 어떤 메시지도 처리되지 않는다(하나라도 틀리면 전부 안 함)
- When `text` 1,500자 Then 앞 1,000자만 읽는다(1,001번째 뒤의 `775`는 읽지 않는다)
- When `messages: []` Then 200 `{ results: [], filters: { skipWords, bankApps } }` — `skipWords`는 R-26 3 목록 9개 그대로, `bankApps`는 DP-9 1 표의 패키지 9개
- 확인: 단위

**AC-SMS3-07** [server] 응답에 읽은 결과가 없다
- Given 실제 방송 중
- When 휴대폰 번호의 `775`, 휴대폰 번호의 `안녕하세요`, 은행 대표번호의 입금 알림, `(광고) 775`를 한 요청으로
- Then `results`는 각각 `SAVED`·`IGNORED`·`SAVED`·`IGNORED`이고 그 밖의 키(찜·입금·번호)는 없다
- 확인: 단위

**AC-SMS3-08** [server] 한도
- When 같은 판매자가 1분에 121번째 메시지를 보낸다 Then 429 `TOO_MANY`, 그 요청은 처리하지 않는다. 1분 뒤 같은 id로 다시 보내면 처리된다
- 확인: 단위(가짜 시계)

**AC-SMS3-09** [server] 받은 시각
- `receivedAt`이 D-SMS2-02 모양(ISO·오프셋 없는 KST·숫자 초/밀리초)이면 그 시각, 없음·못 읽음·서버 시각과 24시간 넘게 차이면 서버 도착 시각을 문자찜 받은 시각·DP-9 `receivedAt`으로 쓴다
- 확인: 단위(표 시험, AC-SMS2-01~03과 같은 값)

### 가르기 C-05 (server)

**AC-SMS3-10** [server] 네 갈래
- Given 실제 방송 b1 중, 15번 판매 중
- When (가) `APP`·`com.kakaobank.channel`·제목 `입금 14,000원`·본문 `이수진` (나) `SMS`·`1588-9999`·`[KB] 홍길동 입금 14,000` (다) `SMS`·`010-2222-3333`·`15 김영희` (라) `SMS`·`1600-0000`·`[KB] 홍길동 입금 14,000` (마) `SMS`·`1600-0000`·`15` (바) `SMS`·`010-2222-3333`·`[KB] 홍길동 입금 14,000`
- Then (가) 휴대폰 알림 입금(믿음) (나) 휴대폰 알림 입금(믿음) (다) 15번 문자찜 `문자찜(김영희)` (라) 휴대폰 알림 입금 확인 필요 `UNTRUSTED_SOURCE` (마) `IGNORED`(DP-9 `NONE`, 찜 없음) (바) 입금이 아님 — R-26으로 읽어 15번 찜이 생기지 않는다(번호 없음 → 찜 아님 → `IGNORED`)
- 확인: 단위 + [e2e]

**AC-SMS3-11** [server] 앱 알림 표 밖
- When `APP`·`com.kakao.talk`·`입금 14,000원 보냈어` Then 입금 확인 필요 `UNTRUSTED_SOURCE`(DP-9 믿지 않음). `APP`·`com.kakao.talk`·`775` Then `IGNORED`(앱 알림은 문자찜이 되지 않는다)
- 확인: 단위

### 같은 것 합치기 C-06 (server)

**AC-SMS3-12** [server] 같은 id·같은 문자
- Given 휴대폰 번호의 `15`(id `a1`)를 받아 15번 문자찜이 됐다
- When 같은 id `a1`을 다시 / id `a2`로 같은 보낸 곳·같은 본문·`receivedAt` 30초 뒤 / id `a3`로 90초 뒤
- Then `DUPLICATE`·`DUPLICATE`·`SAVED`. 찜은 앞 둘에서 늘지 않는다(a3은 같은 구매자의 같은 상품이라 엔진에서도 새 찜이 없다 — R-4)
- And id `a1`을 25시간 뒤 다시 보내면 `DUPLICATE`가 아니다(24시간)
- 확인: 단위

### 방송 창 (server)

**AC-SMS3-13** [server] 실제 방송만, 끝난 뒤 10분
- Given 방송 없음 When 휴대폰 번호의 `15` Then `IGNORED`, 아무것도 저장되지 않는다(본문·번호 모두)
- Given 리허설만 진행 중 Then `IGNORED`
- Given 실제 방송 b1이 20:00:00에 끝났다 When 20:09:59에 `15` Then b1의 15번 문자찜(끝난 방송의 늦은 문자찜). When 20:10:01 Then `IGNORED`
- Given 방송이 없어도 When 은행 대표번호 입금 알림 Then 입금으로 저장된다
- 확인: 단위(가짜 시계)

### 문자찜 넣기 (server)

**AC-SMS3-14** [server] 바로 넣기
- Given b1 중, 15·16번 판매 중
- When `010-1234-5678`의 `15 16 홍길동`, `receivedAt` 20:01:05
- Then `sms` 이벤트 두 개(15·16), 받은 시각 20:01:05, 구매자는 R-11(그 번호의 문자 구매자 — 이벤트엔 불투명 키·뒤 4자리 5678만), 메모 `홍길동`, 표시 `문자찜(홍길동)`. 5초 기다림 없음. 요청 번호 `inbox-<id>-15`·`inbox-<id>-16`
- And 이벤트·DB·로그 어디에도 본문 `15 16 홍길동`과 번호 원문이 없다
- 확인: 단위 + [e2e]

**AC-SMS3-15** [server] 판매 중이 아니면 넣지 않음
- When `15`인데 15번이 없음 / `READY` / `CLOSED` Then 찜 없음, 문자 확인 목록에 `NOT_ON_SALE` 카드("15번은 지금 판매 중이 아니에요"). 1등이 차고 대기 자리가 있으면 넣는다(대기)
- 확인: 단위

**AC-SMS3-16** [server] 취소 요청은 승인 뒤
- Given 010-1234-5678 손님이 15번 1등
- When 그 번호의 `15 취소` Then 찜은 그대로, 문자 확인 목록에 취소 요청 카드
- When 판매자가 "승인" Then 그 손님의 15번 찜이 취소된다(엔진의 시청자 취소와 같은 결과 — 대기 1순위 승계 R-8). When 찜이 없는데 승인 Then "취소할 찜이 없어요", 엔진 기록 없음
- When "무시" Then 기록 없음, 카드 사라짐
- 확인: 단위 + [e2e]

**AC-SMS3-17** [server] 확인 필요 고르기
- When `010-…`의 `15 있나요?`(`UNCLEAR`, 후보 [15]) Then 카드에 번호 단추 15. "넣기" Then 15번 문자찜(그 보낸 번호·메모 없음)
- When 연락처 이름 `홍길동`에서 `15`(`NO_NUMBER`) Then 카드 "이름만 와서 누가 보냈는지 몰라요", 넣으면 메모 = 보낸 이름 `홍길동`인 새 문자 구매자(번호 없음)
- When 옵션 방송에서 `15 홍길동`(`OPTIONS`) Then 카드에서 넣으면 지금 옵션 문자찜 입력과 같은 옵션 고르기를 거친다
- 확인: 단위 + [e2e]

**AC-SMS3-18** [server] 본문 보관
- 확인 필요·취소 요청 카드의 본문만 암호화해 두고, 처리(넣기·승인·무시)하면 바로, 처리하지 않으면 방송이 끝나고 24시간 뒤 지운다. 넣은 문자찜·거름·찜 아님은 본문을 저장하지 않는다
- 확인: 단위(DB 조회, 가짜 시계)

### 은행 알림 저장 DP-9 8·9 (server)

**AC-SMS3-19** [server] 믿을 입금 자동 확인
- Given 실제 범위 김영희 묶음 남은 금액 14,000원(이름 후보 김영희, 판매 시각 20:00)
- When 신한 대표번호 `신한10/31 20:05 110-***-123456 입금 14,000 잔액 1,028,000 김영희`(앞선 신한 잔액 없음)
- Then 원천 "휴대폰 알림" 입금 #n, 자동 확인됨, 메모 `자동 입금 확인 · 입금 #n`(DP-6 그대로)
- 확인: 단위 + [e2e]

**AC-SMS3-20** [server] 믿지 않는 곳
- When AC-SMS3-19와 같은 글이 `1600-0000`에서 Then 입금은 저장되지만 확인 필요 `UNTRUSTED_SOURCE`, 미리 고른 후보 = 김영희 묶음, 자동으로 적지 않는다. 확인 목록을 다시 열어도 `ONE_MATCH`로 바뀌지 않는다
- 확인: 단위

**AC-SMS3-21** [server] 잔액 이어짐
- Given 신한 앞 알림 잔액 1,014,000(20:01)
- When 20:05 입금 14,000·잔액 1,028,000 Then 이어짐(1,014,000 + 14,000) → DP-5 그대로
- When 대신 잔액 1,030,000 Then 확인 필요 `BALANCE_GAP`
- When 출금 알림(잔액 1,009,000, 20:03)이 사이에 있었으면 Then 앞 잔액은 1,009,000 → 1,028,000은 `BALANCE_GAP`, 1,023,000이면 이어짐
- When 다른 은행(KB) 잔액은 신한 이어짐에 쓰지 않는다
- 확인: 단위

**AC-SMS3-22** [server] 외부 키
- When 같은 입금(신한, 같은 시각·금액·잔액)을 문자와 앱 알림으로 받는다 Then 입금은 하나(`bal:` 키), 두 번째 응답도 `SAVED`(처리함 — 입금은 늘지 않음)
- When 잔액 없는 같은 내용 알림 둘(다른 id) Then 입금 둘, 두 번째는 확인 필요 `POSSIBLE_DUPLICATE`(DP-5 1)
- 확인: 단위

**AC-SMS3-23** [server] 출금·입금 취소·읽지 못함
- 믿을 출금 Then 입금 없음, 잔액 기록(은행·시각·잔액)만. 금액·가맹점 저장 없음
- 믿을 입금 취소 Then 입금 확인 화면 위 은행 알림 "입금 취소 알림이 왔어요: 14,000원 홍길동. 이 입금을 확인했다면 되돌려 주세요", 엔진 기록 없음, 입금 상태 그대로
- 믿을 읽지 못함 Then "읽지 못한 은행 알림이에요. …" 줄(은행 이름·받은 시각), 본문 없음
- 믿지 않는 곳의 출금·입금 취소·읽지 못함, `NONE` Then 아무것도 저장되지 않는다(`IGNORED`)
- 은행 알림 줄은 "확인했어요"로 닫히고, 30일 뒤 사라진다
- 확인: 단위 + [e2e]

**AC-SMS3-24** [server] 휴대폰 알림 원천
- 토큰을 처음 만들면 원천 `PHONE` "휴대폰 알림"이 하나 생긴다(다시 만들어도 하나). 원천을 끄면 은행 알림은 `IGNORED`, 손님 문자는 그대로 받는다
- 확인: 단위

**AC-SMS3-25** [server] 로그·DB에 본문 없음 (DP-INV-8, C-07)
- When AC-SMS3-10~23의 요청을 모두 보낸다 Then 서버 로그 전체와 DB 덤프에 알림 본문·제목, 보낸 번호 원문, 토큰 원문이 없다(확인 필요·취소 요청 카드의 암호화된 본문은 평문으로 보이지 않는다)

### 앱 알림 읽기 (device)

**AC-SMS3-26** [device] 무엇을 읽어 보내나
- Given 알림 읽기 권한이 켜졌고 서버가 준 `filters`가 저장돼 있다
- When 가짜 알림: 기본 문자 앱의 문자(보낸 곳·본문), `com.kakaobank.channel` 알림, `com.kakao.talk` 알림, 기본 문자 앱의 `[Web발신] 인증번호 123456`
- Then 앞 둘만 `POST /api/inbox/messages`로 간다(문자는 `channel: "SMS"`·`from` = 알림의 보낸 곳, 은행은 `channel: "APP"`·`from` = 패키지·`title`·`text`). 메신저·인증번호 문자는 보내지 않는다
- And `filters`를 받기 전이면 문자만 보낸다
- 확인: 단위(가짜 알림)

**AC-SMS3-27** [device] 다시 보내기
- When 서버가 응답하지 않음·5xx·429 Then 같은 `id`로 큐에 두고 다시 보낸다(429는 1분 뒤). 앱을 껐다 켜도 큐는 남는다(최대 200건, 넘으면 오래된 것부터 버리고 개수만 기억). 401이면 보내기를 멈추고 "받기 토큰을 다시 넣어 주세요"
- And 같은 알림이 고쳐 다시 뜨면(안드로이드 알림 갱신) 같은 `id`
- 확인: 단위
