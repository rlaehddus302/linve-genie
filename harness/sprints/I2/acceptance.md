## A. 가게 설정 (STL-04 "설정", D-I2-02)

### AC-I2-01 [server] 가게 설정 저장·조회
- 근거: STL-04 "가게 이름(설정)·입금 계좌 안내(설정)", D-I2-02, SYS-02, DAT-06
- Given 로그인한 판매자
- When 가게 설정을 읽거나 고친다
- Then 값은 가게 이름(1~30글자 — 아래 가게 이름 규칙), 입금 계좌(은행 1~20글자 · 계좌번호 = 숫자·`-`·공백만 1~30글자이고 숫자 하나 이상 · 예금주 1~20글자) 또는 계좌 없음(셋 다 빈 값), 안내 문장(0~100글자)이다. 길이는 앞뒤 공백을 지운 뒤 센다. 제어 글자(U+0000~U+001F·U+007F)가 있으면 거절한다.
- Then 계좌 세 칸 중 일부만 적으면 저장하지 않고 "은행·계좌번호·예금주를 모두 적거나 모두 비워 주세요."를 칸별 문제와 함께 돌려준다. 모르는 칸·형식이 틀린 값도 저장하지 않는다(칸별 문제).
- Then 가게 이름은 지금의 판매자 이름(로그인 정보·화면 위에 보이는 가게 이름)과 같은 값이다 — 고치면 그 이름도 바뀐다.
- Then **가게 이름 규칙 하나** (I2 마지막 감사 SA-I2-009·TD-I2-004, D-I2-18·D-I2-15): 운영자 계정 만들기 명령, 시작 마법사·설정의 `PUT /api/shop {name}`, 설정의 `PUT /api/shop` 다섯 칸 모두 — 앞뒤 공백을 지운 뒤 1~30글자(코드 포인트), 제어 글자·서식 글자·U+2028·U+2029·짝 없는 서로게이트 거절, 문장 "가게 이름은 1~30자로 적어 주세요." 하나(칸 `name`). 계정 만들기 명령은 31글자 이름이면 이 문장으로 거절하고 아무것도 만들지 않는다(그림 문자 하나 = 1글자 — 그림 문자 30개 이름은 만들어진다). 예외: (가) 지금 저장된 이름과 같은 이름(앞뒤 공백만 다름)은 길이·글자를 다시 따지지 않는다 — 이 결정 전에 만든 31~50자 이름의 판매자가 계좌만 고쳐 저장된다. 한 글자라도 고친 이름은 새 이름 규칙. (나) 복구·가져오기(AC-I2-62)는 파일의 가게 이름을 그대로 넣는다.
- Then 휴대폰 번호 검사를 하지 않는다: 계좌번호 `010-1234-5678-90`, 안내 문장 `문의 010-1234-5678`이 저장된다(판매자 자신의 공개 정보, 이벤트 로그 밖 — D-I2-02).
- Then 다른 판매자의 가게 설정은 읽지도 고치지도 못한다(세션의 판매자만). 서버 로그에 가게 설정 값이 남지 않는다.
- Then 저장한 값이 그 뒤에 만드는 확인서(AC-I2-10·11)와 포장 라벨(AC-I2-34)에 나온다. 백업·내보내기에 들어간다(AC-I2-60).
- 확인: 서버 시험(PGlite), 로그 포착 시험

### AC-I2-10 [server] 한 사람 확인서 — 데이터·PDF·PNG
- 근거: STL-04, STL-05, D-206, D-I2-01, D-I2-02, NFR-07
- Given 판매자의 범위(날짜 — 실제 또는 리허설)와 구매자 ID(합쳐진 구매자 ID여도 된다 — 지금의 구매자로 푼다)
- When 그 묶음의 확인서 데이터(JSON)·PDF·PNG를 요청한다
- Then 서버는 그 범위의 **지금** 엔진 상태, 가게 설정(AC-I2-01), 범위의 리허설 여부, 서버 시계의 지금 시각으로 `packages/documents`의 `buildReceipt`를 부르고, PDF는 `renderReceiptPdf`, PNG는 `renderReceiptPng`로 같은 확인서 데이터·같은 내장 글꼴(Pretendard)로 그린다. 데이터 응답은 확인서 데이터 그대로다. 문서 패키지 밖에서 금액을 다시 계산하지 않는다.
- Then 금액·줄은 AC-P2-20~22와 같다: G-ENG-201과 같은 판매(같은 날 1부·2부, 닉네임 변경, 확정 뒤 가격 변경, 할인, 부분 입금, 직접 수령 문자찜)를 서버 쓰기 경로로 넣은 범위에서, 가게 설정 = `초록다육`·`농협`·`302-9988-7766-11`·`김판매`·`입금자명은 닉네임으로 적어 주세요`, 서버 시계 = `2026-10-18T14:30:00Z`이면 `UC_A`의 확인서 데이터는 AC-P2-20의 값과 같다(문자 구매자의 구매자 ID는 서버가 만든 ref라 다를 수 있다 — 이름·끝자리·금액이 같다).
- Then 같은 범위 상태·같은 구매자·같은 서버 시각이면 PNG·PDF 바이트가 같다(두 번 요청해 비교).
- Then 품목이 없는 묶음·그 범위가 모르는 구매자 → 파일 없이 "구매 내역이 없어 확인서를 만들 수 없어요." 줄 가격 합 ≠ 코어 상품 합계(AMOUNT_MISMATCH) → 파일 없이 문서 패키지의 문장 + 서버 경보(개인정보 없이). 없는 날짜·다른 판매자의 범위 → 날짜 조회와 같은 404.
- Then PDF `application/pdf`, PNG `image/png`. 내려받기 이름(Content-Disposition — UTF-8 `filename*`와 ASCII 대체 이름)은 D-I2-01(`확인서-2026-10-18-길동이.pdf`, 리허설이면 `리허설-확인서-…`). 이름 다듬기 뒤 헤더에 줄바꿈·따옴표·`/`·`\`가 들어가지 않는다(닉네임 `a"b\r\nSet-Cookie: x`·`../../x`로 시험). 모든 응답 `Cache-Control: no-store`.
- Then 요청 주소에는 날짜·구매자 ID만 들어간다(전화번호·메모 없음). 이 요청은 아무것도 기록하지 않는다(이벤트·발송함·포장 기록 그대로).
- 확인: 서버 시험(PGlite, 가짜 시계, PDF 글자 뽑기·PNG 머리 해석은 `packages/documents` 시험 도구를 써도 된다)

## D. 포장·배송 (STL-08, D-I2-05~D-I2-07, LBL-02)

### AC-I2-30 [server] 포장·배송 상태 계산
- 근거: STL-08, D-I2-05, R-11, R-12
- Given 실제 범위(날짜)와 그 범위의 포장 기록
- Then 묶음(지금의 구매자 X, 날짜)의 상태는 **X의 ID로 적힌 기록만** 차례로 읽어 정한다: 처음 = 포장 대기, 포장 완료(품목 목록 P) → 포장됨(P), 포장 취소 → 포장 대기, 배송 완료(송장) → 배송됨(P, 송장), 배송 취소 → 포장됨(P). 보이는 말: 포장 대기 = `포장 대기`, 포장됨 = 지금 품목 집합이 P와 같으면 `포장 완료`·다르면 `포장 다시 확인`, 배송됨 = 같으면 `배송 완료`·다르면 `배송 뒤 바뀜`.
- Then 지금 품목 = 코어 `getSettlement(X, 날짜)`의 품목마다 (상품 ID, 상품 키 `<방송 ID>/<지금 번호>`) 쌍의 집합이다(I2 마지막 감사 TD-I2-005, D-I2-19 — 상품 ID는 코어 `getProduct`의 `id`, 번호를 바꿔도 그대로이고 재생하면 같은 값). 포장 완료 기록 P는 그때 담은 품목의 쌍이고, 쌍 집합이 같을 때만 "같다"다 — 상품 키가 같아도 다른 상품이면, 같은 상품이어도 번호가 바뀌었으면 다르다. 다시 확인·배송 뒤 바뀜이면 응답에 "새로 담을 것"(지금 있고 P에 없는 쌍 — 방송 제목·지금 번호·품종)과 "뺄 것"(P에 있고 지금 없는 쌍 — 방송 제목·포장 때 번호·그 상품의 지금 품종)을 담는다. 상품 ID가 없는 기록(이 결정 전 형식)은 어떤 지금 품목과도 같지 않다.
- Then 서버 시험으로 고정할 흐름(실제 범위 하나, 방송 b1):
  1. UC_A가 15·28번 1등 → `포장 대기` → 포장 완료([b1/15, b1/28]) → `포장 완료`.
  2. 31번에 UC_A가 1등이 됨(직접 배정) → `포장 다시 확인`(새로 담을 것 31번).
  3. 포장 완료([b1/15, b1/28, b1/31]) → `포장 완료` → 배송 완료(송장 `123456789012`) → `배송 완료`.
  4. 28번 UC_A 찜 취소(승계로 다른 사람 1등) → `배송 뒤 바뀜`(뺄 것 28번). 28번을 이어받은 구매자의 묶음은 `포장 대기`.
  5. 다른 묶음 UC_B 7번 포장 완료([b1/7]) 뒤 7번을 70번으로 번호 변경 → R-10·D-056대로 UC_B의 7번 찜은 무효(`REJECTED(RENUMBERED)`, 승계 없음)라 UC_B 품목이 없다 → UC_B `포장 다시 확인`(뺄 것 7번, 새로 담을 것 없음 — 품목이 없어도 기록이 있어 목록에 남는다). (SA-I2-005 — 두 단계로 고침, D-I2-19)
  5b. 이어서 70번에 UC_B를 직접 배정해 1등 → UC_B `포장 다시 확인`(새로 담을 것 70번 · 뺄 것 7번 — 같은 상품이어도 번호가 바뀌었다). 포장 완료([b1/70]) → `포장 완료`.
  6. UC_C(포장 완료)에 sms:s1(품목 있음)을 합침 → UC_C `포장 다시 확인`. sms:s1 ID에 적힌 기록은 목록에 나오지 않는다. 떼어 내면 UC_C는 `포장 완료`로, sms:s1 묶음은 자기 기록대로 돌아온다.
  7. UC_A 15번 가격을 입금 전 찜까지 바꿈(`UNPAID_CLAIMS`) → 상태 그대로(상품 ID·키가 같다). 품종을 바꿔도 그대로.
  8. (TD-I2-005) UC_D 9번 1등 → 포장 완료([b1/9]) → 9번을 90번으로 번호 변경(UC_D 찜 무효) → 빈 9번에 다른 상품(품종 `라울`)을 새로 등록하고 UC_D를 직접 배정 → UC_D의 상품 키 집합은 {b1/9}로 포장 때와 같지만 다른 상품이라 `포장 다시 확인`(새로 담을 것 9번 `라울` · 뺄 것 9번 — 그 상품의 지금 품종). `포장 완료`로 보이지 않는다.
- Then 포장 목록 = 그날 품목이 있는 지금의 구매자 묶음 + 품목이 없어도 자기 ID에 포장 기록이 있는 지금의 구매자 묶음(뺄 것을 알리려고 — 상태는 기록대로 `포장 다시 확인`·`배송 뒤 바뀜`). 합쳐진 구매자는 따로 나오지 않는다.
- Then 리허설 범위에는 포장 상태·명령이 없다(날짜 조회처럼 404).
- 확인: 서버 시험(PGlite)

### AC-I2-31 [server] 포장·배송 명령
- 근거: D-I2-05, D-I2-06, DAT-02, DAT-05, NFR-03, SYS-02
- When 포장 완료(날짜, 구매자 ID, 담은 품목의 상품 키 목록, 요청 번호) · 포장 취소 · 배송 완료(송장번호 선택) · 배송 취소를 보낸다
- Then 기록 전에 검사하고, 기록이 저장(커밋)된 뒤에만 성공 응답과 실시간 알림을 보낸다(NFR-03). 성공 응답에 새 상태(AC-I2-30 모양).
- Then 받는 경우(그 밖은 아무것도 기록하지 않고 쉬운 오류, 응답에 지금 상태):
  - 포장 완료 ← `포장 대기`·`포장 다시 확인`, 보낸 품목 집합 = 지금 품목 집합(품목 1개 이상). 다르면 "그 사이에 구매 내역이 바뀌었어요. 다시 확인해 주세요."(지금 품목과 함께). `배송 완료`·`배송 뒤 바뀜`이면 "이미 배송 완료로 적었어요. 먼저 배송 완료를 취소해 주세요."
  - 포장 취소 ← `포장 완료`·`포장 다시 확인`.
  - 배송 완료 ← `포장 완료`, 또는 `배송 완료`에서 송장번호만 다를 때(송장 고치기 — 새 기록). `포장 대기`면 "포장 완료 뒤에 배송 완료로 적을 수 있어요.", `포장 다시 확인`·`배송 뒤 바뀜`이면 "구매 내역이 바뀌었어요. 다시 포장 확인부터 해 주세요."
  - 배송 취소 ← `배송 완료`·`배송 뒤 바뀜`.
  - 이미 그 상태인 같은 명령(같은 품목의 포장 완료를 `포장 완료`에서, 같은 송장의 배송 완료를 `배송 완료`에서)은 성공이고 새 기록이 없다.
- Then 송장번호: 공백·`-`를 뺀 숫자 8~20자리, 저장은 숫자만(`1234-5678-9012` → `123456789012`). 아니면 "송장번호는 숫자 8~20자리로 적어 주세요." 휴대폰 번호 모양(R-1 글 칸 판단 `containsPhoneRun` — 예 `01012345678`)이면 "전화번호처럼 보여요. 송장번호를 확인해 주세요." 빈 값·없음 = 송장 없음.
- Then 같은 요청 번호를 다시 보내면 처음 결과다(기록 하나). 기록마다 누가(로그인 계정)·언제(서버 도착 시각 UTC)가 남고, 기록은 고치거나 지우지 않는다(덧붙이기만 — 복구 명령 AC-I2-62만 예외).
- Then 구매자 ID는 그 날짜의 **지금의 구매자**여야 한다(합쳐진 구매자 ID·그 범위가 모르는 구매자 → "구매자를 다시 확인해 주세요."). 리허설 범위·다른 판매자의 범위 → 404. 상품 키 형식이 틀리면 입력 오류.
- Then 포장 명령은 엔진 이벤트 로그·범위 seq·정산 금액을 바꾸지 않는다.
- Then **합치기·떼어 내기 제한** (I2 마지막 감사 RA-I2-009, D-I2-20 — 실제 범위): 합쳐질 구매자 X의 그 날짜 상태가 `포장 대기`가 아니면(`포장 완료`·`포장 다시 확인`·`배송 완료`·`배송 뒤 바뀜`) 서버는 합치기를 기록하지 않고 409 "포장이나 배송을 적은 구매자는 다른 구매자에 합칠 수 없어요. 포장 모드에서 먼저 취소해 주세요." 떼어 낼 구매자가 붙어 있는 지금의 구매자 Y의 상태가 `배송 완료`·`배송 뒤 바뀜`이면 떼어 내기를 기록하지 않고 409 "배송을 적은 구매자에게서는 떼어 낼 수 없어요. 포장 모드에서 배송 완료를 먼저 취소해 주세요." 두 경우 모두 이벤트 로그·seq·포장 기록이 그대로다. 포장을 마친 Y에 다른 구매자를 합치는 것(→ `포장 다시 확인`·`배송 뒤 바뀜`)과 포장만 한 Y에서 떼어 내기(흐름 6)는 된다. X가 포장 취소·배송 취소로 `포장 대기`가 되면 합칠 수 있다. 검사와 기록은 같은 범위 줄에서 한다 — X의 포장 완료 명령과 X를 합치는 명령을 동시에 보내도 "X 포장 완료 기록 + X가 합쳐짐"이 함께 남지 않는다. 화면은 서버 문장을 그대로 보인다.
- 확인: 서버 시험

### AC-I2-32 [server] 포장 상태 실시간 반영
- 근거: SPEC §3, NFR-01, D-085, SYS-02
- Then 포장 기록이 저장되면 그 판매자의 다른 기기 화면이 1초 안에(p99) 새 상태를 본다 — 기존 실시간 연결로 알린다. 다른 판매자의 연결은 알림을 받지 않는다. 품목을 바꾸는 엔진 이벤트(1등·취소·합치기·번호 변경)는 지금처럼 알리고, 화면은 그 알림으로 포장 상태를 다시 받거나 계산한다.
- 확인: 서버 시험(알림), E2E(두 화면)

### AC-I2-33 [server] [web] 다른 곳의 포장·배송 상태
- 근거: STL-06 "배송", SPEC §7 화면 4 "정산 묶음별 목록(…·포장)", D-I2-05

### AC-I2-40 [server] 지난 구매 조회
- 근거: BUY-05, D-I2-08, R-11, R-12, D-069, D-081, DAT-06
- Given 실제 범위 날짜 D와 그 날짜의 구매자(합쳐진 구매자 ID면 지금의 구매자 X로 푼다)
- When 지난 구매를 요청한다(최근 날짜부터 20개, 다음 쪽 표시)
- Then 표지: X와 X 아래 합쳐진 구매자 각각 — 유튜브 구매자는 채널 ID, 문자 구매자는 뒤 4자리가 있으면 그 구매자를 만든 문자찜의 전화번호 키(서버가 자기 이벤트 기록에서 찾는다). 전화번호 없는 문자 구매자는 표지가 없다.
- Then 판매자의 D가 아닌 실제 날짜 D'마다 같은 채널 ID의 유튜브 구매자, 같은 전화번호 키로 만들어진 문자 구매자를 찾아 D'에서 그 구매자의 지금의 구매자 Y의 묶음을 낸다. 같은 날 여러 표지가 같은 Y로 가면 묶음 하나(까닭은 모두). 찾은 묶음의 다른 구매자로 다시 넓히지 않는다. 품목이 없고 받은 금액도 0인 묶음은 뺀다. 리허설 범위는 보지 않는다.
- Then 항목마다: 날짜, 그날 품목이 있는 방송 제목들(선언 순), 그날 이름(Y의 표시 이름), 품목(방송 제목·번호·품종·가격 스냅샷), 상품 합계·배송비·조정·최종 결제 금액·입금 상태·받은 금액·환불할 금액(코어 `getSettlement` 그대로), 포장·배송 상태 말·송장번호(AC-I2-30), 찾은 까닭(`같은 유튜브 채널` / `같은 휴대폰 번호(끝자리 2222)`).
- Then 응답 어디에도 전화번호 키·전화번호 전체가 없다(끝자리 4개만).
- Then 서버 시험으로 고정할 예(실제 범위 셋):
  - 10/18: `UC_A`(홍길동) 15번 1등, `sms:s1`(전화 `010-1111-2222`) 31번 1등.
  - 10/19: `UC_A`(닉네임 길동이) 7번, 문자찜(같은 전화 `010-1111-2222`) 8번, 문자찜(전화 없음, 메모 `홍길동`) 9번, `UC_B`(닉네임 홍길동) 10번.
  - 10/20: `UC_A` 채팅만(품목 없음).
  - → 10/19 `UC_A`의 지난 구매 = 10/18 `UC_A` 묶음 하나(`같은 유튜브 채널`). 10/20은 품목이 없어 빠지고, `UC_B`(같은 닉네임)·메모 `홍길동` 문자 구매자는 나오지 않는다.
  - → 10/19 전화 문자 구매자의 지난 구매 = 10/18 `sms:s1` 묶음(`같은 휴대폰 번호(끝자리 2222)`). 전화 없는 문자 구매자의 지난 구매 = 없음.
  - → 10/19에서 전화 문자 구매자를 `UC_A`에 합친 뒤 `UC_A`의 지난 구매 = 10/18 `UC_A` 묶음과 10/18 `sms:s1` 묶음 두 항목. 10/18에서 `sms:s1`을 `UC_A`에 합쳐 두었다면 10/18 `UC_A` 묶음 한 항목(까닭 둘).
- Then 성능: 실제 범위 100개(범위마다 구매자 50명)에서 첫 쪽 응답이 2초 안이다.
- Then 다른 판매자의 범위·리허설 범위·모르는 구매자 → 404. 다른 판매자의 같은 채널 ID 기록은 찾지 않는다.
- 확인: 서버 시험

### AC-I2-50 [server] 해석 함수와 골든 연결

- Then 백업을 만드는 동안 쓰기(판매)가 막히지 않는다. 범위마다 한 시점의 일관된 기록이다(만드는 중 들어온 이벤트는 그 범위에서 통째로 들어가거나 통째로 빠진다). 성능: 범위 10개(범위마다 상품 500·채팅 1만 건) 판매자의 백업이 60초 안.
- Then 판매자가 자기 백업 목록(만든 시각·크기)·마지막 성공 시각·꺼짐 여부를 조회할 수 있다(다른 판매자 것은 안 보인다). 백업 파일 내용을 내려받는 API는 없다.
- 확인: 서버 시험(가짜 시계·임시 폴더)

### AC-I2-62 [server] 복구·가져오기 명령
- 근거: DAT-04, D-I2-11, DAT-02, D-072, R-13, INV-4
- Given 백업·내보내기 파일과 대상 판매자(있는 판매자)
- When 운영자가 서버 명령을 돌린다(이름·인자는 dev-server가 정해 dev-notes에 — 예: `pnpm --filter @livejjim/server restore -- --seller <ID> --file <경로> [--replace]`)
- Then 먼저 검사한다 — 하나라도 어긋나면 아무것도 바꾸지 않고 까닭을 출력하고 0이 아닌 종료 코드: 형식 이름·번호, 파일 요약값, 이벤트마다 요약값, 범위마다 seq가 1부터 빈틈없음, (날짜, 리허설) 범위가 겹치지 않음, 범위마다 처음부터 재생(실패 표시 이벤트는 건너뜀)이 입력 오류·형식 오류 없이 끝남, 판매 규칙 설정이 `checkSettings`를 통과, 포장 기록의 형식.
- Then (I2 마지막 감사 SA-I2-009, D-I2-18 — RA-I2-002) 파일의 방송 ID가 그 서버의 **다른 판매자** 방송 ID와 같으면(방송 ID는 서버 전체에서 하나) 아무것도 바꾸지 않고(안전 백업도 쓰지 않고) 종료 코드 1과 "이 서버의 다른 판매자에게 같은 방송 기록이 있어 가져올 수 없어요. 아무것도 바꾸지 않았어요." — 같은 서버에서 다른 판매자로 옮기는 일은 하지 않는다(다른 서버나 기록을 잃은 같은 판매자로 가져온다).
- Then 대상 판매자에게 범위가 없으면 가져온다. 범위가 있는데 바꾸기 옵션이 없으면 아무것도 바꾸지 않고 "기록이 있는 판매자예요. 바꾸려면 --replace를 붙여 주세요(지금 기록은 먼저 백업해요)." 바꾸기 옵션이 있으면 먼저 지금 기록의 백업 파일(안전 백업)을 백업 저장소에 쓰고(실패하면 중단), 그 판매자의 범위·방송·이벤트·스냅샷·발송함·포장 기록·가게 설정·판매 규칙 설정을 파일의 것으로 **한 트랜잭션에** 바꾼다. 중간에 실패하면 아무것도 바뀌지 않는다.
- Then 범위마다 재생으로 상태 스냅샷과 발송함을 다시 만든다. 다시 만든 발송함 행은 모두 "실행하지 않음" 표시가 있다(리허설 행처럼 실행 대상 조회에서 빠지는 표시 — 행마다 확인). 범위의 seq·방송 목록이 이벤트와 맞다. 조치자 계정이 그 서버의 그 판매자 계정에 없으면 계정 없이 둔다(조치 기록 화면 "가져온 기록").
- Then 끝나면 재생 무결성 검사 명령과 같은 검사를 그 판매자에 돌려 결과를 출력한다(통과해야 종료 코드 0).
- Then 판매자 ID·로그인 계정·세션·전화번호 키는 그대로다 — 복구 뒤에도 로그인이 유지되고, 같은 전화번호의 새 문자찜이 복구한 문자 구매자와 이어진다(같은 서버·같은 판매자). 다른 판매자의 기록은 바뀌지 않는다.
- 확인: 서버 시험(PGlite — 손상 파일 셋(요약값·seq 빈틈·재생 오류)은 아무것도 바꾸지 않음, 빈 판매자로 가져오기, 바꾸기 없이 거절, 바꾸기)

### AC-I2-63 [server] 백업 → 복구 리허설 (SPEC §8 2단계)
- 근거: SPEC §8 "백업→복구 리허설", DAT-03, DAT-04, D-I2-10, D-I2-11
- Then 자동 시험 하나가 끝까지 돈다: 실제 범위 둘·리허설 범위 하나에 방송·상품(가져오기 포함)·채팅·문자찜(전화번호 있음·없음)·방송자 조치·합치기·정산 기록(입금·환불·배송비 예외·조정)·포장·배송 기록·가게 설정 → 가짜 시계 04:00 자동 백업 → 기록을 더 함(판매·포장) → 바꾸기 복구 → 모든 조회(방송 목록, 날짜마다 상품·구매자·정산·조치 기록, 포장 상태, 가게 설정, 판매 규칙 설정, 확인서 데이터, 판매대장 행, 지난 구매)가 백업 때와 같고, 발송함 실행 대상이 하나도 없고, 재생 검사가 통과한다. 이어서 안전 백업으로 다시 바꾸기 복구하면 첫 복구 직전의 조회와 같다.
- 확인: 서버 시험

### AC-I2-64 [server] 판매자 전체 내려받기
- 근거: DAT-04 "판매자 단위 전체 내보내기(엑셀+JSON)", D-I2-12
- Then 판매자 본인(세션의 판매자)만 두 파일을 내려받는다: JSON(AC-I2-60 형식, gzip, `라이브찜-전체기록-YYYY-MM-DD.json.gz`)과 엑셀(실제 범위 전체 기간의 판매대장 — 366일 상한 없음, 배송 칸 포함, `라이브찜-판매대장-전체-YYYY-MM-DD.xlsx`). 날짜는 서버 시각의 KST 날짜. `Cache-Control: no-store`.
- Then 실제 범위가 없으면 엑셀은 파일 없이 "아직 판매 기록이 없어요." JSON은 빈 기록으로도 만든다.
- Then 내려받은 JSON으로 빈 판매자에 가져오기(AC-I2-62)를 하면 그 판매자의 조회가 원래 판매자와 같다(판매자 ID·계정·문자 구매자 키 연결 빼고).
- 확인: 서버 시험

### AC-I2-65 [web] 설정 화면 — 백업·전체 내려받기
- 근거: D-I2-10, D-I2-11, D-I2-12, UX-01·03
- Then 설정 화면 "백업" 부분: "마지막 자동 백업: 2026년 10월 20일 (화) 04:00"(KST), "백업은 30일 동안 보관해요.", 보관 중인 백업 목록(만든 시각·크기 `1.2MB`), "백업 시점으로 되돌리려면 운영자에게 날짜를 알려 주세요." 복구·백업 파일 내려받기 버튼은 없다.

### AC-I2-66 [server] 봉인한 날짜의 백업·전체 기록·복구 (I2 합치기 후속, D-I2-22)
- 근거: DAT-03, DAT-04, DAT-06, D-Y11, D-I2-11, D-I2-22
- 구현 시점: I2 합치기 후속(backlog carryOver). AC-I2-67보다 먼저 한다 — 봉인 날짜 하나 때문에 판매자 백업 전체를 되돌릴 수 없게 되는 것을 막는다.
- Given 실제 범위 둘 — 날짜 A는 유튜브 채팅·확정·입금·포장·배송 기록이 있고 가짜 시계로 A + 30일 0시(KST)를 지나 봉인됨, 날짜 B는 봉인 전 — 와 리허설 범위 하나
- When 자동 백업·전체 기록(JSON)을 만들고, 그 파일로 바꾸기 복구·빈 판매자(다른 서버)로 가져오기를 한다
- Then 파일에 A는 "봉인 범위"로 들어간다: 날짜·봉인 시각·장부(D-Y11 그대로)·장부 요약값과, 저장된 그대로의 이벤트 기록(채팅 본문·이름 없음). 채팅 원문은 파일에 없다.
- Then 파일 검사는 봉인 범위를 재생하지 않고 seq가 1부터 빈틈없는지, 이벤트 요약값(파일 손상), 장부 요약값을 본다 — 재생 검사 명령이 봉인 범위를 다루는 방식과 같다. 이 파일은 검사를 통과한다. 장부를 한 글자 고친 파일은 "장부 요약값이 맞지 않아요" 같은 까닭으로 거절되고 아무것도 바뀌지 않는다.
- Then 복구·가져오기 뒤 A는 봉인된 날짜 그대로다: 같은 장부·봉인 표시, 상태 스냅샷·발송함·채팅 원문 없음, 그 날짜에 쓰는 요청(포장·배송 명령 포함)은 409 "30일이 지난 방송 기록은 봉인되어 고칠 수 없어요." 재생 검사 명령이 통과한다(A는 장부 요약값 대조, B·리허설은 재생).
- Then 복구 뒤 A의 조회(정산·확인서 데이터·판매대장 행·포장 목록·지난 구매 — AC-I2-67)는 백업 때와 같다.
- 확인: 서버 시험(PGlite, 가짜 시계, 가짜 유튜브 수집 경로로 채팅을 넣고 봉인 작업을 돌린다)

### AC-I2-67 [server] [web] 봉인한 날짜의 문서·포장·지난 구매 (I2 합치기 후속, D-I2-22)
- 근거: STL-04, STL-06, STL-08, STL-10, BUY-05, D-Y11, D-I2-22
- Given AC-I2-66의 날짜 A. 봉인 직전(같은 서버 시각으로 고정)에 A의 확인서 데이터(구매자마다)·전원 PDF 쪽 순서·판매대장 행·포장 목록(상태 말·송장)·포장 라벨 데이터·다른 날짜에서 본 A의 지난 구매 항목을 받아 둔다
- When A가 봉인된 뒤 같은 것을 다시 요청한다
- Then 모두 봉인 직전과 같다(만든 시각만 다름) — 서버는 봉인한 날짜를 봉인 장부로 만든다. 빈 날짜·빈 파일·오류가 아니다. 판매대장 기간·전체 내려받기에 A의 행이 들어간다.
- Then 장부 형식에 판매마다 찜 시각(R-6 실제 시각과 분 단위 여부)이 있다(장부 형식 번호를 올림). 찜 시각이 없는 이전 형식 장부로 만든 판매대장의 "찜 시각" 칸은 빈칸이고 나머지 칸은 같다.
- Then 포장 상태는 장부의 판매(지금의 구매자·상품 ID·상품 키)와 포장 기록으로 AC-I2-30 규칙 그대로 계산한다. 포장·배송 명령은 409(봉인 문장)이고, [web] 봉인된 날짜의 포장 체크리스트는 "30일이 지나 봉인한 날짜예요. 볼 수만 있어요."를 보이고 포장 완료·배송 완료·취소 버튼이 없다(라벨 그림 저장·PDF는 된다).
- Then 응답·파일에 채팅 본문·전화번호 키가 없다(AC-I2-81 그대로).
- 확인: 서버 시험, E2E(봉인 날짜의 포장 화면 한 흐름)
