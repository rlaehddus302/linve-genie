- 정답의 우선순위: 골든(요금 JSON·엔진 YAML) → BILLING_RULES·DOMAIN_RULES·LABEL_RULES·SPEC 규칙 문장 → DECISIONS → 이 문서. 규칙으로도 정해지지 않는 경우를 찾으면 구현으로 정하지 말고 dev-notes·결과의 `disputesWithSpec`으로 올린다(dev-common).

- **합칠 때 겹치지 않게**: 요금 기록은 새 표(이용권·회수·쓴 기록·방송의 이용 방식·결제 주문·사업자 정보·증빙 요청 등)에 두고 마이그레이션은 새 파일로 더한다. 이벤트·발송함·스냅샷·출력 작업 표의 칸은 바꾸지 않는다(라벨 쓴 기록은 출력함을 적는 같은 트랜잭션에서 새 표에 적는다). 병렬 트랙 N1~N4a와 같은 파일을 고칠 일(메뉴 목록, `client-config`, 골든 러너 ID 형식 — N2·N3도 넓힌다)은 최소로 고치고 dev-notes에 남긴다.

### AC-N5-20 [server] 새 실제 방송 시작
- 근거: BL-4, D-N5-03·D-N5-04, G-BIL `start`
- Given 요금 기능 켜짐
- When 실제 방송 만들기 요청(`rehearsal`이 아님)
- Then 그 순간 서버 시각으로 BL-4 1의 순서대로 이용 방식을 정한다: 정액 이용 중 → `FLAT` / 열린 창 → `DAY`(쓰지 않음) / 방송 일 잔량 ≥ 1 → `DAY` + 방송 일 1 쓰기(지금부터 24시간 창) / 주문 건 잔량 ≥ 1 → `ORDERS` / 아니면 422 `NO_PASS` "이용권이 없어 실제 방송을 시작할 수 없어요. 요금 화면에서 이용권을 산 뒤 다시 시작해 주세요. 리허설은 언제든 할 수 있어요."
- Then 시작되면 엔진 `broadcast.start`·방송 행·그 방송의 이용 방식·(3번이면) 방송 일 쓴 기록이 **한 트랜잭션**에 들어간다 — 트랜잭션을 실패시키면(시험용 실패 주입) 넷 다 없다. 응답에 이용 방식·방송 일을 새로 썼는지가 있다.
- Then 거절되면 아무것도 기록하지 않는다(이벤트 로그·방송 목록·이용 방식·쓴 기록·요청 번호 기록 모두 그대로 — 이용권을 산 뒤 **같은 요청 번호로** 다시 보내도 시작된다).
- Then 같은 요청 번호의 재전송은 처음 결과이고 방송 일을 다시 쓰지 않는다. 방송 날짜(`date`)를 무엇으로 보내든 판단은 서버 시각만 본다(지난 날짜로 방송을 열어도 열린 창이 아니면 방송 일을 쓴다).
- Then 같은 판매자의 실제 방송 만들기 두 요청이 동시에 오면(방송 일 잔량 1, 열린 창 없음) 하나가 방송 일을 쓰고 창을 열고, 다른 하나는 그 창으로 `DAY`(쓰지 않음)다 — 방송 일은 1만 빠지고 창은 하나다(BL-INV-2).
- 확인: 서버 단위, 적대

### AC-N5-22 [server] 시작한 방송은 끝까지 — 아무것도 막지 않는다 (BL-0 1, BL-4 4)
- 근거: 백로그 "방송 중 소진 시 그 방송은 끝까지 진행", D-N5-03
- Given `ORDERS` 방식으로 시작한 실제 방송, 주문 건 잔량 1
- When 그 방송에서 상품 셋이 차례로 1등을 얻고(채팅·문자찜·직접 배정·메시지 변환), 승계·취소·라벨 자동 출력·손으로 출력·다시 출력·감사 메시지 효과가 나오고, 방송을 끝낸 뒤 늦은 문자찜으로 넷째 상품이 1등을 얻는다

- Then 같은 식으로 `FLAT` 방식 방송 중에 정액제가 끝나도(주입 시계), `DAY` 방식 방송 중에 24시간 창이 닫혀도 그 방송의 모든 쓰기는 그대로 되고 그 방송의 이용 방식은 그대로다(`FLAT` 방송의 라벨은 계속 세지 않는다).
- Then 판매 기록 조회·구매자·정산·입금 기록·확인서·판매대장·라벨 출력·재출력·포장 라벨·내보내기는 이용권이 없어도(잔량 음수·정액 끝남) 모두 된다.
- 확인: 서버 단위, 적대
