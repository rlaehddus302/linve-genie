## A. 동시 송출 — 플랫폼 공통 연결 (PLT-03, D-N2b-2-01·D-N2b-2-02)

### AC-N2b-2-01 [server] 회차 하나에 플랫폼마다 연결 하나
- 근거: PLT-03 세부, D-N2b-2-01
- Given 끝나지 않은 실제 회차 b, 유튜브·인스타그램 연결과 틱톡 동의·아이디가 준비된 판매자
- When b를 유튜브 라이브에 잇고(Y1 잇기), 인스타그램 기다리기(또는 잇기)를 하고, 틱톡에 잇는다
- Then 셋 다 받는다. 그 뒤 같은 플랫폼으로 다시 잇기·기다리기를 하면 아무것도 바꾸지 않고 409 `ALREADY_LINKED` "이 방송에는 이미 {플랫폼} 라이브가 이어져 있어요. 먼저 연결을 끊어 주세요."이다(플랫폼마다 시험 — 유튜브 잇기도 이 문장).
- Then 한 플랫폼을 끊어도 다른 플랫폼의 연결·수집은 그대로다(끊은 플랫폼만 다시 이을 수 있다).
- Then 리허설 `REHEARSAL`·끝난 회차 `ENDED`·다른 판매자의 회차 404는 플랫폼마다 지금과 같다. 잇기·기다리기·끊기는 엔진 이벤트가 아니고(그 범위의 이벤트 기록·`seq` 그대로) 같은 요청 번호는 한 번만 한다.
- 확인: 통합 시험

### AC-N2b-2-02 [server] 동시 요청과 잠금 — 플랫폼 사이 틈 없음 (N2 carryOver)
- 근거: D-N2b-2-01
- Then 모든 플랫폼의 잇기·기다리기·끊기(유튜브 `youtube_links`, 인스타·틱톡 연결)는 판매자 잠금 하나 안에서 처리하고, (판매자, 회차, 플랫폼)마다 끊지 않은 연결은 DB 유일 제약으로 하나뿐이다.
- Then 시험: (가) 같은 회차에 같은 플랫폼 잇기 두 요청을 동시에 → 하나만 받고 하나는 `ALREADY_LINKED` (나) 같은 회차에 다른 플랫폼 잇기 셋을 동시에 → 셋 다 받음 (다) 같은 인스타 라이브를 두 회차에 동시에 → 하나만(`LIVE_TAKEN`) (라) 한 판매자의 두 회차에 틱톡 잇기를 동시에 → 하나만(`TIKTOK_IN_USE`, AC-N2b-2-30). 어느 경우에도 끊지 않은 연결 수가 규칙을 넘지 않는다(DB를 직접 세어 확인).
- 확인: 통합 시험(동시 요청), 적대 시험

### AC-N2b-2-03 [server] 둘 이상의 플랫폼 = 접수순 — 인스타·틱톡은 실제 시각순 회차에 잇지 않는다
- 근거: PLT-02·PLT-03 세부, R-6, D-N2-05, D-N2b-2-02
- Given 설정 스냅샷 `contention.policy` = `RECEIVED_TIME`인 회차
- Then 틱톡 잇기는 409 `RECEIVED_TIME_NOT_ALLOWED` "틱톡 라이브는 실제 시각순으로 판정할 수 없어요. 판매 규칙을 '접수순'으로 바꾼 뒤 새 방송을 시작해 주세요."(인스타그램은 지금 문장 그대로). 유튜브만 잇기는 지금처럼 받는다.

### AC-N2b-2-54 [server] 이미 들어온 찜과 겹치는 줄 (RA-N2b-2-03)
- 근거: D-N2b-2-14, R-6 4번 줄
- Given 실제 회차 b, 상품 15(재고 2)·16. 틱톡 구매자 `tt:…101`(닉네임 "홍길동")의 `chat` "15"로 15에 활성 찜

- Then `includeOverlaps` 없이 넣으면 `sms`는 16 하나만 기록되고 15에 홍길동 찜은 하나(그대로)다. 응답의 1줄 결과에 같은 겹침 문장, 넣은 찜 수 1.

- Then 겹침의 원천: 틱톡·인스타·유튜브 `chat`의 정리한 닉네임, 앞선 붙여넣기·직접 넣은 문자찜의 메모 — 각각 한 사례. 겹침 아님: 다른 닉네임, 같은 닉네임의 다른 번호, 취소된 찜·`DUPLICATE`·밀려난 찜, 다른 범위(리허설 찜과 실제 줄) — 각각 한 사례. 한 번 넣기 안의 "홍길동: 15"가 두 줄이면 겹침이 아니다(지금처럼 같은 구매자 — 엔진 `DUPLICATE`).
- 확인: 통합 시험

### AC-N2b-2-57 [server] 넣기 — 번호마다 문자찜
