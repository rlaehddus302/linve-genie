- 스프린트: BND1 (6단계, 병렬 트랙 — worktree `livejjim-wt/bnd1`, 브랜치 `track/bnd1-band`, BASE `72c7d4c`) · spec ID: **PLT-04**(새), **PLT-03** (연결: PLT-01·PLT-02, YT-04·YT-05, ORD-01·02·09, BUY-01·03, DAT-04·05·06, NFR-03·06·08, SYS-05, UX-01·03·04, SPEC §5.11·§7 화면 2·8·§9) · 규칙: DOMAIN_RULES v0.1.30 R-0 5, R-1 "밴드 글 댓글의 `chat`", R-6, R-11, R-13 "여러 플랫폼 회차의 감사", INV-3 · 근거 결정: D-036, D-079, D-Y05, D-N2-02·D-N2-11, D-N2b-2-02·D-N2b-2-09·D-N2b-2-16, D-QL2-08, D-MOB1-09, D-LND1-11, **D-BND1-01~D-BND1-15**
- 개발 영역: **server**, **web** · 테스트: **domain**, **e2e**. **dev-core가 없다** — 판정·정산 규칙과 코어 골든 러너는 바꾸지 않는다(새 골든은 서버 시험이 읽는 JSON).
- 사람 확인 지점 **HG-BND1**(실제 네이버 밴드 — 밴드 서비스 등록 뒤, 최종 보고에서 사용자가 확인, 맨 아래 "HG-BND1 확인 목록"). 이번 스프린트는 가짜 밴드 서버로 끝까지 간다(D-BND1-13) — **막힌 항목 없음**.
- 공식 문서(developers.band.us/develop/guide/api, 2026-10-26에 읽음)의 주소·칸 이름·오류 코드를 기준으로 한다. 문서에 없거나 예시와 표가 다른 것은 지어내지 않았다 — 각 기준에 **실물 확인 필요**로 적고, 모르는 응답은 "넣지 않고 알림" 쪽으로 동작한다. 시험은 가짜 밴드 서버가 문서와 같은 모양으로 답하는 것을 기준으로 한다.
- 공통 전제: 지금까지의 결과(`pnpm verify` 7단계 — typecheck·lint·test·golden·adversarial·coverage·e2e)가 그대로 유지된다. 외부 계정·실제 밴드·인터넷은 필요 없다. 시계·타이머는 주입해 시험한다(10초·60초 읽기, 다시 시도 시간표는 주입한 시계로 빠르게 돈다). E2E가 도는 명령엔 `E2E_PORT_OFFSET=28300`.
- 정답의 우선순위: 골든 → DOMAIN_RULES·SPEC 규칙 문장 → DECISIONS → 이 문서. 규칙으로도 정해지지 않는 경우를 찾으면 구현으로 정하지 말고 dev-notes·결과의 `disputesWithSpec`으로 올린다.
- 태그: `[server]` = dev-server(`apps/server/**` — 밴드 코드는 `apps/server/src/band/**`와 플랫폼 공통 파일), `[web]` = dev-web(`apps/web/**`). 경로·필드 이름은 dev-server가 정하고 `harness/sprints/BND1/dev-notes.md` "화면에게" 절에 적는다.
- 이 문서가 따옴표로 정한 판매자에게 보이는 문장(오류·상태·안내)은 서버가 그대로 돌려주고 화면이 글자 그대로 쓴다(UX-01·UX-03). `{…}` 자리는 값이다. 프로그램이 읽는 값은 영문 코드로 함께 준다. 바꿔야 하면 dev-notes에 이유를 남기고 spec-keeper가 판정한다.
- **금지 경로**(맥북 쪽 유튜브 작업): `apps/server/src/youtube/**`, 이름에 `youtube`·`Youtube`가 든 웹 파일, `tests/e2e/y1/**`. 이 경로를 고쳐야만 되는 것은 하지 않고 dev-notes "맥북 쪽에 넘김"에 적는다.

## A. 플랫폼 공통 (PLT-03·PLT-04, D-BND1-02)

### AC-BND1-01 [server][web] 플랫폼 값과 `band:` 접두어
- 근거: PLT-03 세부, D-N2-02, D-BND1-02
- Then 서버 플랫폼 값에 `BAND`가 있고(`PLATFORMS`), 서버 `platformOfKey`와 화면 `platformOfKey`가 `band:`로 시작하는 키를 `BAND`로 본다. 플랫폼 이름은 "밴드"(서버 `PLATFORM_NAMES`, 화면 `PLATFORM_WORD`). 다른 접두어의 결과는 그대로다.
- Then 단위 시험 표: `band:UKEY_A1` → `BAND`, `band:` → `BAND`, `bandUKEY` → `YOUTUBE`(쌍점 없음), `BAND:UKEY` → `YOUTUBE`(대문자는 접두어 아님), `ig:1`·`tt:1`·`sms:s1`·`UC_A`·`sim_a1` → 지금 값.
- 확인: 단위 시험(서버·화면 둘 다)

### AC-BND1-02 [server] 플랫폼 능력 조회의 밴드
- 근거: AC-N2-02, D-BND1-02, D-BND1-13
- Then 플랫폼 능력 조회에 `BAND` 항목이 더해진다: `ready` = 밴드 설정이 있을 때만(AC-BND1-10), `receivedTime` 아니오(이유 "밴드 댓글은 몇 초마다 읽어 와서 실제 시각순으로 판정할 수 없어요."), `thanks` `NONE`(이유 "밴드에는 감사 글을 남기지 않아요."), `videoComment` 아니오. 설정이 없으면 `ready` 이유 "밴드 연동이 아직 준비되지 않았어요. 운영자에게 문의해 주세요."
- Then 다른 플랫폼 항목은 그대로다(기존 시험 통과).
- 확인: 통합 시험

### AC-BND1-03 [server] 감사 경로 — 밴드에 쓰지 않는다
- 근거: R-13 "여러 플랫폼 회차의 감사", D-N2b-2-09, D-BND1-02
- Then `thanksRoute`: 구매자 자신의 키가 `band:`이면 `SKIP_NOT_SUPPORTED`(발송함 행 `SKIPPED`, 게시 보고 없음 — 그 확정은 잠기지 않는다). 유튜브 발송함으로 가지 않는다.
- Then 밴드 연결 기록(끊은 것 포함)이 있는 회차는 "다른 플랫폼 연결 기록이 있음"으로 센다 — 유튜브가 이어진 적 없는 밴드 회차의 문자찜·유튜브 키 감사는 `SKIP_NO_RECIPIENT`.
- Then 시험: 밴드만 이은 회차에서 밴드 댓글 찜 확정 → 감사 효과 1, 발송함 행 `SKIPPED`(`NOT_SUPPORTED`), 유튜브 `NEW` 0. 같은 회차 문자찜 확정 → `SKIPPED`(`NO_RECIPIENT`). 밴드에 나가는 요청 0(가짜 밴드 서버 기록).
- 확인: 통합 시험

### AC-BND1-04 [server] 수집 출처·백업 복구
- 근거: D-QL2-08, D-BND1-02, D-BND1-14, DAT-04
- Then 밴드 댓글 `chat`의 기록 출처는 `other`다(인스타그램·틱톡과 같다). 백업 복구·가져오기의 출처 되살리기는 메시지 ID가 `band:`로 시작하면 `other`(D-QL2-08에 한 갈래 더함 — `ig:`·`tt:` 갈래와 시험 그대로).
- Then 백업 파일에 밴드 토큰·본 댓글 표·경로 표가 없다(시험: 심은 토큰 `PLANTED-BAND-TOKEN`이 백업 바이트에 0번). 복구·가져오기를 하면 그 판매자의 열린 밴드 글 연결이 모두 `FINISHED`가 되고(사유 "복구해서 밴드 글 연결을 끝냈어요. 다시 이어 주세요."), 밴드 계정 연결(토큰)은 남는다.
- 확인: 통합 시험

## B. 설정·계정 연결 (D-BND1-11·D-BND1-13)

### AC-BND1-10 [server] 설정 읽기
- 근거: D-BND1-13, AC-N2b-2-71
- Then 서버 시작 때 `LIVEJJIM_BAND_CLIENT_ID`·`LIVEJJIM_BAND_CLIENT_SECRET`·`LIVEJJIM_BAND_REDIRECT_URI`를 읽는다. 하나라도 비면 밴드는 `NOT_CONFIGURED`(AC-BND1-02 문장)이고 서버는 정상으로 시작한다.
- Then 주소 덮어쓰기 `LIVEJJIM_BAND_AUTH_URL`·`LIVEJJIM_BAND_API_URL`(없으면 `https://auth.band.us`·`https://openapi.band.us`). 돌아오는 주소와 두 주소는 `https://`만 — `http://localhost`·`http://127.0.0.1`·`http://[::1]`(포트 있어도)은 허용. 틀리면 `NOT_CONFIGURED` + 로그 코드 `BAND_CONFIG_INVALID`(값 없이). 시험 표: `http://shop.example` → 설정 없음, `http://localhost:4000` → 준비됨, `ftp://x` → 설정 없음, `https://x.example/band` → 준비됨.
- Then `docs/DEPLOY.md`·`.env.example`에 다섯 이름과 뜻을 적는다(비밀값 표시 — AC-I3-74의 이름 맞대기 시험이 통과한다).
- 확인: 통합 시험, 문서 검토

### AC-BND1-11 [server] 연결 시작
- 근거: D-BND1-11, 공식 문서 "authorization code 받기"
- When 로그인한 판매자가 연결 시작을 요청한다
- Then 서버는 한 번 쓰는 표(추측할 수 없는 값, 10분, 그 판매자 세션에 묶임)를 만들고 브라우저를 `<AUTH_URL>/oauth2/authorize?response_type=code&client_id=<ID>&redirect_uri=<REDIRECT_URI/표 — 주소 부호화>`로 보낸다(`state`도 같은 표로 붙여도 되지만 확인은 경로 표로 한다).
- Then 설정이 없으면 409 `NOT_CONFIGURED`(문장 AC-BND1-02), 보조자·로그인 안 함은 403·401, 아무것도 만들지 않는다.
- 확인: 통합 시험(가짜 밴드 서버)

### AC-BND1-12 [server] 돌아오기 — 토큰 받기
- 근거: D-BND1-11, 공식 문서 "토큰 발급"
- When 밴드가 `<REDIRECT_URI>/<표>?code=…`로 돌려보낸다
- Then 표가 있고·10분 안이고·안 쓴 것이고·지금 세션 판매자의 것일 때만 `GET <AUTH_URL>/oauth2/token?grant_type=authorization_code&code=<code>`를 `Authorization: Basic base64(client_id:client_secret)`로 부른다. 표는 성공·실패와 상관없이 한 번 쓰면 끝난다.
- Then 결과는 앱 화면 주소에 `?band=<결과>`로 돌아간다(문장은 화면이 서버 표대로):

  | 결과 | 언제 | 문장 |
  |---|---|---|
  | `connected` | 토큰·`user_key`를 받고 저장함 | "밴드를 연결했어요." |
  | `denied` | `code`가 없음(밴드에서 거부 등) | "밴드 연결을 취소했어요." |

## 공격 관점 (test-domain 참고 — `tests/adversarial/bnd1/**`)

- 접두어: 손님 `user_key`가 `ig:…`·`tt:…`·`sms:…`·`UC…`처럼 생겼어도 키는 늘 `band:`로 시작해 다른 플랫폼·문자 구매자와 섞이지 않는다. `user_key`가 휴대폰 번호 모양(`01012345678`)이어도 ID 칸 검사에 걸리지 않는다(D-079). 판매자 `user_key`와 대소문자만 다른 손님은 판매자가 아니다(정확히 같을 때만).
- 본문: 손님이 친 `&lt;band:refer …&gt;`·`&amp;lt;`·여러 겹 이스케이프, 닫히지 않은 `<band:refer>`, 태그 안의 태그, 아주 긴 태그 속성 — 태그가 되거나 다른 사람을 부르는 `@`가 생기지 않는다. 500 코드 포인트 경계(이모지·결합 문자), 앞뒤 공백·제어 문자.

4. 토큰 응답에 `user_key`·`scope`·`expires_in`·`refresh_token`이 오는지, `scope`의 실제 이름.
5. 밴드 목록·내 글 목록 — 글과 댓글의 `author.user_key`가 실제로 오는지(공식 예시 응답에는 없다 — 없으면 "내가 쓴 글만 이을 수 있어요."·"작성자를 알 수 없는 밴드 댓글"이 뜬다).
6. 시험 밴드의 내 글을 잇고 다른 휴대폰(다른 밴드 계정)으로 "1번 2개요" → 찜. 판매자 계정 댓글 → 찜 없음. 이을 때 있던 댓글 → 넣지 않음.
7. `created_at`이 밀리초인지 초 단위(끝자리 000)인지, 같은 초 두 댓글의 차례가 최신순을 뒤집은 것과 같은지, 쪽 크기(20?)와 `limit` 칸.
8. 답글(댓글에 단 댓글)이 목록에 섞여 오는지, 스티커·사진·음성 댓글의 `content` 모양, 손님이 `<`·`&`를 친 댓글의 이스케이프 모양.
9. 댓글을 지우면 목록에서 빠지는지, 고치면 `content`가 바뀌는지 → 알림.
10. 밴드 앱에서 앱 연결을 끊었을 때·글을 지웠을 때·밴드에서 나갔을 때의 실제 `result_code`(문서 표의 `10401`·`60102` 등인지).
11. 10초·60초 읽기로 한 시간 방송 — `1001`·`1002`·`1003`이 나오는지.
