## A. 코어 — 합치기 미리 보기 (BUY-03, R-11, D-100)

### AC-S06b-01 [core] `previewMerge` 순수 조회
- 근거: BUY-03, R-0 1, R-11 "구매자 합치기"·"미리 보기", D-057, D-100, RA-S06-003, 골든 G-ENG-174·175
- Given 엔진 상태 `state`와 구매자 ID 둘 `from`·`into`(구매자 자신의 ID — `buyer.merge`의 `from`·`into`와 같다)
- When `previewMerge(state, from, into)`
- Then 다음 정보를 담은 값을 돌려준다(`@livejjim/core`에서 내보내고 타입도 내보낸다. 이름은 아래를 기본으로 하고, 바꾸면 dev-notes에 적는다):
  - `blocked`: `null` 또는 `'UNKNOWN_BUYER' | 'SAME_BUYER' | 'FROM_MERGED' | 'CYCLE' | 'BOTH_CONFIRMED'` — 위에서부터 처음 맞는 것(둘 중 하나를 엔진이 모름 → 같은 구매자 → `from`이 지금 다른 구매자에 합쳐져 있음 → `into`의 지금의 구매자가 `from` → 확정 찜이 둘이 되는 상품이 있음).
  - `target`: 합친 뒤의 지금의 구매자 = `into`의 지금의 구매자(`into`를 모르면 `null`).
  - `bothConfirmed`: `from` 쪽(`from`과 그 아래 합쳐 있던 구매자 전부)과 `target` 쪽이 모두 `CONFIRMED` 찜을 가진 상품 키(`"b1/18"`) 목록, 방송·번호 순. `blocked`가 `BOTH_CONFIRMED`가 아니면 빈 목록.
  - `moving`: `{ buyers, items, subtotal }` — `from`과 그 아래 전부의 ID, 확정 찜 상품 키(`listBuyers`의 `items`와 같은 순서), 가격 스냅샷 합. 모르는 구매자면 빈 목록·0.
  - `after`: 막히면 `null`, 아니면 `{ items, subtotal }` = 합친 뒤 `target`의 확정 찜 상품 키와 합.
  - `duplicates`: 막히면 빈 목록, 아니면 합치면 `DUPLICATE`가 될 찜마다 `{ claim, product, buyer, status, keep }` — 그 찜 ID, 지금의 상품 키, 그 찜의 구매자 자신, 지금 상태(`CONFLICT`·`WAITLISTED`·`PENDING`), 남는 찜 ID. 상품 키(방송·번호) 순. 남는 찜은 R-11 "앞선 쪽"(확정 > 충돌 > 대기 앞 순번 > 보류 판정 순위 R-6)이고 방향(`from`/`into`)과 상관없다.
- Then 막히지 않으면 `applyEvent(state, buyer.merge(from, into))`의 결과와 같다: 상태가 바뀌고, `DUPLICATE`로 바뀐 찜 = `duplicates`의 `claim` 전부, 그 뒤 `getBuyer(target)`의 `items`·`subtotal` = `after`. 막히면 같은 `buyer.merge`는 아무 일도 없다.
- Then 상태를 바꾸지 않고(넘긴 상태를 그대로 둔다 — 부르기 전후 직렬화가 같다), 같은 입력이면 늘 같은 값이다(NFR-02). 시계·난수·환경을 쓰지 않는다(순수성 린트 통과). 엔진 판정이 쓰는 R-11 코드와 같은 함수를 써서 규칙을 두 번 구현하지 않는다(코드 검사).
- 확인: 골든 G-ENG-174·175, 코어 단위 시험(막힘 다섯 가지, 재고 2, 합쳐진 구매자 아래 따라감, 합쳐진 구매자에게 합치기, 보류끼리 실제 시각순), 커버리지 95% 이상

### AC-S06b-02 [core] 골든 러너 `mergePreviews`
- 근거: `tests/golden/README.md` "추가 검사 키"·"`expect` 비교 규칙"의 `mergePreviews`, D-020, D-021, D-100
- Then 러너가 `mergePreviews`를 README대로 읽고 비교한다: 중간 검사·마지막 `expect` 모두. `from`·`into`는 구매자 자신으로 풀어 넘기고(`buyerIdOf`와 같은 풀이 — 풀리지 않는 키는 그대로), 적은 필드만 비교한다. `bothConfirmed`·`moving.items`·`after.items`는 집합, `duplicates`는 `{ product, buyer, status }` 집합이고 `buyer`는 구매자 자신으로 풀어 비교한다(지금의 구매자로 풀지 않는다).
- Then 형식 계약: 항목이 맵이 아니거나, `from`·`into`가 없거나, 표에 없는 키·열거값 밖의 `blocked`·`status`, 정수가 아닌 `subtotal`, 휴대폰 번호인 `from`·`into`(ID 칸)는 읽기 오류다. 불일치는 `mergePreviews[i].<필드>` 경로와 기대값·실제값으로 보인다.
- Then 러너는 `previewMerge`를 부른 뒤 상태가 바뀌지 않았는지 확인한다(바뀌면 러너 오류 — RA-S00-001과 같은 방식). 결정성 검사(두 번 실행)에 미리 보기 결과도 들어간다.
- Then 러너 자체 시험(`compare.test.ts`·`read-errors.test.ts` 등)에 `mergePreviews`의 통과·필드마다 불일치·읽기 오류 사례를 더한다. 가짜 코어(`fake-core.ts`)도 이 조회를 흉내 낼 수 있다(없으면 미구현으로 보고).
- Then 기존 검사 키·비교 규칙·읽기 오류 규칙은 바꾸지 않는다.
- 확인: 러너 단위 시험, `pnpm golden`

### AC-S06b-03 [domain] 미리 보기 = 실제 합치기 (속성 시험)
- 근거: R-11, INV-2, INV-5, NFR-02, D-100
- Given 무작위 이벤트 로그(채팅·문자찜(전화번호 겹침 포함)·재고 1·2 상품·취소·충돌(`RECEIVED_TIME`·`HOST`)·보류·합치기·떼어 내기를 섞음)와 그 상태의 구매자 쌍(모르는 ID, 같은 ID, 합쳐진 구매자, 고리가 되는 쌍 포함)
- Then 모든 쌍에서: `blocked === null` ⇔ `buyer.merge` 적용이 상태를 바꿈. 바뀌면 `DUPLICATE`가 된 찜 집합 = `duplicates`의 `claim` 집합, 적용 뒤 `target`의 확정 상품·합계 = `after`, 적용 전 `from`의 조회 = `moving`. `previewMerge`는 넘긴 상태를 바꾸지 않고 두 번 불러도 같다.
- 확인: `tests/adversarial/s06b/**` 속성 시험(fast-check, 현실적인 크기 — D-036)
