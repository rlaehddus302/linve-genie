# N4b 수용 기준 — 바로 영수증: 확인서 JPG·전원 이미지 묶음·구매자 공유 링크·영수증 보내기 화면

- 스프린트: N4b (5단계, 병렬 트랙 worktree `livejjim-wt/n4b` · 브랜치 `track/n4b-receipts`, BASE `c3d3659`) · spec ID: **RCP-02**, **STL-04**, **STL-05**, **STL-06**, **STL-10** (연결: STL-01·03·07, BUY-01·03, DAT-04·06, SYS-01·02·04·05, UX-01·03·04·07, NFR-03·06·08, SPEC §7 화면 2·10·11·12) · 근거 결정: **D-N4b-01~D-N4b-06**(AUTO), D-206·D-207·D-208, D-I2-01·D-I2-02·D-I2-03·D-I2-04·D-I2-11·D-I2-12·D-I2-22, D-074, D-087, D-102
- 개발 영역: **server**, **web** · 테스트: **e2e**(`tests/e2e/n4b/**`) · 사용성 감사(ux-reviewer) 있음 · 사람 확인 지점 없음(실제 메신저의 링크 미리 보기·JPG 받기·ZIP 한글 이름은 최종 보고 — DECISIONS "사용자 확인 필요"의 "구매자 공유 링크·바로 영수증" 행) · 이 트랙의 E2E는 `E2E_PORT_OFFSET=1700`으로 돈다.
- **dev-core·dev-device가 없다.** 판정·정산 규칙, `packages/documents`의 확인서 데이터·배치·PNG 그리기(D-206·D-207)는 바꾸지 않는다. JPG 인코딩·ZIP 묶기·링크·공개 화면은 서버(`apps/server`)가 이미 있는 `rasterizePage`·확인서 데이터 함수를 불러 만든다. 새 엔진·파서 골든은 없다(`tests/golden/known-unimplemented.yaml`은 계속 빈 목록, sprint 표시만 N4b).
- 목표(백로그): RCP-02 — 라벨 없이 쓰는 판매자를 위해 방송 끝나면 바로 구매자별 확인서 PDF·JPG 한 번에 만들기, 구매자에게 보낼 공유 링크(로그인 없이 그 구매자 것만 보이는 서명된 만료 링크, 전화번호 원문 없음), 엑셀 판매대장 바로 받기. 방송 콘솔에서 "영수증 보내기" 한 화면으로 끝난다. 세법상 증빙 아님 고지(STL-05) 유지.

공통 약속(모든 기준에 적용)
- 금액·문장은 확인서 데이터(STL-04, D-206) 그대로다. 서버·화면이 다시 계산하지 않는다(남은 금액 = 최종 − 받은 금액만 표시용).
- 날짜는 실제 범위 날짜(KST `YYYY-MM-DD`). "묶음" = 그 날짜 정산 묶음(지금의 구매자 하나). "품목 있는 묶음" = I2의 확인서를 만들 수 있는 묶음.
- 서버 응답의 개인 데이터는 `Cache-Control: no-store`. 다른 판매자의 날짜·구매자·링크는 404(있는지 알리지 않음, D-074). 서버 로그에 링크 토큰·링크 주소·구매자 이름·계좌를 남기지 않는다(NFR-06).
- 화면 문구는 쉬운 한국어(영어 상태값·개발 용어 없음, CLAUDE.md 규칙 8). 날짜는 연도·요일까지(D-102).

## A. 서버 — 확인서 JPG·전원 이미지 묶음 (RCP-02, STL-04, D-N4b-03)

### AC-N4b-01 [server] 한 사람 확인서 JPG
- 근거: RCP-02 "구매자별 확인서 PDF·JPG", STL-04 "휴대폰에서 이미지로 공유", D-207, D-N4b-03
- Given 실제 범위 날짜 D에 품목 있는 구매자 A(문자 구매자, 휴대폰 번호 있음)
- When 판매자가 A의 확인서 JPG를 받는다(I2 `receipt.png`와 같은 날짜·구매자 인자)
- Then `Content-Type: image/jpeg`, 파일 이름 `확인서-YYYY-MM-DD-<이름>.jpg`(D-I2-01 이름 규칙, 리허설 범위면 앞에 `리허설-`), `Cache-Control: no-store`.
- Then 바이트는 기본(baseline) JPEG다: `FF D8`로 시작, `FF D9`로 끝남, 프레임 머리 `SOF0`(`FF C0`)이고 `SOF2`(점진)가 아님, 구성 요소 3개(YCbCr), APP1(EXIF)·주석(`FF FE`)이 없다.
- Then 같은 확인서 데이터(같은 만든 시각 — E2E의 `?at=`처럼)로 만든 PNG와 너비(1080)·높이가 같고, 디코드한 밝기의 칸마다 차이 평균이 255 중 4 이하다(같은 그림). 확인서 아래 STL-05 고지 문장이 그림에 들어 있다(PNG와 같은 그림이므로 — PNG 쪽 기존 시험이 문장을 고정한다).
- Then 품목 없는 묶음·없는 구매자는 I2 PNG와 같은 답(같은 상태·문장)이다. 리허설 범위도 만든다(제목 "(리허설)" — PNG와 같은 그림).
- 확인: 서버 단위(JPEG 머리 읽기·디코드 비교 — 디코더는 시험 전용 의존성 가능)

### AC-N4b-02 [server] 전원 이미지 묶음(ZIP)
- 근거: RCP-02 "구매자별 확인서 PDF·JPG 일괄", D-207, D-I2-04, D-N4b-03
- Given 날짜 D에 품목 있는 묶음 3개(찍힌 이름 `🌵가람`, `나비`, `나비` — 서로 다른 구매자)와 품목 없는 묶음 1개
- When 판매자가 D의 전원 이미지 묶음을 받는다
- Then `Content-Type: application/zip`, 파일 이름 `확인서-YYYY-MM-DD-전원-이미지.zip`(리허설 `리허설-확인서-…`). 안에 파일 3개, 순서는 전원 PDF와 같은 일괄 순서(D-I2-04: 찍힌 이름 순, 같으면 구매자 ID 순) — `확인서-YYYY-MM-DD-가람.jpg`, `확인서-YYYY-MM-DD-나비.jpg`, `확인서-YYYY-MM-DD-나비-2.jpg`(겹치면 뒤에 `-2`·`-3`, 순서상 뒤의 것에 붙는다). 품목 없는 묶음은 없다. 폴더 없음.
- Then 각 항목의 이름은 UTF-8로 적고 일반 목적 비트 11(UTF-8)이 켜져 있다. 각 JPG는 그 구매자 한 사람 JPG(AC-N4b-01)와 같은 규칙의 파일이다(같은 만든 시각이면 같은 바이트). 묶음 안 모든 확인서의 만든 시각은 하나(요청 때 서버 시각)다.
- Then 품목 있는 묶음이 없으면 파일 없이 I2 전원 PDF와 같은 답("아직 판매 기록이 없어요." 등 I2 문장)이다.
- Then 성능: 구매자 100명(품목 합 500개) 묶음을 30초 안에 만든다(AC-P2-24와 같은 기준). 파일 작업 한도·바쁠 때 답은 I2 파일 작업과 같다(`WORK_BUSY` 문장, 요청 취소 시 작업 중단).
- 확인: 서버 단위(ZIP 읽기 — 항목 이름·플래그·순서·JPG 머리), 성능은 서버 단위 또는 `*.perf.test.*`

### AC-N4b-03 [server] 기존 파일 그대로
- 근거: STL-04·STL-06·STL-10, D-I2-01·D-I2-03
- Then I2의 한 사람 PDF·PNG, 전원 PDF, 판매대장 엑셀의 경로·이름·내용·오류 답은 바뀌지 않는다(I2 서버 시험이 그대로 통과).
- 확인: 서버 단위(기존 시험)

## B. 서버 — 공유 링크 관리 (RCP-02, D-N4b-01·05·06)

### AC-N4b-10 [server] 링크 만들기
- 근거: RCP-02 "구매자에게 보낼 공유 링크(로그인 없이 그 구매자 것만, 만료)", D-N4b-01
- Given 실제 범위 날짜 D, 품목 있는 지금의 구매자 A, A에게 쓸 수 있는 링크가 없음
- When 판매자가 요청 번호와 함께 (D, A) 링크 만들기를 보낸다
- Then 링크 기록 하나가 저장된 뒤에만 성공이다(NFR-03): 판매자·D·A의 구매자 ID·만든 시각(서버 시계, UTC 저장)·만든 계정·끝나는 시각 = 만든 시각 + 14×24시간. 답: 링크 주소 `<앱 주소>/r/<토큰>`(앱 주소 = 설정한 앱 주소 — `Origin` 검사와 같은 값)·끝나는 시각.
- Then 토큰은 암호학적 무작위 32바이트의 base64url(43글자, `=` 없음)이다. DB에는 토큰 원문이 없다 — 찾기용 SHA-256 해시와, 판매자 키로 암호화한 토큰(다시 복사용)만 있다(DB 행을 읽은 시험이 원문 문자열을 찾지 못한다).
- Then 같은 요청 번호의 재전송은 처음 답을 그대로 돌려주고 새 기록을 만들지 않는다. 다른 요청 번호라도 (D, A)에 쓸 수 있는 링크가 이미 있으면 새로 만들지 않고 그 링크(같은 주소·끝나는 시각)를 돌려준다. 동시에 두 기기가 만들어도 쓸 수 있는 링크는 하나다.
- Then 거절(기록 없음): 리허설 범위 → 409 "리허설 방송은 공유 링크를 만들지 않아요."; 품목이 없는 묶음·다른 구매자에 합쳐진 구매자·없는 구매자 → 409 "확인서를 만들 상품이 없어요." (다른 판매자·없는 날짜는 404). 본문은 요청 번호·구매자만 받는다(다른 칸 `UNKNOWN_FIELD`, 형식 틀림 `INVALID_INPUT` — 기존 API 오류 형식).
- 확인: 서버 단위

### AC-N4b-11 [server] 링크 전부 만들기
- 근거: RCP-02, D-N4b-01·04
- Given 날짜 D에 품목 있는 묶음 5개 — 그중 2개는 쓸 수 있는 링크가 이미 있고, 1개는 기간이 지난 링크, 1개는 끊긴 링크가 있다
- When 판매자가 요청 번호와 함께 D의 링크 전부 만들기를 보낸다
- Then 쓸 수 있는 링크가 없는 3개에만 새 링크를 만든다(한 트랜잭션 — 일부만 저장되지 않는다). 답 = 새로 만든 수(3)와 묶음마다의 링크 상태(AC-N4b-12 목록과 같은 모양). 같은 요청 번호 재전송은 같은 답·새 기록 없음. 모두 이미 있으면 새로 만든 수 0.
- Then 리허설 범위는 AC-N4b-10과 같은 거절. 품목 있는 묶음이 없으면 새로 만든 수 0(오류 아님).
- 확인: 서버 단위

### AC-N4b-12 [server] 링크 목록
- 근거: RCP-02, D-N4b-01·05
- When 판매자가 날짜 D의 링크 목록을 조회한다
- Then 품목 있는 묶음마다 한 줄(일괄 순서): 구매자 ID·링크 상태 `없음`/`있음`/`기간 지남`/`끊김`(가장 최근 링크 기준 — 화면 문구는 화면이 정한다)·`있음`이면 링크 주소와 끝나는 시각, `기간 지남`·`끊김`이면 그 시각. 판매자 키로 토큰을 풀어 주소를 다시 만든다(같은 링크를 다시 복사할 수 있다).
- Then 품목 없는 묶음·합쳐진 구매자의 링크는 목록에 줄이 없다(링크 기록은 남는다).
- Then 리허설 범위 목록은 빈 목록이다(오류 아님 — 화면이 링크 칸을 보이지 않는다).
- 확인: 서버 단위

### AC-N4b-13 [server] 링크 끊기
- 근거: D-N4b-01·05
- Given (D, A)에 쓸 수 있는 링크 L
- When 판매자가 요청 번호와 함께 (D, A) 링크 끊기를 보낸다
- Then L에 끊은 시각·끊은 계정이 저장된 뒤에만 성공이다. 그 뒤 L을 열면 AC-N4b-23의 "열 수 없음"이다(다음 요청부터 — 캐시 없음). 기록은 지우지 않는다.
- Then 쓸 수 있는 링크가 없으면 성공(바뀐 것 없음)이고 같은 요청 번호 재전송도 같은 답이다. 끊은 뒤 "링크 만들기"는 새 토큰(L과 다른 주소)이고 L은 다시 열리지 않는다.
- 확인: 서버 단위

### AC-N4b-14 [server] 권한·복구·백업
- 근거: SYS-02·SYS-04, DAT-04, D-I2-11·D-I2-12, D-N4b-04·06
- Then 링크 만들기·전부 만들기·목록·끊기와 JPG·ZIP은 로그인한 판매자만 쓴다: 로그인 없음 401, 보조자 계정 403(기존 보조자 막기와 같은 답), 상태를 바꾸는 요청은 `/api` 공통 `Origin`·JSON 검사.
- Then 운영자 복구·가져오기 명령(D-I2-11)이 판매자 기록을 바꾸면(바꾸기 옵션) 같은 트랜잭션에서 그 판매자의 링크 기록이 모두 지워진다 — 복구 전에 만든 링크를 열면 "열 수 없음". 기록이 없던 판매자로의 가져오기도 그 판매자 링크가 남지 않는다. 다른 판매자의 링크는 그대로다.
- Then 판매자 백업·전체 기록(JSON, D-I2-10·12)에는 링크 기록이 없고 파일 형식 번호는 바뀌지 않는다(기존 백업 시험 그대로).
- 확인: 서버 단위

## C. 서버 — 구매자 확인서 링크 화면 `/r/<토큰>` (RCP-02, STL-04·05, D-N4b-02)

### AC-N4b-20 [server] 링크를 열면 그 구매자의 지금 확인서
- 근거: RCP-02 "로그인 없이 그 구매자 것만", STL-04, STL-05, D-N4b-02
- Given 가게 이름 "다육이네", 입금 계좌(은행 "국민"·계좌번호 "123-45-6789"·예금주 "김다육")와 안내 문장이 있는 판매자, (D, A) 쓸 수 있는 링크. A는 상품 3개·최종 18,000원·5,000원 부분 입금
- When 로그인하지 않은 브라우저(쿠키 없음)가 `GET /r/<토큰>`
- Then 200, `Content-Type: text/html; charset=utf-8`, 서버가 그린 문서 한 장(앱 화면 `index.html`이 아니다). 문서에 `<script>`가 없다.

- Then **지금 상태**: 판매자가 A의 입금을 더 기록하거나 상품을 취소한 뒤 다시 열면 바뀐 금액·상태가 보인다(사본이 아니다). 확인서의 만든 시각 = 연 때의 서버 시각.

### AC-N4b-40 [e2e] 방송 끝 → 링크 → 구매자가 연다
- 근거: RCP-02 전체, D-N4b-01~05
- Given 실제 방송에 상품 3개, 1등 구매자 2명(유튜브 채팅 구매자 `🌵가람`, 문자 구매자 — 휴대폰 번호 있음), 가게 계좌 설정
- When 판매자가 방송을 끝내고 "영수증 보내기" → "링크 전부 만들기" → 문자 구매자 줄 "링크 복사"
- Then 클립보드 글의 링크를 **로그인하지 않은 새 브라우저 문맥**(쿠키 없음, 휴대폰 크기)으로 열면 그 구매자의 이름·금액·입금 계좌·고지 문장이 보이고, 그림(JPG)이 실제로 그려진다(`naturalWidth` 1080). 문서 글자·HTML에 그 휴대폰 번호 전체·다른 구매자 이름이 없다. "PDF로 받기"가 PDF(`%PDF-`)를 준다.
- When 판매자가 그 구매자에게 입금 기록을 더한 뒤 구매자가 새로고침
- Then 입금 상태가 바뀌어 보인다.
- When 판매자가 "링크 끊기"
- Then 구매자 문맥에서 새로고침하면 "이 링크는 열 수 없어요. 판매자에게 새 링크를 받아 주세요."
- 확인: E2E

### AC-N4b-41 [e2e] 한 번에 받기
- 근거: RCP-02, D-N4b-03·04
- When 같은 화면에서 "전원 확인서 PDF"·"전원 이미지(JPG) 묶음"·"이 방송 판매대장 엑셀"
- Then 받은 파일 이름이 각각 `확인서-YYYY-MM-DD-전원.pdf`·`확인서-YYYY-MM-DD-전원-이미지.zip`·`판매대장-YYYY-MM-DD.xlsx`이고, ZIP 안에 JPG 2개(일괄 순서 이름), 엑셀 첫 시트 "판매대장"에 이 방송의 행만 있다(같은 날 다른 방송 행 없음).
- 확인: E2E

### AC-N4b-42 [e2e] 리허설·보조자·휴대폰
- 근거: D-N4b-04, SYS-04
- Then 리허설 방송을 끝낸 콘솔 → "영수증 보내기"에 링크·판매대장이 없고 안내 문장이 보이며, "전원 이미지(JPG) 묶음" 파일 이름이 `리허설-확인서-…-전원-이미지.zip`이다.
- Then 보조자로 로그인하면 끝난 콘솔(보조자가 볼 수 있는 화면이 아니면 그 안내)에서 "영수증 보내기"를 볼 수 없고 링크 API는 403이다.
- Then 휴대폰 크기(375×812)에서 AC-N4b-34의 가로 스크롤·44px·16px를 영수증 보내기 화면과 구매자 링크 화면 둘 다에서 확인한다.
- 확인: E2E

## 범위 밖 (이번에 하지 않는 것)
- 우리가 링크·확인서를 구매자에게 보내기(유튜브 채팅·인스타그램 DM·문자·카카오 알림톡) — 판매자가 복사·공유로 보낸다(D-N4b-05).
- 링크를 연 기록(구매자가 열어 봤는지)·연 횟수 보기, 링크 기간 늘리기(새 링크로 대신), 링크 비밀번호.
- 구매자가 링크 화면에서 하는 일(입금 알림·주소 입력·취소 요청) — 보기·받기만.
- 현금영수증 발행 기록 칸(STL-05 "별도 기록 칸") — 그 이벤트·화면을 정하는 스프린트.
- 확인서 내용·배치·글꼴·PNG 그리기 변경(device, D-206·D-207), 판정·정산 규칙 변경(core).
- 정산 화면·포장 모드에 링크 버튼을 더하기 — 링크는 "영수증 보내기" 한 화면에서만(길 하나, D-I2-13 취지).
- 판매대장 채널 칸의 인스타그램 표기(N4 — PLT-03).
- 실제 메신저(카카오톡·문자·밴드)의 링크 미리 보기·JPG 받기, 윈도·맥 압축 풀기 한글 이름 — 사람 확인(최종 보고).
