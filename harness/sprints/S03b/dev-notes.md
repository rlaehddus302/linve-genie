# S03b 개발 노트

## dev-core

### 만든 것
- 판정 엔진 (`packages/core/src/engine/**`)
  - **sms 이벤트 (D-061)**: `phone`이 없어지고 `phoneKey`(영문·숫자·`_`·`-` 16~128자)·`phoneLast4`(숫자 4자리)를 함께 받는다. `ref`는 영문·숫자·`_`·`-` 1~64자.
    - 입력 오류: `phone` 필드가 있음(값이 무엇이든, `undefined`여도), `phoneKey`·`phoneLast4` 한쪽만, 각 필드 형식 위반.
    - `checkEvent`는 같은 경우에만 문제를 돌려준다. 짝이 한쪽만이면 빠진 쪽 필드 이름을 짚는다(`phoneKey`만 → `phoneLast4`).
  - **구매자 정하기**: 지정 구매자 → 전화번호 키 → 새 문자 구매자.
    - 새 문자 구매자의 뒤 4자리는 그 구매자를 만든 문자찜의 `phoneLast4`이고, 나중에 바뀌지 않는다.
    - 지정 구매자가 있으면 키를 보지도 기록하지도 않는다.
  - **ref 기록 (D-067)**: ref는 처음 받을 때 기록한다. 모르는 지정 구매자이면 `refs[ref] = null`로 기록하고 찜·구매자·메모는 반영하지 않는다. 같은 ref가 다시 오면, 처음 것이 무엇을 했든 내용이 달라도 아무 일도 없다(같은 상태 객체를 돌려준다).
  - **메시지 변환 (D-062)**: 메시지 기록에 `order`(받을 때 R-3이 주문 번호를 하나라도 읽었는지)와 `converted`(바꾼 번호)를 둔다. 주문이었던 메시지는 어느 번호로도 아무 일도 없다.
  - **시청자 채팅 취소 (D-063)**: 지금의 구매자의 활성 찜이 그 채널 자신의 찜(`claim.buyer === 채널`)일 때만 취소하거나 요청한다. 자기 찜에는 채팅 주문·변환·그 채널에 한 배정·그 채널을 지정한 문자찜이 들어간다.
  - **`host.assign` (D-064·D-065)**: 충돌 중인 상품이면 아무 일도 없다. `replace`·`replaceTo` 한쪽만 오는 것은 이제 입력 오류다(검사 함수). 리듀서의 한쪽만 검사는 닿을 수 없게 되어 지웠다.
  - **넘침 정리 (D-068)**: `rules.releaseConflict`는 충돌 찜을 KEEP처럼 대기 자리에 넣되 정리하지 않는다. 정리는 그다음에 한다.
    - `release()`(방송자 취소·무효·취소 승인·시청자 자동 취소): `releaseConflict` → 승계 → `trimWaitlist`
    - 재고 늘림: `releaseConflict` → 늘린 수만큼 확정 → `trimWaitlist`
    - `host.resolveConflict(KEEP)`·새 찜·밀려난 1등은 S03 그대로 넣자마자 정리한다.
  - **확정버전 (D-066)**: 재고 늘림은 이미 대기 순번 순서였다. 코드는 바꾸지 않았고, 속성·단위 테스트로 그 순서를 고정했다.
- 조회
  - `getBuyer`·`listBuyers`의 `phoneLast4`는 구매자 기록의 뒤 4자리다. 키는 보이지 않는다.
  - `buyerOfRef`는 구매자를 정하지 않은 ref에 `null`을 돌려준다.
  - `listSmsRefs`에는 구매자를 정한 ref만 넣는다. 모르는 지정 구매자의 ref는 넣지 않는다 — AC-S03b-10이 dev-core에 맡긴 선택이고, `SmsRefInfo.buyer`를 `string`으로 유지한다.
- 공개 도우미: `normalizePhone`(그대로), `phoneLast4(정규화한 번호)`(서버가 sms의 `phoneLast4`로 담는다). HMAC은 비밀 키가 필요해서 코어 밖(서버)에 둔다.

### 결정과 이유 (규칙 문장 안에서의 구현 선택)
- **`phone` 필드는 있기만 해도 입력 오류다(`undefined`여도).** 다른 선택 필드는 `undefined`를 없는 것으로 보지만, 전화번호 원문은 "값이 무엇이든"(AC-S03b-01) 엔진·로그에 닿지 않게 보수적으로 했다. 서버는 sms 이벤트에 `phone` 키를 아예 만들지 않아야 한다.
- **짝 검사는 다른 필드 문제와 상관없이 늘 한다.** 다른 문제가 있어도 빠진 쪽을 함께 보고한다.
- **변환이 찜을 만들지 않았으면(같은 사람 반복, R-4 4번 줄) "그 번호로 바꿨다"로 치지 않는다.** S03 그대로이며, 그 사람의 찜이 끝난 뒤에는 다시 변환할 수 있다. 차단·판매 아님으로 거절된 변환 찜은 찜 기록을 만들었으니 바꾼 것으로 친다.
- **취소만 있는 메시지(`15 취소`)는 R-3이 주문 번호를 읽지 않았으므로 "주문이 아니었던 메시지"다.** 글자 그대로라 변환할 수 있다(아래 질문 1).
- **재고 늘림 뒤 정리는 무조건 부른다.** 충돌이 없으면 대기 수가 한도를 넘을 수 없어 아무 일도 하지 않는다. 승계 뒤 정리(`release`)도 마찬가지다.

### spec-keeper에게 (규칙 문장이 정하지 않았거나 판매자에게 어색할 수 있는 것)
1. **취소 메시지의 변환**: `15 취소`는 R-3 주문 번호가 없어 "주문이 아니었던 메시지"이고, 글자 그대로 변환할 수 있다. 판매자에게 어색할 수 있으니, 변환 대상에서 취소 메시지를 뺄지 화면(S05)에서 버튼을 숨길지 판단을 부탁한다. 지금은 규칙 문장대로 받는다.
2. **이벤트 표에 없는 필드**: 엔진은 무시하고 상태에 남기지 않는다. 다만 서버가 받은 이벤트를 그대로 로그에 쓰면, `Phone`·`phoneNumber`처럼 이름이 다른 번호 필드가 로그에 남을 수 있다. S04 서버는 sms 이벤트를 자기 필드로만 다시 만들어야 한다는 문장을 DAT-06/S04 수용 기준에 넣기를 권한다. 엔진에서 모르는 필드를 입력 오류로 할지는 D-050 범위 밖이라 바꾸지 않았다.
