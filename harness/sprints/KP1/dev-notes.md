# KP1 dev-notes

## dev-web 갈래 D — 방송 리포트·방송 일정·방송 알림

만든 것: `apps/web/src/lib/{report,schedule}.ts`, `components/{ReportPage,ScheduleSettings,AlertCounts}.tsx`, `components/kp1-report.css`(공용 styles.css를 건드리지 않으려 따로 둠), 시험 `apps/web/test/kp1-report-schedule.test.tsx`.
붙인 줄: `lib/router.ts`(`/report?date=` — 메뉴는 정산), `App.tsx`(경로 하나), `SettlementsPage.tsx`(날짜 줄 "방송 리포트" — 실제 범위만), `ConsolePage.tsx`(끝낸 실제 방송의 "오늘 리포트 보기"), `SettingsPage.tsx`("방송 일정"·"방송 알림" 절 — 판매자만).

가정
- 리포트 주소에 날짜가 없으면 정산 화면으로 안내만 한다("볼 날짜가 없어요. …"). 오늘 날짜로 짐작해 열지 않는다.
- 비교 문장: 평균 쪽은 "최근 N번 평균보다 …원 많아요/적어요", "…과 같아요". 개수 단위 "개", 손님 "명".
- 몰린 상품 줄은 "N번 이름"만 쓴다 — 하루에 회차가 둘 이상이면 번호가 겹칠 수 있다(응답에 회차 이름이 없음). 필요하면 서버가 회차 이름을 주도록 계약을 늘려야 한다.
- 시간대 칸이 자정을 넘기면 "다음날 00:00~00:10"으로 적는다. 막대 길이는 칸의 판매 금액 기준, 막대는 화면 낭독기에서 숨기고 같은 줄 글("20:00~20:10 · 3개 · 15,000원")로 읽힌다.
- 방송 중 리포트는 저절로 새로 받지 않고 "새로 보기" 버튼으로 다시 받는다(숫자가 눈앞에서 바뀌어 헷갈리지 않게).
- 일정 제목·소개 칸은 화면이 길이를 자르지 않는다(maxLength 없음, "12/40자" 글자 수만). 41자도 보내 서버 문장을 보인다.
- 다가오는 일정이 10개면 적기 양식 위에 "다가오는 방송은 10개까지 적을 수 있어요."를 미리 보이되 버튼은 막지 않는다(누르면 서버 409 문장, 같은 문장 두 번 안 보임).
- 일정 지우기·새 주소 만들기는 확인 창을 한 번 띄운다. 공개 끄기는 바로 하고 "전에 알려 준 주소는 이제 열리지 않아요."를 보인다.

앱(apps/mobile): 정산·리포트 화면이 없어 리포트 링크는 붙이지 않았다. 설정 화면(`src/screens/SettingsScreen.tsx`)에 "방송 일정"·"방송 알림"은 아직 없다 — 웹 설정에서만 한다(이번 갈래 범위 밖으로 남김).

## dev-web 갈래 C — 손님 장부 화면

새 파일: `apps/web/src/lib/ledger.ts`(타입·부르기·문구·`BadgeQueue`·`useChatBadges`·`useLedgerVersion`), `components/{ChatBadges,CustomerLedger,CustomersXlsxDialog}.tsx`, 시험 `apps/web/test/kp1-ledger.test.tsx`.
기존 파일에 붙인 곳(`// KP1` 표시): `ChatPanel.tsx`(줄 이름 뒤 꼬리표), `ConsolePage.tsx`(훅·제공자, 설정 끔이면 1등 옆 주의도 `HIDDEN_CAUTION`), `CustomerSettings.tsx`(같은 "손님 관리" 칸·저장 막대 단계 하나에서 PUT 둘), `ParcelParts.tsx`(확인 전 칸), `AllCustomers.tsx`(엑셀 버튼·자세히 장부 칸), `api/parcel-types.ts`(`BundleView.ledger?`), `lib/stream.ts`(`'customers'`), `styles.css`(끝 덩어리).

가정:
- 꼬리표 조회가 실패한 구매자는 콘솔을 다시 열 때까지 다시 묻지 않는다(요청 수가 늘지 않게 — "실패하면 꼬리표 없이 조용히").
- 설정을 아직 모르거나 설정 조회가 실패하면 CRM1 그대로 1등 옆 주의를 보인다. 설정이 "끔"(설정 조회 또는 꼬리표 응답 `show=false`)일 때만 숨긴다. 끔이면 꼬리표를 묻지 않고, 다시 켜지면(알림 `customers {what:'settings'}`) 받은 구매자를 다시 묻는다.
- 받기 간격 4초는 앞 요청을 보낸 때부터 센다. 한 번에 한 요청만(앞 요청이 끝나야 다음).
- 꼬리표 색은 글로 가른다: "입금 늦음 주의"=주의 색, "단골…"=단골 색, 그 밖("처음")=옅은 파랑. 화면 읽기 문장은 서버 `spoken`, 없으면 " · "→", ".
- 장부 설정 두 칸은 설정 화면 저장 막대(기존 "손님 관리" 단계)로 저장한다 — 누르자마자 저장하지 않는다(다른 "손님 관리" 칸과 같게, 떠날 때 저장 안 함 경고).
- 묶음 자세히 확인 전 칸은 `customers {what:'ledger'}` 알림·다시 붙음 때 묶음을 다시 받아 지운 장부가 바로 사라지게 했다. 잠긴 묶음(살아 있는 접수)엔 확인 전 칸을 보이지 않고 기존 "배송지가 없어요"+잠김 문장.
- [고치기]는 기존 배송지 적기 창을 장부 다섯 칸(메모 빈칸)으로 채워 열고 기존 `PUT …/address`로 저장. 판매자 양식엔 동의 칸이 없다(AC-KP1-04).
- 손님 자세히 장부 칸: 받는 분(가림)·연락처 끝 4자리·손님이 저장한 날·보관 끝나는 날, 이은 계정은 한 줄에 ", "로 잇는다. 장부가 없으면 "저장해 둔 배송지가 없어요. …" 안내.
- 엑셀 창은 열 때마다 "연락처·주소도 넣기"가 빈칸(기억하지 않음). 받은 뒤 창은 닫지 않는다.
- 앱(`apps/mobile`)엔 채팅 칸·손님 화면·택배 묶음 자세히가 없어(채팅 글은 웹으로) 손댈 곳이 없다.
- 콘솔 전체(ConsolePage) 안에서 설정 끔 → 1등 옆 주의가 사라지는 흐름은 단위 시험이 훅(`show=false`)까지만 본다 — 화면 전체는 e2e 몫.

## dev-server 갈래 B — 리포트·방송 일정·메시지 규칙

가정(스펙에 없는 세부 — 판매자에게 안전한 쪽):
- 리포트 `opened`(RPT-06 공개 시각): 그 범위의 실패 아닌 `product.register`(상태를 READY로 적지 않음)·`product.open` 이벤트 중 그 (방송, 번호) 자리의 첫 `at`. `product.renumber`는 자리를 따라 옮긴다. 몰린 찜 = 그 상품 ID에 붙은 찜(판정 전 보류 찜은 상품 키로), 출처 `assign`(직접 배정)은 뺀다.
- 리포트 수량 = 지금 확정 찜(상품의 1등, 옵션 상품은 모든 변형의 1등)의 수량 합 — 판매대장 확정 행과 같은 찜. 돈은 `listSettlements`의 그 날짜 묶음(정산 화면과 같은 값): 판매 = subtotal, 최종 = total, 받은 돈 = received.
- 봉인 날짜 리포트도 `compare`는 낸다(앞선 날짜 숫자는 손님 기록 재료 — 봉인 날짜는 장부). 봉인 장부를 읽을 수 없으면 500 `LEDGER_UNREADABLE`(기존 문장).
- 일정 고치기: 이미 시작 시각이 지난 일정은 404(목록에서 빠진 것). 지우기는 지난 일정도 된다.
- 새 주소(`renew`)는 공개가 켜져 있을 때만 바꾼다 — 꺼져 있으면 그대로 돌려준다.
- 공개 페이지 가게 이름이 비면 "이 가게". 채널 주소는 적은 글 그대로 저장(정규화하지 않음 — 한글 핸들 보존), 페이지에선 이스케이프.
- 알림 양식 한도(1분 10번)는 신청과 그만 받기를 함께 센다(토큰마다·접속 주소마다). 403(Origin 틀림)은 세지 않는다. 양식 본문 2KB 상한.
- 정리 작업(`sweepSchedule`)은 `WITHDRAWN`인데 번호가 남은 줄도 지운다(그만 받기가 이미 지우지만 혹시 남은 것).
- `alert_consents.subscriber_id`는 `alert_subscribers.id` 외래 키(구독자 줄은 지우지 않고 번호 칸만 null).
- 마이그레이션 0032는 저널 `when` 1794960000006 — 0030(`dev/yt-thanks-official`)·0031 자리를 비워 둠. 합칠 때 번호가 겹치면 번호만 바꾼다.
- `index.ts`의 `export * from './messaging/rules.ts'`: 생성기의 `MessageKind`(같은 이름)가 이기므로 메시지 종류는 `MessageRuleKind`로도 낸다.
