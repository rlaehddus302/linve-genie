- **합칠 때 겹치지 않게**: 새 표(공급자 연결·간편 로그인 state)와 세션 칸 하나(만든 방법)는 마이그레이션 하나로 더한다. 기존 표의 칸 뜻은 바꾸지 않는다.

| 코드 | 언제 | 화면 | 문장 |
|---|---|---|---|

| `EXPIRED` | state 없음·모름·이미 씀·10분 지남·브라우저 쿠키와 안 맞음·공급자가 다름, 연결 요청의 세션이 바뀜 | 로그인 / 설정 | "로그인 요청이 오래됐거나 다른 창에서 시작한 요청이에요. 처음부터 다시 해 주세요." |
| `NOT_LINKED` | 로그인: 그 공급자 계정이 어느 판매자 계정에도 연결되지 않음 | 로그인 | "이 {공} 계정에 연결된 라이브찜 계정이 없어요. 아이디로 로그인한 뒤 설정 → 로그인 방법에서 {공} 계정을 연결해 주세요." |

| `LINKED` | 연결 성공 | 설정 | "{공} 계정을 연결했어요. 다음부터 "{공}로 계속하기"로 로그인할 수 있어요." |

## API 뜻 (dev-server가 dev-notes에서 경로 이름을 확정한다)

모든 경로는 기존 `/api` 규칙(D-074: 상태를 바꾸는 요청의 `Origin`·JSON·64KB, 다른 판매자 자원 404, `Cache-Control: no-store`, 받은 값을 오류에 되돌려 보내지 않음, 모르는 항목 400 `UNKNOWN_FIELD`)을 따른다. 설정되지 않은 공급자의 경로는 404다.

| 뜻 | 세션 | 요청 | 응답·동작 |
|---|---|---|---|
| 화면 설정 | 없음 | 기존 `GET /api/client-config` | 더함: 켜진 공급자 목록(순서 카카오·네이버·구글, 이름만 — 클라이언트 ID·주소 없음) |
| 간편 로그인 시작 | 없음 | `POST` `{ provider }` | `{ authorizeUrl }` + state 쿠키(AC-L1-03) |
| 연결 시작 | 판매자 | `POST` `{ provider }` | `{ authorizeUrl }` + state 쿠키. 보조자 403 |
| 돌아오는 주소 | 없음(state·쿠키로 판단) | `GET <앱 주소>/api/auth/<provider>/callback` | 302 → `/?login=<코드>&provider=<p>` 또는 `/settings?login=<코드>&provider=<p>` (AC-L1-04~06) |
| 로그인 방법 목록 | 판매자 | `GET` | `{ loginId, providers: [{ provider, enabled, linked, label, linkedAt }] }` — 켜진 공급자 전부 + 꺼졌지만 연결이 남은 공급자. 보조자 403 |
| 연결 끊기 | 판매자 | `POST` `{ provider }` | 200 새 목록, 연결이 없으면 404, 남는 수단이 없으면 409(AC-L1-07). 보조자 403 |

## A. 서버

### AC-L1-01 [server] 공급자 설정·켜짐·시작 거부
- 근거: D-L1-07, SYS-05, D-I3-13
- Given 공급자마다 환경 변수: 구글 클라이언트 ID·비밀값(유튜브 연결용과 **다른 이름**, 값은 같아도 됨), 카카오 REST API 키(필수)·클라이언트 시크릿(선택), 네이버 클라이언트 ID·비밀값. 이름은 dev-notes에서 정한다
- Then 필요한 값이 모두 있는 공급자만 켜진다. 하나도 없으면 꺼진다(AC-L1 "환경 변수가 없으면 지금과 똑같다").
- Then 필요한 값 중 일부만 있으면 운영 시작(`main`)이 멈추고 "구글 로그인 설정이 반만 적혀 있어요. 둘 다 적거나 둘 다 지워 주세요."(공급자 이름만 바뀜)를 알린다. 카카오는 REST API 키 없이 시크릿만 있을 때 멈춘다. 값은 어떤 출력에도 나오지 않는다.
- Then 공급자 주소(승인·토큰·사용자 정보)는 서버 고정값(https)이고, 주소 바꾸기는 시험·연습 기동에서만 된다 — 운영 시작에는 그 설정이 없다(있으면 무시가 아니라 시작 거부 또는 설정 자체가 없음 — dev-notes에 적는다).
- Then `client-config`는 켜진 공급자 이름만 카카오·네이버·구글 순으로 알린다.
- 확인: 서버 단위(기동 설정)

### AC-L1-02 [server] 표·유일·토큰 칸 없음
- 근거: D-L1-02·D-L1-03·D-L1-04, SYS-02
- Then 새 표 "공급자 연결": 판매자 계정 ID, 판매자 ID, 공급자, 공급자 계정 ID, 가린 이름(빈 값 가능), 연결한 시각, 마지막 로그인 시각. **(공급자, 공급자 계정 ID) 유일**, **(계정 ID, 공급자) 유일**(데이터베이스 제약). 판매자(`SELLER`) 계정만 들어간다.
- Then 새 표 "간편 로그인 state": state 해시, 브라우저 쿠키 값 해시, 공급자, 목적(로그인·연결), 연결이면 계정 ID·세션 해시, PKCE 검증 값(암호화 — D-Y02와 같은 방식, 구글·카카오만), 만든 시각, 끝 시각(10분), 쓴 시각. 지난 행은 정리한다.
- Then 세션 표에 만든 방법(`PASSWORD`·`GOOGLE`·`KAKAO`·`NAVER`) 칸을 더한다. 기존 세션은 `PASSWORD`.
- Then 어느 표에도 액세스·새로 고침·ID 토큰, 인가 코드, 이메일 원문, 닉네임 원문 칸이 없다(스키마 대조 시험).
- Then 마이그레이션 하나로 더하고 기존 `test/schema.test.ts`식 대조 시험이 통과한다. 서버를 다시 켜도 연결이 그대로다.
- 확인: 서버 단위

### AC-L1-03 [server] 시작 — 승인 주소·state·쿠키
- 근거: D-L1-04·D-L1-05
- When 간편 로그인 시작 또는 연결 시작
- Then 응답 `authorizeUrl`은 그 공급자의 승인 주소이고 다음을 담는다: `response_type=code`, 클라이언트 ID, `redirect_uri` = `<앱 주소>/api/auth/<provider>/callback`(설정한 앱 주소로 만든다 — 요청 Host·`X-Forwarded-Host`가 무엇이든 같음), `state`(무작위 32바이트 이상을 base64url로).
  - 구글: `scope=openid email`(유튜브 권한·`include_granted_scopes`·`access_type=offline` 없음), `code_challenge`(S256)·`code_challenge_method=S256`, `prompt=select_account`.
  - 카카오: `scope` 없음(추가 권한을 묻지 않음), `code_challenge`(S256)·`code_challenge_method=S256`.
  - 네이버: PKCE 없음, `state` 늘 있음.
- Then 응답이 state 쿠키를 심는다: 무작위 값, `HttpOnly`·`Secure`·`SameSite=Lax`, 경로 `/api/auth`, 10분. 서버엔 state·쿠키 값 모두 해시만.
- Then 같은 브라우저에서 시작을 여러 번 해도(두 탭) 각 state는 따로 살아 있고, 쿠키는 그 브라우저의 최근 시작들과 짝이 맞는다(앞 탭의 돌아옴이 `EXPIRED`가 되어도 되지만 다른 브라우저의 state로는 절대 통과하지 않는다 — 방식은 dev-notes).
- Then 연결 시작은 판매자 세션만(보조자 403, 세션 없음 401), 그 판매자 계정·세션 해시를 state 행에 묶는다. 간편 로그인 시작은 세션이 필요 없다.
- Then 꺼진 공급자·모르는 공급자는 404. 상태를 바꾸는 요청이라 `Origin`이 앱 주소가 아니면 403(D-074).
- 확인: 서버 단위

### AC-L1-04 [server] 돌아오는 주소 — 검사 순서·한 번만
- 근거: D-L1-04
- When `GET .../callback?code=…&state=…`(또는 `?error=…&state=…`)
- Then 순서대로:
  1. 로그인 IP 한도(D-I3-12)에 한 번 센다 — 넘으면 `RATE_LIMITED`(공급자를 부르지 않음).
  2. `error`가 있으면: 취소 값이면 `CANCELLED`, 아니면 `PROVIDER_ERROR`. state가 맞으면 그 state를 쓴 것으로 표시한다.
  3. state가 없거나·모르거나·이미 썼거나·끝났거나·공급자가 다르거나·브라우저 쿠키 해시와 맞지 않으면 `EXPIRED`(공급자를 부르지 않음).
  4. state를 **쓴 것으로 먼저 표시**한다(한 문장, 동시에 두 번 와도 하나만 다음으로 간다).
  5. 연결 요청이면 그 세션이 아직 살아 있고 state 행의 세션·계정과 같아야 한다 — 아니면 `SESSION_GONE`.
  6. 코드 교환(같은 `redirect_uri`, 구글·카카오는 `code_verifier`, 비밀값은 서버에서만), 사용자 정보 조회(구글 userinfo `sub`, 카카오 `/v2/user/me` `id`, 네이버 `/v1/nid/me` `response.id`) — 실패·10초 넘음·ID 없음은 `PROVIDER_ERROR`.
  7. 받은 토큰은 이 요청 안에서만 쓰고 버린다(AC-L1-09).
- Then 같은 돌아오는 주소(같은 code·state)를 두 번 열면 두 번째는 `EXPIRED`이고 세션이 하나 더 생기지 않으며 공급자를 다시 부르지 않는다.
- Then 302의 `Location`은 늘 앱 주소 안의 고정 경로(`/` 또는 `/settings`) + `login`·`provider` 두 매개변수뿐이다. 요청에 어떤 매개변수(`next`·`redirect`·`return_to` 등)가 와도 바뀌지 않는다. state 쿠키는 지운다.
- Then 응답은 `Cache-Control: no-store`, `Referrer-Policy: no-referrer`(기존 머리글 그대로).
- 확인: 서버 단위

### AC-L1-05 [server] 간편 로그인 결과 — 가입 없음
- 근거: D-L1-01·D-L1-02, D-074
- Given 판매자 A 계정에 카카오 계정 K1이 연결돼 있다
- When K1으로 간편 로그인
- Then A의 세션이 생긴다: 쿠키는 D-074와 똑같다(`lj_session`, `HttpOnly`·`Secure`·`SameSite=Lax`, 30일·쓰는 동안 연장), 세션 만든 방법 `KAKAO`, 302 → `/`(결과 코드 없음 또는 화면이 아무 문장도 보이지 않는 코드). 마지막 로그인 시각·가린 이름이 새로 고쳐진다.
- Then 그 세션으로 할 수 있는 것은 A가 아이디로 로그인했을 때와 정확히 같다(판매자 권한).
- When 어느 판매자에게도 연결되지 않은 카카오 계정 K2로 간편 로그인
- Then 계정·판매자·연결·세션 어느 것도 생기지 않고 302 → `/?login=NOT_LINKED&provider=kakao`. 모든 표의 행 수가 그대로다.
- Then 공급자 계정이 판매자 A와 같은 이메일이어도 결과가 같다(이메일은 찾는 데 쓰지 않는다).
- Then 아이디 잠금(D-074 — 같은 아이디 10번 틀림)이 걸린 계정도 연결한 공급자로는 로그인된다. 이미 로그인한 세션은 어느 쪽이든 그대로다.
- 확인: 서버 단위, 적대

### AC-L1-06 [server] 연결 결과
- 근거: D-L1-02·D-L1-03
- Given 판매자 A가 로그인해 있다(어느 방법이든)
- When 연결 시작 → 공급자에서 동의 → 돌아옴
- Then 처음 연결: 연결 행이 생기고 302 → `/settings?login=LINKED&provider=<p>`. 실시간 알림(설정이 바뀜)으로 A의 다른 화면도 목록을 새로 읽는다(종류는 dev-notes).
- Then 같은 공급자 계정을 다시 연결: `LINKED`, 행은 그대로(가린 이름만 새로 고침).
- Then 그 공급자 계정이 다른 판매자 B에게 연결돼 있으면 `LINKED_ELSEWHERE` — B의 연결은 그대로, A에게 아무것도 생기지 않는다. 응답·문장에 B에 관한 것(아이디·가게 이름)이 없다.
- Then A에게 그 공급자의 다른 계정이 이미 있으면 `ALREADY_LINKED` — 바뀌지 않는다.
- Then 연결 도중 A가 로그아웃했거나 세션이 끝났으면 `SESSION_GONE`, 302 → `/?login=SESSION_GONE&provider=<p>`, 아무것도 생기지 않는다.
- Then 연결 성공은 새 세션을 만들지 않는다(지금 세션 그대로).
- 확인: 서버 단위, 적대

### AC-L1-07 [server] 목록·끊기·보조자
- 근거: D-L1-02·D-L1-03, SYS-04
- Then 목록은 그 판매자 계정의 것만: 아이디, 켜진 공급자마다 `linked`·가린 이름·연결한 시각, 꺼졌지만 연결이 남은 공급자는 `enabled: false`로. 공급자 계정 ID는 응답에 없다.
- When 끊기 `{ provider }`
- Then 연결 행이 지워지고, 그 계정에서 그 공급자로 만든 세션이 모두 지워진다 — **요청한 지금 세션은 그 공급자로 만든 것이어도 남는다**. 지운 세션의 실시간 연결은 닫힌다(보조자 지우기 AC-I3-62와 같은 방식). 아이디로 만든 세션과 다른 공급자로 만든 세션은 그대로다.
- Then 끊은 뒤 그 공급자 계정으로 간편 로그인하면 `NOT_LINKED`이고, 다른 판매자가 그 공급자 계정을 새로 연결할 수 있다.
- Then 연결이 없는 공급자를 끊으면 404, 끊은 뒤 로그인 수단(비밀번호 + 남은 연결)이 0이 되는 요청은 409 — 지금은 비밀번호가 늘 있어 생기지 않지만 서버 단위 시험이 비밀번호 없는 계정을 직접 만들어 409를 확인한다.
- Then 보조자 세션의 목록·연결 시작·끊기는 403(보조자 허용 목록 밖 — AC-I3-61 방식). 보조자 계정 ID로 연결 행을 만들 길이 없다(간편 로그인 결과는 판매자 계정만 찾는다).
- 확인: 서버 단위, 적대

### AC-L1-08 [server] 이메일 없음·가린 이름

### AC-L1-09 [server] 비밀 보호 — 토큰·코드·state·ID

### AC-L1-20 [web] 로그인 화면 버튼
- 근거: D-L1-06, AC-S05-01, UX-03
- Given 세 공급자가 켜진 서버

### AC-L1-22 [web] 설정 "로그인 방법"
- 근거: D-L1-03·D-L1-06, SPEC §7 화면 8
- Given 판매자로 로그인, 공급자가 하나라도 켜져 있음
- Then 설정 화면에 "로그인 방법" 칸: 첫 줄 "아이디 로그인 · 아이디 <아이디> · 늘 켜져 있어요"(끄는 버튼 없음), 공급자마다 카카오·네이버·구글 순으로 "연결 안 됨" + [연결하기] 또는 "<가린 이름, 비면 '카카오 계정'> · <연결한 날짜 YYYY. M. D.>" + [연결 끊기]. 서버에서 꺼진 공급자의 남은 연결은 "지금은 쓸 수 없어요" + [연결 끊기]만.
- When [연결하기]
- Then 버튼이 잠기고 "카카오로 이동하는 중…", 승인 주소로 이동 → 돌아오면 `/settings`에서 결과 문장(AC-L1-21)과 새 목록.
- When [연결 끊기]
- Then 확인 창: "카카오 연결을 끊을까요? 끊으면 카카오로 로그인할 수 없고, 카카오로 로그인해 둔 다른 기기는 로그아웃돼요. 아이디 로그인은 그대로예요." [연결 끊기] / [그만두기](기본 포커스는 그만두기, Esc = 그만두기). 끊으면 "카카오 연결을 끊었어요."와 새 목록, 지금 화면은 로그인된 채다.
- Then 공급자가 하나도 켜져 있지 않고 남은 연결도 없으면 칸이 없다(L1 전과 같다). 휴대폰 폭에서 버튼 44px 이상.
- 확인: E2E

### AC-L1-23 [web] 보조자에게 없음
- 근거: D-L1-02, SYS-04
- Then 보조자로 로그인하면 설정에 "로그인 방법" 칸이 없고 목록 API를 부르지 않는다(403을 보지 않음). 로그인 화면은 누구에게나 같다(보조자도 버튼을 볼 수 있지만, 보조자 계정은 연결할 수 없어 `NOT_LINKED`가 된다).
- 확인: E2E

### AC-L1-24 [server·web] 연습 모드
- 근거: D-L1-07, `docs/TRY-IT.md`
- Then `pnpm try`가 세 공급자를 가짜로 켠다. 가짜 승인 화면은 연습 화면과 같은 주소(연습 전용 경로)로 열려 이 컴퓨터와 같은 와이파이의 휴대폰 모두에서 된다. 연습 승인 화면 위에 "연습용 가짜 화면이에요. 실제 카카오가 아니에요."가 보이고 연습 계정 둘(이메일 있음·없음)을 고를 수 있다.
- Then 판매자가 연습 계정 아이디로 로그인 → 설정에서 카카오 연결 → 로그아웃 → "카카오로 계속하기" → 홈으로 들어온다. `docs/TRY-IT.md`에 이 순서를 몇 줄로 더한다(dev-server).
- Then 운영 기동에는 연습 승인 화면 경로가 없다(404).
- 확인: 서버 단위(연습 스크립트 기동 시험이 있으면 그 시험), 수동(사용성 검토)

## C. 시험

### AC-L1-30 [e2e] 공급자마다 흐름 (`tests/e2e/l1/**`)
- 근거: 백로그 acceptanceHints 1, AC-L1-03~08·20~22
- Given 세 공급자가 켜지고 가짜 OAuth 서버와 함께 뜬 E2E 서버, 판매자 A·B, 보조자 하나
- Then **구글·카카오·네이버 각각** 다음을 브라우저로 끝까지 돈다(공급자를 매개변수로 한 같은 시험 묶음):
  1. **처음 연결**: A가 아이디로 로그인 → 설정 [연결하기] → 가짜 승인 화면 동의 → `LINKED` 문장·목록에 가린 이름.
  2. **처음 로그인**: 로그아웃 → "…로 계속하기" → 동의 → 홈, 위에 A의 가게 이름.
  3. **다시 로그인**: 새 브라우저 문맥에서 한 번 더 → 같은 A로 들어온다(새 판매자·새 계정 없음).
  4. **취소**: 가짜 화면 "취소" → 로그인 화면 `CANCELLED` 문장, 로그인되지 않음.
  5. **state 틀림**: 돌아오는 주소의 `state`를 바꿔 연다 → `EXPIRED`, 로그인되지 않음. 다른 브라우저 문맥에서 시작한 state로 연다 → `EXPIRED`.
  6. **코드 재사용**: 성공한 돌아오는 주소를 다시 연다 → `EXPIRED`, 세션 수 그대로. 가짜 서버에 같은 코드로 두 번째 교환을 시키는 경우(새 state + 옛 코드) → `PROVIDER_ERROR`.
  7. **돌아오는 주소 다름**: 가짜 서버에 다른 돌아오는 주소를 등록해 둔 채 시작 → 가짜 승인 화면이 오류를 보이고 앱으로 돌아오지 않으며 로그인되지 않는다. 받은 요청 보기로 서버가 보낸 `redirect_uri`가 `<앱 주소>/api/auth/<p>/callback`과 글자까지 같음을 단언한다.
  8. **이메일 없음**: 이메일·닉네임 없는 가짜 사용자로 연결·로그인 → 성공, 설정에 "카카오 계정"(공급자 이름).
  9. **연결 안 된 계정**: 연결하지 않은 가짜 사용자로 로그인 → `NOT_LINKED` 문장, 아이디 칸 커서.
  10. **끊기**: 설정 [연결 끊기] → 확인 → 그 공급자로 로그인해 둔 다른 브라우저 문맥은 다음 요청에서 로그인 화면("로그인이 풀렸어요…"), 지금 화면은 그대로. 다시 그 공급자로 로그인 → `NOT_LINKED`.
- Then 구글 묶음은 추가로: 받은 승인 요청의 권한이 정확히 `openid email`이고 유튜브 연결 상태가 그대로다.
- Then 공급자 하나만 켠 서버에서 로그인 화면에 그 버튼 하나만, 하나도 안 켠 기존 기동에서 버튼 없음(기존 로그인 E2E 그대로 통과).
- Then 휴대폰 크기(390×844)에서 1·2를 한 번 더 돈다(버튼 크기 AC-L1-20 단언 포함).
- 확인: E2E

### AC-L1-31 [domain] 적대 시험 (`tests/adversarial/l1/**`)
- 근거: 백로그 acceptanceHints 2·3, D-L1-02·D-L1-04, SYS-02
- Then 다음이 모두 막힌다(서버를 가짜 OAuth 서버와 함께 띄워 HTTP로 공격):
  - **같은 이메일 합치기 없음**: 판매자 A의 연결 사용자와 이메일이 같은 다른 공급자 계정(다른 ID)으로 로그인 → `NOT_LINKED`. 공급자를 바꿔도(구글 A 이메일 = 카카오 이메일) 마찬가지.
  - **테넌트 격리**: B 세션으로 A의 공급자 연결을 끊거나 보거나 바꿀 길이 없다. A의 공급자 계정으로 로그인한 세션은 A의 자원만 보이고, B의 자원은 404(D-074). A의 연결 시작 state를 B 세션의 브라우저로 돌아오게 하면 `EXPIRED`·`SESSION_GONE` — B에게 A의 공급자 계정이 연결되지 않는다.
  - **이미 연결된 계정 빼앗기 없음**: B가 A에 연결된 공급자 계정으로 연결 시도 → `LINKED_ELSEWHERE`, A 그대로. 동시에 두 판매자가 같은 공급자 계정을 연결해도 하나만 성공(유일 제약).
  - **로그인 CSRF**: 공격자가 자기 공급자 계정으로 받은 code·state를 판매자 브라우저(state 쿠키 없음·다른 쿠키)로 열게 해도 로그인되지 않는다(`EXPIRED`).
  - **연결 CSRF**: 연결 시작 `POST`가 다른 `Origin`·폼 본문이면 403·400. 판매자 세션 쿠키만 있는 다른 사이트의 `GET` 돌아오는 주소로 공격자 공급자 계정을 판매자에게 연결할 수 없다.
  - **state 동시 사용**: 같은 돌아오는 주소를 동시에 20번 → 세션 하나, 공급자 교환 한 번.
  - **열린 리디렉션 없음**: `next`·`redirect`·`return_to`·`//evil.example`·`%2F%2Fevil` 등 어떤 매개변수·Host·`X-Forwarded-Host`를 붙여도 `Location`은 앱 주소 안의 고정 경로.
  - **보조자**: 보조자 세션으로 연결 시작·목록·끊기 403. DB에 보조자 계정 ID로 연결 행을 직접 넣어 두어도(손상 흉내) 간편 로그인은 그 보조자 세션을 만들지 않는다(판매자 계정만 찾음).
  - **꺼진 공급자**: 켜지지 않은 공급자의 시작·돌아오는 주소·끊기 404(꺼진 공급자에 남은 연결은 끊기만 200).
  - **결과 문장 주입**: `?login=<script>`·긴 글 → 화면에 그 글이 없음(E2E 쪽 AC-L1-21과 짝, 여기선 서버가 주소 글을 되돌려 보내지 않음만).
  - **비밀 누출 없음**: AC-L1-09의 표시 값 검사를 공격 흐름 전부(실패·동시·재사용 포함) 뒤 로그·DB 덤프·응답 전체에 다시 한다.
- 확인: 적대
