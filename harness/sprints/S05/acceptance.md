## A. 로그인·방송 목록 (SYS-01, SPEC §7 화면 1, R-1 방송 시작·종료)

### AC-S05-01 [web] 로그인 화면
- 근거: SYS-01, D-074, UX-03
- Given 운영자가 만든 판매자 계정(S04 계정 명령)
- When 로그인하지 않은 채 앱 주소를 연다
- Then 로그인 화면(아이디·비밀번호 칸, "로그인" 버튼)이 보인다. 가입 화면·링크는 없다.
- When 맞는 아이디·비밀번호로 로그인
- Then 방송 목록(홈)으로 간다. 화면 위에 가게 이름이 보인다. "로그아웃" 버튼이 있고 누르면 로그인 화면으로 돌아간다.
- Then 틀리면 서버의 문장("아이디나 비밀번호가 맞지 않아요.")을, 잠기면 서버의 잠금 문장을 그대로 보인다. 비밀번호 칸은 가려져 있고 실패해도 아이디는 남는다.
- When 쓰는 중에 세션이 끝난다(어떤 API든 401)
- Then 로그인 화면으로 가며 "로그인이 풀렸어요. 다시 로그인해 주세요."를 보이고, 다시 로그인하면 보던 화면(같은 방송의 콘솔)으로 돌아간다. 5초 대기 중이던 방송자 조치는 보내지 않는다(D-083).
- 확인: E2E

### AC-S05-02 [web] 방송 목록·새 방송·끝내기
- 근거: SPEC §7 화면 1, R-1 "방송 시작·종료", D-069, D-070, D-081
- Then 홈에 판매자의 방송이 날짜(KST) 최근 순으로 보인다: 제목, 날짜, "진행 중"/"끝남", 리허설 방송은 "리허설" 글자. 누르면 그 방송의 콘솔로 간다.
- When "새 방송 시작" → 제목(비우면 서버 기본 "N부")·날짜(기본 오늘, KST)를 확인하고 시작
- Then 서버에 방송을 만들고(요청 번호 포함) 그 방송의 콘솔로 간다. 만든 방송의 설정 스냅샷은 서버가 판매자 설정으로 채운다(화면은 설정을 보내지 않는다).
- When "리허설 해 보기"
- Then 리허설 방송을 만들고(AC-S05-50) 리허설 콘솔(AC-S05-53)로 간다.
- When 콘솔의 "방송 끝내기" → 확인 창("방송을 끝낼까요? 끝난 뒤에도 늦게 온 채팅·문자찜은 처리돼요.") → 끝내기
- Then 서버에 끝내기를 보내고, 콘솔 위에 "끝난 방송이에요"를 보인다. 끝난 방송의 콘솔도 조회·조치는 그대로 할 수 있다(R-1 — 끝난 뒤의 입력도 평소대로 처리).
- Then 방송 제목에 휴대폰 번호가 있어 거절되면 서버 문장(D-079 ⑥)을 제목 칸 아래에 보이고 방송은 만들어지지 않는다.
- 확인: E2E

## B. 빠른 입력·현재 상품·상품 보드 (PRD-01, PRD-02 AC2, PRD-03 AC3, PRD-04, UX-05, D-084)

### AC-S05-10 [web] 빠른 입력으로 등록
- 근거: PRD-01 AC1·AC2·AC5, R-16, D-007, D-084
- Given 판매 중인 방송의 콘솔(설정 스냅샷 기본: 천원 단위, 번호 최대 999)
- Then 빠른 입력칸은 콘솔 위쪽에 늘 보이고, 콘솔을 열면 포커스가 그 칸에 있다.
- When `15 핑크프릴 10000` / `15 핑크프릴 1만` / `15번 핑크프릴 만원` / `15/핑크프릴/10`을 치고 Enter (각각 다른 번호로 바꿔 넣어도 같다)
- Then 각각 품종 "핑크프릴"·가격 10,000원인 상품이 `OPEN`으로 등록된다(`product.register`, 요청 번호 포함). `31 방울복랑 금 15000` → 품종 "방울복랑 금"·15,000원. 품종이 비면("15 10000") 보드에 "품종 미입력".
- Then 해석은 코어 `parseQuickInput`에 그 방송 스냅샷의 `price.unit`·`claim.maxNumber`를 넣은 결과와 같다(화면이 따로 해석하지 않는다).
- Then 등록 응답을 받기 전에는 칸 옆에 "등록하는 중…"만 보이고, 받은 뒤 칸이 비고 상품이 보드·현재 상품에 나타난다(NFR-03). 등록 직후 5초 동안 "되돌리기"가 보인다(AC-S05-40).
- Then 빠르게 연달아 친 줄(Enter 다섯 번)이 모두 순서대로 등록되고 빠지거나 두 번 등록되지 않는다.
- 확인: E2E, 화면 단위 시험

### AC-S05-11 [web] 빠른 입력 오류 → 고칠 칸으로
- 근거: PRD-01 AC3, R-16 1·3·4·6, UX-03, D-084
- When 해석 결과가 오류
- Then 등록하지 않는다(서버에 아무것도 보내지 않는다). 번호·품종·가격 고치기 칸이 열리고 결과에 있던 번호·품종이 채워진다. 문장과 커서:

  | 오류 | 문장 | 커서 |
  |---|---|---|
  | `PRICE_MISSING` | "가격을 알아보지 못했어요. 가격 칸에 적어 주세요." | 가격 칸 |
  | `PRICE_TOO_LOW` | "가격이 100원보다 적어요. 가격을 확인해 주세요." | 가격 칸 |
  | `NUMBER_MISSING` | "맨 앞에 상품 번호를 적어 주세요. 예: 15 핑크프릴 10000" | 번호 칸 |
  | `NUMBER_INVALID` | "번호는 1부터 {최대 번호}까지예요. 번호를 확인해 주세요." | 번호 칸 |
  | `EMPTY` | (아무 일도 없다) | 빠른 입력칸 그대로 |

- Then 고치기 칸에서 Enter = 그 값으로 등록(가격 칸은 빠른 입력과 같은 금액 해석 — 코어 `parseAmount`, 실패하면 같은 문장). Esc = 고치기 칸을 닫고 빠른 입력칸으로(아무것도 등록하지 않음).
- Then 예외: `PRICE_MISSING`이고 품종이 비었으며 그 번호의 상품이 이미 있으면 고치기 칸 대신 그 상품 자세히 보기를 연다(AC-S05-12).
- 확인: E2E

### AC-S05-12 [web] 번호 찾기 (PRD-03 AC3)
- 근거: PRD-03 AC1·AC3, D-084
- When 빠른 입력칸에 치는 동안 첫 토큰이 그 방송에 있는 상품 번호다(예: `15`, `15 핑`)

### AC-S05-34 [web] 찜 조치와 사유
- 근거: ORD-07, ORD-12, R-8, R-9, R-11, DAT-05, D-039, D-040, D-064, D-079, D-083
- Then 상품 자세히(AC-S05-15)의 찜마다 그 상태에 맞는 조치만 보인다:

  | 찜 | 조치 (이벤트) |
  |---|---|
  | 1등 | "취소"(`host.cancel`), "무효"(`host.reject`), "확인(잠금)"(`host.confirm`), "다른 사람으로 바꾸기"(`host.assign` + `replace` — 기존 1등은 "대기로"/"취소" 중 고름) |
  | 대기 | "취소", "무효", "1등으로" — 빈 자리가 있으면 `host.promote`, 없으면 `host.assign` + `replace`(지금 1등을 대기로/취소로 고름) |
  | 보류·충돌 | "취소", "무효" (충돌은 충돌 창도 연다) |
  | 구매자 | "차단"(`host.blockBuyer`) / 차단 중이면 "차단 풀기"(`host.unblockBuyer`) |

- Then 상품에 "직접 배정"(`host.assign`): 엔진이 아는 구매자 중에서 고른다 — 닉네임으로 찾고 같은 닉네임은 채널 끝 4자리로 구분. 빈 자리가 없으면 교체할 1등과 "대기로"/"취소"를 함께 고른다.
- Then 사유가 필수인 조치(`cancel`·`reject`·`promote`·`assign`·`reopen`·`blockBuyer`·`unblockBuyer`)는 사유를 받는다: 빠른 선택("시청자 요청"·"장난 찜"·"번호 착오"·"입금 안 함")과 직접 입력, 비면 보낼 수 없다. 선택 사유인 조치(`confirm`·`approveCancel`·`dismissCancel`·`resolveConflict`·`convertMessage`)는 사유를 묻지 않는다.
- Then "차단"은 먼저 확인을 묻는다: "차단하면 이 사람의 대기·보류 찜이 모두 거절되고 다시 풀어도 돌아오지 않아요. 1등 찜은 그대로예요. 다음 날짜 방송에서도 차단돼요."(리허설 방송이면 마지막 문장 없음, D-081).
- Then 모든 방송자 조치는 5초 뒤에 보낸다(AC-S05-41). 보낸 뒤 `changed: false`면 "적용되지 않았어요. 지금 상태를 확인해 주세요."를 보인다.
- Then 사유에 휴대폰 번호가 있어 거절되면 서버 문장과 `hint`를 사유 칸 아래에 보이고 사유를 고칠 수 있게 창을 연 채 둔다(D-079 ⑥). 그 밖의 서버 오류도 AC-S05-71.
- 확인: E2E

### AC-S05-35 [server] [web] 상품별 조치 기록
- 근거: ORD-12 "모든 조치는 사유와 함께 이력에 남는다", DAT-05, D-072
- Then [server] 이력 조회에 방송·번호로 거르는 조건을 더한다: 그 방송·번호를 대상으로 한 `product.*`·`host.*` 이벤트(번호 변경은 이전·새 번호 모두)를 `seq` 순으로, 이어 받기·개수 상한은 기존과 같다. 응답 모양은 S04 이력 조회와 같다(`phoneKey` 없음).
- Then [web] 상품 자세히에 "조치 기록": 시각(KST)·조치 낱말("취소"·"무효"·"직접 배정"·"일시 중지"·…)·대상 구매자 표시 이름·사유·조치자(로그인 아이디 / "서버" / "수집기"). 이벤트 기록에는 적용됐는지가 없으므로 맞지 않아 아무 일도 없었던 조치도 기록으로 보인다(그대로 둔다).
- 확인: 서버 시험, E2E

## E. 되돌리기·단축키·포커스 (UX-05, UX-06, NFR-03, NFR-08, D-083, D-087)

### AC-S05-40 [web] 등록 되돌리기
- 근거: UX-06, R-2, D-083, G-ENG-167
- When 빠른 입력(또는 고치기 칸)으로 등록이 저장된 뒤 5초 안
- Then 화면에 "15번을 등록했어요" + "되돌리기" 버튼과 남은 시간이 보인다.
- When 5초 안에 "되돌리기"(또는 Ctrl+Z — AC-S05-42)
- Then 그 상품에 확정·대기 찜이 없으면 `product.close`를 보내고 "15번 등록을 되돌렸어요(판매 종료)"를 보인다. 상품은 보드에 "판매 종료"로 남는다.
- Then 그 상품에 확정·대기 찜이 이미 있으면(보류 찜이 등록 순간 1등이 된 경우 포함) 보내지 않고 "찜이 들어와서 되돌릴 수 없어요. 고치기로 바로잡아 주세요."를 보인다. 화면이 몰랐던 찜 때문에 서버가 `changed: false`를 돌려줘도 같은 문장이다.
- Then 5초가 지나면 되돌리기는 사라진다. 고치기(`product.update`)·상품 명령에는 되돌리기가 없다.
- 확인: E2E, 화면 단위 시험

### AC-S05-41 [web] 방송자 조치는 5초 뒤에 보낸다
- 근거: UX-06, NFR-03, D-039, D-083, G-ENG-168
- When `host.*` 조치(12종 전부)를 누른다(사유·확인을 마친 뒤)
- Then 바로 보내지 않는다. 화면에 "5초 뒤 보내요: 15번 홍길동 취소"와 남은 시간, "되돌리기"가 보이고, 대상 찜·상품에 "보내기 전" 표시가 붙는다. 이때는 접수됨·바뀐 상태로 보이지 않는다.
- When 5초 안에 되돌리기(또는 Ctrl+Z)
- Then 아무것도 보내지 않는다(서버 이력에 그 조치가 없다). "보내지 않았어요"를 보인다.
- When 5초가 지난다
- Then 누를 때 만든 요청 번호로 보낸다. 저장 응답을 받으면 결과를 보인다(`changed: false`면 AC-S05-34의 "적용되지 않았어요").
- Then 여러 조치를 잇달아 누르면 각각 자기 5초 뒤에 누른 순서대로 보내고, 되돌리기는 각각 따로 된다(Ctrl+Z는 가장 최근 것부터).
- Then 5초 안에 새로고침·탭 닫기·로그아웃·세션 만료가 일어나면 그 조치는 보내지 않는다. 다시 열면 바뀌지 않은 상태가 보인다.
- Then 대기 시간은 5초다. E2E용으로 줄이는 설정(시험용 기동에서만)을 둘 수 있고, 운영 빌드의 값이 5초임을 시험으로 확인한다.
- 확인: E2E(5초 값 확인 하나 이상), 화면 단위 시험(가짜 시계)

### AC-S05-42 [web] 단축키·포커스
- 근거: UX-05, NFR-08, D-087
- Then 단축키:

  | 키 | 하는 일 |
  |---|---|
  | Enter (빠른 입력칸) | 등록·찾기 (AC-S05-10~13) |
  | Esc | 열린 창·고치기 칸을 닫고 빠른 입력칸으로 (5초 대기 중인 조치는 그대로 간다) |
  | Ctrl+Z (맥 ⌘Z) | 빠른 입력칸이 비어 있거나 포커스가 글 칸 밖이면: 가장 최근의 되돌릴 수 있는 것을 되돌린다(5초 대기 중인 조치 → 보내지 않음, 5초 안의 등록 → AC-S05-40). 글자가 있는 칸 안이면 브라우저의 글자 되돌리기 그대로 |
  | Alt+1 (맥 ⌥1) | 알림 띠의 첫 알림 창을 연다: 충돌 → 취소 요청 → 승계 결정 필요 → 확인 필요 순으로 처음 있는 것. 칸에 글자가 입력되지 않는다 |
  | 1·2·3 (알림·확인 창 안) | 그 창의 번호 붙은 선택 버튼 |

- Then 알림·확인 창의 처음 포커스는 아무것도 바꾸지 않는 "닫기"(또는 "아니요")다. 창을 닫거나 조치를 마치면 포커스는 빠른 입력칸으로 돌아간다. 마우스 없이 키보드(Tab·Enter·Esc·위 단축키)만으로 등록·찾기·고치기·찜 취소·충돌 결정·취소 요청 처리·되돌리기를 끝까지 할 수 있다(NFR-08).
- Then 단축키를 화면에 적어 둔다(콘솔 아래 한 줄 또는 도움말).
- 확인: E2E(키보드만으로 흐름 하나)

## F. 리허설 (YT-09, D-081, D-082)

### AC-S05-50 [server] 리허설 방송과 범위 분리
- 근거: YT-09 AC1·AC3, R-0 6, R-9, R-12, R-13, D-069, D-070, D-081
- Then 방송 만들기에 "리허설" 여부(기본 아님)를 받는다. 리허설 방송은 엔진 범위 (판매자, 날짜, 리허설)에 들어가고, 같은 날 실제 방송과 범위·`seq`·이벤트 로그·스냅샷·발송함이 따로다. 리허설인지는 바꿀 수 없다. 기존 데이터는 모두 실제 범위다(마이그레이션).
- Then 방송 목록은 리허설인지를 함께 준다. 날짜로 범위를 고르는 모든 조회·쓰기(범위 조회, 증분 조회, 이력, `b` 없는 이벤트 쓰기)는 리허설을 명시해야 리허설 범위를 고르고, 적지 않으면 실제 범위다. `b`가 있는 이벤트는 그 방송의 범위로 간다. 실시간 알림은 범위를 날짜와 리허설인지로 알린다(`ready`의 범위 목록 포함).
- Then 같은 날 리허설 방송을 먼저 만들고 실제 방송을 만들어도 실제 정산 묶음의 배송비 설정은 실제 첫 방송의 스냅샷이다. 리허설의 구매자·정산 묶음은 실제 범위 조회에 없다.
- Then 차단 이어받기: 실제 범위는 실제 범위에서만 이어받고, 리허설 범위는 이어받지도(실제·리허설 어느 쪽에서도) 넘겨주지도 않는다.
- Then 리허설 범위의 발송함 행은 리허설 표시를 단다(발송함 실행기 S08·S11이 건너뛸 수 있게). 이번 스프린트에 실행기는 없다.
- Then 재생 무결성 검사 명령은 리허설 범위도 검사한다. 판매자 격리(SYS-02)는 리허설에도 같다(다른 판매자의 리허설 방송은 404).
- 확인: 서버 시험

### AC-S05-51 [server] 가짜 채팅 생성기
- 근거: YT-09 AC2, D-082, R-3, R-4
- Then 리허설 방송마다 생성기 시작·멈춤·상태 API: 시작(총 개수 1~10,000 기본 300, 초당 1~50 기본 1, 시드 선택 — 범위 밖이면 400과 쉬운 문장), 멈춤, 상태(실행 중인지, 보낸 수·총 개수·초당·시드, 다시 보낸 사본 수, 멈춘 까닭). 실제 방송·다른 판매자의 방송·없는 방송이면 404이고 아무것도 기록하지 않는다. 이미 도는 방송에 다시 시작하면 409(쉬운 문장), 하나만 돈다.
- Then 생성기는 메시지마다 서버 수집 함수(`ingestChat`, 조치자 collector)로만 쓴다 — 이력의 조치자가 "수집기"다. 화면 이벤트 쓰기 API는 여전히 `chat`을 받지 않는다(S04 그대로).
- Then 다음 메시지는 시드와 그 시점의 리허설 범위 상태(그 방송 상품의 번호·상태)로만 정한다. 시계·타이머는 주입할 수 있다(시험에서 기다리지 않고 돌린다). 같은 시드·같은 상태 순서면 같은 메시지 순서다.
- Then 섞는 것(시드 고정 1,000건 실행에서 각각 1번 이상): 판매 중인 상품 번호 주문(`15`·`15번`·`15번이요`·`찜15` 같은 여러 표기), 아직 등록하지 않은 번호 주문(보류 찜이 된다), 언급·질문(`15번 예뻐요`·`3개 남았나요?`), 시청자 취소(`15 취소`), 일반 대화, 같은 채널의 닉네임 바꾸기, 같은 닉네임·다른 채널, 방송자 본인 채팅(`owner: true`), 같은 메시지 ID 다시 보내기(수집 함수가 `duplicate`로 걸러 기록하지 않는다). 주문 번호는 그 방송의 `claim.maxNumber` 안이다.
- Then 가짜 채널 ID는 실제 유튜브 채널 ID 모양(`UC`로 시작하는 24자)과 겹치지 않는다. 닉네임·본문에 휴대폰 번호 모양을 만들지 않는다.
- Then 멈추는 때: 총 개수를 다 보냄, 멈춤 요청, 그 방송을 끝냄, 서버 종료(다시 시작해도 이어서 하지 않는다 — 상태는 "멈춤"). 저장 실패(`save_failed`)가 나면 그 메시지를 다시 시도하지 않고 다음으로 가며 상태에 실패 수를 센다.
- Then 생성기의 쓰기는 다른 입력과 같은 범위별 직렬 처리를 탄다 — 판매자의 등록·조치와 섞여도 `seq` 빈틈·중복이 없다. 로그에 본문·닉네임을 남기지 않는다.
- 확인: 서버 시험(주입 시계로 1,000건, 실제 방송 거절, 조치자, 섞는 것, 같은 시드 재현, 멈춤·끝냄)

### AC-S05-52 [server] 시청자로 채팅 보내기
- 근거: YT-09 AC2, D-082
- Then 리허설 방송에 판매자가 가짜 시청자로 한 줄을 보내는 API: 요청 번호, 닉네임(1~30자), 본문(1~200자), 선택 채널(생성기가 쓴 가짜 채널 또는 새 가짜 채널 — 없으면 닉네임마다 같은 가짜 채널). 서버가 메시지 ID를 만들고 수집 함수로 기록한다(조치자 collector). 같은 요청 번호는 한 번만 기록한다.

## G. 실시간·화면 반영 (SPEC §3, NFR-01, NFR-03, NFR-04, D-075, D-085)

### AC-S05-60 [server] 범위별 지금 `seq`를 집계 없이 (RA-S04-008)
- 근거: D-075, D-085

개발자 보고를 믿지 말고 위 기준을 공격한다. **비례 원칙(D-036)**: 기본 설정과 실제 방송·리허설에서 나올 법한 순서·장애(네트워크 재시도, 두 기기 동시 조작, 서버 재시작, 생성기와 판매자 조작이 섞임)를 먼저 본다. 심각도는 "실제 방송 사고(이중 판매·엉뚱한 1등·돈 오류·판매 기록 손실·다른 판매자 데이터 노출·개인정보 노출)로 이어지는가". 서버는 `@livejjim/server`를 프로세스 안에서 PGlite로 띄워 공격한다.

- **리허설 분리** (AC-S05-50): 같은 날 리허설 → 실제 방송 순서에서 실제 정산 묶음 배송비·구매자 목록·범위 목록·실시간 알림에 리허설이 섞이는 길, 날짜만 적은 쓰기·조회가 리허설 범위로 가는 길, 리허설 차단이 실제 다음 날로·실제 차단이 리허설로 가는 길, 리허설 방송 ID로 실제 범위에 쓰는 길, 리허설 발송함 행 표시 누락, 다른 판매자의 리허설.
- **수집기 경로** (AC-S05-51·52): 생성기·시청자로 보내기 API로 실제 방송에 채팅을 넣는 길, `POST /api/events`의 `chat`, 조치자가 수집기가 아닌 채팅 행, 생성기 두 개 동시 시작, 멈춤·끝냄 뒤 계속 쓰기, 저장 실패 주입, 생성기와 판매자 쓰기가 섞일 때 `seq` 빈틈·중복, 같은 시드 재현.
- **증분 조회** (AC-S05-61): 무작위 이벤트 순서(등록·채팅·문자찜·조치·차단·충돌·번호 변경·합치기·정산)에서 "전체(a) + 증분(a → b) = 전체(b)" 성질, 사라진 키 누락(보류가 풀린 번호, 정리된 대기), 오래된·미래 `seq`, 리허설 범위.
- **범위 `seq`** (AC-S05-60): 실패 표시 이벤트·차단 이어받기 이벤트·두 인스턴스 뒤의 범위 `seq`, 검사 명령이 어긋남을 잡는지.
- **메시지 조회** (AC-S05-20): 주문·취소·무시 판단이 엔진과 어긋나는 길(LOOSE·`IGNORE`·`maxNumber`·방송자 무시 끔 방송), 이미 바꾼 번호, 리허설.
- **차단 이어받기** (AC-S05-80): S04 이어받기 회귀(미리 차단한 채널·번호 모양 ID·풀린 차단).
- **S04 적대 시험 회귀**: 범위 키에 리허설이 더해진 뒤에도 S04 저장·중복·격리·개인정보 시험이 그대로 통과하는지. 바뀐 계약 때문에 고쳐야 하는 기존 시험은 교체이지 약화가 아니다(test-notes에 목록).

## L. 테스트 관점 — test-e2e (`tests/e2e/**`)

수용 기준의 화면 흐름을 스펙 기준으로 확인한다(구현을 보고 기대값을 정하지 않는다). 기다림은 상태로(`waitForTimeout` 금지).

- **기본 흐름**: 로그인 → 새 방송 → 빠른 입력 네 가지 표기 등록 → 번호 찾기 → 같은 번호 고치기(가격 적용 질문) → 오류별 커서(AC-S05-01·02·10~15).
- **리허설 끝까지 (SPEC §8 1단계 완료 기준)**: 리허설 방송에서 생성기를 켜고(1,000건, 시드 고정, 시험 속도) 그동안 빠른 입력으로 상품 30개(1~30번)를 등록하며 충돌·취소 요청을 화면에서 처리한다. 끝난 뒤 30개 상품마다 보드의 상태·1등 표시 이름·대기 수와 서버 정산 묶음(구매자별 합계)이, 그 리허설 범위의 이력(이벤트 기록)을 코어 `applyEvent`로 처음부터 재생한 결과와 같다. 같은 메시지 ID 사본이 찜을 두 번 만들지 않는다. 실제 범위에는 아무것도 생기지 않는다.
- **두 기기**: PC(1440)와 휴대폰(375) 두 컨텍스트에서 같은 방송 — 등록·채팅 주문·조치·알림이 양쪽에 1초 안에 보인다(AC-S05-64는 NFR-04 규모에서 p99).
- **채팅·변환**: 주문·취소·언급·방송자 표시, 주문·취소 메시지에 변환 버튼 없음, 언급 → 변환 → 충돌 → 알림 띠 → 그대로 유지/바꾸기(AC-S05-21·22·31).
- **알림·조치**: 취소 요청 승인·무시, 승계 결정(묻기 방송), 보류 찜 "번호 넣기"·만료 표시, 직접 배정·교체·차단(확인 문장), 사유 필수·휴대폰 번호 사유 거절 문장(AC-S05-30~35).
- **되돌리기**: 등록 되돌리기(찜 없음 → 판매 종료 / 찜 있음 → 되돌릴 수 없음 문장), 방송자 조치 5초 안 되돌리기 → 서버 이력에 없음, 5초 뒤 → 이력에 있음, 대기 중 새로고침 → 보내지 않음, 5초 값 확인(AC-S05-40·41).
- **키보드만**: 등록 → Ctrl+Z → Alt+1 → 숫자 키 → Esc, 처음 포커스 "닫기"(AC-S05-42).
- **실시간·끊김**: SSE 끊기 → 다른 기기 변경 → 다시 붙어 같은 화면, 알림마다 전체 조회를 하지 않음(네트워크 요청), 오프라인 중 입력 → 한 번만 등록(AC-S05-62·63).
- **말·보안·폭**: 영어 상태값 없음, 악성 본문·닉네임이 글자로만, 375px 가로 스크롤 없음, 글자 16px·누르는 곳 44px(AC-S05-70~74).
