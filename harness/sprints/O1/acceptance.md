## A. 판매 방식과 설정 (OPT-04, R-19 "판매 방식", 설정값 범위, D-O-02)

### AC-O1-01 [core] 설정 값과 범위
- 근거: OPT-04, DOMAIN_RULES 설정표·설정값 범위, D-O-02, D-O-06
- Given 코어 `checkSettings`·`resolveSettings`
- When `claim.parseMode`에 `STRICT`·`LOOSE`·`OPTIONS`, `claim.maxQuantity`에 1·10·99, 0·100·1.5·`"10"`을 각각 넣는다
- Then `OPTIONS`와 1~99 정수는 받고, 기본값은 `STRICT`·`10`이다. 0·100·소수·문자열은 설정 문제로 돌려준다. `claim.parseMode: OPTIONS`와 `contention.policy: RECEIVED_TIME`을 함께 넣으면 설정 문제다(어느 한쪽만이면 받는다)
- 확인: 단위(코어) · 골든(README 설정 키 — 러너가 같은 검사로 읽기 오류)

### AC-O1-02 [core] 옵션 방송만의 입력은 다른 방송에서 입력 오류
- 근거: R-19 "판매 방식", D-O-02
- Given `STRICT` 방송 b1과 `OPTIONS` 방송 b2가 있는 엔진 상태
- When b1에 `options`·`aliases`·`stocks`가 있는 `product.register`/`update`, `qty`·`options`가 있는 `sms`·`host.assign`, `product.focus`·`host.resolveReview`·`host.dismissReview`를 `checkEvent`로 검사한다
- Then 모두 입력 오류(`InvalidEventError`)이고 상태가 바뀌지 않는다. 같은 이벤트를 b2에 보내면 받는다(아래 검사를 통과할 때). `qty: 1`만 적은 `sms`도 b1에선 입력 오류다(필드가 있으면 옵션 방송 입력)
- 확인: 단위(코어) · 적대

### AC-O1-03 [core] 다육 방송은 하나도 바뀌지 않는다
- 근거: CMT-07, R-19 "다육 회귀 없음", D-O-02
- Given 기존 골든 전체(파일 30개 — 이번 스프린트 전의 모든 `parser/*.yaml`·`engine/*.yaml`)와 다육 회귀 골든(G-ENG-O0-01, `chat.yaml` 마지막 문서 7사례)
- When 바뀐 코어로 돌린다
- Then 모두 통과한다. 기존 골든 파일의 바뀐 줄은 `parser/chat.yaml` 끝에 붙인 문서뿐이다(`git diff BASE -- tests/golden` 확인). `STRICT`·`LOOSE` 방송의 `parseChat` 결과는 이번 스프린트 전과 같다
- 확인: 골든 · 적대(속성 — 무작위 채팅 글에서 `parseChat`의 결과가 BASE 코어와 같다, `STRICT`·`LOOSE` 둘 다. BASE 코어 결과는 시험 안에 고정한 사례표 또는 BASE에서 만든 기록 파일로 비교한다)

## B. 옵션 모델과 입력 검사 (OPT-01, R-19 "옵션 모델", D-O-04, D-O1-03)

### AC-O1-04 [core] 옵션·별칭의 모양 검사
- 근거: OPT-01, R-19 "옵션 모델", D-O-04
- Given 옵션 방송
- When `product.register`에 다음을 각각 넣는다: 항목 4개 / 항목 이름 11자·빈 이름·같은 이름 둘 / 선택지 0개·21개 / `label` 21자·`/`·`#`·제어 글자가 든 `label` / 별칭 11개·21자 / `price` 1,000,001·−1,000,001·1.5 / 변형 110개(선택지 11 × 10) / 상품 별칭 11개
- Then 모두 입력 오류다. 경계값(항목 3개, 이름 10자, 선택지 20개, `label` 20자, 별칭 10개, `price` ±1,000,000, 변형 100개, 상품 별칭 10개)은 받는다
- 확인: 단위 · 적대

### AC-O1-05 [core] 비교 글자 겹침과 휴대폰 번호
- 근거: R-19 "비교 글자", R-1 "판매자가 적는 칸의 휴대폰 번호", D-O-04
- When 한 상품 안에서 `17 Pro`와 `17pro`(다른 선택지), 색상 `M`과 사이즈 `m`(다른 항목), 선택지 `label` `엠`과 다른 선택지의 별칭 `엠`을 넣는다 / 상품 이름·상품 별칭·항목 이름·`label`·선택지 별칭 중 하나에 `010-1234-5678`을 넣는다
- Then 모두 입력 오류다. 상품 이름·별칭이 선택지 이름과 같은 글자인 것(`초코` 상품 별칭 + `초코` 맛 선택지)은 받는다
- 확인: 단위 · 적대

### AC-O1-06 [core] 변형 단가·재고 검사
- 근거: R-19 "가격"·"변형과 재고 단위", D-O-05, D-O1-03
- When 상품 가격 1,000 + 선택지 가격 차이 −2,000인 변형이 생기는 등록 / `stock: 0`인 옵션 상품 / `stocks: { "XL": 1 }`(없는 옵션 글) / 옵션 없는 상품의 `stocks` / `stocks` 값 −1·1.5를 넣는다
- Then 모두 입력 오류다. `stocks: { "100": 0 }`(G-ENG-O1-09)과 항목 둘의 `stocks: { "105/검정색": 3 }`(G-ENG-O1-03)은 받는다
- 확인: 단위 · 골든(G-ENG-O1-03·09)

### AC-O1-07 [core] 옵션 바꾸기
- 근거: R-19 "옵션 바꾸기", D-O-14
- Given 찜이 없는 옵션 상품 / 찜이 하나라도 있는 옵션 상품
- When `product.update`로 항목 더하기·빼기, 선택지 빼기·이름 바꾸기, 선택지 끝에 더하기, 가격 차이 바꾸기, 변형 재고 바꾸기를 한다
- Then 찜이 없으면 전체 바꾸기가 된다. 찜이 있으면 선택지 더하기(기존 항목 끝)·가격 차이 바꾸기·변형 재고 바꾸기만 되고, 나머지는 **이벤트 전체가 아무 일도 없다**(같은 이벤트의 다른 값도 그대로). 변형 재고를 확정 수량보다 작게 하면 이벤트 전체가 아무 일도 없다. 재고를 늘리면 풀린 수량만큼 대기 1순위부터 확정한다. `applyTo: UNPAID_CLAIMS`면 입금 전 찜의 단가가 그 변형의 새 단가가 된다
- 확인: 골든(G-ENG-O1-09) · 단위

## C. 변형 판정·수량·금액 (OPT-02, OPT-03, R-19, D-O-03·D-O-05·D-O-06, D-O1-01·02·05)

### AC-O1-08 [core] 변형마다 재고·1등·대기·승계
- 근거: OPT-02, R-19 "판정 단위는 변형이다", D-O-03
- Given 반바지 S/M/L(재고 각 1)
- When `반바지 M`(A) → `반바지 엠`(B) → `21 L`(C) → `반바지 L`(A) → `반바지 M`(A 반복) → 판매자가 A의 M을 취소(`options: { 사이즈: M }`)
- Then M은 B 확정·대기 없음, L은 C 확정·A 대기 1, S는 비어 있고 상품은 `OPEN`, 찜 4개(반복은 찜 없음), 확정버전은 상품마다 센다(M의 A = 1, L의 C = 2, M의 B = 3)
- 확인: 골든(G-ENG-O1-01)

### AC-O1-09 [core] 수량 판정 — 맞으면 확정, 모자라면 확인 필요, 0이면 품절, 수량 2 이상은 대기 없음
- 근거: OPT-03, R-19 "수량", D-O-06
