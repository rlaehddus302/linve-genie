### AC-Y1-01 [server] 연결 시작 — 승인 주소
- 근거: YT-01, D-Y02
- Given 로그인한 판매자(세션), 연결 없음
- When 연결을 시작한다(상태를 바꾸는 요청 — `Origin` 검사·JSON, D-074)
- Then 구글 승인 주소를 돌려준다: 클라이언트 ID, 설정에 고정한 돌아오는 주소 하나, `response_type=code`, `scope` = `https://www.googleapis.com/auth/youtube.readonly` **하나만**(이메일·프로필·`youtube.force-ssl` 없음), `access_type=offline`, `code_challenge_method=S256`과 `code_challenge`(검증 값 43~128자), `state`(무작위 32바이트 이상).
- Then `state`는 그 로그인 세션에 묶여 서버에 저장되고 10분 뒤 또는 한 번 쓰면 무효다. 검증 값(`code_verifier`)·`state`는 응답의 승인 주소 밖 어디에도(로그·이벤트 기록) 남지 않는다.
- Then 이 판매자의 연결이 이미 있을 때(다시 연결)의 `scope`는 AC-Y1-31을 따른다 — 게시 권한을 받았거나 동의가 켜져 있던 연결이면 읽기와 게시 권한 둘이다(D-Y1-01). 그 밖(처음 연결, 게시 권한도 동의도 없던 연결)은 위대로 읽기 하나다.
- 확인: 단위·통합 시험(가짜 서버)

### AC-Y1-02 [server] 돌아오기 — 토큰 받기·채널 확인
- 근거: YT-01, SYS-02, D-Y02
- Given AC-Y1-01의 승인 주소로 가짜 구글에서 승인하고 돌아왔다(`code`, `state`)
- When 돌아오는 주소 요청을 받는다
- Then `state`가 그 세션의 것이고 10분 안이고 처음 쓰는 것일 때만 `code`를 토큰으로 바꾼다(`code_verifier` 함께). 연결한 채널을 확인(`channels.list mine=true`)해 채널 ID·이름을 저장하고, 화면 주소로 돌려보낸다(결과는 `connected` 같은 코드로만 — 토큰·`code`는 주소에 넣지 않는다).
- Then 받지 않는 경우(토큰을 저장하지 않고 화면 주소로 돌려보내며 코드와 문장을 준다):
  - `state`가 없음·다름·10분 지남·이미 씀, 다른 세션: "연결 시간이 지났어요. 다시 시도해 주세요."
  - 사용자가 구글에서 거절(`error=access_denied`): "구글에서 연결을 허락하지 않았어요. 다시 시도해 주세요."
  - 그 구글 계정에 유튜브 채널이 없음: "이 구글 계정에는 유튜브 채널이 없어요."
  - 그 채널이 이미 다른 판매자에 연결됨: "이 채널은 연결할 수 없어요. 운영자에게 문의해 주세요."(다른 판매자를 알리지 않는다)
  - 이 판매자가 이미 다른 채널에 연결됨(연결됨·다시 연결 필요 모두): "처음 연결한 채널과 달라요. 바꾸려면 먼저 연결을 끊어 주세요." — 같은 채널이면 받고 토큰만 바꾼다(다시 연결).
- Then 같은 `code`·`state`로 두 번 와도 한 번만 처리한다.
- 확인: 통합 시험(가짜 서버)

### AC-Y1-03 [server] 토큰 보관 — 암호화, 내보내지 않음
- 근거: DAT-06, NFR-06, D-073, D-Y02
- Then 새로 고침 토큰·접근 토큰은 서버 마스터 키로 암호화해 저장한다(판매자 비밀 키와 같은 방식). 데이터베이스의 어느 표·열에도 토큰 원문이 없다 — 시험: 가짜 서버가 준 토큰 문자열로 데이터베이스 전체(모든 표의 모든 글 열)를 찾아 0건.
- Then 토큰·`code`·`code_verifier`·`state`는 어떤 응답·실시간 알림·서버 로그·이벤트 기록·발송함·스냅샷에도 나가지 않는다.
- Then 마스터 키가 바뀌어 토큰을 풀 수 없으면 서버는 죽지 않고 그 판매자의 연결을 "다시 연결 필요"로 본다.
- 확인: 통합 시험

### AC-Y1-04 [server] 토큰 새로 고침과 "다시 연결 필요"
- 근거: YT-01, D-Y02
- Then 유튜브 호출 전에 접근 토큰이 60초 안에 만료되면 새로 고친다. 같은 판매자의 새로 고침은 동시에 하나만 한다 — 수집기·발송함·목록 요청이 동시에 와도 토큰 요청은 1번(가짜 서버 횟수).
- Then 유튜브가 401을 주면 한 번 새로 고쳐 같은 요청을 한 번 더 한다.
- Then 새로 고침이 `invalid_grant`(사용자가 권한을 거둠 등)면 연결 상태를 "다시 연결 필요"로 바꾸고, 그 판매자의 수집기를 모두 멈추며(상태 "유튜브 연결을 다시 해 주세요."), 발송함은 보내지 않고 기다린다(기한이 지나면 보내지 못함, AC-Y1-37). 판매 기록·찜·1등은 그대로다.
- Then 같은 채널로 다시 연결하면(AC-Y1-02) 끝나지 않은 방송의 수집기가 저장한 이어받기 지점부터 다시 돈다(AC-Y1-23).
- 확인: 통합 시험(가짜 서버 `invalid_grant`·401 주입)

### AC-Y1-05 [server] 연결 상태 조회
- 근거: YT-01, YT-04 AC2, D-Y02, D-Y12
- Then 판매자는 자기 연결 상태를 본다: 상태(`NOT_CONNECTED` 연결 안 됨 · `CONNECTED` 연결됨 · `RECONNECT_NEEDED` 다시 연결 필요), 채널 ID·이름, 받은 권한(읽기·게시 각각 예/아니오), 게시 동의(실시간 채팅·영상 댓글 각각 — 켜짐 여부·켠 시각). 토큰·만료 시각은 보이지 않는다.
- Then 상태가 바뀌면 그 판매자의 실시간 알림(SSE)으로 알린다(NFR-01 — 1초 안).
- 확인: 통합 시험

### AC-Y1-06 [server] 연결 끊기
- 근거: YT-01, DAT-06, D-Y02, D-Y12
- When 판매자가 연결을 끊는다
- Then 구글에 토큰 폐기를 요청하고(가짜 서버가 받음. 실패·타임아웃이어도 계속), 저장한 토큰과 게시 동의를 지우며, 그 판매자의 모든 수집기를 멈춘다. 상태는 `NOT_CONNECTED`.
- Then 이미 기록한 채팅·판정·발송함 기록은 그대로다. 게시 동의가 꺼지므로 기다리던 발송함 행은 바로 `FAILED(NO_CONSENT)`가 된다(AC-Y1-31). 끊은 동안 새로 나온 감사도 같다.
- Then 끊은 뒤에는 다른 채널도 연결할 수 있다. 이전 채널의 방송에 이어 둔 회차는 수집하지 않는다(상태 "내 채널의 방송이 아니에요."), 같은 채널로 다시 연결하면 이어서 수집한다.
- 확인: 통합 시험

## B. 방송 잇기 (YT-02, D-Y03)

### AC-Y1-10 [server] 내 라이브 목록
- 근거: YT-02, D-Y03
- Given 연결됨
- Then 연결한 채널의 진행 중·예정 라이브 방송 목록을 돌려준다: 영상 ID, 제목, 상태(진행 중/예정), 예정 시작 시각·실제 시작 시각(UTC ISO), 이미 어느 회차에 이어져 있는지(이 판매자의 회차 ID 또는 없음). 끝난 방송은 넣지 않는다. 할당량에 호출 비용을 센다(AC-Y1-50).
- Then 연결 안 됨·다시 연결 필요면 목록을 부르지 않고 그 상태를 코드로 돌려준다.
- 확인: 통합 시험(가짜 서버에 진행 중·예정·끝난 방송, 다른 채널 방송)

### AC-Y1-11 [server] 주소·영상 ID 읽기
- 근거: YT-02, D-Y03
- Then 다음에서 영상 ID(11자 `[A-Za-z0-9_-]`)를 읽는다: `https://www.youtube.com/watch?v=ID`, `youtube.com/watch?v=ID&t=10s`(다른 매개변수·순서 상관없음), `https://m.youtube.com/watch?v=ID`, `https://youtu.be/ID?si=…`, `https://www.youtube.com/live/ID?feature=share`, `https://studio.youtube.com/video/ID/livestreaming`, `ID` 그 자체, 앞뒤 공백. `http://`·주소 앞 `www.` 없음도 받는다.
- Then 그 밖(다른 사이트, 채널 주소, 재생 목록만, ID 길이·글자가 다름, 빈 값)은 "유튜브 방송 주소를 확인해 주세요."(유튜브를 부르지 않는다).
- 확인: 단위 시험(표)

### AC-Y1-12 [server] 잇기 조건
- 근거: YT-02, YT-09 AC1·AC2, D-081, D-082, D-Y03
- Given 연결됨, 라이브찜 회차(방송) b
- When 영상 ID(목록에서 고름 또는 AC-Y1-11)로 b에 잇는다
- Then 아래를 모두 만족할 때만 잇고 바로 수집을 시작한다(AC-Y1-20). 하나라도 아니면 잇지 않고 문장을 준다:
  - b가 이 판매자의 회차다 — 아니면 404(다른 판매자의 회차가 있는지 알리지 않는다)
  - b가 리허설이 아니다: "리허설 방송에는 유튜브 방송을 이을 수 없어요."
  - b가 끝나지 않았다: "끝난 방송에는 유튜브 방송을 이을 수 없어요."
  - b에 이어진 유튜브 방송이 없다: "이 방송에는 이미 유튜브 방송이 이어져 있어요. 먼저 연결을 끊어 주세요."
  - 그 영상이 연결한 채널의 방송이다: "내 채널의 방송만 연결할 수 있어요."
  - 진행 중이거나 예정이고 채팅 ID가 있다: "채팅을 받을 수 없는 방송이에요. 끝났거나 채팅이 꺼져 있어요."
  - 그 영상이 끝나지 않은 다른 회차에 이어져 있지 않다: "이미 다른 방송에 이어진 유튜브 방송이에요." — 동시에 이어도 같다(AC-Y1-98)
- Then 이은 시각(서버 시계)을 남긴다(AC-Y1-25의 기준). 잇기는 엔진 이벤트가 아니다(판정과 상관없음) — 누가·언제 이었는지는 서버 기록에 남긴다(DAT-05).
- Then 같은 요청 번호로 두 번 보내도 한 번만 잇는다.
- 확인: 통합 시험

### AC-Y1-13 [server] 연결 끊기·다시 잇기
- 근거: YT-02, D-Y03
- When 판매자가 회차 b의 유튜브 연결을 끊는다
- Then b의 수집기가 멈추고 이미 기록한 채팅·판정은 그대로다. b의 기다리던 실시간 채팅 감사는 보내지 못함(이어진 유튜브 방송 없음)이 된다.
- Then b에 다른 유튜브 방송(또는 같은 방송)을 다시 이을 수 있다. 다시 이은 때부터는 AC-Y1-25(잇기 전 채팅)를 다시 적용한다 — 같은 메시지 ID는 어차피 두 번 기록되지 않는다.
- 확인: 통합 시험

## C. 채팅 수집 (YT-03, NFR-03, NFR-04, R-1, R-11, D-Y04, D-Y05, D-Y10)

### AC-Y1-20 [server] 어댑터 셋과 대체 경로
- 근거: YT-03, D-010, D-Y04, D-Y13
- Then 채팅 원천(ChatSource)은 하나의 모양(시작 지점 → 메시지 묶음·다음 지점·끝남 신호·오류)이고 구현이 셋이다: `streamList`(기본), `list` 폴링(대체), 시험용 가짜. 수집 관리자·이어받기·기록 코드는 셋에 똑같다.
- Then streamList가 응답을 하나도 받지 못한 채 연속 3번 실패하거나 지원하지 않는다고 답하면(`UNIMPLEMENTED`·404 등) 그 수집기는 폴링으로 바꿔 같은 지점부터 이어 간다. 폴링은 응답의 `pollingIntervalMillis`보다 자주 부르지 않는다. 호출 간격의 아래 한도(2초)·스트림 다시 열기(5초)·예정 방송(30초마다 상태 확인)은 AC-Y1-94.
- Then 실제 어댑터(스트림·폴링)는 가짜 서버(AC-Y1-80)에 실제 통신 방식으로 붙어 시험된다 — 주소만 다르다.
- 확인: 통합 시험

### AC-Y1-21 [server] 메시지 → `chat` 이벤트
- 근거: YT-03, R-0 6, R-1 `chat`, R-4 머리말, R-11, D-045, D-072, D-082, D-Y04
- Given 회차 b(실제 방송)에 이어진 유튜브 방송의 채팅
- Then 메시지마다 수집 경로(`ingestChat`, 조치자 `collector`)로 b의 실제 범위에 `chat` 이벤트를 기록한다: `b`, `id` = 메시지 ID, `ch` = 작성자 채널 ID, `nick` = 작성자 표시 이름을 AC-Y1-22로 정리한 것, `text`, `publishedAt` = 게시 시각, `owner` = 채팅 소유자(`isChatOwner`)일 때만 `true`(운영자·후원자는 시청자). `at`은 서버 도착 시각이다(접수순 판정 — G-ENG-402).
- Then `text`: 일반 채팅은 그 글(`textMessageDetails.messageText`). 슈퍼챗·멤버십 축하는 시청자 댓글(`userComment`)이 비어 있지 않을 때만 그 글로 기록하고, 없으면 기록하지 않는다. 그 밖의 종류(스티커, 멤버십 가입·선물, 투표, 삭제·차단 알림, 시스템 메시지)는 `chat`으로 기록하지 않는다(삭제·차단은 AC-Y1-27).
- Then 같은 (판매자, 회차, 메시지 ID)는 한 번만 기록한다(D-072) — 두 번째는 아무 일도 없다(INV-3).
- Then 리허설 회차에는 유튜브 채팅이 들어가지 않는다(AC-Y1-12로 이을 수 없다).
- 확인: 통합 시험(가짜 서버 → 기록된 이벤트 본문 비교)

### AC-Y1-22 [server] 이름 정리 (RA-S02-004)
- 근거: R-11 "닉네임 정리", R-13 감사 문구, YT-04, D-Y05

자동 시험으로 대신할 수 없는 "실제 유튜브에서 되는가"를 본다. 사용자의 구글 계정·구글 클라우드 프로젝트(D-019)가 필요하다. 약 30분.
