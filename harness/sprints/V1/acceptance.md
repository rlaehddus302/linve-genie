# V1 수용 기준 — 음성 문자찜 ("165번 문자찜 끝자리 1234" → 저절로 문자찜)

- 스프린트: V1 (6단계) · spec ID: **ORD-07**, **ORD-08**(새 AC9), **VOC-01**, **VOC-02** (연결: VOC-04·VOC-05, ORD-09, R-4·R-6·R-8·R-11, DAT-06, UX-01, UX-04, §9 HG-4) · 규칙: DOMAIN_RULES v0.1.24 **새 R-21**(음성 문자찜 문장), R-17 1~3·R-20 재사용 · 근거 결정: **D-V1-01~D-V1-11**(AUTO), D-I4-01~09, D-099, D-089, D-061
- 사용자 결정(2026-10-23): 문자찜은 음성 인식으로. 카카오 채널(판매자가 직접 개설)·문자 중계 가상 번호(CS와 같은 번호를 못 씀)는 쓰지 않는다. M1은 중단.
- 개발 영역: **device**(`packages/voice/**`), **server**(`apps/server/**`), **web**(`apps/web/**`) · 테스트: **domain**(`tests/adversarial/v1/**`), **e2e**(`tests/e2e/v1/**`) · **dev-core 없음** — 판정·정산 규칙과 엔진은 바꾸지 않는다. 넣는 것은 지금의 `sms` 이벤트다(R-1·R-11).
- 의존 순서: device(R-21 함수·골든 시험·카드 상태) → server(`last4` 쓰기·409) → web(카드 화면·설정·정산 안내). dev-device·dev-server는 바뀐 API(함수 이름·요청·응답 모양)를 `harness/sprints/V1/dev-notes.md`에 먼저 적는다.
- 가짜 음성 인식은 I4 시험 계약 그대로다(`page.addInitScript`로 `window.SpeechRecognition`을 가짜 생성자로 — 화면 코드에 시험용 갈림길 없음). 외부 계정·마이크·네트워크는 필요 없다.
- 정답의 우선순위: 골든 → DOMAIN_RULES·SPEC 규칙 문장 → DECISIONS → 이 문서. 규칙으로 정해지지 않는 경우는 구현으로 정하지 말고 dev-notes·`disputesWithSpec`으로 올린다.
- 화면 문장 중 이 문서가 따옴표로 정한 것은 그대로 쓴다(E2E가 글자로 찾는다). 바꿔야 하면 dev-notes에 이유를 남기고 spec-keeper가 판정한다.

## A. 문자찜 문장 읽기 (VOC-02, R-21, D-V1-01·02·04·08) — `[device]`

### AC-V1-01 [device] R-21 함수와 골든
- 근거: R-21 1~9, D-V1-01·02·04·08, 골든 `tests/golden/voice/voice-sms.json`
- Given 문장 하나와 설정(`parseMode`·`maxNumber`·`maxQuantity`), 옵션 방식이면 상품 목록·지금 상품
- When `packages/voice`가 내보내는 문자찜 문장 읽기 함수(이름은 dev-notes)를 부른다
- Then 결과는 `null` 또는 정확히 `{ orders, last4, name, time, problem }`이고 골든 48사례가 모두 같다. 함수는 순수하다(같은 입력 같은 결과, 넘긴 값을 바꾸지 않음, 시계·난수·네트워크 없음, 어떤 문자열에도 예외 없음).
- Then 옵션 방식은 코어 `parseOptionComment`를 그대로 부른다(R-20을 다시 구현하지 않는다). 번호 표시·끊어 말한 번호는 R-17 추출기의 같은 코드를 쓴다.
- Then 골든 시험은 `voice/` 폴더의 모든 `*.json`을 읽고, 모르는 키·`kind`·겹친 `id`는 실패, 파일 1 · 사례 48 합계를 고정값으로 단언한다(README "음성 문자찜 골든").
- 확인: 골든(단위 시험이 읽음), 속성 시험(임의 문장 → 예외 없음·결과 모양, `문자찜`으로 시작하는 토큰이 없고 `문자`+`찜…` 짝도 없으면 늘 `null`, `problem`이 있으면 `orders`가 비어 있음, `orders`의 `no`는 늘 `1..maxNumber`)

### AC-V1-02 [device] 상품 등록 추출과 겹치지 않음
- 근거: R-21 2, SPEC VOC-02, D-V1-01
- Given 음성 카드를 만드는 패키지 입구(문장 → 상품 카드 또는 문자찜 카드)
- When 문장에 문자찜 표시가 있다(`15번 핑크프릴 만원 문자찜`)
- Then 상품 등록 카드(R-17)는 만들지 않고 문자찜 결과만 낸다. 표시가 없는 문장(`15번 핑크프릴 만오천 원`)은 지금과 똑같이 R-17만 — `voice-extract.yaml` 81사례 결과가 바뀌지 않는다.
- Then "문자찜도 듣기"가 꺼져 있으면 문자찜 표시가 있는 문장은 어떤 카드도 만들지 않는다(SPEC VOC-01, D-V1-09).
- 확인: 단위 시험, 골든(`voice-extract.yaml` 그대로 통과)

### AC-V1-03 [device] 문자찜 카드 상태 — 자동으로 넣기 조건
- 근거: SPEC VOC-04 문자찜 카드, D-V1-05·D-V1-07
- Given 문자찜 카드(만든 시각은 부르는 쪽이 넘긴다 — 패키지는 시계를 읽지 않는다), 설정 `smsAutoSec`(정수 0~10, 기본 3)
- Then 자동으로 넣을 수 있는 카드 = 주문 하나 · `problem` 없음 · 손대지 않음 · 받을 수 있는 상품(부르는 쪽이 넘긴 상품 상태가 `OPEN`, 또는 `SOLD`이고 대기 자리 있음) · 말한 시각이 지금보다 늦지 않음 · 구매자 고르기를 기다리지 않음 · 열린 창 없음 · 음성 켜짐. 그런 카드만 만든 뒤 `smsAutoSec`초가 지나면 "넣기"가 된다(0이면 바로).
- Then 번호 둘 이상, 손댄 카드("넣지 않기"·"지금 넣기" 밖의 조작), 시각 확인이 필요한 카드, 고르기 카드는 자동으로 넣지 않는다. 문제(`problem`)나 넣을 수 없는 상품의 카드는 넣을 수 없다(누르기로도).
- Then 설정 값을 못 읽거나 범위 밖이면 기본 3초다. "문자찜도 듣기"(기본 켬) 설정도 같은 방식으로 검사한다.
- Then 열린 카드 수 규칙(D-204·D-I4-02)은 상품 카드와 문자찜 카드를 함께 센다. 기다리는 문자찜 카드는 "손대지 않은 카드"로 닫힐 수 있다 — 닫힌 카드는 넣지 않는다.
- 확인: 단위 시험(가짜 시각), 속성 시험(임의 조작 순서 → 자동으로 넣는 카드는 위 조건을 모두 만족, 같은 카드를 두 번 넣지 않음)

### AC-V1-04 [device] 같은 말 중복 막기
- 근거: D-V1-06
- Given 문자찜 카드 `165번 · 끝자리 1234`를 시각 t에 만들었다
- When t+10초 안에 같은 주문(번호 목록·옵션·수량)·같은 구매자 말(같은 뒤 4자리 / 같은 이름 / 둘 다 없음)의 문장이 또 들린다(앞 카드를 이미 넣었거나 닫았어도)
- Then 새 카드를 만들지 않고 앞 카드에 "같은 말을 한 번 더 들었어요"를 표시한다. t+10초 뒤이거나 구매자 말이 다르면(끝자리 5678) 새 카드다. 문제 카드끼리도 같은 규칙이다.
- 확인: 단위 시험(경계 10초 정각은 새 카드 아님 — "10초 안" = 차이 ≤ 10,000ms), E2E(AC-V1-24)

### AC-V1-05 [device] 정확도 측정 스크립트에 문자찜 줄
- 근거: D-V1-11, D-I4-08, HG-4
- Given 측정 CSV에 선택 열 `종류`(`등록`/`문자찜`, 빈칸 = 등록)·`기대 끝자리`·`기대 이름`(열이 없으면 지금 표와 똑같이 읽는다 — 기존 예시 파일·시험은 그대로 통과)
- When 스크립트(`accuracy`)를 돌린다
- Then 문자찜 줄은 R-21로 읽어 번호 목록·끝자리·이름을 맞음/빈칸/틀림으로 채점하고, 보고서 요약에 **"문자찜이 아닌데 문자찜으로 읽음"**, **"문자찜인데 문자찜으로 못 읽음"**, **"다른 번호·끝자리로 저절로 넣을 문장"**(자동 넣기 조건을 만족하는데 기대와 다른 주문·끝자리) 수가 따로 나온다. 예시 표본에 문자찜 문장 10행 이상(만든 문장 — 표본 이름 `예시-문자찜-01`…)을 더한다.
- Then 잘못된 `종류` 값·`기대 끝자리`가 숫자 4개가 아님은 몇 번째 줄인지와 쉬운 한국어 한 문장 + 종료 코드 1.
- 확인: 단위 시험, 명령 출력

## B. 서버 — 뒤 4자리로 구매자 정하기 (ORD-08 AC9, R-11, D-V1-03·D-V1-10) — `[server]`

### AC-V1-10 [server] `sms` 쓰기의 `last4`
- 근거: SPEC ORD-08 AC9 구매자, D-V1-03
- Given `POST /api/events`의 `sms` 본문에 새 선택 칸 `last4`(반각 숫자 정확히 4개 글)
- Then `last4`가 숫자 4개 글이 아니면 400(칸 오류, 쉬운 한국어). `last4`와 `phone`을 함께, 또는 `last4`와 `buyer`를 함께 보내면 400(하나만).
- Then 서버는 쓰기 직전의 그 범위(날짜·리허설 여부) 엔진 상태에서 문자 구매자(구매자 종류 문자) 중 `phoneLast4`가 같은 구매자를 **지금의 구매자**로 묶어 센다.
  - 한 사람 → 그 지금의 구매자를 지정 구매자(`buyer`)로 한 `sms` 이벤트를 기록한다(`phoneKey`·`phoneLast4` 없이 — R-11 1).
  - 없음 → `phoneKey` = 판매자 비밀 키의 HMAC(정규화한 전화번호와 겹칠 수 없는 글 — 범위·뒤 4자리를 담은 글), `phoneLast4` = 그 뒤 4자리인 `sms` 이벤트를 기록한다(R-11 2 — 새 문자 구매자). 같은 범위에서 같은 뒤 4자리를 다시 말하면 이 구매자가 찾아진다.
  - 둘 이상 → 기록하지 않고 409 `{ error: 'BUYER_AMBIGUOUS', message, candidates: [{ buyer, display, phoneLast4 }] }`(후보 = 그 지금의 구매자들, 처음 생긴 순서). `message`는 "끝자리 1234 손님이 여러 명이에요. 누구인지 골라 주세요."
- Then 성공 응답은 지금의 `sms` 응답과 같다(`seq`, `buyer` — D-099). 같은 요청 번호를 다시 보내면 처음과 같은 응답이고 찜은 하나다(409였으면 다시 409 — 그 사이 상태가 바뀌었으면 새로 판단해도 된다: 409는 기록이 없으므로).
- Then 메모·옵션·수량·받은 시각·방송 검사는 손 입력 `sms`와 같다(메모의 휴대폰 번호 검사 D-079 포함).
- 확인: 서버 단위·통합 시험(한 사람·없음·둘 이상·합친 구매자는 한 사람으로·리허설 범위와 실제 범위 분리·같은 요청 번호)

### AC-V1-11 [server] 끝자리 키는 범위 밖과 이어지지 않는다
- 근거: D-V1-03, DAT-06, BUY-05
- Given 판매자 A의 10/22 범위에서 "끝자리 1234"로 넣은 문자 구매자, 10/23 범위에서 다시 "끝자리 1234"
- Then 10/23에는 10/22 구매자가 후보가 아니고(범위 안만 찾는다) 새 구매자의 `phoneKey`는 10/22 것과 다르다. 지난 구매(BUY-05)가 끝자리 키로 두 날을 잇지 않는다. 판매자 B의 같은 끝자리와도 키가 다르다. 손 입력의 전화번호 `010-1111-1234` 구매자의 키와도 다르다(그 사람이 범위에 한 명이면 키가 아니라 지정 구매자로 이어진다 — AC-V1-10).
- 확인: 서버 시험, 적대 시험(AC-V1-50)
