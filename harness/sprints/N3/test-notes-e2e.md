# N3 test-e2e 노트 (라운드 0)

이 트랙의 E2E는 `E2E_PORT_OFFSET=1200`으로 돈다. 시험 모드 가짜 원천(`POST /api/deposits/sources {kind:'FAKE'}` → `POST /api/deposits/test/rows`, 받아 오기 주기 1초)으로 입금을 넣는다.

## 시험 자료 만드는 법
- 실제 범위 판매: 지난 날짜(13~29일 전, `recentDate()` — 입금 후보 창 DP-4 안, 다른 시험 파일의 오늘·2005~2024년·I4 판매 이력 시험의 오늘 앞 12일과 겹치지 않음)에 실제 방송을 만들고 문자찜(메모 = 이름, 전화번호)으로 1등 → 그 문자 구매자 묶음. 판매 시각은 문자찜 이벤트의 서버 도착 시각(지금)이라 입금 `at`은 지금 + 몇 초로 넣는다.
- 금액은 시험마다 다르게(`oddPrice()`), 이름은 `uniq()` — 같은 서버를 쓰는 다른 시험의 묶음과 이름·남은 금액이 겹치지 않게.
- 기대값: 사유 문장·메모·낱말은 DEPOSIT_RULES DP-5·DP-6·DP-8과 acceptance.md 문장 그대로, 금액은 범위 조회(코어 정산)의 `total − received`.
- **기억한 입금자명(유튜브 구매자만)**: E2E에 실제 범위 유튜브 구매자를 만드는 화면 경로가 없다(`/rehearsal/chat`은 리허설만). `@fill` 묶음(chromium-fill, `--fill yes` — 오늘 실제 범위 시청자 채팅 1만)의 유튜브 구매자 묶음을 써서 돌린다(`remember.spec.ts`). 한 날짜 안에서 "부분 입금 확정·기억 → 나머지 금액의 같은 이름 입금 = 자동 확인"으로 다른 날짜 없이 확인한다.

## 일부러 실패하는 시험 (지적)
- **TE-N3-001** `screens.spec.ts` "TE-N3-001: 375px 아래 메뉴(여섯 항목)의 링크가 모두 44×44px 이상 …"
  - 메뉴에 "입금 확인"이 더해져 여섯 항목이 되자 375px에서 "방송"·"정산"·"라벨" 링크가 41~42×44px다(UX-04 누르는 곳 44px, AC-N3-49). 기존 시험 `s06/devices.spec.ts` AC-S06-02·AC-S06-40의 375px 검사도 같은 이유로 실패한다(라운드 0 기준 — 기존 시험이 이미 잡는 회귀).
  - 원인으로 보이는 곳: `apps/web/src/styles.css` 휴대폰 폭의 `.menu-link { flex: 1 1 auto; padding: 0.25rem 0.125rem }` — 두 글자 항목은 글자 폭만큼만 넓어진다. `min-width: 44px`(또는 고른 폭 + 두 줄 허용) 같은 바닥이 없다.

## 지적만 (시험 없음)
- **TE-N3-002 (스펙 확인 필요)**: 문자 구매자는 범위(날짜)마다 다른 구매자 ID다. 그래서 같은 전화번호·같은 메모의 **단골 문자 손님**이 30일 안에 다른 날 묶음(이미 입금 완료여도)을 가지고 있으면, 새 묶음의 남은 금액과 정확히 같은 입금도 S = 2 → `SAME_NAME`("같은 이름의 구매자가 여럿이에요")로 확인 필요가 되고, 3단 제안에 입금 완료 묶음이 들어가 미리 고르지도 않는다(손으로 확인 — `reasons.spec.ts`의 두 시험이 이 동작을 지금 스펙대로 고정). 안전한 쪽(자동으로 적지 않음)이라 사고는 아니지만, 문자 단골이 많은 판매자는 자동 확인이 거의 안 된다. 같은 전화번호 키의 문자 구매자를 날짜를 넘어 한 사람으로 볼지(유튜브 채널처럼) spec-keeper 판단이 필요하다.
