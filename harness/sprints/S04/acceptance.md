## A. 방송 시작·종료와 설정 스냅샷 (R-0 5·6, R-1, 설정 스냅샷, R-12, D-069~D-071)

### AC-S04-01 [core] `broadcast.start` — 새 방송 선언
- 근거: R-1 "방송 시작·종료", 설정표 아래 "설정 스냅샷", D-070
- Given 엔진 상태(빈 엔진 `initEngine({ broadcasts: [], settings: {} })` 포함)
- When `broadcast.start { b, date, title, settings? }`
- Then 방송이 선언되고, 그 뒤의 이벤트가 `b`를 쓸 수 있다. 선언 전에 `b`를 쓴 이벤트는 입력 오류다(지금처럼 "선언하지 않은 방송").
- Then 그 방송의 스냅샷 = DOMAIN_RULES 기본값 위에 `settings`를 덮어쓴 값이다(엔진 시작 설정과 상관없다, G-ENG-161의 b2는 대기 한도 5·배송비 4,000). 코어 조회 함수로 방송 목록(ID·날짜·제목·끝났는지·끝난 시각·설정 스냅샷)을 선언 순서대로 볼 수 있다.
- Then 이미 선언한 방송(엔진 시작 때 또는 앞선 `broadcast.start`)의 `broadcast.start`는 날짜·제목·설정이 달라도 아무 일도 없다(돌려받은 상태가 넘긴 상태와 같다, G-ENG-160·162).
- Then 입력 오류(상태 그대로, `checkEvent`가 같은 경우에만 필드 이름과 함께 문제를 돌려준다): `b`가 빈 문자열·문자열 아님, `date`가 실제 있는 `YYYY-MM-DD`가 아님, `title`이 문자열 아님, `settings`가 객체 아님(배열·`null` 포함)·모르는 키·선택지 밖·범위 밖 값(AC-S04-05), 표에 없는 필드.
- Then `settings`의 `settlement.groupBy`가 `MANUAL`이면 `NotImplementedError`, 상태 그대로(D-059).
- 확인: 골든(G-ENG-160~162), 단위 테스트

### AC-S04-02 [core] 판정은 그 방송의 설정으로
- 근거: 설정 스냅샷, R-0 5, D-070
- Then 판정에 쓰는 설정은 그 메시지·찜·상품이 속한 방송의 스냅샷이다: `claim.*`(주문 인식·방송자 무시·공개 전 찜 유효 시간), `waitlist.max`, `cancel.buyerChat`, `cancel.succession`, `contention.*`, `print.autoOnConfirm`, `thanks.*`. 엔진 시작 때 선언한 방송은 시작 설정이 스냅샷이다(기존 골든 전부 그대로 통과).
- Then 같은 범위에서 방송마다 설정이 달라도 서로 번지지 않는다: 같은 본문이 LOOSE 방송에선 주문, STRICT 방송에선 언급(G-ENG-160), 같은 늦은 문자찜이 접수순 방송에선 대기, 실제 시각순 방송에선 역전(G-ENG-161), 감사·라벨을 끈 방송의 확정은 효과가 없다(G-ENG-160).
- 확인: 골든(G-ENG-160·161), 단위 테스트(두 방송의 승계·시청자 취소·공개 전 찜 유효 시간·대기 한도가 다를 때)

### AC-S04-03 [core] 정산 설정은 그날 첫 방송
- 근거: 설정 스냅샷, R-12, D-070
- Then 묶음(구매자, 날짜)의 배송비에 쓰는 `shipping.baseFee`·`shipping.freeThreshold`는 그 날짜의 방송 중 선언 순서가 처음인 방송의 스냅샷이다. 그날 뒤에 시작한 방송의 정산 설정은 쓰이지 않는다 — 2부에서만 산 구매자도 1부 배송비(G-ENG-160). 날짜마다 그날 첫 방송(G-ENG-161).
- Then 그 날짜에 방송이 없는 묶음(품목 없이 입금만 있는 경우)은 품목이 없어 배송비 0이다(R-12 1).
- 확인: 골든(G-ENG-160·161), 단위 테스트(뒤 방송을 시작해도 앞서 계산한 묶음 금액이 바뀌지 않는다)

### AC-S04-04 [core] `broadcast.end` — 끝났다는 기록만
- 근거: R-1 "방송 시작·종료", D-070
- When `broadcast.end { b }`
- Then 방송 조회에 끝남과 끝난 시각(그 이벤트의 `at`)이 보인다. 판정·정산·효과는 바뀌지 않는다: 끝난 뒤의 채팅(끝나기 전에 게시)·문자찜·방송자 조치·정산 기록은 끝나지 않은 방송과 같은 결과다(G-ENG-162).
- Then 이미 끝난 방송의 `broadcast.end`는 아무 일도 없다. 선언하지 않은 방송·표에 없는 필드는 입력 오류.
- 확인: 골든(G-ENG-162), 단위 테스트, 속성 테스트(같은 로그에서 `broadcast.end`를 빼도 방송 조회 밖의 조회 결과가 같다)

### AC-S04-05 [core] 설정값 검사 함수
- 근거: 설정표 아래 "설정값 범위", D-071
- Then 코어가 설정 덮어쓰기 객체를 검사하는 순수 함수를 내보낸다: 문제(키, 쉬운 이유) 목록, 문제가 없으면 빈 목록. 모르는 키, 선택지 밖 열거값, `true`·`false`가 아닌 예/아니오 값, 정수가 아닌 수(`1.5`·`NaN`·`Infinity`·문자열 `"5"`), 범위 밖(`claim.maxNumber` 1~9999, `claim.preOpenWindowSec` 0~300, `waitlist.max` 0~100, `shipping.baseFee` 0~1,000,000, `shipping.freeThreshold` `null` 또는 0~100,000,000, `thanks.batchWindowSec` 0~600)이 문제다. `settlement.groupBy: MANUAL`은 문제가 아니다(미구현은 엔진이 알린다).
- Then `broadcast.start`의 `settings` 검사(AC-S04-01)와 서버 설정 저장(AC-S04-50)이 이 함수와 같은 판정을 한다. `initEngine`의 시작 설정이 범위 밖이면 오류를 던진다(시작 설정은 서버·러너가 만드는 값이라 프로그램 오류). `resolveSettings`의 기존 동작은 바꾸지 않는다.

### AC-S04-34 [server] 로그·응답에 개인정보·비밀값이 없다

## F. 로그인·격리·요청 보호 (SYS-01, SYS-02, NFR-06, D-074)

### AC-S04-40 [server] 로그인·세션
- 근거: SYS-01, D-074
- Then 계정 만들기 명령: 판매자(가게 이름)·아이디·비밀번호. 비밀번호는 명령행 인자로 받지 않는다(입력·표준 입력). 판매자 전화번호 키도 이때 만든다(AC-S04-32). 가입 API는 없다. 비밀번호는 scrypt 또는 argon2id 해시로만 저장한다.
- When 로그인(아이디·비밀번호)
- Then 성공: 세션 쿠키(무작위 토큰, `HttpOnly`·`Secure`·`SameSite=Lax`·`Path=/`), 서버엔 토큰의 해시만, 30일·쓰는 동안 연장. 실패: 아이디 없음과 비밀번호 틀림이 같은 상태 코드·같은 본문이다.
- Then 같은 아이디로 연속 10번 틀리면 15분 동안 그 아이디의 로그인을 받지 않는다(맞는 비밀번호도 429, 쉬운 문장). 이미 로그인한 세션은 그대로 쓸 수 있다. 성공하면 연속 실패 수가 0이 된다.
- Then 로그아웃: 서버에서 세션을 지우고 쿠키를 지운다. 그 토큰으로 다시 요청하면 401.

- 확인: 서버 시험(시계를 바꿔 만료·잠금 해제 확인)

### AC-S04-41 [server] 요청 보호 (CSRF·CORS)

### AC-S04-51 [server] 이벤트 쓰기 API
- 근거: R-1, D-069, D-072, D-073
- Then 화면이 보낼 수 있는 종류: `product.*`(6), `sms`(AC-S04-31 경로), `host.*`(12), `buyer.merge`·`buyer.unmerge`, `settlement.*`(4). `broadcast.*`는 방송 만들기·끝내기로만(AC-S04-21), `chat`은 서버 수집 함수로만(AC-S04-33), `effect.*`는 S08·S11.

### AC-S04-52 [server] 조회·이력 API

## H. 실시간 (SPEC §3, NFR-01, D-075)

### AC-S04-60 [server] 실시간 푸시 (SSE)
- 근거: SPEC §3, NFR-01, D-075
- Then 로그인한 판매자의 스트림 연결(`text/event-stream`). 연결 직후 판매자의 범위별 지금 `seq`를 보낸다. 커밋된 입력마다 (범위 날짜, `seq`, 이벤트 종류) 알림을 이어지는 `id`와 함께 보낸다.

## K. 테스트 관점 (test-domain, `tests/adversarial/s04/**`)

개발자 보고를 믿지 말고 위 기준을 공격한다. 무엇을 남길지는 test-domain이 정한다. 검증 파이프라인 자체는 공격 대상이 아니다(D-027). **비례 원칙(D-036)**: 기본 설정과 실제 방송에서 나올 법한 순서·장애(네트워크 재시도, 두 기기 동시 조작, 서버 재시작)를 먼저 본다. 심각도는 "실제 방송 사고(이중 판매·엉뚱한 1등·돈 오류·판매 기록 손실·다른 판매자 데이터 노출·개인정보 노출)로 이어지는가"로 매긴다. 서버는 `@livejjim/server`를 프로세스 안에서(`app.request` 등) PGlite로 띄워 공격한다.

- **S03b 적대 테스트 갱신**: 표에 없는 필드·형식 번호·`broadcast.*` 미구현을 가정한 항목이 있으면 바뀐 규칙에 맞춘다(교체이지 약화 아님).
- **방송·설정** (AC-S04-01~05): 사본의 날짜·제목·설정 바꾸기, 선언 전 사용, 같은 날 여러 방송의 정산 설정·판정 설정 섞임, 끝난 방송의 입력, 범위 경계 값, `MANUAL`이 로그에 남는 길.
- **입력 검사** (AC-S04-06~08): 필드 이름 변형·중첩으로 번호 밀어 넣기, `ref`·`memo` 번호 모양(전각·띄어쓰기·접두어), 형식이 다른 상태.
- **판정 규칙** (AC-S04-10·11): 취소 메시지(LOOSE·OFF·AUTO·남의 찜) 변환, 대기 한도 0의 `ASK`에서 취소·무효·승인·자동 취소·재고 늘림.
- **입력 우선 기록·중복** (AC-S04-22~26·30): 같은 요청 번호 동시 전송(입금 두 번), 거른 입력이 로그·발송함·알림에 남는 길, 저장 실패·엔진 예외 주입 뒤 상태·알림, 두 인스턴스 동시 쓰기, `seq` 빈틈, 발송함 중복.
- **재시작·검사** (AC-S04-27~29): 스냅샷 형식·손상, 실패 표시 입력이 재생에서 다르게 처리되는 길, 검사 명령이 바뀐 행을 놓치는 길, 차단 이어받기 누락·과잉(풀린 차단, 문자 구매자).
- **개인정보** (AC-S04-31·32·34): DB 전체·로그·응답·이력·스트림에서 번호·키·메모·비밀값 찾기(오류 경로 포함), 다른 판매자 키로 같은 번호 잇기, 서버 코드의 골든 import.
- **인증·격리** (AC-S04-40~42·60): 세션 없이·만료·위조, 잠금으로 판매자 쫓아내기, Origin 없는 쓰기, 다른 판매자 자원(쓰기·조회·이력·스트림)의 존재 알아내기.
- **지연** (AC-S04-70): 지연 시험이 p99·준비 구간 제외로 재는지, 큰 범위에서 쓰기 경로가 상태 전체를 매번 쓰지 않는지.
