# S01 수용 기준 — 코어 I: 파서 (채팅·금액·빠른 입력)

- 스프린트: S01 (1단계) · spec ID: **ORD-01**, **PRD-01** · 규칙: DOMAIN_RULES R-3, R-14, R-15, R-16 · 근거 결정: D-006, D-007, D-028, D-029, D-030, D-032~D-035
- 개발 영역: **core** · 테스트: **domain** · 사람 확인 지점 없음
- 목표(백로그): 채팅 주문 인식(R-3), 한글 금액·수사 파서, 빠른 입력 파서. 골든 `parser/*` 전부 통과.

- 정답의 우선순위: 골든 사례 → DOMAIN_RULES 규칙 문장 → 이 문서. 골든에 없는 입력은 규칙 문장을 따른다. 규칙 문장으로도 정해지지 않는 경우를 찾으면 구현으로 정하지 말고 dev-notes·결과의 `disputesWithSpec`으로 올린다(dev-common).

모든 기준의 정답 사례는 `tests/golden/parser/chat.yaml`이다. 아래 예시는 그 일부다.

### AC-S01-10 [core] STRICT 주문
- 근거: ORD-01 AC1, R-3 문법·세부 "번호"·"찜·꼬리말"
- Given 기본 설정
- When 메시지 전체가 `[찜] 번호목록 [꼬리말] [꼬리 기호]`이면
- Then `claims` = 번호들(나온 순서, 중복은 처음 자리 하나), 나머지 두 배열은 빈 배열.
  - `"15"`, `"15번"`, `"  15  번 "`, `"찜15"`, `"15찜"`, `"15번 찜할게요"`, `"015"`, `"0015"`, `"１５"` → `[15]`
  - `"15,28,31"` → `[15, 28, 31]`, `"28 15"` → `[28, 15]`, `"15 28 15"` → `[15, 28]`
- Then 꼬리말은 R-3 목록에 있는 말만 받는다: `"15번 살게요"` → 언급 `[15]`.
- 확인: 골든

### AC-S01-11 [core] 꼬리 기호와 질문
- 근거: R-3 세부 "꼬리 기호"·"꼬리 그림 이모지 허용 목록", D-028, D-033
- Then 꼬리 기호는 `! ~ . ^ * ♡ ♥ ☆ ★ ㅎ ㅋ`, R-3 세부 **허용 목록의 그림 이모지 83자**, U+FE0F, U+200D, 피부색 U+1F3FB~U+1F3FF뿐이다: `"15 ❤️"`, `"15 👍🏻"`, `"15번^^"`, `"15번 ㅋㅋㅋ"`, `"15 🥰"`, `"15 🙏🏻"`, `"15‼"`, `"15 🙋‍♀️"`, `"15 ❤️‍🔥"` → 주문.
- Then 꼬리 안의 그림 이모지 글자(`Extended_Pictographic`)는 하나하나가 모두 허용 목록에 있어야 한다. 목록 밖 그림 이모지는 "그 밖의 문자"다: `"15❓"`, `"15⁉"`, `"15번 😭"`, `"15 ❌"`, `"15 🤔"`, `"15 💔"`, `"15 👀"`, `"15 🙅‍♀️"`, `"15 ❤️‍🩹"` → 언급 `[15]`.
- Then 그 밖의 문자가 붙으면 주문이 아니다: `"15?"`, `"15번요?"`, `"15번 ㅠㅠ"`, `"15%"` → 언급 `[15]`.
- Then STRICT에서 끝에 `?`·❓·❔·⁉가 있는 메시지는 어떤 경우에도 `claims`·`cancels`가 비어 있다.
- 확인: 골든, 속성 테스트(`?`로 끝나는 임의 메시지, 허용 목록 83자 각각을 꼬리로 붙인 주문 → 주문, 목록 밖 `Extended_Pictographic` 글자를 꼬리로 붙인 주문 → 주문 아님)

### AC-S01-12 [core] 번호 범위·자릿수
- 근거: R-3 "번호는 1..claim.maxNumber", 세부 "번호"·"범위", D-028
- Then 번호는 숫자 1~4자리, 값 `1..claim.maxNumber`. `"0"`, `"1000"`, `"15000"`, `"00015"` → `{}`.
- Then 범위 밖 번호가 하나라도 섞이면 주문·취소가 아니다: `"15 1000"`, `"15 0"` → 언급 `[15]`.
- Given `claim.maxNumber` = 50
- Then `"50"` → 주문 `[50]`, `"51"` → `{}`, `"15 51"` → 언급 `[15]`, `"51 취소"` → `{}`.
- 확인: 골든, 속성 테스트(n=1..999 → `"n"`·`"n번"`은 `claims [n]`, n=1000..9999 → 세 배열 모두 빔)

### AC-S01-13 [core] 금액 모양은 번호가 아니다
- 근거: R-3 세부 "금액 모양", D-028
- Then 천 단위 쉼표 묶음 전체(`\d{1,3}(,\d{3})+`)와 숫자`.`숫자는 금액 덩어리다. 그런 덩어리가 있으면 주문·취소가 아니고, 그 덩어리는 언급에도 넣지 않는다.
  - `"12,500"`, `"12,500이요"`, `"15,000원이요?"`, `"1.5만 맞나요?"` → `{}`
  - 묶음 모양이 아닌 `"15,28,31"`, `"15, 28"`은 번호 목록이다.
- 확인: 골든

### AC-S01-14 [core] 여러 번호 설정 (`claim.multiNumber`)
- 근거: R-3, 세부 "여러 번호"
- Then `ALL`: 전부. `FIRST`: 첫 번호만(`"28 15"` → `[28]`), 나머지는 언급에도 넣지 않는다. `IGNORE`: 서로 다른 번호가 둘 이상이면 주문이 아니고 전부 언급(`"15,28,31"` → 언급 `[15, 28, 31]`), 같은 번호 반복(`"15 15"`)은 주문 `[15]`.
- Then 취소와 주문이 아닌 메시지의 언급은 이 설정과 상관없다.
- Then 번호 개수 상한(AC-S01-19)은 이 설정을 적용하기 전에 본다: `FIRST`의 `"1 2 3 4 5 6"` → 언급 `[1, 2, 3, 4, 5, 6]`, `"1 2 3 4 5"` → 주문 `[1]`.
- 확인: 골든, 속성 테스트(같은 메시지·같은 `parseMode`에서 `ALL`의 `claims`가 비어 있으면 `FIRST`의 `claims`도 비고, 아니면 `FIRST`의 `claims` = `[ALL의 첫 원소]`)

### AC-S01-15 [core] 취소
- 근거: ORD-07 AC4의 입력 쪽, R-3 취소 문법, 세부 "취소"
- Then 메시지 전체가 `번호 [번] (취소|취소요|취소할게요|취소해주세요) [꼬리 기호 또는 ㅠ·ㅜ·😢·😭·🥲]`이면 `cancels` = `[번호]`: `"15 취소"`, `"15번 취소!!"`, `"15번 취소요 ㅠㅠ"`, `"015 취소"`, `"15번 취소 😭"`.

- Then 번호 여러 개·앞에 오는 취소는 취소가 아니다: `"15 28 취소"` → 언급 `[15, 28]`, `"취소 15"` → 언급 `[15]`, `"취소"` → `{}`.
- 취소 요청을 승인 대기로 띄우는 일(`cancel.buyerChat`)은 엔진 몫이다(S02).
- 확인: 골든

### AC-S01-16 [core] 언급
- 근거: ORD-01 AC2(입력 쪽), R-3 세부 "언급"
- Then 주문도 취소도 아닌 메시지에서, 금액 덩어리가 아닌 1~4자리 숫자 덩어리 중 값이 `1..claim.maxNumber`인 것을 나온 순서대로 중복 없이 돌려준다: `"15번 2개 가능해요?"` → `[15, 2]`, `"15번 15번 예뻐요"` → `[15]`, `"<script>15</script>"` → `[15]`.
- Then 주문이나 취소가 나온 메시지의 언급은 빈 배열이다. 한 결과에서 비어 있지 않은 배열은 많아야 하나다.
- Then 한글 수사는 채팅 번호가 아니다: `"십오번"` → `{}`.
- 확인: 골든, 속성 테스트(세 배열 중 비어 있지 않은 것 ≤ 1, 각 배열 중복 없음, 모든 값 `1..maxNumber` 정수)

### AC-S01-17 [core] LOOSE
- 근거: R-3 LOOSE 모드와 세부(끝 신호 포함), D-028, D-033, D-034, D-035
- Given `claim.parseMode` = `LOOSE`
- Then 맨 앞 주문 부분이 메시지 끝·공백 앞에서 끝나거나 공백·꼬리 기호로 끝나면 주문이고, 그런 부분 중 가장 긴 것을 쓴다.
  - `"15번 너무 예뻐요 살게요"` → `[15]`, `"15번 18번 중에 뭐가 나아요?"` → `[15, 18]`, `"15!!예뻐요"` → `[15]`, `"15번 2개 가능해요?"` → `[15]`(언급 없음)
  - `"3개 남았나요?"`, `"15개요"`, `"15?"`, `"예뻐요 15번"` → 언급만
- Then 취소가 먼저다: `"15 취소할게요 죄송해요"` → 취소 `[15]`. `취소`가 들어간 메시지는 주문이 아니다: `"15번 사려다 취소"` → 언급 `[15]`.
- Then 금액 덩어리·범위·꼬리 기호(허용 목록)·번호 개수 상한·여러 번호·언급 규칙은 STRICT와 같다: `"12,500원이요"` → `{}`, `"15❓ 남았나요"`·`"15😭 놓쳤어요"` → 언급 `[15]`, `"15🥰예뻐요"` → 주문 `[15]`.
- Then 번호 개수 상한은 고른(가장 긴) 주문 부분에 적용하고, 넘으면 더 짧은 앞부분으로 물러나지 않는다: `"1 2 3 4 5 6 다 주세요"` → 언급 `[1, 2, 3, 4, 5, 6]`, `"1 2 3 4 5 다 주세요"` → 주문 `[1, 2, 3, 4, 5]`.
- Then 끝 신호(D-035): 두 자리 — 고른 주문·취소 부분 바로 뒤, 끝 경계와 상관없이 문법에 맞는 가장 긴 맨 앞 부분 바로 뒤 — 에서 공백·피부색 수식 문자·`Default_Ignorable_Code_Point` 글자를 건너뛴 첫 글자가 질문 기호(`?` `？` ❓ ❔ ⁉), 그 부분의 꼬리 기호가 아닌 한글 호환 자모, 그 부분의 꼬리 기호가 아닌 그림 이모지, `번`, 공백 없이 붙은 숫자이면 주문·취소가 아니고 언급(메시지 전체 번호)을 돌려준다.
  - `"15번 😭"`, `"15 ❌"`, `"15 ❓ 남았나요"`, `"15 ？ 남았나요"`, `"15번 ㅠㅠ"`, `"15 ㄴㄴ"`, `"15 ㅇㅇ"`, `"15!❓"`, `"15👍👎"`, `"15 ⟨U+200B⟩😭"`, `"15 번째 사진 예뻐요"` → 언급 `[15]`, `"15~28"`, `"15 28 ❓"` → 언급 `[15, 28]`
  - 물러나지 않는다: `"15 ❤️ 😭"` → 언급 `[15]`. 고른 부분이 더 짧아도 가장 긴 부분 뒤를 본다: `"15 28❓"`, `"15 28ㅠ"` → 언급 `[15, 28]`, `"15 찜❓"` → 언급 `[15]`, `"1 2 3 4 5 6❓"` → 언급 `[1, 2, 3, 4, 5, 6]`. `claim.multiNumber` 전에 본다: `FIRST`의 `"15 28 ❓"` → 언급 `[15, 28]`, `"15 28 예뻐요"` → 주문 `[15]`.
  - 두 자리의 첫 글자만 본다: `"15 ❤️ 예뻐요"`, `"15 ㅋㅋ 예뻐요"`, `"15 번 예뻐요"`, `"15번 너무 예뻐요 ❓"`, `"15 말고 16"` → 주문 `[15]`.
  - 취소는 취소 꼬리 기준: `"15번 취소 😭 죄송해요"` → 취소 `[15]`, `"15번 취소 ❓"`, `"15 취소 번복할게요"`, `"15 취소 ㄴㄴ"` → 언급 `[15]`.
- 확인: 골든, 속성 테스트(LOOSE에서 주문 문법 메시지 뒤에 공백 0~1칸, 끝 신호 1~3번 글자(질문 기호·`ㅎ`·`ㅋ`와 한글 채움 문자 U+3164가 아닌 자모·목록 밖 그림 이모지) 하나, 한글 음절과 공백으로 된 임의의 말을 차례로 붙이면 `claims`·`cancels`가 빈다. 공백 하나와 `번`이 아닌 한글 음절로 시작하고 한글 음절·공백으로만 된 말(`취소`가 들어 있지 않은 말)을 붙이면 원래 메시지의 STRICT 결과와 같다. U+3164는 보이지 않는 글자라 끝 신호 검사에서 건너뛰고, `취소`가 들어간 메시지는 LOOSE에서 주문이 아니다 — S02 spec 단계에서 TD-S01-019에 따라 고침)

- Then 품종은 비어도 성공이다: `"15 10000"` → `{ no: 15, name: "", price: 10000 }`.
- Then `NUMBER_MISSING`(`"핑크프릴 10000"`), `NUMBER_INVALID`(`"0 핑크프릴 10000"`, `"15.5 핑크프릴 10"`), `EMPTY`(`""`, `"   "`)는 `error` 키만 있다. `PRICE_MISSING`·`PRICE_TOO_LOW`는 정확히 `error`·`no`·`name`. 성공은 정확히 `no`·`name`·`price`. 값이 `undefined`인 키도 두지 않는다.
- 커서 이동·"15번이 이미 있어요" 확인(PRD-01 AC3 화면, AC4)은 범위 밖이다.
- 확인: 골든

### AC-S01-42 [core] 번호 범위
- 근거: R-16 3, D-030, R-3
- Then 번호는 `1..claim.maxNumber`: `"999 핑크프릴 10"` 성공, `"1000 핑크프릴 10"` → `NUMBER_INVALID`.
- Given `claim.maxNumber` = 50 (골든 suite에는 이 설정 키가 없으므로 단위 테스트로 확인)
- Then `"50 핑크프릴 10"` 성공, `"51 핑크프릴 10"` → `NUMBER_INVALID`.
- 확인: 골든, 단위 테스트

### AC-S01-43 [core] 가격 하한 100원
- 근거: R-16 4, D-030
- Then 가격이 100원 미만이면 단위 설정과 상관없이 `PRICE_TOO_LOW`(+`no`·`name`): `WON`의 `"15 핑크프릴 99"`·`"15 핑크프릴 10"`, `THOUSAND`의 `"15 핑크프릴 0"`·`"15 핑크프릴 10원"`. `WON`의 `"15 핑크프릴 100"`은 성공.
- Then `THOUSAND`에서 1000 이상은 원 그대로: `"15 핑크프릴 1500"` → 1500.
- 확인: 골든

### AC-S01-44 [core] 빠른 입력 속성
- 근거: PRD-01, R-16
- Then 1 ≤ no ≤ 999, 100 ≤ price ≤ 10^7, 품종이 금액으로 끝나지 않고 마지막 토큰이 금액 글자(숫자·한글 숫자 `일`~`구`·단위 `십`·`백`·`천`·`만`)와 쉼표·점으로만 된 토큰이 아닌 이름(빈 품종 포함)일 때 `WON`에서 `"{no} {name} {price}"` → `{ no, name, price }`. (마지막 토큰이 금액 조각이면 R-16 4 "금액 조각"으로 `PRICE_MISSING`일 수 있다 — D-048, S02 spec 단계에서 고침)
- Then 임의 문자열에서 예외 없이 R-16 6의 결과 모양 중 하나를 돌려주고, 성공이면 `price ≥ 100`, `1 ≤ no ≤ claim.maxNumber`, `name`에 앞뒤 공백·연속 공백이 없다.
- 확인: 속성 테스트

## F. 테스트 관점 (test-domain, `tests/adversarial/s01/**`)

개발자 보고를 믿지 말고 아래를 공격한다. 무엇을 남길지는 test-domain이 정한다. 확인 대상은 위 기준(AC)이다. 검증 파이프라인 자체는 공격 대상이 아니다(D-027).

- **오인 주문** (AC-S01-10~13·17·19): 숫자가 든 평범한 채팅이 주문이 되는 경우를 찾는다. 가격 말하기(`12,500`·`1.5만`·`만원`), 질문(`?`·❓), 아쉬움(`ㅠ`·😭), 허용 목록 밖 그림 이모지와 그 ZWJ 조합, LOOSE 주문 부분 뒤의 끝 신호(공백·보이지 않는 글자를 사이에 둔 질문 기호·자모·목록 밖 이모지, D-035), 번호 6개 이상 나열, 수량(`2개`), 전화번호·시각(`010-1234-5678`, `8:30`), 여러 줄, 보이지 않는 문자(제로폭 공백 U+200B, 방향 표시 U+200E, NBSP), 키캡 이모지(`1️⃣5️⃣`), 다른 문자 체계의 숫자(아라비아·데바나가리 숫자). 규칙 문장이 정하지 않은 경우를 찾으면 결함이 아니라 스펙 질문으로 보고한다.
- **놓친 주문** (AC-S01-10·15): 골든과 규칙이 주문이라고 정한 형태가 띄어쓰기·전각 숫자·꼬리말 조합에서 빠지지 않는지.
- **취소 ↔ 주문 뒤바뀜** (AC-S01-15·17): 취소 의도의 메시지가 주문이 되는 경우(특히 LOOSE).
- **설정 조합** (AC-S01-12·14): `claim.maxNumber` 경계(1, 50, 999, 9999), `multiNumber` × `parseMode` 조합.
- **금액 오해석** (AC-S01-20~22): 잘못된 가격이 숫자로 나오는 경우. 단위 경계(`999`/`1000`, `999.9`, `0.1`), 큰 수, 소수 자릿수, `원` 위치, 한자어·숫자 섞기, 이상한 쉼표, 단위 바로 뒤 한글 일의 자리(`만오`·`삼천오`·`백오만`, D-032).
- **빠른 입력 분해** (AC-S01-40~44): 품종이 가격으로 먹히거나 가격이 품종으로 들어가는 경우, 오류 결과에 잘못된 키가 있는 경우.
- **속성** (AC-S01-02·16·18·21·30·44): 위 속성들을 fast-check로 넓게 확인한다.
- **시간** (AC-S01-03): 역추적 폭주 입력.

## 범위 밖 (이번 스프린트에서 하지 않는다)

- 방송자 본인 채팅 무시(ORD-01 AC3, `claim.ignoreOwner`, D-018): 방송자 여부는 채팅 이벤트의 값이라 엔진이 처리한다 → S02(G-ENG-005). 파서는 본문만 본다.
- 언급 번호 강조와 클릭 한 번 찜 변환(ORD-01 AC2 화면, ORD-12): 화면은 S05, `host.convertMessage` 판정은 S02.
- 시청자 취소 요청 처리(`cancel.buyerChat`, ORD-07 AC4)와 모든 판정·효과·정산 → S02·S03. 엔진 골든 `G-ENG-*`는 계속 미구현(허용). 골든 러너 보강(RA-S00-001·002, TD-S00-009·010)은 엔진 관찰이 붙는 S02에서 한다.
- 빠른 입력 화면: 가격 칸으로 커서 이동(PRD-01 AC3), "15번이 이미 있어요. 고칠까요?"(PRD-01 AC4), 단축키·되돌리기 → S05. 같은 번호 재등록 판정은 엔진(S02).
- 감사 메시지·라벨의 금액 표기(`10,000원`, `8 천원`) → S02(엔진 효과 문구), S07(라벨).
- 음성 인식·문장에서 번호/가격 뽑기·품종 사전(VOC-01~04) → S13. 이번엔 공용 함수 `parseAmount`·`parseKoreanNumber`만.
