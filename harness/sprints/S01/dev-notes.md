# S01 개발 노트

## dev-core

### 만든 것
- `@livejjim/core` 공개 API (이름·결과 모양은 S00 그대로)
  - `parseChat(text, settings?)` → `{ claims, cancels, mentions }` (R-3, D-028)

### 결정과 이유 (규칙 문장 안에서의 구현 선택)
- **파서는 손으로 짠 앞→뒤 한 번 훑기 스캐너**다. 되돌아가며 맞춰 보는 정규식이 없어 적대 입력 10,000자도 ms 단위다(AC-S01-03). 정규식은 겹치는 반복이 없는 `\s+`·`[\uFF10-\uFF19]`·`\p{Extended_Pictographic}` 한 글자 검사만 쓴다. 끝의 0 떼기도 `0+$` 대신 반복문으로 했다(0이 길게 이어지면 제곱 시간).
- **정규화의 공백 = JavaScript `\s`에서 U+FEFF를 뺀 것**(유니코드 공백: 탭·줄바꿈·NBSP·U+3000 등. 라운드 1에서 U+FEFF 제외, TD-S01-001). 제로폭 공백 U+200B·방향 표시 U+200E·U+FEFF는 공백이 아니어서 그대로 남고, 문법에 맞지 않게 되어 주문이 아니다(언급으로 감). 다른 문자 체계의 숫자(아라비아·데바나가리)는 숫자로 보지 않는다.
- **LOOSE "가장 긴 부분"은 경계 조건을 만족하는 부분 중에서 고른다.** 골든 `"15번 2개 가능해요?" → [15]`가 이 해석을 정한다(문법상 가장 긴 `15번 2`는 `개` 앞이라 안 됨). 범위는 라운드 1부터 메시지 전체로 본다(TD-S01-002): `"15 1000원이에요"`·`"15 1000"` 둘 다 언급 `[15]`.
- **금액 덩어리 판정은 숫자 덩어리 단위**: 점으로 이어진 양쪽 숫자 덩어리, 그리고 쉼표로만 이어진 덩어리 묶음이 `\d{1,3}(,\d{3})+` 전체 모양이면 그 묶음 전체. 쉼표 묶음은 숫자 사이의 쉼표 하나로만 잇는다(`12,500,` → 묶음 `12,500` = 금액). `15,28.5` → `28.5`는 금액, `15`는 언급.
- **설정값이 이상할 때**(범위 밖 동작은 이번 스프린트에서 정하지 않음, AC-S01-02): 예외 없이 `parseMode`가 `LOOSE`가 아니면 STRICT, `multiNumber`가 `FIRST`·`IGNORE`가 아니면 ALL, `price.unit`이 `WON`이 아니면 THOUSAND(기본값), `maxNumber`가 NaN이면 어떤 번호도 범위 밖. 설정 객체는 자기 속성만 보고 바꾸지 않는다.
- **문자열이 아닌 입력**(JS에서 부르는 경우): 빈 문자열로 본다 → 채팅 `{}`, 금액·수사 `null`, 빠른 입력 `EMPTY`.
- **한글 금액 세부**: `0만`·`0.0만`(값 0인 한글 단위) `null`, `1만 0500`(만 뒤 네 자리의 선행 0) `null`, `12천`(천·백·십 계수는 한 자리) `null`, 소수 계수 정수부는 만이면 0 또는 선행 0 없는 1~4자리, 천·백·십이면 한 자리. 모두 "애매하면 null"(R-14 머리말) 쪽이다.
- **빠른 입력 가격 찾기는 끝에서 6토큰까지만** 본다. R-14로 해석되는 문자열은 공백 토큰이 최대 6개(`[계수]만` + 천·백·십·일 4묶음 + `원`)이기 때문이다. 단위 테스트가 "모든 묶음을 보는 찾기"와 결과가 같음을 속성으로 확인한다(`quick-input.test.ts`). R-14 형식을 넓히면 `AMOUNT_MAX_TOKENS`도 같이 바꿔야 한다(같은 파일의 테스트가 잡는다).
- **골든 러너 시각 표시 수정**(내 영역): `formatUtcIso`가 UTC 10000년을 `10000-…`로 써서 `toISOString`(`+010000-…`)과 달랐다. S00 적대 테스트 `resolveAt` 속성이 무작위로 `9999-12-31T01:00:00-23:00`을 뽑으면 adversarial 단계가 실패했다(이번 verify에서 seed 198148563로 재현). 확장 연도 형식으로 고치고 단위 테스트를 더했다. 비교 규칙·러너 검사는 그대로다.

### spec-keeper에게: 규칙 문장이 정하지 않았거나 애매해서 안전한 쪽으로 정한 것 (disputesWithSpec)
1. **수식 문자만으로 끝난 LOOSE 부분.** R-3 세부는 꼬리 기호에 "그림 이모지와 그 수식 문자(U+FE0F, U+200D, 피부색)"를 넣는다. 글자 그대로면 LOOSE에서 `"1\u200D5"`(화면엔 `15`), 키캡 `"1\uFE0F\u20E35\uFE0F\u20E3"`(= `1` U+FE0F U+20E3 `5` …)가 "꼬리 기호로 끝난 부분 `1\u200D`·`1\uFE0F`"이 되어 **1번 주문**이 된다(오인 주문, D-006). 구현: 수식 문자는 꼬리 기호로 받되(STRICT `"15\uFE0F"` → 주문 15, AC-S01-11 그대로), LOOSE의 "꼬리 기호로 끝남"은 뒤따르는 수식 문자를 건너뛴 마지막 글자가 **보이는 꼬리 기호(또는 공백)**일 때만 인정한다. 결과: LOOSE `"1\u200D5"`·`"1\uFE0F\u20E35\uFE0F\u20E3"`·`"15\uFE0F예뻐요"` → 언급, `"15❤\uFE0F예뻐요"` → 주문 15. R-3 LOOSE 세부에 이 문장을 넣을지 판단 부탁.
2. **묶음 모양이 아닌 쉼표 목록 안의 금액 같은 조각.** 규칙대로 `"1,500,28"`은 `\d{1,3}(,\d{3})+` 전체 모양이 아니므로 번호 목록 → 주문 `[1, 500, 28]`. `1,500`원 + `28`번처럼 읽힐 여지가 있어 오인 주문 위험이 있다. 세 자리 묶음(`,\d{3}`)이 하나라도 있으면 금액으로 볼지 결정 부탁. 지금은 규칙 문장(골든 `15,28,31` → 주문)대로 했다.
3. **한글 `만오`·`천오`.** R-14 4는 `만오`를 "줄임말(15,000)인지 글자 그대로(10,005)인지 애매"한 예로 들지만, 문법(`[계수]만 … [일의 자리]`)과 AC-S01-21 속성(10005의 표준 읽기 `만오` → 10005)은 10,005를 요구한다. 속성대로 `만오` → 10005, `천오` → 1005, `이만오` → 20005로 했다. 판매 현장에서 `만오`는 보통 15,000이라 잘못된 가격 등록 위험이 있다. 단위 바로 뒤에 일의 자리만 오는 한글 표현(`만오`, `천오`, `이만오`)을 null로 바꾸려면 AC-S01-21 속성의 예외로 적어야 한다.
4. **LOOSE의 공백 뒤 단어.** 규칙대로 `"15 번째 사진"` → 주문 15(`15`가 공백 앞에서 끝남), `"15 00015"` → 주문 15(5자리 숫자는 번호가 아니라 부분이 `15`에서 끝남). `"15번째"`(붙여 씀)는 언급이다. LOOSE가 기본 꺼짐이라 그대로 두었다.
5. **유니코드 정규화(NFC)를 하지 않는다.** 자모로 풀어 쓴 한글(NFD, 예: 일부 macOS 붙여넣기)의 `취소`·`찜`·`번`은 맞지 않아 주문·취소가 안 된다(놓친 주문 쪽). 정규화 범위(R-3)에 NFC를 넣을지 판단 부탁. `String.prototype.normalize`는 실행 환경 설정과 무관해 코어에서 써도 된다.

**빠른 입력 "금액 조각" 규칙** (`quick-input.ts` `isSplitAmount`). 가격 묶음 앞 토큰 P가 금액 글자(ASCII 숫자·`일`~`구`·`십백천만`)와 쉼표·점으로만 되어 있고(금액 글자 하나 이상), 다음 중 하나이면 `PRICE_MISSING`(품종 = 번호 뒤 전부).
- P가 단위·숫자·쉼표·점으로 끝난다: `1만 500`(10,500 → 예전엔 500,000), `1만 5`, `1.5만 5천`, `5천 1만`, `1 500`, `2 만원`, `5 만`, `2 만 5천`
- P가 한글 숫자로 끝나고 가격 묶음이 단위로 시작한다(계수와 단위를 띄어 씀): `오 천`, `이만오 천`, `십오 만`

### spec-keeper에게 (라운드 1 추가)
6. **R-16 4 예외 문장과 골든** (RA-S01-001·TD-S01-003, 구현함). 위 "금액 조각" 규칙을 R-16 4에 적고, 골든 quick-input에 `15 핑크프릴 1만 500`·`15 핑크프릴 5 만`·`15 핑크프릴 2 만원`·`15 핑크 오 천` → `PRICE_MISSING`, `15 천사 5천`·`15 핑크 10원 20` → 성공을 넣어 주면 고정된다. AC-S01-44의 "금액으로 끝나지 않는 이름"은 "금액 글자로만 된 토큰으로 끝나지 않는 이름"으로 읽어야 맞다(`핑크 1만5`·`핑크 만만` 같은 품종).
7. **R-14 단위 뒤 한글 일의 자리** (RA-S01-002, 분쟁). 제안: 금액(R-14)에서만, 한글 일의 자리(`일`~`구`)는 단위가 앞에 없거나 바로 앞 단위가 `십`일 때만 받는다. `만오`·`이만오`·`천오`·`삼천오`·`백오`·`만 오`·`1천오` → null, 만의 계수도 같음(`백오만` null). `십오`·`만십오`·`오`·`오십오만`·`칠천오백원`은 그대로. R-15(번호)는 그대로 둔다(AC-S01-30 `백이` → 102, 번호는 글자 그대로 읽는 것이 보통). AC-S01-21 속성에는 "만 미만 네 자리 묶음(만의 계수 묶음 포함)에서 십의 자리가 0이고 일의 자리가 0이 아니며 더 큰 단위가 있는 수"를 예외로 적어야 한다(예: 10005, 1005, 105, 1050000). 판정이 나면 다음 라운드에 `parseBelowMan` 옵션 하나로 구현하고 단위 테스트(`만오`·`천오` 고정)를 새 스펙에 맞춘다.
8. **R-3 꼬리 기호에서 뺄 그림 이모지** (RA-S01-003, 분쟁). 제안: 물음표 이모지 ❓(U+2753) ❔(U+2754) ⁉(U+2049)는 `?`와 같이 질문, 부정·금지 ❌(U+274C) ❎(U+274E) ⛔(U+26D4) 🚫(U+1F6AB) ✖(U+2716) 🙅(U+1F645), 아쉬움·고민 😢 😭 🥲 🤔 😞 😔 😟 😥 😰 😓 😩 😫 ☹ 🙁 😕 💔는 `ㅠ`와 같이 주문 아님(언급). 느낌표 이모지 ❗❕‼는 `!`와 같으니 그대로. 판정이 나면 `chat.ts`에 목록 하나로 구현한다.
9. **메시지당 주문 번호 상한** (RA-S01-004, 분쟁). 제안: 서로 다른 번호가 5개를 넘으면 주문이 아니고 전부 언급(`ALL`·`FIRST`·`IGNORE` 모두, 취소와 무관). 적대 테스트 성질 "ALL의 claims가 비면 FIRST도 같다"와 맞추려면 `multiNumber` 적용 전에 막아야 한다. 설정 키로 둘지(예: `claim.maxNumbersPerMessage`, 기본 5)는 설정표 소유자 결정.
10. **R-3 정규화 문장** (TD-S01-001, 구현함). "연속 공백"의 공백이 유니코드 공백이고 U+FEFF·U+200B 같은 보이지 않는 글자는 공백이 아니라는 것을 문장으로 적어 주면 좋다.
11. **LOOSE 범위의 5자리 이상 숫자** (TD-S01-002 관련 질문). R-3 세부 "번호"가 5자리 이상은 번호가 아니라고 해서 범위 판정에 넣지 않았다: LOOSE `15 10000원이에요` → 주문 `[15]`, `15 1000원이에요` → 언급. 5자리 이상도 막을지 정해 주면 따른다. 골든 LOOSE에 `15 1000원이에요`·`15 0개`·`15 1,000원이에요` → 언급을 넣어 달라는 테스터 요청도 같이.
