# N2b-1 수용 기준 — 틱톡 라이브 베타 ① 연결 모듈 (읽기 전용 웹캐스트 연결기 어댑터, 병렬 트랙)

- 스프린트: N2b-1 (5단계, 병렬 트랙 — 브랜치 `track/n2b1-tiktok`, 작업 폴더 `livejjim-wt/n2b1`) · spec ID: **PLT-02** (연결: D-904, D-018, D-036, D-073, DAT-06, NFR-02, NFR-04, NFR-06, NFR-07, SYS-02, UX-01, UX-03)
- 개발 영역: **server** · 테스트: **domain** (test-e2e 없음 — 화면은 N2b-2). **dev-core가 없다.** 판정·정산 규칙과 엔진·파서 골든(`*.yaml`)은 바꾸지 않는다.
- 목표(백로그): D-904대로 틱톡 라이브 댓글 **읽기 전용** 연결기를 독립 모듈(`apps/server/src/tiktok/**`)로 만든다. 비공식 웹캐스트 연결기(MIT)를 고정 판으로 감싸고, 입력 = 틱톡 아이디(또는 방송 주소), 출력 = 공통 댓글 레코드. 연결·다시 연결(지수 백오프)·차단/서명 실패를 쉬운 한국어 상태로 알리고, 같은 댓글 ID는 한 번만, 판매자 세션 쿠키는 받지도 저장하지도 않으며 글 올리기는 없다. 운영자 전체 끄기(환경 변수)와 판매자별 동의를 확인하는 자리(인터페이스)만 둔다. 실제 틱톡 연결은 시험에서 쓰지 않는다 — 가짜 웹캐스트로 시험한다.
- 공통 전제: 지금까지의 결과(`pnpm verify` 7단계 — typecheck·lint·test·golden·adversarial·e2e·coverage)가 그대로 유지된다. 외부 계정·실기기·인터넷은 필요 없다. 시계·타이머는 주입해 시험한다(기다림이 있는 기준 — 다시 시도 간격·시간 초과·60초 유지 — 은 주입한 시계로 빠르게 돈다).
- 정답의 우선순위: 골든(`tests/golden/tiktok/*.json`) → SPEC PLT-02·D-904 → DECISIONS(D-N2b-1-01~08) → 이 문서. 규칙으로도 정해지지 않는 경우를 찾으면 구현으로 정하지 말고 dev-notes·결과의 `disputesWithSpec`으로 올린다.
- 태그: `[server]` = dev-server(`apps/server/**`). 이번 스프린트의 모든 기준이 `[server]`다. dev-server는 N2b-2가 쓸 계약(내보내는 함수·형, 상태 칸, 문장 상수, 실패 종류 대응표, 가짜 웹캐스트 사용법)을 `harness/sprints/N2b-1/dev-notes.md` "N2b-2에게" 절에 적는다(AC-N2b-1-62). 이름은 dev-server가 정하되 이 문서가 정한 코드·칸 이름·문장은 그대로 쓴다.
- 이 문서가 따옴표로 정한 판매자에게 보이는 문장은 모듈이 그대로 돌려준다(N2b-2 화면이 글자로 쓴다, UX-01·UX-03). 프로그램이 읽는 값은 영문 코드로 함께 준다.

## A. 모듈 경계·라이브러리 (D-904, D-N2b-1-01·06·08)

### AC-N2b-1-01 [server] 독립 모듈

- Then 라이브러리(`tiktok-live-connector`)를 import하는 파일은 모듈 안 감싸개 파일 하나뿐이다.

### AC-N2b-1-02 [server] 연결기 판·라이선스 고정
- 근거: D-904, D-N2b-1-01, PRT-01과 같은 기준(GPL 계열 복사 금지)
- Then `apps/server/package.json`의 `dependencies`에 `"tiktok-live-connector": "2.1.0"`(범위 기호 없음)이 있고 잠금 파일도 2.1.0으로 풀린다.

- 확인: 단위 시험, 리뷰

### AC-N2b-1-03 [server] 읽기만 — 글 올리기·세션 쿠키 없음
- 근거: D-904, D-N2b-1-06
- Then 모듈이 내보내는 것 중에 틱톡에 무엇을 보내는(글·좋아요·선물 등) 함수가 없다. 연결 객체가 가진 조작은 `start`·`stop`과 상태 조회뿐이다(시험: 연결 객체의 함수 이름 목록).
- Then `apps/server/src/tiktok/**`의 소스에 `sendMessage`라는 이름이 없다(정적 시험).
- Then 라이브러리 생성자를 시험용으로 바꿔 끼우면, 감싸개가 넘기는 값은 (아이디, 옵션)이고 옵션의 키는 허용 목록 안이다: `processInitialData: false`, `fetchRoomInfoOnConnect: true`, `enableExtendedGiftInfo: false`, `signApiKey`(설정했을 때만, AC-N2b-1-42). 그 밖의 키가 꼭 필요하면 dev-notes에 이유를 적고 spec-keeper가 판정한다 — 단 세션·쿠키·인증·로그인·프록시와 관련된 키(`session`·`sessionId`·`cookie`·`authenticateWs`·`useMobile`·`oAuthToken` 등, 대소문자 무관)와 HTTP·웹소켓 머리글 덮어쓰기는 어떤 경우에도 넘기지 않는다.
- Then 연결을 만드는 함수의 입력 형에는 쿠키·세션·로그인 칸이 없다. 실행 중 입력 객체에 그런 키(예: `sessionId: 'planted'`)가 섞여 들어와도 라이브러리 옵션에 들어가지 않는다(감싸개는 허용 목록의 키만 골라 넘긴다).
- 확인: 단위 시험(생성자 바꿔 끼우기), 정적 시험

### AC-N2b-1-04 [server] 시험의 바깥 연결 막기
- 근거: 백로그("실제 틱톡 연결은 시험에서 쓰지 않는다"), D-N2b-1-07
- Then 서버 시험(`apps/server`의 모든 vitest 프로젝트) 시작 때 바깥 연결 막기 장치가 깔린다: 호스트가 `tiktok.com`·`tiktokv.com`·`tiktokcdn.com`·`eulerstream.com`이거나 그 하위 도메인인 곳으로 나가는 HTTP(S)·웹소켓·TCP 연결 시도를 실제로 나가기 전에 막고 센다. 막힌 시도가 하나라도 있으면 그 시험 파일이 실패한다.
- Then 자체 시험: 실제 감싸개 + 실제 라이브러리 2.1.0으로 `seller_kim`에 연결을 시도하면 (가) 막기 장치가 위 호스트 중 하나로 가는 시도를 1번 이상 센다 (나) 감싸개는 그 실패를 실패 종류(`NETWORK` 또는 `SIGN_FAILED`)로 바꿔 돌려주고 예외가 새지 않는다. 이 시험은 센 값을 확인한 뒤 되돌려 파일이 실패하지 않게 한다. (= 감싸개가 정말 라이브러리의 통신 경로를 부른다는 증거.)
- Then 다른 병렬 트랙(Y1)의 구글 막기 장치와 함께 깔려도 서로를 지우지 않는다(합칠 때 오케스트레이터가 시험 준비 파일을 합친다).
- 확인: 단위 시험(막기 장치 자체 시험 포함)

### AC-N2b-1-23 [server] 중복 기억

### AC-N2b-1-24 [server] 도착 시각·순서·이전 댓글·버린 연결

### AC-N2b-1-30 [server] 상태와 문장
- 근거: D-N2b-1-05, UX-01, UX-03
- Then 상태 조회는 `{ state, reason, message, failures, nextAttemptAt, lastFailure, missed, counts: { received, duplicates, dropped } }`를 돌려준다. `reason`·`nextAttemptAt`·`lastFailure`는 없으면 `null`, `nextAttemptAt`은 `RETRYING`일 때만 값(UTC ISO 밀리초), `failures` = 지금 연속 실패 수, `lastFailure` = 마지막 실패 종류, `missed` = AC-N2b-1-37, `counts` = 내보낸 레코드·중복·그 밖의 버림 수.
- Then `state`·`reason`·`message`는 이 표 그대로다(문장은 글자 그대로):

  | state | reason | message |
  |---|---|---|
  | `IDLE` | `null` | 틱톡에 아직 연결하지 않았어요. |
  | `CONNECTING` | `null` | 틱톡에 연결하는 중이에요. |
  | `CONNECTED` | `null` | 틱톡 댓글을 받고 있어요. |
  | `RETRYING` | `NETWORK` | 틱톡 연결이 끊겨 다시 연결하는 중이에요. |
  | `RETRYING` | `NOT_LIVE` | 틱톡 방송이 아직 시작되지 않았어요. 잠시 뒤 다시 확인해요. |
  | `RETRYING` | `BLOCKED` | 틱톡이 연결을 막아 다시 시도하는 중이에요. 그동안 댓글을 직접 넣어 주세요. |
  | `RETRYING` | `SIGN_FAILED` | 틱톡 연결 준비에 실패해 다시 시도하는 중이에요. 그동안 댓글을 직접 넣어 주세요. |
  | `STOPPED` | `USER_NOT_FOUND` | 그런 틱톡 아이디를 찾지 못했어요. 아이디를 확인해 주세요. |
  | `STOPPED` | `GAVE_UP` | 틱톡에 다시 연결하지 못했어요. 다시 연결을 누르거나 댓글을 직접 넣어 주세요. |
  | `STOPPED` | `BY_SELLER` | 틱톡 연결을 끊었어요. |
  | `ENDED` | `null` | 틱톡 방송이 끝났어요. |
  | `OFF` | `OPERATOR_OFF` | 지금은 틱톡 연결을 쓸 수 없어요. 댓글을 직접 넣어 주세요. |
  | `OFF` | `NO_CONSENT` | 틱톡 연결이 꺼져 있어요. 안내를 읽고 동의하면 켤 수 있어요. |

- Then 이 모듈이 판매자에게 보이려고 내보내는 모든 문장(위 표, AC-N2b-1-11, AC-N2b-1-37)에는 영문 글자(`[A-Za-z]`)·숫자 오류 코드·기술 낱말(연결기·서명·웹소켓·프로토콜 등)이 없다(시험: 문장 상수 전부를 검사).
- Then 새로 만든 연결 객체는 `IDLE`이다.
- 확인: 단위 시험

### AC-N2b-1-34 [server] 연결 시간 초과·연결은 하나

### AC-N2b-1-35 [server] 라이브러리 오류 → 실패 종류

- 확인: 단위 시험

### AC-N2b-1-36 [server] `start()`·`stop()`
- 근거: D-N2b-1-05
- Then `start()`는 `IDLE`·`RETRYING`·`STOPPED`·`ENDED`·`OFF`에서 연속 실패 0으로 바로 연결 시도를 한다(운영자 스위치·동의 확인 먼저, AC-N2b-1-40·41). `CONNECTING`·`CONNECTED`에서는 아무 일도 없다. 같은 순간에 두 번 불러도 시도는 하나다.
- Then `stop()`은 어느 상태에서든 `STOPPED`/`BY_SELLER`로 바꾸고, 남은 다시 시도 타이머를 지우고(시계 1시간 → 시도 수 그대로), 열린 연결을 닫는다(가짜 웹캐스트가 닫힘을 본다). 연결 중이던 시도가 `stop()` 뒤에 성공하면 바로 닫고 상태는 `STOPPED` 그대로다.
- Then `stop()` 뒤 가짜 웹캐스트가 그 연결로 댓글을 보내도 레코드 0(AC-N2b-1-24).
- 확인: 통합 시험

### AC-N2b-1-37 [server] 끊김 안내
- 근거: D-N2b-1-04
- Then `CONNECTED`였던 연결이 `stop()`이 아닌 이유로 끊기면 상태의 `missed`가 `true`가 되고, 판매자가 `start()`를 부를 때까지 `true`로 남는다(다시 연결에 성공해도). 모듈은 이 문장을 상수로 내보낸다: "끊긴 동안의 틱톡 댓글은 받지 못했을 수 있어요. 틱톡 앱에서 확인해 주세요."
- Then 한 번도 `CONNECTED`가 되지 않은 실패(방송 전·막힘 등)에서는 `missed`가 `false`다.
- 확인: 통합 시험

### AC-N2b-1-38 [server] 상태 알림
- 근거: D-N2b-1-05
- Then `state`·`reason`·`failures`·`missed` 중 하나라도 바뀔 때마다 상태 알림 콜백을 정확히 한 번 부르고, 바뀌지 않았으면 부르지 않는다. 댓글마다(`counts`가 바뀔 때마다) 부르지는 않는다 — `counts`는 상태 조회로 본다.
- Then 상태 알림 콜백이 예외를 던져도 연결·다시 시도·댓글 흐름은 그대로다.
- 확인: 통합 시험

### AC-N2b-1-40 [server] 운영자 전체 끄기

## 공격 관점 (test-domain 참고)

- 해석: 닮은 호스트(`tiktok.com.evil.example`, `evil.example/tiktok.com/@x`, 사용자 정보·포트), 아주 긴 입력·되풀이 패턴으로 정규식 시간 늘리기, 전각·보이지 않는 글자 섞인 아이디(`​`) → `INVALID`.
- 레코드: 2^53 넘는 ID의 모든 입력 모양(숫자·`bigint`·라이브러리 정수 객체), 앞자리 0으로 같은 사람 둘 만들기, 같은 ID에 다른 내용, 버린 뒤 같은 ID, 2만 개 넘는 ID로 기억 밀어내기 뒤 재전송(엔진의 메시지 ID 중복 막기가 2차 방어 — N2b-2), 거대한 닉네임·본문.
- 연결: 붙었다 바로 끊기기 반복으로 한도 피하기, 시간 초과 직후 성공, `stop()`과 성공 경합, `start()` 연타, 이전 연결 손잡이로 댓글, 동의가 다시 시도 사이에 바뀜, 동의 확인이 끝나지 않음(AC-N2b-1-41 (바)), 콜백·상태 알림 예외.
- 비밀: 서명 키·심은 댓글 값이 로그·상태·오류에 새는지, 입력 객체에 섞은 `sessionId`·`cookie`가 라이브러리에 닿는지, 시험 중 실제 틱톡·서명 서비스로 나가는 연결.
