## 지적

- **TD-QS1-001** (major, web `apps/web/src/lib/printer-station.ts`): 저절로 이어진 뒤 출력할 때마다 60초 타이머가 다시 시작된다. `#onAdapterState`가 `CONNECTED`를 받을 때마다 `#autoUsed > 0`이면 `#armStable()`을 부르는데, 출력 한 장마다 `PRINTING → CONNECTED`가 오기 때문이다. 그래서 60초보다 자주 출력하는 방송에서는 횟수가 새로 세어지지 않는다. 6번째 시도로 이어진 뒤라면 다음 끊김에 저절로 잇기가 한 번도 일어나지 않는다. D-QS1-02 (3) "이어진 뒤 60초가 지나 끊기면 1초부터 새로"와 어긋난다. 고칠 길: 60초 타이머를 `DISCONNECTED`에서 `CONNECTED`로 처음 바뀔 때만 건다(`previous`가 `PRINTING`이면 다시 걸지 않는다).
- **TD-QS1-002** (major, server `apps/server/src/extension/routes.ts`, `apps/server/src/login-limit.ts`): 믿는 주소의 주소마다 20번은 밀어낼 수 있다. 주소 기록(`IpLimiter`)은 1만 개를 넘으면 가장 오래 안 쓴 주소부터 지운다. 그리고 코드 넣기 요청은 전체 한도에 막혀도 주소 기록에는 남는다. 그래서 다른 IPv6 /64 주소 1만 개로 한 번씩 보내면 믿는 주소 A의 기록이 지워지고, A는 바로 20번을 새로 얻는다. 믿는 주소는 전체 3,000번에도 세지 않으니, 판매자 계정 하나와 /48 하나만 있으면 코드 맞혀 보기의 서버 전체 상한이 없어진다(D-QS1-06 (d), AC-QS1-32 "주소 한도 20번에 막힌다"). 고칠 길(예): 지금 한도에 걸린 주소나 믿는 주소의 기록은 밀어내지 않는다. 또는 전체 한도에 막힌 요청은 주소 기록에 새로 넣지 않는다.

## 통과한 공격 (버그 아님)
- 연결 시도 겹침·기억한 기기 길의 고르기 창·6번 상한·"연결 끊기" 뒤 저절로 잇기·끊긴 동안 받기·상세 문장: 속성 시험 120번(따로 600번까지 돌려 봄)에서 위반 없음
- 실시간 한도: 실제 소켓에서도 @hono/node-server가 drain을 기다리므로 안 읽은 글이 스트림 큐에 쌓여 한도가 걸린다
- 참고(지적 아님): 읽는 연결도 한 번의 `publish`(한 틱)로 1 MiB를 넘게 받으면 닫힌다. 한도가 "안 읽고 쌓인 양"이라 정한 대로이고, 실제 커밋 하나의 알림은 그만큼 크지 않다
