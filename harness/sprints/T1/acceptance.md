## A. 서버 — 순수 함수·배송지 저장 (PC-2·PC-3·PC-4)

### AC-T1-01 [server] 배송지 읽기 골든
- 근거: PC-2, D-T1-03
- Given `tests/golden/parcel/address.json`(26사례)
- When 서버 단위 시험이 모든 사례의 `in`을 서버의 배송지 읽기 함수에 넣는다
- Then 결과가 `out`과 깊은 같음이다. 시험은 `parcel/` 폴더의 파일 수 2·사례 수 47(address 26 · eligibility 21)을 고정값으로 단언하고, 모르는 `kind`·모르는 키·중복 ID·ID 형식 오류·표 밖 열거값을 읽기 오류로 실패시킨다(`tests/golden/README.md` "택배 골든"). 미구현 허용 장치가 없다.
- Then 같은 함수가 구매자 링크 양식·판매자 배송지 API·설정의 보내는 사람 검사에 쓰인다(세 곳의 서버 시험이 같은 틀린 입력에 같은 칸 코드를 받는다).
- 확인: 골든(서버 단위)

### AC-T1-02 [server] 배송지 저장은 암호문뿐
- 근거: PC-3 "저장", DAT-06 배송지, D-T1-04
- Given 판매자 S의 실제 날짜 D, 구매자 A의 묶음에 배송지(받는 분 `홍길동`, 연락처 `01012345678`, 주소 `서울특별시 중구 세종대로 110`, 상세 `101동 202호`, 메모 `문 앞에`)를 저장했다
- When 시험이 DB의 모든 표·모든 행을 글로 읽는다
- Then `홍길동`·`01012345678`·`세종대로`·`101동`·`문 앞에`가 어느 행에도 없다(암호문만). 따로 있는 칸은 출처(구매자/판매자)·확인 여부·확인한 계정·고친 시각뿐이다.
- Then 그 암호문을 다른 (판매자, 날짜, 구매자) 행으로 옮기면 풀리지 않고 서버는 "배송지 없음"으로 다룬다(D-073 방식).
- Then 배송지를 고치면 이전 내용은 어디에도 남지 않는다(고친 기록은 누가·언제만).
- 확인: 서버 단위(PGlite)

### AC-T1-03 [server] 30일에 지운다
- 근거: PC-3 "보관", D-T1-04
- Given 날짜 2026-10-01 묶음의 배송지와 `BOOKED` 접수(송장 `900000000001`)
- When 주입한 시계가 2026-10-31 00:00(KST)을 지나 정리 작업이 돈다
- Then 그 날짜의 모든 배송지 행이 지워진다(봉인 대상이 아닌 문자찜만 있는 날짜도). 접수 기록의 택배사·송장번호·상태는 남는다.
- Then 2026-10-30 23:59(KST)에는 지우지 않는다. 같은 작업을 두 번 돌려도 결과가 같다.
- Then 지운 뒤 그 묶음의 운송장 요청은 409 "배송지 보관 기간이 지나 운송장을 만들 수 없어요.", 봉인한 날짜는 접수 목록에 나오지 않고, 봉인하지 않는 날짜(문자찜만)의 아직 접수하지 않은 묶음은 `NO_ADDRESS`로 나온다.
- 확인: 서버 단위(주입한 시계)

### AC-T1-04 [server] 접수할 수 있는지 골든
- 근거: PC-4, D-T1-05

### AC-T1-05 [server] 합치기·떼어 내기와 배송지
- 근거: PC-3 "합치기·떼어 내기", R-11, D-T1-07
- Given 날짜 D에 구매자 X(배송지 있음, 확인함)·Y(배송지 없음), 날짜 E에 X·Y 둘 다 배송지(Y 것 확인함)
- When 판매자가 X를 Y에 합친다
- Then D의 Y 묶음 배송지 = X가 적은 것, "확인 전". E의 Y 묶음 배송지 = Y의 것 그대로, "확인 전". X의 배송지 행은 D·E 모두 없다.
- When 그 뒤 X를 떼어 낸다 Then 배송지는 Y에 남고 X에는 없다.
- Then 접수한 묶음(포장 기록 배송 완료)이 있는 구매자의 합치기·떼어 내기는 지금 규칙대로 막힌다(D-I2-20 — 같은 상태·문장).
- Given X가 Y에 합쳐져 있고 그 날짜 Y 묶음의 가장 나중 시도가 `PENDING`(2분 전·후 모두) 또는 `UNKNOWN` When X를 떼어 낸다 Then 409 `PACKING_RECORDED`, 문장 "택배 접수 결과를 기다리는 구매자에게서는 떼어 낼 수 없어요. 택배 화면에서 접수 결과를 먼저 확인해 주세요.", 엔진 이벤트 수·구매자 묶음이 그대로다. 가장 나중 시도가 `FAILED`·`CANCELLED`면 떼어 내기가 된다(D-T1-07 보탬).
- 확인: 서버 단위

### AC-T1-06 [server] 백업·전체 기록·복구

- 확인: 서버 단위

### AC-T1-07 [server] 권한과 판매자 나눔
- 근거: PC-3 "누가 적나", SYS-04, D-T1-14
- Given 판매자 S와 S의 보조자 H, 다른 판매자 T
- When H가 배송지 읽기·쓰기·확인, 접수 목록·접수·다시 확인·취소, 운송장 PDF, 택배 설정 읽기·쓰기 API를 부른다 Then 모두 403이고 아무것도 바뀌지 않는다.

### AC-T1-11 [server] 구매자가 적기
- 근거: PC-2·PC-3, D-T1-06
- When 구매자가 양식을 보낸다(`POST`, `Origin` = 앱 주소)
- Then 맞으면 저장(출처 구매자, "확인 전") 뒤 303으로 같은 링크로 돌아가고, 그 쪽에는 "배송지를 받았어요" + 받는 분 이름 + "연락처 끝 5678"만 있고 주소·상세·메모·연락처 전체는 없다. "다시 적기"는 빈 양식이다.
- Then 틀리면 저장하지 않고 400으로 같은 쪽을 그리며 칸마다 문장을 보인다(예: `PHONE_INVALID` → "연락처는 010으로 시작하는 숫자로 적어 주세요.", `ADDRESS_EMPTY` → "주소를 적어 주세요."). 적은 값은 그 응답에만 다시 채운다.
- Then `Origin: null` + `Sec-Fetch-Site: same-origin`이면 앱 주소와 같게 받는다(링크 화면이 no-referrer라 브라우저가 보내는 모양). `Origin`이 없거나 다르면, 또는 `Origin: null`인데 `Sec-Fetch-Site`가 없거나 `cross-site`·`same-site`·`none`이면 403("다른 곳에서 보낸 양식이라 받지 않았어요. …")이고 저장하지 않는다(D-T1-06 보탬 — `Sec-Fetch-Site`를 보내지 않는 옛 브라우저도 403). 양식 보내기도 링크마다 1분 60번 한도에 함께 센다(넘으면 429, 저장 없음).
- Then 확인 전/확인함 배송지를 구매자가 다시 적으면 덮어쓰고 "확인 전"이 된다.
- 확인: 서버 단위
