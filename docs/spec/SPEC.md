## 0. 읽는 법

- 요구사항 ID: `영역-번호` (예: `ORD-03`). 커밋·테스트·감사 지적은 이 ID로 연결한다.
- 우선순위: **P1** 출시 필수 · **P2** 출시 직후 · **P3** 나중에.
- 단계: 1 기본 판매 관리 · 2 라벨·정산 · 3 유튜브 연동 · 4 음성·고급 (요청서 6장과 같다. 단, 입금·배송비는 명세서에 필요하므로 2단계로 당겼다).
- **AC** = 수용 기준(Acceptance Criteria). 테스트로 확인할 수 있게 쓴다.
- 판정·정산 규칙의 세부(상태, 우선순위, 예외)는 DOMAIN_RULES.md의 `R-*`, 불변식은 `INV-*`.
- 라벨·출력 세부(크기, 찍는 글, 쪽 나누기, 템플릿, 내보내기, 프린터, 출력 대기열)는 LABEL_RULES.md의 `L-*` (P1, D-P1-01).

## 1. 목적과 성공 기준

유튜브 라이브로 다육이를 파는 판매자가 **스태프 없이** 상품 등록 → 찜 접수 → 선착순 판정 → 라벨 → 정산 → 포장까지 처리하게 한다.

| 지표 | 목표 |
|---|---|
| 판정 정확도 | 리허설 기준 방송 1회(상품 100개, 채팅 3,000건)에서 선착순 판정 오류 0건 |
| 금액 정확도 | 구매자별 합계·배송비·최종 금액 오류 0건 (골든 시나리오 + 속성 테스트로 보장) |
| 방송 중 조작 | 상품 1개 등록 = 키보드 한 줄 + Enter. 라벨 출력은 자동(0클릭) 또는 1클릭 |
| 방송 후 정산 | 방송 종료 → 전원 명세서 PDF·엑셀 판매대장 10분 이내 |
| 장비 비용 | 이미 가진 NIIMBOT B1 + PC(크롬) + 휴대폰 외 추가 장비 0 |

## 2. 범위

**포함**: 상품 등록(직접·빠른 입력·음성), 유튜브 채팅 주문 수집·판정, 문자찜 수동 입력, 라벨(B1 직접·이미지·PDF), 구매자별 합산·회차 통합, 명세서 PDF, 엑셀 판매대장, 감사 메시지, 입금·포장·배송 상태, 백업·복구.

**초기 제외 (향후 후보)**: 문자 자동 수집(P3: 안드로이드 '공유하기'로 붙여넣기), 결제대행(PG)·가상계좌, 세금계산서·현금영수증 자동 발행, 밴드 라이브, 택배사 송장 연동, 명세서 문자/알림톡 자동 발송(P2 후보). (인스타그램·틱톡 라이브는 추가 요구사항 v2로 들어왔다 — §5.11 PLT-01·PLT-02, D-903·D-904. 틱톡은 읽기 전용 베타.)

## 3. 사용자와 사용 환경

- **판매자(방송자)**: 1인 운영이 기본. 컴퓨터에 익숙하지 않을 수 있다. 방송 중엔 손이 바쁘다.
- **보조자(선택)**: 휴대폰으로 문자찜 입력, 포장 확인.
- **기기 역할**

| 기기 | 역할 |
|---|---|
| PC (크롬/엣지, Windows 10+·macOS) | 메인 콘솔: 상품 등록, 판정 현황, 채팅, 정산. B1 직접 연결 가능 |
| 안드로이드 폰 (크롬) | 문자찜 입력, 포장 모드, **프린트 스테이션**(B1 블루투스 연결) |
| 아이폰 (사파리) | 문자찜 입력, 포장 모드, 조회. B1 직접 출력 불가 → 라벨 이미지 공유로 대체 |

모든 기기는 같은 판매 데이터를 실시간으로 본다(한 기기에서 바꾸면 1초 안에 다른 기기에 반영). 실시간 푸시는 서버 전송 이벤트(SSE)로 한다(D-075).

## 5. 기능 요구사항

### 5.1 상품 (PRD)

**PRD-01 빠른 입력 등록** · P1 · 1단계
한 줄 입력으로 번호·품종·가격을 등록한다.
- AC1 `15 핑크프릴 10000`, `15 핑크프릴 1만`, `15번 핑크프릴 만원`, `15/핑크프릴/10`(가격 단위=천원) → 모두 15번·핑크프릴·10,000원.
- AC2 품종이 여러 단어여도 된다: `31 방울복랑 금 15000` → 품종 "방울복랑 금".
- AC3 가격이 빠지면 등록하지 않고 가격 입력칸으로 커서를 옮긴다. 품종은 비워도 등록할 수 있다("품종 미입력" 표시).
- AC4 같은 방송에 이미 있는 번호면 "15번이 이미 있어요. 고칠까요?"를 묻는다. 예면 바뀐 품종·가격만 고치고, 판매 종료된 상품이면 고친 뒤 다시 공개한다(D-084).
- AC5 한글 금액 파싱 규칙은 `tests/golden/parser/amount.yaml`, 빠른 입력은 `quick-input.yaml`을 따른다. 규칙 문장은 DOMAIN_RULES R-14(금액)·R-16(빠른 입력) (D-029, D-030).

**PRD-02 상품 수정·이력** · P1 · 1단계
품종·가격·번호·재고·상태를 고칠 수 있고, 가격 변경 이력이 남는다 (R-10).
- AC1 가격을 바꾸면 이전 가격·변경 시각·변경자가 이력에 남는다.
- AC2 이미 1등이 있는 상품의 가격을 바꾸면 "확정된 찜에도 새 가격을 적용할까요?"를 묻는다. 기본은 적용 안 함(찜 시점 가격 유지).
- AC3 번호를 바꾸면 R-10의 번호 변경 규칙을 따른다.
- AC4 수정의 세부(한 번에 적용, 입금 전 찜, 재고 늘림, 재출력 필요, 번호 변경)는 DOMAIN_RULES R-10 (D-055, D-056).

**PRD-03 번호 검색·과거 상품** · P1 · 1단계
방송이 진행돼도 과거에 등록한 상품은 계속 유효하다.
- AC1 15번 등록 후 50번까지 진행한 상태에서 "15" 찜이 오면 15번 상품으로 판정한다(요청서 3-3).
- AC2 15번이 이미 판매됐으면 확정되지 않고 대기 또는 품절 처리된다.
- AC3 콘솔에서 번호를 입력하면 상품·1등·대기자·가격을 즉시 보여준다. 빠른 입력칸에서 번호를 치는 동안 보이고, 번호만 치고 Enter면 그 상품을 자세히 연다(D-084).

**PRD-04 상품 상태** · P1 · 1단계
`READY`(공개 전) · `OPEN`(판매 중) · `SOLD`(재고 소진) · `HOLD`(일시 중지) · `CLOSED`(판매 종료). 빠른 입력으로 등록하면 바로 `OPEN`. 방송 전 미리 등록한 목록은 `READY`로 두고 소개할 때 공개한다 (R-2).

**PRD-05 방송 전 상품 목록 가져오기** · P2 · 2단계
엑셀/CSV(번호, 품종, 가격)를 붙여넣거나 올려서 `READY` 상품으로 일괄 등록한다.

**PRD-06 음성 자동 등록** · P2 · 4단계 → 5.8 VOC 참고. 음성 카드로 등록한 상품은 빠른 입력으로 등록한 것과 같은 상품 등록이다(같은 기록·같은 5초 되돌리기·같은 "고칠까요?", D-I4-03).

### 5.2 주문·선착순 판정 (ORD)

**ORD-01 채팅 주문 인식** · P1 · 1단계(시뮬레이터) / 3단계(실채팅)
채팅 메시지에서 주문(찜)과 취소 요청을 인식한다. 기본은 엄격 모드(R-3).
- AC1 `tests/golden/parser/chat.yaml`의 모든 사례를 통과한다. 골든에 없는 경우는 DOMAIN_RULES R-3 세부 규칙(D-028)을 따른다.
- AC2 숫자가 들어 있어도 주문이 아닌 메시지("15번 너무 예뻐요", "3개 남았나요?")는 주문으로 처리하지 않되, 콘솔 채팅창에 번호를 강조해 방송자가 한 번 클릭으로 주문으로 바꿀 수 있다(ORD-12).
- AC3 방송자 본인 채널의 메시지는 주문으로 처리하지 않는다(설정 가능).

**ORD-02 중복 수신 방지** · P1 · 1단계
같은 채팅 메시지(같은 메시지 ID)가 여러 번 들어와도 찜은 한 번만 생긴다 (INV-3).
- AC1 같은 메시지 ID를 3번 넣어도 찜 수·판정 결과가 같다.
- AC2 같은 사람이 같은 상품을 여러 번 쓰면 첫 번째만 유효하다 (INV-2).

**ORD-03 상품별 선착순 판정** · P1 · 1단계
상품마다 독립적으로, 판정 순위(R-6)가 가장 앞선 유효 찜을 1등으로 확정한다.
- AC1 15번에 A→B→C 순으로 찜하면 A 확정, B·C 대기.
- AC2 15번과 28번의 판정은 서로 영향을 주지 않는다.
- AC3 1등 확정과 동시에 최초 유효 주문의 접수 시각(시스템 시각, 유튜브 게시 시각)을 기록한다.

**ORD-04 대기·품절** · P1 · 1단계
1등 이후의 찜은 대기 인원 한도까지 대기, 넘으면 품절 처리한다 (R-4).
- AC1 대기 한도 2에서 A·B·C·D가 찜하면 A 확정, B·C 대기, D 품절.
- AC2 대기 한도 0이면 1등 외 모두 품절.

**ORD-05 중복 판매 방지** · P1 · 1단계
한 상품의 확정 찜 수는 재고를 넘지 않는다 (INV-1). 여러 기기·여러 입력 경로가 동시에 들어와도 지켜져야 한다.

**ORD-06 공개 전 찜 처리** · P1 · 1단계
방송자가 번호를 말하자마자 시청자가 찜을 쓰면, 상품 등록보다 찜이 먼저 도착할 수 있다. 이런 찜은 버리지 않고 보류했다가 상품이 공개되는 순간 순서대로 판정한다 (R-5).
- AC1 15번 등록 10초 전에 온 "15" 찜은 등록 시 판정에 포함된다(기본 유효 시간 30초).
- AC2 유효 시간보다 오래된 보류 찜은 "만료"로 처리하고 콘솔에 보여준다.

**ORD-07 취소와 승계** · P1 · 1단계
방송자가 찜을 취소할 수 있고, 1등이 취소되면 승계 설정(자동/묻기/재오픈)에 따른다 (R-8).
- AC1 승계=자동: A 취소 → B 확정, B에게 라벨·감사 메시지 발생.
- AC2 승계=재오픈: A 취소 → 대기자 정리, 상품은 다시 판매 중.
- AC3 승계=묻기: A 취소 → 상품에 "승계 결정 필요" 표시, 방송자가 고를 때까지 새 찜은 대기로만 들어간다. 대기 한도가 0이면 물을 대기가 없으므로 자동 승계와 같다(DOMAIN_RULES R-8, D-077).
- AC4 시청자 채팅 취소("15 취소")는 기본적으로 방송자 승인 요청으로 표시된다. 시청자 채팅 취소는 그 채널 자신의 찜에만 걸린다 — 합친 다른 구매자의 찜은 채팅으로 취소·요청되지 않는다(DOMAIN_RULES R-8, D-063).

**ORD-08 문자찜 입력** · P1 · 1단계
문자로 받은 찜을 번호만으로 빠르게 입력한다. 휴대폰에서도 가능해야 한다.
- AC1 입력 항목: 상품 번호(필수), 실제 수신 시각(기본=지금, 시:분 또는 시:분:초), 보낸 사람 메모/전화번호(선택).
- AC2 구매자 표시는 기본 "문자찜", 메모가 있으면 "문자찜(메모)".
- AC3 유튜브 찜과 같은 상품·같은 판정 체계로 처리된다.
- AC4 전화번호는 암호화해 저장하고(원문을 보관할 때) 화면엔 뒤 4자리만 보인다. 판정 엔진의 이벤트·상태에는 전화번호 원문이 들어가지 않고, 서버가 만든 불투명 키와 뒤 4자리만 들어간다(DAT-06, DOMAIN_RULES R-1·R-11, D-061).
- AC5 구매자 정하기(지정 구매자 → 휴대폰 번호 → 새 문자 구매자), 표시 이름, 같은 입력 재전송은 DOMAIN_RULES R-11 (D-051). 보류 찜 유효 시간은 수신 시각이 아니라 입력(도착) 시각으로 잰다(R-5).
- AC6 입력 화면 (S06, D-089): 방송은 끝나지 않은 실제 방송 중 가장 최근 것이 기본이고 없으면 직접 고른다. 번호를 치는 동안 그 상품을 보인다. 수신 시각을 비우면 서버가 입력(도착) 시각을 초까지 적는다(실제 시각순에서 입력보다 앞서지 않는다). `8:01`처럼 오전·오후 없이 적은 1~12시는 지금과 가까운 쪽으로 읽고, 읽은 수신 시각이 지금보다 늦으면 확인을 묻는다. 휴대폰 번호로 읽히지 않는 전화번호는 보내지 않는다. 문자찜은 5초 대기 없이 바로 보내고(잘못 넣으면 찜 취소로 바로잡는다), 보낸 뒤 보낸 사람 칸은 비운다 — 같은 사람의 다른 번호는 "같은 사람 하나 더".
- AC7 결과의 구매자 (S06b, D-099): 쓰기 응답에 엔진이 정한 구매자(`buyer` — 지정 구매자·전화번호로 이은 구매자·새 문자 구매자, 정하지 못했으면 없음)를 담는다. 화면은 찜이 생기지 않은 결과("이미 찜한 구매자라…")와 "같은 사람 하나 더"를 이 값으로 정하고, 뒤 4자리로 구매자를 짐작하지 않는다. 받은 시각은 날짜와 함께 보인다(`10/18 20:01:05`).

**ORD-09 채널 경합 규칙** · P1 · 1단계
유튜브 찜과 문자찜이 같은 상품을 두고 겨룰 때의 우선 규칙을 설정한다 (R-6, R-7).
- 정책 `ARRIVAL`(기본, 시스템 접수순) / `RECEIVED_TIME`(실제 시각순) + 같은 분 동률 처리(유튜브 우선 / 문자 우선 / 방송자 결정).
- AC1 `ARRIVAL`: 문자 수신이 더 빨랐어도 늦게 입력됐으면 대기로 들어간다. 이미 확정된 1등은 바뀌지 않는다.
- AC2 `RECEIVED_TIME`: 더 빠른 문자찜이 늦게 입력되면, 1등이 아직 '잠금' 전이면 자동 역전, 잠금 후면 "충돌 — 방송자 결정"으로 표시한다.
- AC3 정렬 키·동률·대기 자리·잠금(입금 기록, 직접 배정) 세부는 DOMAIN_RULES R-4·R-6·R-7 (D-052, D-053).

**ORD-10 충돌 처리** · P1 · 1단계
자동으로 정할 수 없는 경우(잠금 후 역전, 동률-방송자 결정, 메시지 소급 변환) 상품에 충돌 표시를 하고 콘솔 상단 알림으로 띄운다. 방송자는 "그대로 유지" / "바꾸기" 중 하나를 고른다. 충돌은 상품마다 하나이고, 충돌이 있는 동안 그 상품의 직접 배정·교체는 받지 않는다. 1등 자리가 비어 충돌이 저절로 풀릴 때 대기가 꽉 차 있어도 대기자가 이유 없이 품절되지 않는다. 세부는 DOMAIN_RULES R-7 4·7 (D-053, D-054, D-062, D-064, D-068).

**ORD-11 재고 2개 이상** · P2 · 1단계(엔진) / 2단계(화면)
같은 번호로 여러 개를 파는 경우 앞선 N명을 확정한다. 엔진은 처음부터 재고 값을 지원한다(기본 1).

**ORD-12 방송자 수동 조치** · P1 · 1단계
직접 배정, 1등 변경, 찜 무효 처리, 대기자 수동 승계, 채팅 메시지를 찜으로 변환, 구매자 차단. 모든 조치는 사유와 함께 이력에 남는다.
- 찜으로 변환할 수 있는 것은 주문도 취소도 아니었던 메시지다(언급 강조된 메시지 등). 주문이었던 메시지와 취소 메시지("15 취소")는 어느 번호로도 변환하지 않고, 번호를 잘못 쓴 주문은 직접 배정으로 바로잡는다(DOMAIN_RULES R-7 4, D-062, D-076).
- 충돌 중인 상품에는 직접 배정·1등 교체를 받지 않는다. 방송자는 충돌부터 정한다(DOMAIN_RULES R-9, D-064).
- AC1 장난 찜을 무효 처리하면 다음 순번이 승계 규칙에 따라 처리된다.
- AC2 차단된 구매자의 이후 찜은 자동으로 거절된다. 다음 날짜의 방송에서도 같다 — 서버가 새 날짜를 시작할 때 차단한 유튜브 채널을 이어 쓴다(DOMAIN_RULES R-9, D-069). 리허설에서 한 차단은 이어지지 않는다(D-081).
- 콘솔 (S05): 채팅 패널에서 주문도 취소도 아니었던 메시지에만 "찜으로 바꾸기"를 보인다(D-076·D-086). 방송자 조치는 누른 뒤 5초 뒤에 보내고 그동안 되돌릴 수 있다(UX-06, D-083).
- 상품별 조치 기록은 그 상품 기준이다 — 번호를 바꿔도 같은 상품의 기록이고, 바꾼 뒤 같은 번호에 새로 등록한 상품의 기록에는 옛 상품의 조치가 없다(D-095).

### 5.3 구매자 (BUY)

**BUY-01 유튜브 구매자 식별** · P1 · 1단계
유튜브 채널 고유 ID로 구매자를 식별한다. 닉네임이 바뀌어도 같은 사람으로 이어지고, 닉네임 이력이 남는다.
- AC1 같은 채널 ID가 1부엔 "홍길동", 2부엔 "길동이"로 와도 한 구매자로 합산된다.
- AC2 닉네임이 같고 채널 ID가 다른 두 사람은 별개 구매자이며, 화면에 "같은 닉네임 2명" 표시와 구분자(채널 프로필·ID 끝자리)를 보여준다.
- 이름 표기 (S06b, D-098): 모든 화면이 한 규칙으로 구매자 이름을 적는다. 그날 같은 표시 이름의 구매자가 둘 이상이면 이름 뒤에 " · "와 구분 글자 하나 — 유튜브 "끝 1234", 뒤 4자리가 있는 문자 구매자 "뒤 4자리 5678", 전화번호 없는 문자 구매자 "문자 20:01:05"(처음 받은 문자의 받은 시각). 그래도 겹치면 생긴 순서로 " · 2"부터 붙인다. 괄호를 더하지 않는다.

**BUY-02 문자 구매자** · P1 · 1단계
전화번호가 있으면 전화번호로 같은 사람을 이어 준다. 없으면 입력할 때 기존 구매자를 고르거나 새 문자 구매자로 만든다.
- 잇는 기준은 서버가 정규화한 휴대폰 번호로 만든 불투명 키다(형식이 달라도 같은 번호면 같은 사람, 번호 일부만 같으면 다른 사람). 같은 문자찜 입력을 다시 보내도 찜이 둘 생기지 않는다(DOMAIN_RULES R-11, D-051, D-061, D-067).

**BUY-03 구매자 연결·분리** · P1 · 1단계
두 구매자 기록을 하나로 합치거나(예: 문자찜 = 유튜브 시청자 X) 잘못 합친 것을 되돌릴 수 있다. 합치면 모든 찜·합계가 이동하고 이력이 남는다. 세부(중복 찜, 합치지 않는 경우, 감사 문구 이름)는 DOMAIN_RULES R-11 (D-057).
- 화면 (S06, D-091): 합치기는 같은 날짜 안에서만 된다. 둘 중 하나만 유튜브 구매자면 유튜브 쪽 이름이 남는 것이 기본이다. 보내기 전에 옮길 찜·합계와 "중복"으로 정리될 찜(떼어 내도 돌아오지 않음)을 보이고, 두 사람 모두 1등인 상품이 있으면 막고 "먼저 한 사람의 찜을 취소해 주세요"를 알린다. 합치기·떼어 내기는 확인 뒤 바로 보낸다(방송자 조치의 5초 대기 없음).
- 미리 보기 (S06b, D-100): 옮길 찜·합친 뒤 합계·중복으로 정리될 찜·막는 이유는 서버가 그 범위의 지금 상태로 코어 `previewMerge`(DOMAIN_RULES R-11 "미리 보기")를 불러 계산한 값이다. 화면은 이 규칙을 다시 구현하지 않고, 미리 본 뒤 상태가 바뀌면 새 미리 보기를 받기 전엔 보내지 않는다. 막힌 합치기에서 상품 자세히로 갔다 오면 같은 상대·방향의 합치기 창으로 돌아온다.

**BUY-04 구매자별 찜 목록·합계** · P1 · 1단계
구매자마다 확정된 찜을 자동으로 묶어 상품 수·합계를 보여준다. 취소·무효·거절된 찜은 합계에서 빠진다 (INV-5, INV-9).
- AC1 요청서 3-7 예시(15번 10,000 + 28번 5,000 + 31번 15,000) → 3개, 30,000원.
- 화면 (S06, D-090): 날짜 하나의 구매자 목록. 기본은 확정 찜이 있는 사람이고, 찾기는 그날 기록된 모든 구매자(표시 이름·닉네임·메모·전화번호 뒤 4자리·채널 ID 끝 4자리)에서 한다. 같은 닉네임은 채널 ID 끝 4자리로 구분한다(BUY-01 AC2).

**BUY-05 과거 구매 내역** · P2 · 2단계
구매자의 이전 방송 구매·결제·배송 이력을 조회한다.

### 5.4 라벨·인쇄 (LBL)

**LBL-01 상품 라벨** · P1 · 2단계
번호·품종·가격·구매자 표시(닉네임 또는 "문자찜")를 담은 라벨. 기본 템플릿은 판매자 샘플 라벨을 따른다:
```
        -가게이름-
번호: 194   가격: 8 천원        26.10.08
품종:   왕비뇌신금
닉네임: 우주천사
```
- AC1 가게 이름·날짜 표시·가격 표기(`8 천원` / `8,000원`)를 설정할 수 있다.
- 세부 (P1, D-P1-03·04): 찍는 글·가격 표기 경계·날짜(방송 날짜)·구매자(문자찜은 언제나 "문자찜")·글 다듬기는 LABEL_RULES L-2·L-3.
- 세부 (I1, D-I1-04): 엔진 상태에서 라벨 데이터를 만드는 법(번호·품종은 출력 기기가 받을 때의 지금 값, 가격은 찜의 가격 스냅샷, 구매자 이름은 그 라벨의 첫 작업 때 정해 고정)은 LABEL_RULES L-9.

**LBL-02 포장 라벨** · P1 · 2단계
구매자 한 명의 정산 묶음: 구매자 표시, 상품 수, 상품 번호 목록, 합계, 방송 날짜. 번호가 많으면 여러 장(`1/2`, `2/2`)으로 나눈다.
- 세부 (P1, D-P1-05): 합계는 "상품 합계"(코어 정산 결과 그대로), 방송마다 따로 쪽, 쪽마다 정해진 개수 — LABEL_RULES L-4.
- 화면 (I1, D-I1-10): 정산 자세히에서 그 묶음의 포장 라벨을 미리 보고 출력·PNG·PDF로 낸다. 요청할 때의 묶음으로 쪽마다 한 장씩 대기열에 들어가고, 묶음이 바뀌면 "재출력 필요"가 보인다 — LABEL_RULES L-11 12. 포장 모드 안의 흐름은 I2.

**LBL-03 미리보기** · P1 · 2단계
인쇄 전 실제 크기 비율로 미리 본다. 미리보기 이미지 = 인쇄 이미지 (같은 렌더러).
- 세부 (P1, D-P1-07): 미리보기·PNG·PDF·프린터가 모두 같은 1비트 그림 — LABEL_RULES L-0 1.

**LBL-04 템플릿 조정** · P1 · 2단계
라벨 크기(기본 50×30mm, B1 지원 규격 목록), 항목 켜기/끄기, 글자 크기, 위치를 조정한다. 긴 품종명은 자동으로 글자를 줄이고, 최소 크기보다 작아지면 두 줄로 나눈다.
- 세부 (P1, D-P1-02·06): 크기 목록(50×30·50×20·50×40)과 점 계산은 LABEL_RULES L-1, 템플릿·글 맞추기(숫자 항목은 자르지 않는다)는 L-5.
- 화면 (I1, D-I1-05): 판매자마다 상품·포장 템플릿 한 벌씩 서버에 저장하고, 크기·가게 이름·가격 표기·항목 켜기/끄기·글자 크기·위치를 고치며 같은 렌더러로 미리 본다. 저장 전에 최악값(번호 9999·`99,999,999원` 등)이 들어가는지 그려 보고 안 들어가면 저장하지 않는다 — LABEL_RULES L-11 13.

**LBL-05 한글 보장** · P1 · 2단계
프린터 글꼴에 의존하지 않는다. 한글 글꼴을 내장해 이미지로 렌더링한 뒤 출력한다 → 깨짐 없음.
- 세부 (P1, D-P1-04): 내장 글꼴로만 그리고(시스템 글꼴 대체 없음), 없는 글자는 빈 네모 — LABEL_RULES L-2.

**LBL-06 B1 직접 출력** · P1 · 2단계
PC 크롬 또는 안드로이드 크롬에서 B1에 블루투스(또는 USB)로 직접 연결해 출력한다. 기술 근거는 TECH_REVIEW.md §1.
- AC1 연결 마법사: 프린터 찾기 → 연결 → 테스트 인쇄.
- AC2 연결이 끊기면 대기열을 멈추고 "프린터 연결이 끊겼어요. 다시 연결" 버튼을 보여준다. 출력 못 한 라벨은 사라지지 않는다.
- 세부 (P1, D-P1-08·09): 어댑터·B1 프로필·마지막 줄 대응·오류 문장·테스트 라벨은 LABEL_RULES L-7, 대기열 멈춤·이어서는 L-8.
- 화면 (I1, D-I1-03·06): 연결 마법사 = 연결 방법 고르기(이 브라우저에 있는 것만, 블루투스 먼저) → 프린터 고르기 → 테스트 인쇄 → "네 변 테두리와 한글이 모두 보이나요?" 확인 → "이 기기에서 출력". 바로 연결할 수 없는 브라우저(아이폰 등)는 L-7 `UNSUPPORTED` 문장과 그림 파일 경로(LBL-07)를 보인다. 끊기면 대기열이 멈추고 출력 기기에 "다시 연결"이 보인다 — 출력 못 한 라벨은 대기 맨 앞에 남는다(LABEL_RULES L-11 8·10).

**LBL-07 대체 출력** · P1 · 2단계
직접 출력이 안 되는 환경(아이폰 등)을 위해: 라벨 PNG 저장/공유(→ NIIMBOT 공식 앱에서 인쇄), 라벨 크기 PDF, A4 모아찍기 PDF.
- 세부 (P1, D-P1-07): LABEL_RULES L-6.
- 화면 (I1, D-I1-07): 상품 자세히에서 그 라벨의 PNG 저장·공유·라벨 크기 PDF, 라벨 화면에서 한 방송의 1등 라벨 모두·대기 중인 라벨을 A4 모아찍기 PDF로. 파일로 내보낸 것은 출력함으로 치지 않는다(엔진 보고 없음). 파일 이름에는 날짜·번호·쪽만 — LABEL_RULES L-11 16.

**LBL-08 연속 출력·대기열** · P1 · 2단계
여러 라벨을 순서대로 출력한다. 출력 작업은 서버에 기록되어 어느 기기에서 출력했는지, 성공/실패가 남는다.
- 세부 (P1, D-P1-09): 대기열 순수 로직은 LABEL_RULES L-8.
- 세부 (I1, D-I1-01): 대기열은 판매자 단위로 서버가 기록한다(작업·시도마다 결과·출력한 기기·시각·멈춤). 모든 기기가 같은 대기열을 보고, 출력은 출력 기기 하나가 한다 — LABEL_RULES L-11.

**LBL-09 자동 출력** · P1 · 2단계
1등 확정 시 상품 라벨을 자동 출력한다(설정, 프린터 연결 시 기본 켜짐). 승계로 1등이 바뀌면 새 라벨을 자동 출력하고 이전 라벨은 "폐기" 표시한다.
- 세부 (P1, D-P1-09·10): 폐기 표시는 LABEL_RULES L-8 4, 효과 → 라벨 데이터·작업 ID·라벨 키는 L-9.
- 세부 (I1, D-I1-02): 자동 출력 작업은 효과와 같은 기록에서 생기고, 출력 기기가 연결돼 있으면 판매자가 누르지 않아도 출력된다. 라벨 키의 찜이 그 확정버전의 1등이 아니게 되면 그 라벨은 폐기되고, 이미 출력한 것은 "버릴 라벨"로 판매자가 확인할 때까지 알린다. 출력함은 서버가 엔진에 출력 보고(`effect.labelPrinted`)로 기록한다(잠금, R-7 3) — LABEL_RULES L-11 2·5·7, 골든 G-ENG-301~304. 자동 출력 켜기/끄기는 판매 규칙 설정이고 다음에 시작하는 방송부터 적용된다(D-070, D-I1-05).

**LBL-10 프린트 스테이션** · P2 · 2단계
B1이 연결된 기기(예: 안드로이드 폰)를 "프린트 스테이션"으로 지정하면, 다른 기기(PC)에서 생긴 출력 작업을 그 기기가 받아서 출력한다.
- 세부 (I1, D-I1-01·03): 프린트 스테이션 = 출력 기기. 판매자마다 하나이고, 바꿀 때는 확인한다. 새로 정할 때 쌓인 대기 라벨이 있으면 "출력 시작"을 누를 때까지 멈춰 있다 — LABEL_RULES L-11 10.

**LBL-11 재출력·이력** · P1 · 2단계
이미 출력한 라벨을 다시 출력한다. 출력 횟수·시각이 남는다. 상품 정보가 바뀐 뒤엔 "재출력 필요"를 표시한다.
- 세부 (P1, D-P1-09·10): 재출력·이력은 LABEL_RULES L-8 5·7, 재출력 필요(내용 키)는 L-10.
- 세부 (I1, D-I1-04): 재출력은 그 찜이 지금도 그 확정버전의 1등일 때만, 데이터는 출력 기기가 받을 때의 지금 값(구매자 이름만 처음 것). 화면의 "재출력 필요"는 서버가 L-10으로 정한다. 단축키 Alt+P(⌥P) = 현재 상품의 1등 라벨 다시 출력 확인 창 — LABEL_RULES L-9·L-10·L-11 9·11.

**LBL-12 다른 프린터 확장** · P3
프린터 드라이버를 어댑터로 분리해 다른 라벨프린터(B21, D110 등)를 추가할 수 있는 구조.
- 세부 (P1, D-P1-08): 모델 프로필 구조, 지금 켠 프로필은 B1 하나 — LABEL_RULES L-7.
- 세부 (N1, D-N1-02·03): Marklife 9종(P50·S2·X2 — YXQ, P11·P12·P15·L13·LP90·LP15 — L11 테이프)과 바우아토 스티코팝(실험적) 프로필·작업 바이트·이름으로 고르기·보내기·끝 알림은 LABEL_RULES L-12, 프로필마다의 크기(50×15·50×50·테이프 세 가지)와 작은 템플릿은 L-1·L-4·L-5. 화면 연결은 통합 스프린트.

### 5.5 정산·명세서 (STL)

**STL-01 회차 통합 합산** · P1 · 2단계
같은 구매자의 여러 방송(1부·2부·3부) 구매를 정산 묶음으로 합친다. 방송별 상세도 따로 본다 (R-12).
- AC1 요청서 3-8 예시: 1부 20,000 + 2부 15,000 + 3부 10,000 → 45,000원.

**STL-02 배송비** · P1 · 2단계
기본 배송비, 무료배송 기준 금액, 구매자별 예외(직접 수령, 합배송, 도서산간 추가). 정산 묶음당 한 번 붙는다.
- 화면 (S06, D-092): 예외는 "기본 배송비로"·"직접 수령"·"합배송"·"배송비 직접 정함(금액)" 중 고르고, 바뀔 배송비와 최종 금액을 미리 보인다. 도서산간 추가는 금액 지정이나 조정(추가)으로 적는다.

**STL-03 금액 계산** · P1 · 2단계
상품 합계 + 배송비 + 조정(할인/추가, 사유 필수) = 최종 결제 금액. 모든 금액은 정수(원) (INV-6). 배송비 예외 지우기, 최종 금액 0 하한 등 세부는 DOMAIN_RULES R-12 (D-058). 직접 묶기(`MANUAL`)는 아직 지원하지 않는다 (D-059).
- 화면 (S06, D-092): 조정은 "할인"/"추가"를 고르고 금액과 사유를 적는다. 돈을 적는 칸은 늘 원 단위다(천원 단위 설정을 쓰지 않는다).

**STL-04 명세서 PDF** · P1 · 2단계
구매자 표시명, 상품 번호, 품종, 상품별 가격, 상품 합계, 배송비, 최종 결제 금액, 주문 날짜·방송 회차, 입금 계좌 안내(설정). 한 명씩 또는 전원 일괄로 PDF 저장/인쇄. 휴대폰에서 이미지로 공유할 수 있다.
- 금액 (P2, D-206): 문서 패키지(`packages/documents`)는 코어 정산 결과(R-12)를 그대로 적고 다시 계산하지 않는다 — 상품별 가격은 찜 시점 가격 스냅샷(확정 뒤 상품 가격을 바꿔도 그 줄은 그대로, R-10), 상품 합계·배송비·조정·최종 결제 금액·받은 금액·환불 필요는 코어 묶음 값. 표시용으로 "남은 금액 = 최종 − 받은 금액"(부분 입금일 때) 하나만 뺀다. 줄 가격의 합이 코어 상품 합계와 다르면 문서를 만들지 않는다(틀린 숫자를 내보내지 않게).
- 담는 것 (P2, D-206): 제목·가게 이름(설정)·구매자 표시 이름(문자 구매자는 휴대폰 끝자리 4개만 — 전화번호 전체·채널 ID는 넣지 않는다)·주문 날짜(방송 날짜)·방송 회차·상품 줄(회차·번호·품종·가격, 방송 순서 → 번호 순)·상품 수·상품 합계·배송비(예외면 그 이름, 예외 없이 0원이면 "무료 배송")·할인 또는 추가(조정 합계 한 줄 — 사유는 적지 않는다)·최종 결제 금액·입금 상태(받은 금액·남은 금액·입금 완료·환불할 금액)·입금 계좌 안내(설정이 없으면 그 칸 없음)·만든 시각(KST)·하단 고지(STL-05)·쪽 번호. 품목이 없는 묶음은 확인서를 만들지 않는다. 리허설 범위의 확인서는 제목에 "(리허설)"과 "실제 거래가 아니에요" 줄이 붙는다.
- 일괄·이미지 (P2, D-207): 전원 일괄 = 그 날짜 범위에서 품목이 있는 묶음 전부를 PDF 하나로, 구매자마다 새 쪽, 표시 이름 글자 순. 휴대폰 공유 이미지 = 한 사람 확인서를 폭 1080px PNG 한 장(같은 내용·같은 글꼴). 한글 글꼴(OFL)을 문서 안에 넣고, 글꼴로 그릴 수 없는 글자(이모지 등)와 제어 글자는 빼고 그린다(문서 전체가 실패하지 않게). 화면·서버 연결(어느 화면에서 누르나, 파일 이름, 공유 방법)은 I2·I4.

**STL-05 확인서와 법정 증빙 구분** · P1 · 2단계
명세서 제목은 "구매 내역 확인서"로 하고, 하단에 "본 문서는 거래 확인용이며 세금계산서·현금영수증 등 세법상 적격증빙이 아닙니다"를 표시한다. 현금영수증 발행 여부·승인번호는 별도 기록 칸으로 관리한다(발행 자체는 홈택스 등 외부에서).
- 세부 (P2, D-206): 고지 문장은 PDF의 **모든 쪽** 하단, 이미지는 맨 아래에 글자 그대로 넣는다. 현금영수증 기록 칸은 그 기록을 남기는 이벤트·화면을 정하는 스프린트에서 넣는다(P2 범위 밖).

**STL-06 엑셀 판매대장** · P1 · 2단계
열: 방송 날짜, 회차, 상품 번호, 품종, 가격, 구매자, 채널, 찜 시각, 상태, 입금, 배송. 기간·방송 선택해서 내보낸다.
- 세부 (P2, D-208): 시트 "판매대장" 하나, 첫 줄은 위 열 이름(이 순서). 행 = 고른 방송의 상품마다 확정 찜 하나에 한 행(재고 2 이상이면 확정 순서대로 여러 행), 확정이 없는 상품은 한 행(구매자·채널·찜 시각·입금 칸 비움). 취소·대기·거절 찜은 행이 없다. 순서: 방송 날짜 → 그날 방송 선언 순서 → 상품 번호 → 확정 순서. 값: 방송 날짜 `YYYY-MM-DD`(글), 회차 = 방송 제목, 상품 번호(수), 품종 = 지금 이름, 가격(수, 원) = 확정 행은 찜 시점 가격 스냅샷·확정 없는 행은 지금 가격, 구매자 = 지금의 구매자 표시 이름(문자 구매자에 뒤 4자리가 있으면 ` / 끝자리 1234`), 채널 = 유튜브(채팅·메시지 변환)·문자·직접 배정, 찜 시각 = DOMAIN_RULES R-6 "찜마다의 순위 재료"의 실제 시각을 KST로(분까지만 적은 문자찜은 `YYYY-MM-DD HH:MM`, 나머지는 초까지), 상태 = 확정 행은 "1등", 확정 없는 행은 상품 상태 말(D-088), 입금 = 그 구매자의 그 날짜 정산 묶음 입금 상태(미입금·부분 입금·입금 완료·과입금), 배송 = 포장·배송 상태(S09 전까지 빈칸). 금액·상태는 코어 결과 그대로다. 리허설 범위는 넣지 않는다(넘기면 오류). 글 값은 글 칸으로만 쓴다(`=`로 시작하는 닉네임도 수식이 되지 않는다).

**STL-07 입금 관리** · P1 · 2단계
정산 묶음별 미입금 / 부분 입금 / 입금 완료 / 과입금(환불 필요). 입금액·날짜·메모.
- 화면 (S06, D-092): 입금 금액의 기본값은 남은 금액이고, 다른 금액이면 한 번 더 묻는다. 입금 날짜는 기록한 시각이다(실제 입금일이 다르면 메모에 적는다). 잘못 적은 입금은 같은 금액의 환불 기록으로 바로잡는다. 정산 기록은 확인 뒤 바로 보낸다.
- 입력 창 (S06b, D-101): 입금 금액 칸은 1원~100,000,000원(화면의 오타 막기 — 엔진은 1 이상 정수). 입력 창마다 누구의 어느 날 묶음인지와, 보내면 바뀔 입금 상태("입금 완료 → 과입금(환불 필요 4,000원)")를 보인다. 날짜 고르기는 연도·요일까지 보인다.

**STL-08 포장·배송 상태** · P1 · 2단계
포장 대기 → 포장 완료 → 배송 완료(송장번호 선택). **포장 모드**: 구매자별로 담아야 할 상품 번호를 크게 보여주고 하나씩 체크, 다 담으면 포장 라벨 출력 + 포장 완료.

**STL-09 취소·환불 이력** · P1 · 2단계
입금 후 취소되면 환불 필요 금액을 계산하고 환불 기록(금액·날짜·사유)을 남긴다.
- 화면 (S06, D-092): 환불 기록은 받은 금액 이하만 적을 수 있고 사유가 필요하다. 날짜는 기록한 시각이다.

**STL-10 다시 보기·재출력** · P1 · 2단계
지난 방송의 판매 내역·명세서·라벨을 언제든 다시 조회·출력한다.

### 5.6 유튜브 연동 (YT)

**YT-01 계정 연결** · P1 · 3단계
구글 로그인으로 판매자의 유튜브 채널을 연결한다. 어떤 권한을 왜 요청하는지 한글로 안내한다.
- 세부 (Y1, D-Y02): 연결 때는 읽기 권한(`youtube.readonly`)만 받고, 감사 메시지 게시에 동의할 때 게시 권한(`youtube.force-ssl`)을 더 받는다. 판매자마다 채널 하나, 같은 채널은 한 판매자에만. 다시 연결할 때 다른 채널을 고르면 받지 않는다. 토큰은 암호화해 저장하고 응답·로그에 내보내지 않는다. 토큰이 더는 쓸 수 없으면 "다시 연결 필요"로 수집·게시를 멈춘다(판매 기록은 그대로). 연결 끊기는 토큰 폐기·삭제와 게시 동의 삭제다. 게시 권한이나 동의가 있던 연결을 다시 연결할 때는 읽기·게시 권한을 함께 요청하고, 게시 권한을 받지 못하면 동의를 끈다(D-Y1-01). 이미 켜진 동의를 다시 켜도 동의 시각은 그대로다(D-Y1-05).
- 화면 (I3, D-I3-02): 설정의 유튜브 칸(`/settings/youtube`)이 연결 전에 받을 권한과 이유를 우리 말로 보인다("연결만으로는 내 채널에 글을 쓰지 않아요."). 구글 화면으로는 최상위 이동하고, 시작한 곳(설정·시작 마법사)으로 돌아와 결과를 한 번 보인다. 연결 끊기는 확인 창을 거친다.

**YT-02 방송 선택** · P1 · 3단계
내 채널의 진행 중/예정 라이브 목록에서 고르거나 방송 주소를 붙여 넣어 방송 회차에 연결한다.
- 세부 (Y1, D-Y03): 연결한 채널의 진행 중·예정이고 채팅이 있는 방송만, 끝나지 않은 실제 방송 회차에만(리허설에는 잇지 않는다) 잇는다. 유튜브 방송 하나는 끝나지 않은 회차 하나에만(동시에 이어도, D-Y1-08), 회차 하나에는 유튜브 방송 하나만 이어진다.
- 화면 (I3, D-I3-04): 실제 방송 콘솔의 유튜브 칸에서 내 라이브 목록으로 고르거나 주소를 붙여 넣어 잇는다. 리허설·끝난 방송에는 잇는 버튼이 없다.

**YT-03 채팅 자동 수집** · P1 · 3단계
연결된 방송의 실시간 채팅을 수집해 ORD-01 규칙으로 주문을 만든다. 끊기면 자동 재연결하고, 이어받기 지점부터 다시 받는다(누락·중복 없음).
- 세부 (Y1, D-Y04·D-Y05·D-Y10): 수집기는 리허설 생성기와 같은 수집 경로로 그 회차의 범위에 채팅 이벤트를 기록한다(도착 시각으로 판정 — 접수순). 이어받기 지점은 기록을 마친 뒤에만 저장한다. 회차를 잇기 전에 게시된 채팅과 회차를 끝낸 뒤 게시된 채팅은 받지 않고, 끝낸 뒤 10분(또는 유튜브 채팅이 끝날 때)에 멈춘다. 발송함이 게시한 감사 메시지는 채팅으로 기록하지 않는다. 시청자 이름은 기록하기 전에 정리한다(제어·보이지 않는 글자·줄바꿈·`@` 제거, 점은 `·`, 30자, 비면 "시청자"). 시청자가 지운 메시지·유튜브에서 차단된 시청자는 알림만 남기고 판정은 바꾸지 않는다. 유튜브 호출은 2초보다 자주 하지 않고 스트림은 5초보다 자주 다시 열지 않으며, 시작 전(예정) 방송은 30초마다 상태만 확인하다 시작한 뒤의 채팅부터 받는다(D-Y1-04).
- 화면 (I3, D-I3-04·D-I3-07): 콘솔이 수집 상태를 보이고, 수집이 멈추면(`STOPPED`, 10초 넘게 이어진 `RETRYING`) 콘솔 고정 영역에 경고 한 줄과 할 일 버튼을 보인다. 지운 메시지·유튜브 차단 알림은 콘솔 유튜브 칸에 보인다(판정은 그대로).

**YT-04 감사 메시지 — 실시간 채팅** · P1 · 3단계
1등 확정 시 라이브 채팅에 감사 메시지를 남긴다. 기본 문구: `{번호}번 {품종} {가격} {구매자}님 구매 감사합니다`. 문자찜은 구매자 자리에 "문자찜".
- AC1 문자찜의 메모·전화번호는 어떤 경우에도 공개 메시지에 넣지 않는다(항상 "문자찜").
- AC2 판매자가 자동 게시에 명시적으로 동의(설정 화면 체크)하기 전에는 게시하지 않는다(유튜브 개발자 정책).
- 세부 (Y1, D-Y06·D-Y12): 동의는 대상(실시간 채팅·영상 댓글)마다 따로이고 판매 규칙 `thanks.*`와 별개다 — 둘 다 있어야 자동 게시한다. 동의하기 전에 나온 감사는 나중에 동의해도 자동으로 보내지 않는다(수동 재전송은 된다). 자동 게시는 감사가 나온 뒤 실시간 채팅 10분, 영상 댓글 24시간 안에만 한다. 리허설 방송의 감사는 어떤 경우에도 게시하지 않는다(YT-09 AC3).
- 화면 (I3, D-I3-03): 설정의 감사 메시지 칸이 "만들기"(판매 규칙 `thanks.*`, 다음 방송부터)와 "자동 게시 동의"(대상마다, 바로)를 나눠 보이고, 대상마다 지금 설정의 결과를 한 줄로 말한다. 동의는 설명 창("동의한 뒤에 확정된 판매부터 남기고, 그 전 판매는 남기지 않아요.")에서 "동의해요"로 받는다.
- 여러 플랫폼 회차 (N2b-2, D-N2b-2-09): 감사는 그 찜의 구매자 자신의 플랫폼으로만 간다 — 인스타그램 구매자는 아래 DM, 틱톡 구매자는 보내지 않음, 유튜브 구매자·문자찜은 그 회차에 유튜브가 이어진 적이 있을 때 유튜브 채팅(유튜브·인스타·틱톡 어느 것도 이은 적이 없는 회차는 지금처럼 유튜브 발송함).
- 인스타그램 (N2, D-N2-09·D-N2-10): 인스타그램 회차의 실시간 감사는 공개 글이 아니라 **그 찜을 만든 댓글에 대한 개인 답장(DM) 한 번**이다. 같은 댓글의 감사는 한 DM으로 모으고, 그 댓글로 이미 DM을 보냈으면 뒤 감사는 보내지 않고 알린다. 찜을 만든 댓글이 없는 찜(문자찜·직접 배정)은 DM이 없다. DM 자동 발송도 판매자의 동의(유튜브와 따로, 기본 꺼짐) 전에는 보내지 않는다. 문구는 같다(AC1 그대로).

**YT-05 감사 메시지 — 영상 댓글** · P2 · 3단계
방송 영상의 일반 댓글로 남기는 기능. 실시간 채팅과 별도로 켜고 끈다. 판매마다 / 방송 종료 후 요약 1건 중 선택.
- 세부 (Y1, D-Y08): 요약은 회차를 끝내고 10분 뒤 그 회차의 확정 판매로 한 번 만든다(첫 줄 "구매 감사합니다", 판매마다 `{번호}번 {품종} {가격} {구매자}님`, 문자찜은 "문자찜"). 판매가 없으면 보내지 않는다.

**YT-06 게시 실패·중복 방지** · P1 · 3단계
감사 메시지는 판매 기록과 분리된 발송함(outbox)으로 처리한다. 실패해도 판매 기록은 그대로이고, 재시도·수동 재전송이 가능하며, 같은 메시지는 두 번 게시되지 않는다 (R-13).
- 세부 (Y1, D-Y01·D-Y06): 실패·재시도·건너뜀은 발송함 상태로만 남고(엔진 이벤트 없음), 게시 성공만 효과마다 게시 보고(`effect.thanksSent`)로 기록해 그 확정을 잠근다. 다시 시도는 2초부터 두 배씩 최대 5번, 응답이 없으면 먼저 우리 채널이 같은 글을 올렸는지 확인한다(다른 감사가 이미 가진 메시지는 제외, D-Y1-03). 끝내 확인하지 못하면 다시 게시하지 않고 "확인 필요"로 남겨 판매자가 고른다(이중 게시보다 누락, D-Y1-06). 게시 직전에 확정이 풀렸으면 보내지 않는다. 그 방송을 이은 채널과 지금 연결한 채널이 다르면 보내지 않는다(D-Y1-02).
- 화면 (I3, D-I3-05): 콘솔 알림 띠 "감사 실패"(판매자가 할 일이 있는 실패만 — 동의하지 않음·방송을 잇지 않음은 세지 않는다)와 그날의 감사 메시지 목록에서 보내지 못한 감사를 바로 다시 보낸다. 확인하지 못한 감사(`UNCONFIRMED`)는 "이미 올라갔을 수 있어요" 경고와 확인 창을 거치고, 유튜브에서 본 판매자는 "유튜브에 올라가 있어요"로 게시됨(게시 보고·잠금)으로 적는다. 그 밖의 실패는 "알림에서 빼기"로 알림 띠에서만 뺀다.
- 세부 (I3, D-I3-17): 게시·조회에 쓰는 토큰은 그 방송을 이은 채널의 연결에서만 꺼낸다(확인과 게시 사이에 채널이 바뀌어도 다른 채널로 나가지 않는다). "못 찾음"은 그 시도 뒤의 글을 모두 본 조회일 때만이고(다음 쪽을 따라감, 5쪽까지), 한 시도의 조회는 이른 조회 1번 + 끝 조회 3번까지, 10초 간격이다.
- 인스타그램 DM (N2, D-N2-10): 같은 규칙(효과 ID 멱등, 2·4·8·16·32초 최대 5번 다시 시도, 타임아웃 뒤 대화 조회로 확인하고 확인하지 못하면 다시 보내지 않음, 기한 10분, 수동 재전송, 효과마다 게시 보고)이고, 라이브가 끝나면 보낼 수 없다.

**YT-07 묶음 감사** · P2 · 3단계
N초 안에 확정된 여러 판매를 한 메시지로 묶어 게시한다(채팅 도배·API 사용량 절감). 채팅 글자 수 제한을 넘으면 나눈다.
- 세부 (Y1, D-Y07): `15번 핑크프릴 10,000원 홍길동님, 16번 라울 5,000원 김철수님 구매 감사합니다`처럼 끝말을 한 번만 쓴다. 메시지 하나는 200자까지, 넘으면 판매 경계에서 나눈다.

**YT-08 사용량 표시** · P1 · 3단계
오늘 사용한 유튜브 API 할당량과 남은 양을 보여주고, 부족해지면 감사 메시지를 묶음 모드로 자동 전환한다.
- 세부 (Y1, D-Y09): 호출마다 구글의 비용 표대로 세고(실패한 호출도), 하루는 태평양 시간 자정에 바뀐다. 남은 양이 예산의 20% 미만이면 묶음, 5% 미만이면 감사 게시를 멈추고 남은 양을 채팅 수집에 둔다. 모드가 바뀌면 이유와 상관없이(다른 판매자의 사용·자정·서버 다시 시작 포함) 판매자에게 알린다(D-Y1-07).
- 화면 (I3, D-I3-06): 설정에 오늘 쓴 양·남은 양·한국 시간으로 다시 채워지는 때·모드를, 콘솔에 묶음·멈춤 안내를 보인다.

**YT-09 리허설(시뮬레이터) 모드** · P1 · 1단계
가짜 채팅을 만들어 실제 방송 없이 판매 흐름을 연습·테스트한다. 개발·테스트·사용자 교육에 모두 쓴다.
- AC1 리허설 방송은 실제 방송과 기록이 섞이지 않는다: 엔진 범위가 따로이고(DOMAIN_RULES R-0 6), 정산·차단 이어받기·그날 첫 방송의 정산 설정에 들어가지 않는다. 화면은 리허설 방송을 늘 "리허설"로 구분한다(D-081).
- AC2 가짜 채팅은 서버의 생성기가 수집기 경로로만 넣는다(실제 유튜브 수집기와 같은 기록·판정). 판매자는 생성기를 시작·멈추고, 가짜 시청자 이름으로 한 줄을 보낼 수 있다. 실제 방송에는 가짜 채팅이 들어가지 않는다(D-082).
- AC3 리허설의 라벨·감사 메시지 효과는 기록만 하고 실행하지 않는다 — 유튜브에 게시하지 않는다(D-081).

### 5.7 데이터 (DAT)

**DAT-01 영구 저장** · P1 · 1단계 — 종료·재실행·새로고침 후에도 모든 기록 유지.
- 서버는 판매자마다, 방송 날짜마다 엔진 범위 하나(이벤트 로그)를 두고, 재시작하면 저장한 상태(스냅샷)와 그 뒤의 이벤트를 재생해 같은 상태로 돌아온다(DOMAIN_RULES R-0 6, D-069, D-072). PostgreSQL에 저장하고, 시험은 PGlite로 도커 없이 돈다.
**DAT-02 입력 우선 기록** · P1 · 1단계 — 모든 입력(채팅·문자찜·조작)은 처리 전에 먼저 이벤트로 저장한다. 판정 결과는 이벤트를 다시 재생해 똑같이 만들 수 있어야 한다 (INV-4).
- 저장이 끝나기 전에는 그 입력의 결과가 어디에도(응답·실시간 푸시·발송함) 나가지 않는다. 형식이 틀렸거나 아직 지원하지 않는 입력은 기록하지 않고 오류로 돌려준다. 기록한 입력을 엔진이 처리하지 못하면 그 입력에 실패 표시를 남기고 상태는 그 전 그대로 둔 채 경보하고 다음 입력을 처리한다 — 재생도 같은 입력을 건너뛴다. 같은 외부 ID(채팅 메시지 ID, 요청 번호)는 두 번 기록하지 않는다(D-072). 재생 무결성 검사 명령으로 로그 재생 결과와 저장한 상태·발송함이 같은지 언제든 확인한다.
**DAT-03 정기 백업** · P1 · 2단계 — 매일 자동 백업, 30일 보관.
- 운영 백업 (I3, D-I3-14): 운영자가 서버 명령 `backup`을 매일 04:00(KST) 돌려 데이터베이스 전체를 30일 보관한다(반쯤 쓴 파일 없음, 실패하면 지우지 않음). 판매자 단위 복구·내보내기·가져오기는 DAT-04(I2).
**DAT-04 복구** · P1 · 2단계 — 백업 시점으로 되돌리기, 판매자 단위 전체 내보내기(엑셀+JSON)·가져오기.
**DAT-05 변경 이력** · P1 · 1단계 — 가격·번호·1등 변경·취소·무효·구매자 합치기는 누가/언제/왜를 남긴다. 누가 = 그 입력을 보낸 로그인 계정(서버가 이벤트 기록에 적는다, 채팅은 그 채널), 언제 = 서버 도착 시각(UTC), 왜 = 이벤트의 사유(D-072).
**DAT-06 개인정보 보호** · P1 · 1단계 — 전화번호·주소·유튜브 토큰은 암호화 저장, 로그에 남기지 않는다.
- 문자찜 전화번호: 서버는 받은 번호를 코어 `normalizePhone`으로 정규화하고, 휴대폰 번호 모양이면 판매자마다 고정한 비밀 키의 HMAC으로 만든 불투명 키 `phoneKey`와 뒤 4자리 `phoneLast4`만 이벤트에 담는다. 이벤트 로그·엔진 상태에는 전화번호 원문·정규화한 번호가 남지 않는다. 원문 번호가 필요하면(연락·배송) 이벤트 로그 밖에 암호화해 저장한다(DOMAIN_RULES R-1, D-061).
- 문자찜 `ref`는 서버가 만든 무작위·일련 ID이고 전화번호·이름·메모를 담지 않는다(문자 구매자 ID·효과에 들어간다).
- S04 서버는 문자찜 전화번호 원문을 저장하지 않는다(키·뒤 4자리만 — 연락처 보관이 필요해지면 그때 암호화 저장을 정한다). 판매자별 비밀 키는 판매자를 만들 때 무작위로 만들어 서버 마스터 키로 암호화해 저장하고, 화면·로그·응답에 내보내지 않는다. 서버 로그에는 요청 본문·전화번호·키·메모·닉네임·채팅 본문·비밀번호·세션 값을 남기지 않는다(D-073).
- 유튜브 토큰(Y1, D-Y02)은 서버 마스터 키로 암호화해 저장하고 응답·로그·이벤트 기록에 남기지 않는다. 유튜브에서 받은 채팅 본문·닉네임은 이벤트 기록과 따로 두고, 방송 날짜 + 30일에 판매자 장부(확정 판매·구매자 표시 이름·정산)만 남기고 지운다 — 그 뒤 그날 기록은 고칠 수 없다(D-Y11, D-012 법률 검토는 사용자 몫). 화면은 봉인 날짜를 늘 보이고 7일 전부터 경고하며, 봉인 뒤 쓰기 버튼을 잠근다(I3, D-I3-07).
- 판매자가 손으로 적는 글 칸(문자찜 메모, 입금 메모, 사유, 방송 제목, 상품 이름)과 ID 칸(구매자·메시지 ID)의 휴대폰 번호는 서버가 기록 전에 거른다. 무엇을 휴대폰 번호로 보는지는 DOMAIN_RULES R-1 "판매자가 적는 칸의 휴대폰 번호" 하나뿐이고(`010`을 뺀 8자리·국가 번호 표기는 번호로 보지 않는다), 이미 기록된 로그를 재생할 때는 다시 검사하지 않는다(D-079·D-080).

### 5.8 음성 등록 (VOC) — 4단계

**VOC-01 음성 수집** · P2 — 브라우저에서 마이크를 켜고 방송자 말을 실시간 인식한다.
- 세부 (P2, D-205): 음성 패키지(`packages/voice`)의 `SpeechEngine` 어댑터 하나로 쓴다 — 크롬 Web Speech(기본, `ko-KR`, 연속·중간 결과), Deepgram·리턴제로(골격 — 서버 중계로만 연결하고 키는 브라우저에 두지 않는다). 중간 결과는 자막으로만 쓰고 추출은 최종 결과만 한다. 인식이 저절로 멈추면 다시 시작하되, 최종 결과 없이 1분 안에 5번 넘게 멈추면 멈추고 알린다. 권한 거부·마이크 없음·지원하지 않는 브라우저는 다시 시작하지 않고 쉬운 문장으로 알린다. 음성이 인식을 위해 외부(구글 등)로 보내진다는 안내는 켤 때 화면이 보인다(I4).
- 화면 (I4, D-I4-04·D-I4-07·D-I4-09): 콘솔의 "음성 켜기"로만 켠다 — 콘솔을 열 때마다 꺼진 상태로 시작하고(새로 고침해도 저절로 켜지지 않는다), 그 기기에서 처음 켤 때는 외부 전송·마이크 권한 안내 창을 거친다. 켜져 있는 동안 "음성은 인식을 위해 구글로 보내져요." 한 줄과 상태(듣는 중·다시 시작 중·멈춤)가 늘 보이고, 중간 결과는 자막 한 줄, 최종 결과는 최근 기록으로 보인다. 인식 문장은 그 브라우저 탭의 메모리에만 있고 서버로 보내거나 저장하지 않는다. 화면은 Web Speech만 쓴다 — 클라우드 음성(Deepgram·리턴제로)의 서버 중계·키 보관은 서버 작업과 외부 계정이 필요해 뒤로 미룬다(D-I4-07).
**VOC-02 추출** · P2 — 문장에서 번호·품종·가격을 뽑는다. 한글 숫자("십오 번", "만오천 원") 처리 (`parser/amount.yaml` 공용).
- 규칙은 DOMAIN_RULES R-17, 사례는 `tests/golden/parser/voice-extract.yaml` (D-202). 애매하면 그 칸을 비운다. 번호는 `N번`만(고유어 `한 번`·`이번`은 아니다), 가격은 원 단위로 읽고 숫자만 있는 말은 가격이 아니다. 번호 바로 앞 토큰과 이으면 다른 번호가 되는 말(끊어 말한 번호 — `1 5번`·`십 오번`·`이 십 번`·`백 오번`)은 번호·가격을 모두 비운다(R-17 3·4, D-I4-01).
**VOC-03 품종 사전** · P2 — 판매자가 판 적 있는 품종 + 기본 다육 품종 사전으로 비슷한 이름을 바로잡는다("핑크 프릴" → "핑크프릴").
- 세부 (D-203): 사전 = 판매 이력 이름(최근 것 먼저) 다음 기본 사전, 공백만 다른 이름은 앞의 것. 자모 유사도 0.8 이상만 바로잡고, 사전에 없는 말은 품종 칸에 넣지 않는다(R-17 5).
- 판매 이력 (I4, D-I4-06): 지금 콘솔 범위의 상품 이름(상품이 바뀌면 다음 문장부터 반영) 다음, 지금 범위를 뺀 실제(리허설 아님) 범위 중 날짜가 가장 늦은 10개의 상품 이름(늦은 날짜 먼저), 정리 뒤 2,000개까지. 지난 날짜는 음성을 켤 때 한 번 받아 오고, 못 받으면 지금 범위 + 기본 사전으로 계속한다.
**VOC-04 제안 카드** · P2 — 인식 결과는 바로 등록하지 않고 "15번 핑크프릴 10,000원 — 등록할까요?" 카드로 보여준다. Enter/탭 한 번으로 확정, 바로 고치기 가능. 신뢰도가 높으면 N초 후 자동 확정(설정).
- 세부 (P2 데이터 모델, D-204): 카드는 번호가 있거나 품종·가격이 둘 다 있을 때만 만든다. 확정은 번호·가격이 있어야 하고(품종은 비어도 "품종 미입력"), 이미 있는 번호면 등록하지 않고 "고칠까요?"(PRD-01 AC4)로 보낸다. 자동 확정은 설정(기본 **꺼짐**, 기다림 기본 5초·3~30초)이 켜져 있고 신뢰도 `HIGH`이고 방송자가 카드를 건드리지 않았고 그 번호가 아직 없을 때만, 카드를 만든 뒤 기다림이 지나면 한다. 열린 카드는 3장까지(넘으면 건드리지 않은 가장 오래된 카드를 닫는다). 새 카드와 손댄 카드는 닫지 않으므로 손댄 카드가 3장 이상 열려 있으면 열린 카드가 3장을 넘을 수 있다(최대 = 손댄 열린 카드 수 + 1, D-I4-02).
- 화면 (I4, D-I4-03·D-I4-05): 카드는 빠른 입력칸 가까이에 새 것이 맨 앞으로 보인다. 확정 = 카드의 "등록"을 누르기, 또는 빠른 입력칸이 비어 있을 때 Enter(맨 앞 열린 카드 — 그 카드가 맨 앞이 된 지 1초가 지나 "Enter 등록" 표시가 보일 때만). 빠른 입력칸에 글자가 있으면 Enter는 늘 빠른 입력이다. PC에선 카드가 빠른 입력칸과 함께 늘 보이고(고정 영역), 휴대폰(폭 768px 미만)에선 Enter로 카드를 확정하지 않는다(누르기만). 번호·가격이 없으면 그 카드의 고치기 칸을 열고, 이미 있는 번호면 빠른 입력과 같은 "고칠까요?"로 보낸다. 고치기 칸의 해석은 빠른 입력 고치기 칸과 같다(그 방송의 `price.unit`). 자동 확정 설정은 그 기기에 저장하고(기본 꺼짐·5초), 기다리는 동안 카드에 남은 초와 "자동 등록 멈추기"가 보이며, 창이 열려 있는 동안·음성을 끈 뒤에는 자동 확정하지 않는다.
**VOC-05 끄기** · P1 — 음성 기능 없이도 모든 기능이 동작한다.
- 세부 (D-205): 음성은 기본 꺼짐. 엔진을 만들기만 해서는 마이크 권한을 묻지 않고(시작할 때만), 음성 패키지 밖의 판매 기능은 음성 패키지 없이 돈다.
- 화면 (I4, D-I4-04·D-I4-09): 콘솔은 "음성 켜기"를 누르기 전에는 음성 코드를 불러오지 않고 인식 객체·마이크를 만들지 않는다. 음성을 끄면 인식을 멈추고 열린 카드의 자동 확정을 멈춘다(카드는 남아 손으로 등록·닫기). 콘솔을 떠나면 인식을 멈춘다. 음성을 한 번도 켜지 않은 콘솔·화면은 음성 없을 때와 똑같이 동작한다.

### 5.9 사용 환경 (UX)

**UX-01 쉬운 한국어** · P1 — 개발 용어·영어 금지(예: "CONFIRMED" 대신 "1등 확정"). 기본 글자 16px 이상, 상태를 색만으로 구분하지 않는다. 상태값의 화면 낱말은 D-088.
- 색의 뜻 (S06b, D-102): 성공(원하던 대로 됨)·주의(확인이 필요함)·위험(실패·막힘)·보통(정보) 넷만 쓰고, 결과·안내의 색은 그 뜻과 맞는다(찜이 생기지 않은 결과는 주의, 저장 완료는 성공). 화면마다 주 버튼(채운 색)은 많아야 하나이고 지금 할 일이다.
**UX-02 시작 마법사** · P1 · 2~3단계 — 가게 이름 → 판매 규칙 확인 → 프린터 연결·테스트 인쇄 → 유튜브 연결 → 리허설 해보기.
- 세부 (I3, D-I3-09·D-I3-10): 주소 `/start`, 다섯 단계마다 "나중에 할게요". 판매자 계정이 방송 목록에 왔을 때, 마치거나 닫은 적이 없고 실제 방송이 하나도 없을 때만 자동으로 열린다(서버에 판매자마다 기록 — 다른 기기에서도 다시 뜨지 않는다). 설정에서 언제든 다시 연다. 가게 이름은 1~30자. 프린터 단계의 연결·테스트 인쇄는 라벨·프린터 화면(I1)이 채우고, 그 전에는 설명과 "다음"만 둔다. 자동 게시 동의는 마법사에서 묻지 않는다.
- 세부 (I1, D-I1-06): "프린터 연결·테스트 인쇄" 단계는 I1의 연결 마법사(LBL-06 화면)를 그대로 쓰고, 건너뛸 수 있다(프린터 없이 그림 파일로도 운영한다). 마법사 전체 흐름은 I3.
**UX-03 알기 쉬운 오류** · P1 — 무엇이 잘못됐고 무엇을 하면 되는지 한 문장씩. 기술 상세는 접어서.
**UX-04 휴대폰 화면** · P1 — 문자찜 입력·포장 모드·조회는 375px 폭에서 편하게. 기준(D-094): 375×812에서 가로 스크롤 없음, 글자 16px 이상, 누르는 곳 44px 이상, 번호·금액 칸은 숫자 키패드, 마우스를 올려야만 보이는 조작 없음. 콘솔의 고정 영역은 화면 높이의 35% 이하.
- 목록 모양 (S06b, D-101·D-102): 화면 폭 48rem(768px) 이상이면 구매자·정산 목록은 열 머리가 있는 표, 그보다 좁으면 카드. 휴대폰의 조치 기록은 표 대신 기록마다 한 묶음이고 낱말이 중간에서 끊기지 않는다.
**UX-05 키보드 우선 콘솔** · P1 — 방송 중 빠른 입력칸이 항상 활성. 단축키로 취소(되돌리기)·재출력·충돌 처리. 창을 닫거나 조치를 마치면 포커스는 빠른 입력칸으로 돌아간다. 단축키: Esc 창 닫기, Ctrl+Z(⌘Z) 되돌리기(빠른 입력칸이 비었거나 글 칸 밖일 때), Alt+1(⌥1) 첫 알림 열기, 알림 창 선택은 숫자 키 — 알림 창의 처음 포커스는 아무것도 바꾸지 않는 "닫기"(D-087). 재출력 단축키 Alt+P(⌥P) — 현재 상품의 1등 라벨을 다시 출력할지 묻는 창(처음 포커스 "닫기", 숫자 키 1 = 다시 출력, I1, D-I1-04). Alt+1의 알림 순서에 "출력 멈춤"·"버릴 라벨"이 더해진다(D-I1-08).
**UX-06 되돌리기** · P1 — 등록·취소·배정 직후 5초간 "되돌리기" 제공.
- 상품 등록은 바로 기록하고, 5초 안에 되돌리면 그 상품을 판매 종료한다. 그 상품에 찜이 들어왔으면 되돌릴 수 없다고 알리고 고치기로 안내한다(D-083).
- 방송자 조치(취소·무효·배정·교체·승계·충돌 결정·취소 요청 처리·메시지 변환·차단 등)는 누른 뒤 5초 기다렸다가 보낸다. 그동안 되돌리면 보내지 않고, 보내기 전엔 접수됨으로 보이지 않는다(NFR-03, D-083).
- 떠나기 확인 (S06b, D-103): 떠날지 묻는 동안 멈춘 조치는 "닫기"(머무르기) 뒤에 다시 5초 전체를 기다린다. 홈 화면 앱으로 연 첫 화면에서도 뒤로 가기가 떠날지 묻는다. 앱을 닫거나(아이폰에서 위로 밀기 등 웹이 막을 수 없는 경우 포함) 떠나면 보내기 전인 조치는 보내지 않는다.

**UX-07 설치 없음** · P1 — 크롬으로 주소만 열면 시작. 홈 화면/바탕화면에 앱처럼 추가(PWA).
- 세부 (S06, D-093): 서비스 워커는 앱 껍데기(화면 파일)만 저장하고 `/api/`(판매 데이터·실시간·쓰기)는 가로채지 않는다 — 오프라인에 판매 데이터를 두거나 쓰기를 쌓아 두지 않는다. 새 버전은 다음에 열 때(또는 판매자가 "지금 새로고침"을 누를 때) 바뀐다.

### 5.10 서비스 구조 (SYS)

**SYS-01 판매자 계정** · P1 · 1단계 — 로그인한 판매자만 자기 데이터에 접근한다. 아이디·비밀번호로 로그인하고 세션 쿠키로 유지한다. 계정은 운영자가 서버 명령으로 만든다(가입 화면 없음). 방송 중에 로그인이 풀리지 않게 세션은 쓰는 동안 연장된다(D-074).
- 로그인 속도 제한 (I3, D-I3-12): 같은 IP에서 10분에 20번을 넘거나, 서버마다 비밀번호 확인이 동시에 4개(기다림 32개·10초)를 넘으면 비밀번호를 확인하지 않고 429로 돌려준다. IP는 연결 주소이고 앞단 프록시는 설정한 수만큼만 믿는다. 보조자 계정은 판매자가 만든다(SYS-04).
**SYS-02 다중 판매자** · P2 — 모든 데이터는 판매자 단위로 분리(테넌트 격리). 처음엔 판매자 1명으로 운영해도 구조는 다중 판매자. 다른 판매자의 방송·이벤트·조회·실시간 푸시는 있는지조차 알 수 없다(D-069, D-074).
**SYS-03 요금제 대비** · P3 — 기능 제한·사용량(방송 수, 라벨 수)을 요금제별로 켜고 끌 수 있는 구조.
**SYS-04 보조자 계정** · P2 — 판매자가 보조자를 초대(문자찜 입력·포장만 가능 같은 권한).
- 세부 (I3, D-I3-11): 판매자가 설정에서 보조자를 5명까지 만든다 — 서버가 만든 아이디·비밀번호를 한 번만 보인다(가입 화면·초대 링크 없음). 보조자는 문자찜 입력(실제 방송의 문자찜, 문자찜으로 생긴 찜의 취소)과 그에 필요한 읽기만 할 수 있고, 나머지는 서버가 403으로 막는다. 지우면 그 세션이 바로 끝난다. 보조자가 한 기록의 "누가"는 그 보조자 계정이다(DAT-05). 포장 권한은 포장 모드와 함께(I2).
**SYS-05 배포·운영** · P1 · 3단계 (I3, D-I3-13~D-I3-16) — 컨테이너 이미지 하나로 서버가 화면을 같은 출처로 함께 내고(보안 머리글·CSP), 앱 주소가 https가 아니면(내 컴퓨터 시험 제외) 시작하지 않는다. 환경변수·처음 배포·새 버전·마이그레이션·계정 만들기·구글 OAuth 설정·백업·복구·모니터링 절차는 `docs/DEPLOY.md`에 있다. 운영 백업은 DAT-03. 준비 확인(`/health/ready`)·운영 상태(`/ops/status`, 운영 토큰, 판매자 정보 없이 합친 숫자만)·경보 기록(`level: alert`)으로 서버를 지켜본다. 개인정보처리방침·이용약관 초안 페이지(`/privacy`·`/terms`)는 로그인 없이 열린다(법률 문장은 사용자 검토, D-012). 호스팅 업체·도메인은 사용자가 고른다(D-001).

**PLT-03 세부 — 플랫폼 공통 연결** (N2, D-N2-02·D-N2-05·D-N2-08·D-N2-12·D-N2-15)
- 플랫폼은 `YOUTUBE`·`INSTAGRAM`·`TIKTOK`. 실제(리허설 아님) 회차 하나에는 플랫폼마다 라이브 하나씩 이어질 수 있다 — 유튜브·인스타그램·틱톡을 함께 이으면 모든 댓글이 그 회차의 한 상품 보드로 모인다(동시 송출, N2b-2, D-N2b-2-01). 같은 플랫폼 둘은 잇지 않는다. 한 라이브는 끝나지 않은 회차 하나에만 이어진다. 잇기는 엔진 이벤트가 아니다 — 누가·언제 이었는지는 서버가 기록한다(DAT-05).
- 채팅 구매자 키·메시지 ID: 유튜브는 원래 값(채널 ID·메시지 ID), 인스타그램은 `ig:<IGSID>`·`ig:<댓글 ID>`, 틱톡은 `tt:<숫자 사용자 ID>`·`tt:<댓글 ID>`(D-N2b-2-03). 같은 사람이 여러 플랫폼에서 주문하면 플랫폼마다 다른 구매자로 잡히고, 판매자가 "구매자 합치기"로 잇는다(저절로 잇지 않는다). 플랫폼은 키 접두어로 안다(`sms:`는 문자 구매자). 엔진은 바뀌지 않는다(DOMAIN_RULES R-11).
- 플랫폼마다 할 수 있는 것(서버가 조회로 알려 화면이 미리 안내한다): 실제 시각순(`RECEIVED_TIME`) — 유튜브 가능, 인스타그램·틱톡 불가(이을 때 막는다). 그래서 둘 이상의 플랫폼을 이은 회차는 늘 접수순이고, 플랫폼 사이 선착순은 서버에 도착한 순서다 — 콘솔이 "플랫폼마다 댓글이 도착하는 속도가 조금씩 달라요"를 알린다(D-N2b-2-02). 실시간 감사 — 유튜브 공개 채팅, 인스타그램 댓글마다 DM 한 번, 틱톡 없음(글을 올리지 않는다). 영상 댓글·방송 후 요약 — 유튜브만. 여러 플랫폼 회차의 감사는 그 찜의 구매자가 있는 플랫폼으로만 간다(DOMAIN_RULES R-13 "여러 플랫폼 회차의 감사", D-N2b-2-09).
- 화면·문서는 키 접두어로 플랫폼 이름(유튜브·인스타그램·틱톡)을 적는다 — 채팅 패널·구매자 목록·합치기는 N2b-2(인스타그램·틱톡이 섞인 방송·목록에서). 판매대장 채널 칸(STL-06)의 인스타그램·틱톡 표기는 N4.

**PLT-02 세부 — 틱톡 라이브(베타)** (N2b-1·N2b-2, D-904, D-N2b-1-01~D-N2b-1-09, D-N2b-2-02~D-N2b-2-08·D-N2b-2-11·D-N2b-2-14)
- 연결 모듈(N2b-1): 비공식 웹캐스트 연결기(`tiktok-live-connector@2.1.0` MIT 고정)를 감싼 읽기 전용 연결 — 아이디·주소 해석, 공통 댓글 레코드, 중복 제거, 연결 상태·다시 연결, 글 올리기·판매자 세션 쿠키 없음. 상태 문장과 다시 시도 시간표는 `harness/sprints/N2b-1/acceptance.md` — 방송 전(`NOT_LIVE`)은 1분마다 60분까지 기다리며 확인하고 연속 실패에 세지 않는다(N2b-2, D-N2b-2-11).
- 켜기(N2b-2): 운영자 스위치(`LIVEJJIM_TIKTOK_BETA`)가 켜져 있어야 하고, 판매자가 설정에서 위험 고지(판 `TT-BETA-1`)를 읽고 "켜기"를 눌러야 한다. 서버는 켬·끔을 판매자 계정·시각·고지 판과 함께 쌓아 기록한다. 판매자가 끄면 그 판매자의 틱톡 연결이 바로 멈춘다. 틱톡 아이디는 판매자마다 하나(설정).
- 잇기: 회차를 틱톡에 이으면 바로 연결을 시작한다(방송 전이면 기다리며 확인). 판매자의 틱톡 연결은 모든 회차를 통틀어 하나, 실제 시각순 회차·리허설·끝난 회차에는 잇지 않는다. 끊거나 회차를 끝내면 연결을 멈춘다. 서버가 다시 켜지면 끝나지 않은 회차의 틱톡 연결을 다시 시작하고 "끊긴 동안의 틱톡 댓글은 받지 못했을 수 있어요."를 알린다.
- 댓글: 이어진 동안 받은 댓글만 `chat`으로 기록한다(`tt:` 키, 이름 정리, 방송자 댓글은 엔진이 무시, 게시 시각 없음 — 판정은 서버 도착순). 감사 메시지는 없다.
- 수동 입력(대체): 연결이 막히거나 끊기면 콘솔·문자찜 화면에서 "닉네임: 댓글" 줄을 여러 개 붙여 넣는다. 미리 보기로 줄마다 결과(찜 번호·주문 아님·취소는 넣지 않음·모양 오류)를 보고 "넣기"를 누르면 번호마다 문자찜으로 기록한다 — 판정은 문자찜과 같고, 한 번 넣기 안의 같은 닉네임은 한 구매자, 다른 구매자에게 저절로 잇지 않는다(D-N2b-2-07·D-N2b-2-08). 그 회차에 같은 번호·같은 닉네임의 활성 찜이 이미 있으면(틱톡 연결로 받은 댓글·앞선 붙여넣기·문자찜) 그 번호는 "이미 있어 넣지 않아요"로 보이고 기본으로 넣지 않는다 — 판매자가 줄마다 "그래도 넣기"로 고를 수 있다(D-N2b-2-14). 줄 읽기 골든 `tests/golden/tiktok/paste.json`.
- 실제 틱톡 방송 확인은 HG-N2b, 상용 출시 전 법률 검토는 사용자 몫(DECISIONS "사용자 확인 필요").

**PLT-01 세부 — 인스타그램 라이브** (N2, D-N2-03~D-N2-11·D-N2-14)
- 공식 Instagram Platform API만 쓴다. 판매자 계정 연결(인스타그램 프로페셔널 계정 하나 — 페이스북 로그인 기본, 인스타그램 로그인도 어댑터로), 진행 중 라이브 찾기(`live_media`), `live_comments` 웹훅(앱 시크릿 서명 검증, 같은 댓글 ID는 한 번만), 댓글 → `chat` 이벤트(수집 경로, 조치자 수집기). 이름 = username 그대로, 게시 시각 없음(엔진은 서버 도착 시각).
- 방송이 끝나면 댓글을 다시 가져올 수 없으므로 받는 즉시 기록하고, 기록한 뒤에만 메타에 받았다고 답한다. 라이브를 켜기 전에 회차를 "인스타그램 기다리기"로 정해 두면 첫 댓글이 올 때 그 회차에 저절로 이어진다(기다리는 회차가 하나일 때만). 저절로 이어진 회차는 같은 계정이 새 라이브를 켜면 새 라이브의 (늦지 않은) 첫 댓글에 새 라이브로 옮겨진다 — 인스타 계정은 라이브를 한 번에 하나만 하므로(판매자가 손으로 이은 회차는 옮기지 않고 알린다, D-N2-16). 끝나지 않은 다른 방송이 있거나 그 방송의 마지막 댓글에서 1시간 넘게 지난 새 라이브면 어느 방송의 라이브인지 모호해 옮기지 않고 이유를 알린다 — 자정을 넘겨 다시 켠 라이브는 같은 방송으로 옮긴다(방송 날짜·달력 날짜는 보지 않는다). 옮긴 사실은 그 방송의 연결 정보에 남는다(D-N2-17). 방송을 라이브에 이은·옮긴 지 1분 안에 온 다른 라이브 댓글로는 옮기지 않고 알린다 — 빠르게 두 번 다시 켤 때 늦게 도착한 끝난 라이브의 댓글로 되돌아가지 않게 하고, 진짜 새 라이브면 1분 뒤 그 라이브의 다음 댓글에 옮긴다(D-N2-18). 같은 댓글은 어느 회차든 한 번만 기록한다. 이어지지 않은 라이브의 댓글과 회차를 끝낸 뒤 도착한 댓글은 기록하지 않고 수를 알린다.
- 인스타그램 회차는 접수순(`ARRIVAL`)만 쓴다 — 실제 시각순 회차에는 이을 수 없다.
- 감사는 YT-04·YT-06의 인스타그램 문장. 메타 앱 심사(고급 액세스·비즈니스 인증)는 사용자 몫이고, 그 전까지 가짜 메타 서버로 모든 시험을 돈다. 실제 라이브 확인은 HG-N2.

## 9. 사람 확인 지점 (Human Gates)

자동 테스트로 대신할 수 없어 사용자가 직접 확인해야 하는 지점. 하네스는 여기서 멈추고 사용자에게 요청한다.

- **HG-1** 리허설 사용성 확인 (1단계 끝) — 판매자가 직접 리허설 방송 1회
- **HG-2** 실제 B1 출력 (2단계 중) — 연결·한글·연속 출력·라벨 크기
- **HG-3** 실제 유튜브 테스트 방송 (3단계 중) — 채팅 수집·감사 메시지
- **HG-4** 실제 목소리 음성 등록 (4단계 중)
- **HG-5** 실제 Marklife·바우아토 출력 (N1 뒤) — 모델마다 이름으로 고르기·연결·테스트 라벨(한글·네 변 테두리·라벨 위의 위치·테이프 글 방향)·끝 알림(`AA`)·연속 출력·MTU와 크레딧 알림·큰 라벨(50×50·테이프 15×50) 한 장의 출력 시간(D-N1-12), 바우아토 스티코팝은 통신 방식 자체(L11 계열 추정)를 확인한다. 확인 목록은 `harness/sprints/N1/acceptance.md` "HG-5 확인 목록"
- **HG-N2** 실제 인스타그램 라이브 (N2 뒤, 메타 앱 심사 뒤) — 계정 연결·기다리기·댓글 수집·감사 DM·한 계정 동시 라이브 하나와 새 라이브로 옮기기 (병렬 트랙 번호, D-N2-11·D-N2-16)
- **HG-N2b** 실제 틱톡 라이브·동시 송출 (N2b-2 뒤) — 위험 고지·켜기·방송 전에 잇기·라이브 시작 뒤 댓글 받기·방송자 댓글·끊김과 다시 연결·막힘 때 붙여넣기, 유튜브·인스타·틱톡을 한 방송에 함께 이어 도착 속도 차이. 확인 목록은 `harness/sprints/N2b-2/acceptance.md` "HG-N2b 확인 목록"
