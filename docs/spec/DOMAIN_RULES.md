## R-0. 엔진의 기본 원칙

1. **순수 함수**: `apply(state, event) → { state, effects }`. 엔진은 시계·난수·네트워크·DB를 직접 쓰지 않는다. 시간은 이벤트의 `at`으로만 들어온다.
2. **전순서 이벤트**: 모든 입력은 서버가 붙인 일련번호 `seq`로 한 줄로 세워진다. 같은 이벤트 로그를 재생하면 항상 같은 결과가 나온다 (INV-4).
3. **부수효과는 출력일 뿐**: 라벨 출력·감사 메시지는 엔진이 `effects`로 "해야 할 일"을 내놓고, 실행은 바깥(outbox)이 한다. 실행 결과(출력 완료, 게시 완료)는 다시 이벤트로 들어온다.
4. **금액은 정수 원**. 부동소수점 금지.
5. **방송 단위 판정**: 상품 번호는 방송(회차) 안에서 유일하다. 채팅(유튜브 채팅·인스타그램 댓글)은 그 채팅이 속한 방송의 상품에만 적용된다. 문자찜은 입력할 때 방송을 고른다(기본: 진행 중 방송). 방송은 `broadcast.start`로 선언하고, 판정은 그 방송의 설정 스냅샷으로 한다(아래 "설정 스냅샷", R-1).
6. **엔진 범위** (D-069): 엔진 상태 하나에는 여러 방송이 들어갈 수 있다(날짜가 달라도 된다 — 골든은 그렇게 쓴다). 서버는 판매자마다, 방송 날짜마다 엔진 상태(이벤트 로그) 하나를 두고 그 안의 이벤트를 한 줄로 처리한다 — 정산 묶음(R-12)과 구매자 합치기(R-11)가 같은 날의 방송을 합치므로 한 범위에 들어가야 한다. `seq`·찜 ID·구매자 ID(`sms:<ref>`)·효과 ID는 그 범위 안에서만 유일하다.
   - **리허설** (D-081): 리허설 방송(YT-09)은 실제 방송과 다른 범위에 둔다 — 범위 = (판매자, 방송 날짜, 리허설인지). 리허설인지는 방송을 만들 때 정하고 바꾸지 않는다. 같은 날 리허설 방송끼리는 한 범위다. 엔진 안의 판정·정산 규칙은 실제 범위와 똑같고, 범위가 달라 정산 묶음·그날 첫 방송(정산 설정)·구매자 합치기·차단이 실제 범위와 섞이지 않는다.

**설정 스냅샷** (D-070 — 이전 문장 "방송 중 바꾸면 그 시점 이후 이벤트에만 적용되고, 변경 자체가 이벤트로 남는다"는 그 이벤트가 R-1에 없어 지킬 수 없었다)
- 설정은 방송을 시작할 때(`broadcast.start`, R-1) 그 방송에 스냅샷으로 저장한다. 엔진을 시작할 때 선언한 방송은 시작 설정이 스냅샷이다.
- 판정(주문 인식·대기 한도·공개 전 찜·승계·시청자 취소·경합·확정 효과)은 그 메시지·찜·상품이 속한 방송의 스냅샷으로 한다.
- 정산 설정(`shipping.baseFee`·`shipping.freeThreshold`·`settlement.groupBy`)은 그 날짜의 **첫 방송**(선언 순서)의 스냅샷으로 한다. 정산 묶음은 같은 날의 여러 방송을 합치므로(R-12) 하나로 정해야 하고, 뒤 방송을 시작했다고 이미 안내하거나 입금받은 묶음 금액이 바뀌면 안 된다.
- 방송 중에 설정을 바꾸는 이벤트는 아직 없다. 바꾼 설정은 그다음에 시작하는 방송부터 적용된다(정산 설정은 그날 첫 방송이 이미 있으면 다음 날짜부터). 방송 중 바꾸기가 필요해지면 그때 R-1에 이벤트를 더한다.
- **라벨 기능 켜기/끄기**(SPEC RCP-01)는 판매 규칙 설정이 아니다 (N4a, D-N4a-01). 이 표·설정 스냅샷·엔진 입력에 없고 엔진은 모른다 — 꺼져 있어도 엔진은 `print.autoOnConfirm`대로 `PRINT_PRODUCT_LABEL`을 내고(판정·감사 문구도 그대로), 서버가 그 효과를 출력 작업으로 만들지 않을 뿐이다. 켬/끔은 바꾼 때부터 적용된다(LABEL_RULES L-13).

**설정값 범위** (D-071): 표의 선택지 밖이거나 아래 범위 밖이면 입력 오류다(R-1). 코어가 이 검사를 하는 순수 함수를 내보내고, 서버는 설정을 저장할 때도 같은 함수를 쓴다.

| 키 | 범위 |
|---|---|
| `claim.maxNumber` | 정수 1~9999 (번호는 숫자 1~4자리, R-3) |
| `claim.maxQuantity` | 정수 1~99 (O1부터). `claim.parseMode=OPTIONS`이면 `contention.policy`는 `ARRIVAL`이어야 한다 — 함께 `RECEIVED_TIME`이면 입력 오류(R-19, D-O-02) |
| `claim.preOpenWindowSec` | 정수 0~300 |
| `waitlist.max` | 정수 0~100 |
| `shipping.baseFee` | 정수 0~1,000,000 (원) |
| `shipping.freeThreshold` | `null`(없음) 또는 정수 0~100,000,000 (원) |
| `thanks.batchWindowSec` | 정수 0~600 |

- 예/아니오 키(`claim.ignoreOwner`·`print.autoOnConfirm`·`thanks.liveChat`)는 `true`·`false`만 받는다. 표에 없는 키는 입력 오류다.
- `settlement.groupBy=MANUAL`은 형식은 맞지만 아직 지원하지 않는다 — 엔진은 미구현을 알린다(D-059).

**옵션 방송의 이벤트** (O0 초안 — O1이 R-1·골든 README 표에 넣는다, R-19·R-20, D-O-02): `product.register`·`product.update`에 `aliases`(상품 별칭)·`options`(옵션 항목)·`stocks`(변형 재고), `sms`·`host.assign`에 `options`(항목 → 선택지 이름)·`qty`(수량), 새 이벤트 `product.focus`(번호 — 지금 상품, R-20 6)·`host.resolveReview`(출처, 번호, 옵션, 수량, 사유 선택)·`host.dismissReview`(출처, 사유 선택). 모두 옵션 방송에서만 받고 다른 방송이면 입력 오류다. 새 찜 거절 사유 `OPTION_MISSING`(R-19 "공개 전 찜").

모든 이벤트에는 `seq`(서버 일련번호 — 엔진 범위 안에서 1부터, R-0 6)와 `at`(서버 도착 시각)이 붙는다. 이벤트 이름과 필드는 `tests/golden/README.md` 이벤트 표와 같다. 다른 점은 둘이다: 엔진의 효과 보고는 효과 ID로 가리키고, 문자찜의 전화번호는 엔진에선 `phoneKey`·`phoneLast4`다(골든의 `phone`은 러너가 서버처럼 바꿔 넘긴다).

**인스타그램 댓글의 `chat`** (N2, D-N2-02·D-N2-03·D-N2-04 — 엔진 규칙은 유튜브 채팅과 같다)
- 서버가 인스타그램 라이브 댓글을 `chat`으로 적을 때: `id` = `ig:<댓글 ID>`, `ch` = `ig:<IGSID>`, `nick` = username(모양이 아니면 `시청자`), `text` = 댓글 본문 그대로, `owner` = 판매자 계정의 댓글일 때만 `true`. `publishedAt`은 넣지 않는다 — 댓글마다의 게시 시각이 없어 엔진은 `at`(서버 도착 시각)을 쓴다(R-6). 재수신은 유튜브처럼 (방송, 메시지 ID)로 본다(R-4 머리말).
- 접두어가 있는 키는 영문이 섞여 아래 "ID 칸" 검사에 걸리지 않는다 — 숫자만인 IGSID가 휴대폰 번호 모양이어도 방송자 조치·합치기·정산 기록의 구매자 칸에 쓸 수 있다(G-ENG-N2-02). 골든 G-ENG-N2-01~03.

**문자찜 `ref`와 전화번호** (D-061 — 엔진 상태와 이벤트 로그에 휴대폰 번호 평문이 남지 않게, DAT-06)
- `ref`는 서버가 만든 무작위·일련 ID다. 문자찜 입력 하나마다 하나이고, 같은 입력을 다시 보내면(네트워크 재시도) 같은 `ref`다. 전화번호·이름·메모 같은 개인정보를 담지 않는다 — `ref`는 문자 구매자 ID(`sms:<ref>`)와 효과의 구매자 칸에 들어간다. 형식: 영문·숫자·`_`·`-`로 된 1~64자.
- 엔진은 전화번호 원문을 받지 않는다. 서버가 받은 번호를 코어 `normalizePhone`(R-11)으로 정규화하고, 휴대폰 번호 모양이면 판매자마다 다른 비밀 키의 HMAC으로 만든 불투명 키 `phoneKey`와 정규화한 번호의 뒤 4자리 `phoneLast4`를 이벤트에 담는다. 모양이 아니면 둘 다 담지 않는다(전화번호 없음과 같다). 같은 번호면 같은 키가 나와야 하므로 키는 판매자마다 고정한다(바꾸면 이후 문자찜이 이전 구매자와 이어지지 않는다).
- 형식: `phoneKey`는 영문·숫자·`_`·`-`로 된 16~128자(정규화한 번호 11자리·하이픈 13자는 이 길이에 못 미친다), `phoneLast4`는 숫자 4자리. 둘은 함께 온다.

**방송 시작·종료** (D-070)
- `broadcast.start`는 새 방송을 선언한다. 그보다 앞선 이벤트는 그 방송을 쓸 수 없다(선언하지 않은 방송 = 입력 오류). 이미 선언한 방송(엔진 시작 때 또는 앞선 `broadcast.start`)의 `broadcast.start`는 내용(날짜·제목·설정)이 달라도 아무 일도 없다 — 같은 입력의 재전송이다(INV-3).
- 설정 스냅샷은 DOMAIN_RULES 기본값 위에 덮어쓴 값이고, 키·값은 "설정값 범위" 안이어야 한다(밖이면 입력 오류). `settlement.groupBy=MANUAL`이면 미구현(`NotImplementedError`, D-059)이고 상태는 바뀌지 않는다.
- 서버는 빈 엔진에서 시작해 모든 방송을 `broadcast.start`로 선언하고, 스냅샷에는 **모든** 설정 키를 적는다 — 나중에 기본값이 바뀌어도 같은 로그를 재생하면 같은 결과가 나오게(NFR-02, INV-4).
- `broadcast.end`는 그 방송이 끝났다는 기록(끝난 시각 = 그 이벤트의 `at`)만 남긴다. 판정·정산은 바뀌지 않는다 — 끝난 뒤 도착한 채팅(끝나기 전에 게시된 것), 늦게 입력한 문자찜, 방송자 조치, 정산 기록도 평소대로 처리한다. 이미 끝난 방송의 `broadcast.end`는 아무 일도 없다. 끝난 방송을 다시 여는 이벤트는 없다.

**입력 오류와 맞지 않는 명령** (D-050 — 이전에는 모르는 이벤트 종류·형식이 틀린 이벤트를 조용히 무시해 `sms.claim`처럼 이름만 틀린 문자찜이 알림 없이 사라졌다)
- **입력 오류**: 이 표에 없는 종류, 필수 필드가 없거나 값의 형식이 틀림(번호·금액·재고 범위, 열거값, 사유는 빈 문자열이 아닌 문자열, 문자 수신 시각 `HH:MM`·`HH:MM:SS`, 문자찜 `ref`·`phoneKey`·`phoneLast4` 형식, 방송 날짜 `YYYY-MM-DD`, 설정 스냅샷의 키·값·범위), 표에 없는 필드(모든 종류 — `type`·`seq`·`at`과 그 종류의 필드 밖, D-073), 함께 와야 하는 필드가 한쪽만 옴(`host.assign`의 `replace`·`replaceTo` — D-065, `sms`의 `phoneKey`·`phoneLast4`), `sms`에 전화번호 원문 필드 `phone`이 있음(D-061), 선언하지 않은 방송, `seq`·`at`이 수가 아님. 엔진(`applyEvent`)은 상태를 바꾸지 않고 입력 오류(`NotImplementedError`와 다른 오류 하나)를 던진다. 같은 검사에 아래 "판매자가 적는 칸의 휴대폰 번호" 검사를 더한 순수 함수 `checkEvent`를 코어가 내보내고, 서버는 기록하기 전에 그 함수로 걸러 로그에 쓰지 않는다. 아직 지원하지 않는 종류(아래)도 기록하지 않는다(D-072).
- **판매자가 적는 칸의 휴대폰 번호** (D-079·D-080 — D-073의 "`ref`·`memo`에서 숫자만 모은 것이 휴대폰 번호 모양" 판단을 대신한다. 글의 숫자를 전부 모아 번호 모양을 보는 판단(`normalizePhone`을 글 전체에 적용)은 어디에도 쓰지 않는다 — `normalizePhone`은 전화번호 칸(R-11)과 아래 ID 칸에만 쓴다. 평문 번호가 지울 수 없는 이벤트 로그·엔진 상태·백업에 남지 않게, DAT-06): 아래 두 경우는 `checkEvent`의 입력 오류다.
  - **글 칸** — `sms`의 `ref`·`memo`, `settlement.payment`의 `memo`, 모든 사유(`reason` — `host.*`·`buyer.*`·`settlement.adjust`·`settlement.refund`), `broadcast.start`의 `title`, 상품 이름(`product.register`·`product.update`의 `name`)에 휴대폰 번호가 들어 있음. 휴대폰 번호 판단(코어 `containsPhoneRun`)은 하나뿐이다.
    - 숫자 덩어리 = 이어 적은 숫자(전각 숫자는 반각으로 본다). 덩어리 사이에 구분자만 있으면 이어진 덩어리 배열이다. **구분자** = 공백(줄바꿈 포함)·문장 부호·기호(`-`·`.`·`,`·`~`·`*`·`:`·`/`·`(`·`)`·`+`·이모지 등)·보이지 않는 글자, 그리고 줄·점 대신 치는 한글 자모 `ㅡ`·`ㅣ`·`ㆍ`(반각·조합형 모양 포함). 그 밖의 글자(한글 음절·영문 같은 글자, `①`·`²` 같은 다른 숫자 문자)가 끼면 배열이 끊긴다.
    - **번호다** = (가) 덩어리 하나가 `01X`(X는 `0`·`1`·`6`·`7`·`8`·`9`)로 시작하는 10~11자리 전체이거나, (나) 배열 안의 `01X` 세 자리 덩어리 바로 뒤에 이어진 덩어리들을 차례로 붙여 정확히 7자리나 8자리가 되는 곳이 있음. 덩어리 일부만 떼어 보지 않는다.
    - 번호인 예: `010-1234-5678`, `김영희 010 1234 5678`, `01012345678`, `3시,010,1234,5678`, `010:1234:5678 3시`, `3시 010ㅡ1234ㅡ5678`, `010-1234-5678 2개`, `(010)1234.5678`, `010 12345678`, `０１０-１２３４-５６７８`, `+82 010-1234-5678`, `ref` `s01012345678`.
    - 번호가 아닌 예: `01/05 3개 25,000원`, `01/05 구피 30종 1000원`, `01/05 100,000원 이상 무료`(시작 덩어리가 `01X` 세 자리가 아니다), `1234-5678`(`010`을 뺀 8자리는 번호로 보지 않는다), `3시 15번 2개`, `101동 1203호`, `1,2,3번 각 1개`, `r-20261018-0001`, `010123456789`(12자리 한 덩어리), `+82 10-1234-5678`(국가 번호 표기 — R-11 `normalizePhone`도 번호로 보지 않는다).
  - **ID 칸** — 판매자가 적는 구매자·메시지 ID: `buyer`(`host.*`·`sms`·`settlement.*`), `buyer.merge`의 `from`·`into`, `buyer.unmerge`의 `from`, `host.assign`의 `replace`, `host.convertMessage`의 `msg`의 값 전체가 숫자와 구분자(위와 같다)로만 되어 있고 R-11 `normalizePhone`의 결과가 있음(코어 `looksLikePhoneId`). 예: `010-5151-6161`, `01051516162`, `010 5151 6163`. 영문 같은 글자가 하나라도 섞인 ID(`UC_A`, `sms:s1`, `UC01012345678abcdEFGH_-`)는 걸리지 않는다.
  - 시청자 쪽 값(`chat`의 `id`·`ch`·`nick`·`text`)에는 어느 판단도 쓰지 않는다 — 찜을 버리게 되므로(R-3).
  - **기록 전에만 검사한다** (D-079 ⑤): 이 두 검사는 기록 전 검사 `checkEvent`에서만 한다. **재생 때는 글 칸·ID 칸 번호 검사를 하지 않는다** — `applyEvent`(서버가 기록된 로그를 다시 읽는 재생 포함)는 번호 검사로 입력 오류를 내지 않고 그 이벤트를 평소대로 처리한다. 규칙이 바뀌어도 이미 기록된 이벤트가 재생에서 조용히 빠지거나 방송 전체가 무너지지 않게(RA-S04-011). 그래서 이 두 검사에 한해 `checkEvent`가 문제를 돌려줘도 `applyEvent`는 처리한다. 그 밖의 입력 오류는 둘의 판정이 같다.
  - 서버가 이 검사로 거절할 때 쉬운 문장은 "전화번호처럼 보이는 숫자(010-…)가 있어요. 빼고 적어 주세요."다(글 칸·ID 칸 모두, D-079 ⑥).
- **맞지 않는 명령**: 형식은 맞지만 지금 상태에 맞지 않는 명령(없는 상품·찜·메시지, 조건이 안 맞는 조치)은 지금처럼 아무것도 바꾸지 않는다(D-039).
- 포장·배송 상태는 엔진 이벤트가 아니다(위 표, D-I2-05 — 이전 문장 "포장·배송 상태 → S09"를 대신한다). `effect.failed`는 쓰지 않는다 — 게시 실패·재시도·포기는 발송함 상태로만 남는다(R-13 "게시 실패는 판매 상태를 바꾸지 않는다", D-Y01). 코어는 계속 `NotImplementedError`로 알리고 서버는 기록하지 않는다. (`broadcast.start`·`broadcast.end`는 S04부터 위 "방송 시작·종료"대로 처리한다.)
- **상태 형식** (D-072): 엔진 상태에는 형식 번호(`format`)가 있다. `applyEvent`·`checkEvent`는 지금 코어의 형식과 다른 상태를 받으면 입력 오류·미구현과 다른 오류 하나로 알리고 아무것도 하지 않는다. 저장해 둔 상태를 읽는 쪽(서버)은 형식이 다르면 그 상태를 쓰지 않고 이벤트 로그를 처음부터 재생한다.

## R-2. 상품 상태

```
           register(OPEN)
   ┌──────────────────────────────┐
register(READY)        open         ▼        재고 소진
 ──────▶ READY ─────────────▶ OPEN ─────────────▶ SOLD
                               ▲ │ hold            │ 1등 취소(재고 회복)
                         open  │ ▼                 ▼
                              HOLD               OPEN (또는 승계로 SOLD 유지)
          close (확정·대기 찜이 없을 때만) → CLOSED
```

- `SOLD` = 확정 찜 수가 재고와 같음. 확정이 취소되어 자리가 비면 R-8에 따라 다시 `OPEN` 또는 승계.
- `CLOSED`는 소프트 삭제. 확정·대기 찜이 남아 있으면 닫을 수 없다(먼저 취소).

**상품 명령 세부** (D-039 — 맞지 않는 상태에 온 명령은 아무것도 바꾸지 않는다)

| 명령 | 받는 경우 | 결과 |
|---|---|---|
| `register` | 그 방송에 같은 번호의 상품이 없을 때 | 새 상품. 상태가 `OPEN`(기본)이면 R-5 |
| `open` | `READY`·`HOLD`·`CLOSED` | 판매 중. R-5 |
| `hold` | 판매 중(`OPEN`·`SOLD`) | `HOLD` |
| `close` | `READY`·`OPEN`·`HOLD`이고 확정·대기 찜이 없을 때 | `CLOSED`. 그 번호의 보류 찜은 `REJECTED(NOT_ON_SALE)` |

- 표에 없는 경우(같은 번호 다시 등록, 없는 상품, 이미 판매 중인 상품 `open`, `READY` 상품 `hold`, 찜이 남은 상품 `close` 등)는 아무 일도 없다(상태·효과·이력 그대로). 같은 번호를 고치려면 화면이 먼저 묻고(PRD-01 AC4) `product.update`를 보낸다(R-10).
- `READY`·`HOLD`·`CLOSED`는 방송자가 정한 상태다. 판매 중인 상품의 상태는 확정 찜 수로 정한다: 재고와 같으면 `SOLD`, 적으면 `OPEN`. `HOLD`를 풀면(`open`) 그때의 확정 수로 정한다.
- `HOLD`는 새 찜만 막는다(R-4 3번 줄). 이미 있는 찜의 취소·승계(R-8)는 그대로 된다.

## R-3. 채팅 주문 인식 (파서)

> 옵션 방송(`claim.parseMode=OPTIONS`)의 인식은 R-20이다. R-20도 메시지 전체가 아래 `STRICT` 문법이면 먼저 이 절대로 읽는다. 이 절(`STRICT`·`LOOSE`)은 옵션 방송 때문에 바뀌지 않는다.

**정규화**: 앞뒤 공백 제거, 전각 숫자→반각, 연속 공백 1칸.

**STRICT 모드 — 메시지 전체가 아래 문법일 때만 주문**
```
주문   := [찜] 번호목록 [꼬리말]
번호목록 := 번호 ( 구분자 번호 )*        구분자 := ( 공백 | , | / | · )+
번호   := 숫자{1,4} [번]                 (선행 0 허용: "015" → 15)
꼬리말  := (이요|요|여|찜|찜이요|찜할게요|주세요|할게요|구매|구매요|구매합니다)?  [기호/이모지/ㅎ/ㅋ/!/~/.]*
취소   := 번호 [번] (취소|취소요|취소할게요|취소해주세요)  [기호]*
```
- 번호는 `1..claim.maxNumber`. 범위 밖이면 주문 아님.
- 같은 메시지 안의 같은 번호는 하나로 친다.
- 번호 여러 개: `claim.multiNumber`에 따라 전부/첫 번째만/무시. 단 서로 다른 번호가 6개 이상이면 주문이 아니다(세부 "번호 개수 상한", D-034).
- 문법에 안 맞지만 숫자가 들어 있으면 `mentions`(언급된 번호)로 돌려줘서 콘솔이 강조 표시한다. 주문은 아니다.
- 방송자 본인 메시지(`isChatOwner`)는 `claim.ignoreOwner`가 켜져 있으면 무시.
- 사례 전체: `tests/golden/parser/chat.yaml`.

**세부 규칙** (D-028 — 위 문법이 말하지 않은 경우. 오인 주문이 놓친 주문보다 위험하다는 D-006을 따른다)
- **번호**: 정규화 뒤 숫자 1~4자리(선행 0 포함, `0015` → 15). 숫자와 `번` 사이 공백 하나 허용(`15 번`). 숫자가 5자리 이상 이어지면 번호가 아니다.
- **금액 모양은 번호가 아니다**: 공백 없이 숫자와 쉼표로 이어진 덩어리가 천 단위 묶음 모양 전체(`\d{1,3}(,\d{3})+`, 예: `12,500`)이면 금액 하나로 본다. 숫자`.`숫자(`1.5`)도 금액이다. 금액 덩어리가 있는 메시지는 주문·취소가 아니고, 그 덩어리는 언급에도 넣지 않는다. 묶음 모양이 아니면(`15,28,31`) 번호 목록이다.
- **범위**: 주문·취소가 될 메시지에 `1..claim.maxNumber` 밖의 번호가 하나라도 있으면 주문·취소가 아니다(`15 1000` → 언급 `[15]`).

- **꼬리 그림 이모지 허용 목록** (D-033 — 그림 이모지 전체를 받으면 `15❓`(질문)·`15 ❌`(부정)·`15 😭`(놓쳐서 아쉬움)가 주문이 된다). 주문 의사·호감·응원을 나타내는 아래 83자만 꼬리 기호다. 꼬리 안의 그림 이모지 글자(Unicode `Extended_Pictographic`)는 하나하나가 모두 이 목록이나 위 기호 목록(`♥` U+2665는 그림 이모지이기도 하다)에 있어야 하고, 수식 문자는 위대로 사이사이에 와도 된다(`❤️‍🔥` = U+2764 U+FE0F U+200D U+1F525 → 받음, `❤️‍🩹` → U+1FA79가 목록 밖이라 주문 아님, `🙋‍♀️` → 받음, `🙅‍♀️` → 주문 아님).

- **찜·꼬리말**: `찜` 접두 뒤, 번호와 꼬리말 사이의 공백은 있어도 없어도 된다(`찜15`, `15찜`, `15 찜`). 꼬리말은 위 목록에 있는 말만(`15번 살게요` → 언급).
- **취소**: 번호 하나만. 꼬리 기호에 더해 `ㅠ` `ㅜ`와 그 이모지 😢 U+1F622 · 😭 U+1F62D · 🥲 U+1F972를 허용한다(`15번 취소요 ㅠㅠ`, `15번 취소 😭`). 그 밖의 목록 밖 그림 이모지가 붙으면 취소가 아니다(`15 취소❓` → 언급). 번호 여러 개(`15 28 취소`)나 `취소 15`는 취소가 아니다(언급).
- **같은 번호·순서**: 결과 목록은 메시지에 나온 순서이고, 같은 번호는 처음 나온 자리에 하나만 남긴다. 언급도 같다.
- **번호 개수 상한** (D-034 — 채팅은 신뢰할 수 없는 입력이다. `1 2 3 … 60` 한 줄로 수십 개 상품이 1등 확정되고 라벨·감사 메시지가 줄줄이 나가는 일을 막는다): 주문이 될 메시지에 **서로 다른 번호가 6개 이상**이면 주문이 아니다. 그 메시지는 주문도 취소도 아닌 메시지로서 언급 규칙대로 번호를 돌려준다(`1 2 3 4 5 6` → 언급 `[1, 2, 3, 4, 5, 6]`). 같은 번호 반복은 하나로 센다(`15 15 15 15 15 15` → 주문 `[15]`, `1 2 3 4 5 5 1` → 주문 `[1, 2, 3, 4, 5]`). 이 검사는 `claim.multiNumber`를 적용하기 **전에** 한다 — `FIRST`·`IGNORE`에서도 같다(`FIRST`의 `1 2 3 4 5 6` → 언급 전부). 상한 5는 설정 키가 아니라 고정값이다.
- **여러 번호** (`claim.multiNumber`): `ALL` 전부 / `FIRST` 첫 번호만, 나머지는 버린다(언급에도 넣지 않음) / `IGNORE` 서로 다른 번호가 둘 이상이면 주문이 아니고 전부 언급. 같은 번호 반복(`15 15`)은 번호 하나다. 취소에는 영향 없다.
- **언급**: 주문도 취소도 아닌 메시지에서, 금액 덩어리가 아닌 1~4자리 숫자 덩어리 중 값이 `1..claim.maxNumber` 안인 것. 주문이나 취소가 나온 메시지의 언급은 비어 있다. 즉 주문·취소·언급 중 많아야 하나만 비어 있지 않다.
- 한글 수사(`십오번`)는 채팅 주문 번호로 보지 않는다.

**LOOSE 모드**: 메시지 맨 앞이 주문 문법(`[찜] 번호목록 [꼬리말] [꼬리 기호]`)이면 뒤에 무엇이 와도 주문 (예: "15번 이쁘다 살게요"). 단 주문 부분 바로 뒤의 첫 글자가 질문·아쉬움·부정 같은 끝 신호이면 주문이 아니다(아래 "끝 신호", D-035). "15번 18번 중에 뭐가 나아요?" 같은 질문도 주문이 되는 등 오인 위험이 커서 기본은 꺼둔다. 세부 (D-028, D-035):
- 맨 앞 주문 부분은 메시지 끝이나 공백 앞에서 끝나거나, 공백·꼬리 기호로 끝나야 한다. 그런 부분 중 가장 긴 것을 쓴다(`15개요`·`3개 남았나요?` → 주문 아님, `15!!예뻐요` → 15, `15번 2개 가능해요?` → 15).
- 취소가 먼저다: 맨 앞이 같은 조건(끝 경계·끝 신호)의 취소 문법이면 취소(`15 취소할게요 죄송해요`). 메시지에 `취소`가 들어 있으면 주문으로 보지 않는다(`15번 사려다 취소` → 언급).
- 금액 덩어리·범위·꼬리 기호(허용 목록 포함)·번호 개수 상한·여러 번호·언급 규칙은 STRICT와 같다. 번호 개수 상한은 고른(가장 긴) 주문 부분에 적용하고, 넘으면 더 짧은 앞부분으로 물러나지 않고 주문이 아니다(`1 2 3 4 5 6 다 주세요` → 언급 `[1, 2, 3, 4, 5, 6]`).
- **끝 신호** (D-035 — 위 끝 경계만 보면 공백 하나를 사이에 둔 `15 ❌`·`15번 😭`·`15 ❓ 남았나요`가 "공백 앞에서 끝난 부분"이라 주문이 되어, D-033이 막은 질문·부정·아쉬움이 LOOSE에서 돌아온다): 두 자리를 본다 — (가) 고른(가장 긴) 주문 부분 바로 뒤, (나) 끝 경계와 상관없이 문법에 맞게 읽히는 가장 긴 맨 앞 부분 바로 뒤. 보통 두 자리는 같다. (나)가 더 길면 고른 부분 뒤에 이어진 번호·꼬리말에 붙은 신호도 잡는다(`15 28❓`: 고른 부분 `15`, 가장 긴 부분 `15 28` → 언급 `[15, 28]`. `15 찜❓` → 언급 `[15]`. `1 2 3 4 5 6❓`: 고른 부분 `1 2 3 4 5` → 언급 `[1, 2, 3, 4, 5, 6]`). 각 자리에서 공백, 피부색 수식 문자(U+1F3FB~U+1F3FF), 보이지 않는 글자(Unicode `Default_Ignorable_Code_Point` — U+FE0F·U+200D·U+200B·U+200E·U+2060·U+FEFF·한글 채움 문자 U+3164 등)를 모두 건너뛴 **첫 글자**가 아래 중 하나이면 그 메시지는 주문이 아니다(언급). 건너뛰고 나서 메시지가 끝나면 그 자리에는 볼 글자가 없다.
  1. 질문 기호: `?` U+003F, `？` U+FF1F, ❓ U+2753, ❔ U+2754, ⁉ U+2049 (`15 ?`, `15 ❓ 남았나요`, `15!❓`)
  2. 꼬리 기호가 아닌 한글 호환 자모(U+3131~U+318E 중 `ㅎ`·`ㅋ` 밖): `ㅠ` `ㅜ` `ㄴ` `ㅡ` `ㄷ` `ㅇ` 등 (`15번 ㅠㅠ`, `15 ㄴㄴ`). 자모 줄임말은 아쉬움·부정·동의로 뜻이 갈리므로 모두 주문으로 보지 않는다(`15 ㅇㅇ`도 언급 — 놓친 주문 쪽).
  3. 꼬리 기호가 아닌 그림 이모지(`Extended_Pictographic` 중 기호 목록·허용 목록 밖): ❌ 😭 🤔 👀 👎 🙅 등 (`15 ❌`, `15번 😭`, `15👍👎`, `15 ❤️ 😭`)
  4. `번`: 숫자와 공백 하나 뒤의 `번`이 번호 부분에 들어가지 못하고 남은 경우(`15 번째 사진`, `15 번호 맞나요` → `15번째`와 같이 언급). `15 번 예뻐요`는 `15 번`까지가 부분이라 주문이다.
  5. 부분과 사이에 공백 없이 붙은 숫자: `15~28`(범위), `15 ❤️28`, `15 28~3` → 언급.
  - 취소 부분에도 같게 적용하되, 2·3의 "꼬리 기호"는 취소 꼬리다(`ㅠ` `ㅜ` 😢 😭 🥲는 끝 신호가 아니다): `15번 취소 😭 죄송해요` → 취소. `15번 취소 ❓`, `15 취소 번복할게요`(4), `15 취소 ㄴㄴ`(2) → 취소가 아니고, `취소`가 들어 있어 주문도 아니다(언급 `[15]`).
  - 걸리면 더 짧은 앞부분으로 물러나지 않는다(`15 ❤️ 😭` → 언급, `15 28 ❓` → 언급 `[15, 28]`). 번호 개수 상한처럼 `claim.multiNumber`를 적용하기 **전에** 본다(`FIRST`의 `15 28 ❓` → 언급 `[15, 28]`).
  - 두 자리의 첫 글자만 본다. 그 뒤의 말(글자)은 보지 않으므로 `15번 너무 예뻐요 ❓`, `15 말고 16`은 그대로 주문이다(위 머리말의 오인 위험, 기본 꺼짐). 끝 신호를 넓히려면 DECISIONS를 거친다.
  - STRICT에서는 메시지 전체가 부분이라 뒤에 글자가 없으므로 영향이 없다.

## R-4. 찜 판정 (상품 p에 대한 찜 c)

**채팅 메시지에서 찜까지** (D-045)
1. (방송, 메시지 ID)가 이미 받은 메시지면 아무 일도 없다. 본문·닉네임이 달라도 같다 (재수신, INV-3·INV-12).
2. 방송자 본인 메시지이고 `claim.ignoreOwner`가 켜져 있으면 아무 일도 없다. 꺼져 있으면 다른 시청자와 같다.
3. 보낸 채널을 구매자로 기록하고 닉네임을 갱신한다(R-11). 주문이 아닌 메시지도 같다.
4. 본문을 그 방송의 설정으로 R-3대로 읽는다. 주문 번호마다 메시지에 나온 순서대로 아래 표로 판정하고, 취소는 R-8 "시청자 채팅 취소"로 처리한다. 언급은 아무것도 바꾸지 않는다(콘솔 강조용).

위에서부터 처음 맞는 줄을 적용한다. 단 **4번 줄은 맨 먼저 본다** (D-038 — 보류·일시 중지·차단 상태에서도 같은 사람의 두 번째 찜이 생기지 않게, INV-2). "p에 활성 찜"은 같은 방송의 같은 번호에 대한 찜이다(상품이 아직 없는 보류 찜 포함). "같은 구매자"는 지금의 구매자(합친 결과, R-11)로 본다. "구매자가 차단됨"은 그 찜의 구매자 자신으로 본다(R-11 합치기).

| # | 조건 | 결과 |
|---|---|---|
| 1 | 구매자가 차단됨 | `REJECTED(BLOCKED)` |
| 2 | p가 없음 또는 `READY` | `PENDING(UNOPENED)` — R-5에서 처리 |
| 3 | p가 `HOLD` 또는 `CLOSED` | `REJECTED(NOT_ON_SALE)` |
| 4 | 같은 구매자가 p에 활성 찜(확정·대기·보류·충돌)이 이미 있음 | 새 찜 없음, 메시지는 `DUPLICATE`로 기록 |
| 5 | p가 "승계 결정 필요" 상태 | 대기 한도 안이면 `WAITLISTED`, 아니면 `REJECTED(SOLD_OUT)` |
| 6 | 확정 찜 수 < 재고 | `CONFIRMED` |
| 7 | 대기 수 < `waitlist.max` | `WAITLISTED` (순번 = 대기 수 + 1) |
| 8 | 그 외 | `REJECTED(SOLD_OUT)` |

- 문자찜(`sms`)·메시지 변환(`host.convertMessage`)으로 생기는 찜도 같은 표다. 재고가 다 찼을 때 늦게 온 선순위 찜(`RECEIVED_TIME`)과 메시지 변환은 7·8번 줄 전에 R-7(역전·충돌)을 본다.
- 5·7·8번 줄의 대기 자리는 아래 "대기에 넣는 자리"로 정한다. `ARRIVAL`의 새 찜은 늘 순위가 맨 뒤라 표 그대로다(순번 = 대기 수 + 1, 대기가 찼으면 그 찜이 품절).

**대기에 넣는 자리** (D-053)
- 새 찜(5·7번 줄), 충돌 `KEEP`과 충돌이 풀린 찜(R-7 7), 대기로 가는 메시지 변환 찜은 판정 순위(R-6)로 자리를 찾는다: 자기보다 순위가 앞서는 대기자 중 가장 뒤에 있는 대기자 바로 뒤, 그런 대기자가 없으면 1순위.
- 확정에서 밀려나 대기로 가는 찜(역전, 충돌 `SWITCH`, 교체 `WAITLIST`)은 대기 1순위다(차단 중이면 대기에 넣지 않고 `REJECTED(BLOCKED)`, D-049).
- 넣은 뒤 대기 수가 `waitlist.max`를 넘으면 맨 끝 대기자부터 `REJECTED(SOLD_OUT)`(넣은 찜 자신일 수도 있다. 대기 한도 0이면 늘 넣은 찜 자신). 단 확정 자리가 비어 풀린 충돌 찜은 승계·재고 규칙을 적용한 뒤에 정리한다(R-7 7, D-068).

`CONFIRMED`가 되면 엔진은 효과를 낸다: 상품 라벨 출력(설정 시), 감사 메시지(켜진 대상마다). 화면 알림은 효과가 아니라 상태 변화로 보인다(R-13, D-044). 가격 스냅샷 = 확정 시점 상품 가격.

## R-5. 공개 전 찜 (보류 찜 처리)

상품 p(번호 n)가 시각 T에 공개(`register(OPEN)` 또는 `open`)되면:
1. 방송의 번호 n에 대한 `PENDING` 찜을 판정 순위(R-6) 순서로 정렬한다.
2. `at ≥ T − claim.preOpenWindowSec`인 찜은 순서대로 R-4를 적용한다. 경계는 포함한다(T − 30초 정각에 온 찜은 판정에 들어간다). 재고가 2 이상이면 순서대로 여럿이 확정될 수 있다.
3. 더 오래된 찜은 `REJECTED(EXPIRED)`.

- 만료는 공개 순간에만 정한다. 공개되지 않은 번호의 보류 찜은 계속 보류이고, 콘솔이 보류 찜 목록으로 보여 준다.
- 보류 찜은 방송자 취소·무효와 시청자 취소(R-8), 차단(R-9), 판매 종료(R-2 `close`), 구매자 합치기(R-11 `DUPLICATE`)로도 끝난다.
- 유효 시간은 판정 정책과 상관없이 찜의 `at`(서버 도착 시각)으로 잰다. 문자 수신 시각·유튜브 게시 시각으로 재지 않는다 (D-052). 메시지 변환 찜의 `at`은 원래 메시지의 `at`이다(R-7 4).
- 2의 "순서대로 R-4"는 하나씩 새 찜처럼 판정한다는 뜻이다: 재고가 다 찬 뒤의 찜은 R-7을 본다(정렬했으므로 앞선 찜이 뒤에 오지 않지만, `HOST` 동률이면 공개 순간에도 충돌이 생긴다).
- 번호 변경(R-10)도 바뀐 상품이 판매 중이면 바뀐 번호에 대해 이 규칙을 적용한다(T = 변경 시각).

## R-6. 판정 순위

| 정책 | 순위 키 (앞설수록 우선) |
|---|---|
| `ARRIVAL` (기본) | `seq` — 서버에 들어온 순서. 문자 수신 시각은 기록만 한다 |
| `RECEIVED_TIME` | `(실제 시각, 동률 처리, seq)`. 유튜브 = `publishedAt`. 문자 = 입력한 수신 시각. 인스타그램 회차는 이 정책을 쓸 수 없다 — 댓글에 게시 시각이 없어 서버가 실제 시각순 회차에는 인스타그램 라이브를 잇지 않는다(D-N2-05). 엔진은 방송마다 따로 판정하므로 같은 날 유튜브 회차는 쓸 수 있다(G-ENG-N2-03) |

**`RECEIVED_TIME`의 분 단위 문제**: 휴대폰 문자는 보통 "오후 8:01"처럼 분까지만 보인다. 초 없이 입력된 문자 시각 `HH:MM`은 구간 `[HH:MM:00, HH:MM+1:00)`으로 본다. 정확한 시각 t(유튜브 또는 초까지 입력한 문자)와 비교할 때:
- t ≥ 구간 끝 → 문자가 앞선다.
- t < 구간 시작 → t 쪽이 앞선다.
- t가 구간 안 → 동률 → `contention.sameMinuteTieBreaker`: `YOUTUBE`(유튜브 우선) / `SMS`(문자 우선) / `HOST`(충돌로 표시, R-7).
- 분 단위 문자끼리 같은 분이면 `seq` 순.

**찜마다의 순위 재료** (D-052)

| 찜 | `seq` | 실제 시각 (`RECEIVED_TIME`) |
|---|---|---|
| 채팅 찜 | 그 메시지의 `seq` | `publishedAt` (정확한 시각) |
| 문자찜 | 그 `sms` 이벤트의 `seq` | 수신 시각(아래 날짜 규칙). 초까지 입력하면 그 초 정각의 정확한 시각, 분까지만이면 그 분의 구간 |
| 메시지 변환 찜 (R-7 4) | 원래 메시지의 `seq` | 원래 메시지의 `publishedAt` |
| 직접 배정으로 새로 만든 찜 (R-9) | 그 조치의 `seq` | 그 조치의 `at` (정확한 시각) |

- 순위 재료는 찜이 생길 때 정해지고 바뀌지 않는다. 확정에서 밀려나 대기로 가도 같다(그 자리는 R-4 "대기에 넣는 자리").
- `ARRIVAL`의 순위 키는 위 `seq` 하나다.

**`RECEIVED_TIME`의 정렬 키** (D-052 — 위 분 단위 규칙을 그대로 지키면서, 어느 세 찜에서도 순서가 고리처럼 뒤엉키지 않게 찜마다 키 하나로 정한다): `(T, r, seq)`를 앞에서부터 비교한다.
- 정확한 시각 t: `T = t`, `r = 1`.
- 분 단위 문자 `[m, m+1분)`: `sameMinuteTieBreaker`가 `SMS`면 `T = m`, `YOUTUBE`·`HOST`면 `T = m+1분`. `r = 0`.
- 이 키는 위 분 단위 규칙과 같은 답을 낸다: t ≥ 구간 끝이면 문자가 앞서고(구간 끝 정각과 같으면 `r`로 문자가 앞선다), t < 구간 시작이면 t가 앞서고, 구간 안이면 `YOUTUBE`·`HOST`는 t, `SMS`는 문자가 앞선다. 분 단위 문자끼리 같은 분이면 `seq` 순, 정확한 시각끼리 같으면 `seq` 순.
- **동률**: 분 단위 문자 `[m, m+1분)`와 정확한 시각 t 사이에서 `m ≤ t < m+1분`인 경우뿐이다. 정확한 시각 쪽이 초까지 입력한 문자여도 같다(설정 이름은 흔한 경우인 유튜브 대 분 단위 문자에서 땄다: `YOUTUBE` = 정확한 시각 쪽, `SMS` = 분 단위 문자 쪽). `HOST`는 정렬을 `YOUTUBE`처럼 하고, 동률인 두 찜이 1등 자리를 다툴 때만 충돌이다(R-7 6). 대기열 안의 동률은 키 순서대로 둔다.

**문자 수신 시각의 날짜** (D-023): 휴대폰 문자에는 보통 날짜 없이 시각만 보인다. 입력한 수신 시각 `HH:MM[:SS]`은 입력 시각(서버 도착 시각 `at`, KST)의 전날·당일·다음날 중 **`at`에 가장 가까운 날짜**의 시각으로 본다. 분 단위면 구간 시작(`HH:MM:00`)으로 거리를 잰다. 거리가 같으면 늦은 날짜를 고른다.
- 예: 00:01:30에 입력한 "23:59:40" → 전날 23:59:40 (자정 직전에 받은 문자를 자정 뒤에 입력).
- 예: 20:10:06에 입력한 "20:10:08" → 당일 20:10:08 (휴대폰 시계가 조금 빠른 경우). "가장 가까운 과거"로 해석하면 전날이 되어 1등을 부당하게 빼앗으므로 그렇게 하지 않는다.
- 이 해석은 `packages/core`의 순수 함수 하나로 구현하고 서버·화면·골든 러너가 함께 쓴다. 입력 시각보다 늦은 수신 시각은 화면에서 확인을 묻는다(S06 — 분까지만 적었으면 그 분의 시작으로 비교, D-089).
- 화면에서 수신 시각을 비우면 서버가 그 입력의 도착 시각(KST)을 초까지(`HH:MM:SS`) 적는다(D-089). 정확한 시각이라 실제 시각순에서 입력 시각보다 앞서지 않고, 같은 분의 유튜브 찜과 동률(충돌)도 만들지 않는다(G-ENG-169). 판매자가 분까지만 적으면 위 분 단위 규칙 그대로다.

## R-7. 늦게 도착한 선순위 찜 (역전과 충돌)

`ARRIVAL` 정책에선 늦게 들어온 찜이 앞설 수 없으므로 이 규칙이 적용되지 않는다. 예외는 방송자의 메시지 변환(아래 4)뿐이다.

**누구와 비교하나** (D-053): 판매 중인 상품 p에 새 찜 c(공개 순간의 보류 찜, 메시지 변환 포함)가 R-4 1~5번 줄에 걸리지 않고 들어올 때, 확정 수 < 재고면 R-4 6번 줄대로 확정한다(누구도 밀어내지 않는다). 자리가 다 찼으면 지금 확정 찜 중 판정 순위(R-6)가 가장 뒤인 찜 w와 비교한다(재고 1이면 1등). c가 w보다 앞서지도 동률(`HOST`)이지도 않으면 R-4 7·8번 줄(대기 자리)이다.

`RECEIVED_TIME`에서 새 찜 c가 w보다 순위가 앞서면:
1. **w가 잠금 전이면 자동 역전.** c → `CONFIRMED`, w → 대기 1순위(대기가 넘치면 맨 끝 대기자가 `REJECTED(SOLD_OUT)` — 대기 한도 0이면 w 자신. w가 차단 중이면 대기에 넣지 않고 `REJECTED(BLOCKED)`, D-049). w의 확정이 풀릴 때 규칙(R-13)을 적용한다: w에게 나가기로 한 효과 중 아직 실행되지 않은 것은 취소된다.
2. **w가 잠금 후면 충돌.** c → `CONFLICT`, 상품에 충돌 표시. 방송자가 고른다: `KEEP`(c를 순위대로 대기열에 넣거나, 대기가 넘치면 품절) / `SWITCH`(c 확정, w는 대기 1순위로). 세부는 7.
3. **잠금 조건**: w의 지금 확정에 대해 `effect.labelPrinted`, `effect.thanksSent`, `host.confirm`, 입금 기록 중 하나라도 있으면 잠금. 입금 기록 = w가 속한 정산 묶음(R-12)의 받은 금액(입금 합 − 환불 합)이 0보다 큼(D-053). 직접 배정으로 새로 만든 찜(R-9 `host.assign`)은 이 비교에서 늘 잠금 후로 본다 — 배정 순위는 방송자가 정한 것이라 늦게 온 찜이 자동으로 밀어내지 않는다(시청자 자동 취소 R-8의 잠금 판단에는 쓰지 않는다).
4. **방송자가 채팅 메시지를 찜으로 바꿀 때**(`host.convertMessage`): 정책과 상관없이 원래 메시지의 순위로 판정한다. 그 결과 기존 1등을 밀어내야 하면(c가 w보다 앞서거나 `HOST` 동률) 잠금과 상관없이 항상 충돌(2)로 처리한다. 세부 (D-054):
   - 대상은 그 방송에서 받은 메시지(방송, 메시지 ID)다. 모르는 메시지와 무시한 방송자 메시지(`claim.ignoreOwner`)는 아무 일도 없다.
   - 그 메시지가 주문이나 취소였으면(R-3이 주문 번호나 취소 번호를 하나라도 읽은 메시지 — 찜을 만들었든, 같은 사람 반복(R-4 4번 줄)이라 만들지 않았든, 취소가 처리됐든 요청이 됐든 무시됐든(R-8), 그 찜이 지금 어떤 상태든) 어느 번호로도 아무 일도 없다(취소 메시지는 D-076 — `15 취소`라고 쓴 사람이 그 메시지의 순위로 산 사람이 되지 않게). 주문도 취소도 아니었던 메시지(언급·한글 수사·그 밖)는 번호마다 한 번만 바꾼다(이미 그 번호로 바꿨으면 아무 일도 없다) — 취소·거절된 찜이 옛 순위로 되살아나거나 두 번 눌러 찜이 둘 생기지 않게 (D-062). 시청자가 번호를 잘못 쓴 주문(15번을 원했는데 `51`)은 직접 배정(R-9)으로 바로잡는다.
   - 새 찜의 구매자는 그 메시지의 채널이고, 순위 재료(R-6)와 `at`(보류 찜 유효 시간, R-5)은 원래 메시지의 것이다. 다른 새 찜처럼 R-4 1~5번 줄(차단·보류·판매 아님·같은 사람 반복·승계 결정 필요)을 먼저 적용한다.
   - 번호는 방송자가 고른 것이다. 메시지에 그 번호가 없어도 된다(`십오번이요`).
5. 대기열 안에서는 잠금이 없다. 늦게 온 선순위 찜은 맞는 자리에 끼워 넣는다(R-4 "대기에 넣는 자리").
6. 동률-방송자 결정(R-6 `HOST`)도 충돌(2)로 처리한다: c와 w가 동률이면 잠금과 상관없이 충돌이다.
7. **충돌 세부** (D-053):
   - 상품마다 충돌은 하나다. 충돌 중인 상품에서는 자동 역전도 새 충돌도 없다: 그동안 들어온 찜(변환 포함)은 1등을 밀어내야 해도 대기 자리로 간다(방송자가 결정하는 동안 1등이 바뀌지 않게).
   - `CONFLICT` 찜은 활성 찜이다(INV-2, R-4 4번 줄). 방송자 취소(`CANCELLED`)·무효(`REJECTED(BY_HOST)`), 시청자 취소(잠금이 없으므로 대기 찜과 같다), 차단(`REJECTED(BLOCKED)`), 번호 변경(`REJECTED(RENUMBERED)`), 구매자 합치기(`DUPLICATE`)로 끝나고, 끝나면 충돌 표시도 사라진다. 충돌 찜은 효과를 내지 않는다.
   - 충돌 중에 확정 자리가 비면(1등 취소·무효·취소 승인·시청자 자동 취소, 재고 늘림) 충돌이 먼저 풀린다: c를 `KEEP`처럼 대기 자리에 넣은 뒤 승계 규칙(R-8)·재고 규칙(R-10)을 적용한다. 이때 대기 넘침 정리(맨 끝 `REJECTED(SOLD_OUT)`)는 c를 넣을 때가 아니라 승계·재고 규칙을 적용한 **뒤에** 한다 (D-068 — 자리 하나가 비고 c 하나가 들어오므로, 먼저 정리하면 대기가 꽉 찬 상품에서 맨 끝 대기자가 곧 생길 빈자리를 두고 품절되고, 대기 한도 0이면 1등보다 앞선 c 자신이 품절된다). 승계 `AUTO`·재고 늘림이면 정리할 것이 남지 않고, `ASK`면 빈 자리는 방송자 결정으로 남아 한도를 넘는 맨 끝이 품절되며(대기 한도 0이면 `ASK`는 `AUTO`와 같다 — R-8, D-077), `REOPEN`이면 c도 대기자와 함께 정리된다.
   - 충돌 중인 상품에는 직접 배정(`host.assign`, 교체 포함)이 아무 일도 없다(R-9, D-064). 방송자는 충돌부터 정한다.
   - `host.resolveConflict(KEEP)`: c를 대기 자리(R-4 "대기에 넣는 자리")에 넣는다. `SWITCH`: c를 확정하고, 그때 판정 순위가 가장 뒤인 확정 찜 w의 확정을 풀어 대기 1순위로 보낸다(1의 w와 같게: R-13, 차단 중이면 `REJECTED(BLOCKED)`, 넘치면 맨 끝 품절). 충돌이 없는 상품의 `resolveConflict`는 아무 일도 없다(D-039).

## R-8. 취소와 승계

**방송자 취소** (`host.cancel`, 사유 필수)
- 확정 찜 취소 → `CANCELLED`. 이어서 `cancel.succession`을 적용한다.
  - `AUTO`: 대기 1순위가 `CONFIRMED`가 되고 새 효과(라벨·감사)가 나간다. 대기가 없으면 상품은 `OPEN`.
  - `ASK`: 상품을 "승계 결정 필요"로 표시한다. 방송자가 `host.promote`(대기자 지정) 또는 재오픈을 고를 때까지 새 찜은 R-4의 5번 줄로 처리한다.
    - 세부 (D-041): 대기가 없으면 결정할 것이 없으므로 표시 없이 `OPEN`이다(`AUTO`와 같다). 표시는 확정 수가 재고와 같아지거나(`host.promote`·`host.assign`), 대기가 비거나, 방송자가 `host.reopen`을 보내면 사라진다. `host.reopen`은 아래 `REOPEN`과 같고, 표시가 없으면 아무 일도 없다.
    - 대기 한도(`waitlist.max`)가 0이면 `ASK`는 `AUTO`와 같다 (D-077 — 대기가 없으니 물을 것이 없다. 대기에 들어올 수 있는 것은 자리가 비어 풀린 충돌 찜(R-7 7)뿐인데, 한도 0이라 넘침 정리로 품절시키면 1등보다 앞선 사람이 이유 없이 빠지고 표시도 사라져 아무나 다시 찜하게 된다. 그 찜이 빈 자리를 채운다).
  - `REOPEN`: 대기자 전원 `REJECTED(WAITLIST_CLEARED)`, 상품 `OPEN`. 재고가 2 이상이면 남은 확정 찜은 그대로 둔다.
- 대기 찜 취소 → `CANCELLED`, 뒤 순번이 하나씩 당겨진다 (INV-7).
- 보류 찜 취소 → `CANCELLED`.
- 충돌 찜(R-7) 취소 → `CANCELLED`, 충돌 표시가 사라진다. 1등은 그대로다.
- 대상 구매자의 활성 찜(확정·대기·보류·충돌)이 그 번호에 없으면 취소·무효 조치는 아무 일도 없다 (D-039). 대상 구매자는 지금의 구매자(합친 결과, R-11)로 찾는다.
- 확정 찜 취소로 자리가 빌 때 그 상품에 충돌이 있으면 충돌이 먼저 풀린 뒤 승계를 적용한다(R-7 7).

**시청자 채팅 취소** ("15 취소")
- `OFF`: 무시(메시지만 기록).
- `REQUEST`: 취소 요청을 콘솔에 띄운다. 상태는 방송자가 `host.approveCancel` 할 때 바뀐다.
- `AUTO`: 잠금 전이면 방송자 취소와 같게 처리하고, 잠금 후면 `REQUEST`로 처리한다. 잠금은 확정 찜에만 있으므로 대기·보류·충돌 찜은 바로 취소된다. 입금 기록(R-7 3)이 있는 확정 찜은 잠금 후다.
- 취소 요청자가 그 상품에 활성 찜이 없으면 무시한다.
- **대상 찾기** (D-063): 그 번호에서 지금의 구매자(합친 결과, R-11)의 활성 찜이 그 채널 **자신의** 찜(구매자 자신이 그 채널인 찜 — 채팅 주문·메시지 변환·그 채널에 한 직접 배정·지정 구매자가 그 채널인 문자찜)일 때만 위 규칙을 적용한다. 합친 다른 구매자(문자 구매자 등)의 찜이면 무시한다(취소도 요청도 없다). 합치기는 장부 정리라 채팅 한 줄이 할 수 있는 일을 넓히지 않는다 — 잘못 합친 경우에도 남의 찜이 시청자 채팅으로 취소되지 않게. 방송자 조치(`host.*`)의 대상 찾기는 그대로 지금의 구매자로 한다.
- **취소 요청 세부** (D-043): 같은 (상품, 구매자)의 요청은 하나만 둔다. `host.approveCancel`은 그 찜을 방송자 취소와 같게 처리한다(대기 중에 요청하고 승계로 확정된 뒤 승인해도 그 찜을 취소한다). `host.dismissCancel`은 요청만 지우고 찜은 그대로 둔다. 요청한 찜이 다른 이유로 활성이 아니게 되면(방송자 취소·무효 등) 요청도 사라진다. 요청이 없는데 온 `approveCancel`·`dismissCancel`은 아무 일도 없다.

**무효 처리** (`host.reject`): 확정 찜을 무효로 하면 취소와 같은 승계 규칙을 탄다. 상태는 `REJECTED(BY_HOST)`. 대기·보류·충돌 찜을 무효로 하면 `REJECTED(BY_HOST)`이고 대기 순번은 당겨진다(충돌 찜이면 충돌 표시가 사라진다).

**입금 후 취소**: 판정 상태는 똑같이 바뀌고, 정산 묶음에 환불 필요 금액이 생긴다 (R-12).

## R-9. 방송자 수동 조치

- `host.assign(상품, 구매자)`: 해당 구매자로 확정 찜을 만든다. 이미 1등이 있으면 "교체" 옵션이 필요하고, 기존 1등은 대기 1순위 또는 취소(사유) 중 고른다.
  - 세부 (D-042): 판매 중(`OPEN`·`SOLD`)인 상품에서만 된다. 충돌 중인 상품(R-7)이면 교체가 있든 없든 아무 일도 없다 — 방송자는 충돌부터 정한다(`host.resolveConflict`, D-064. 받으면 1등이 바뀐 채 충돌이 남아 화면의 질문이 낡고, 그 뒤 `SWITCH`가 방금 배정한 1등을 밀어낼 수 있다). `replace`·`replaceTo`는 함께 쓰고, 한쪽만 있으면 입력 오류다(R-1, D-065). 구매자는 엔진이 이미 아는 구매자(채팅을 쓴 적 있는 채널, 문자찜 구매자)여야 한다. 배정받는 구매자의 차단 여부는 보지 않는다(방송자의 명시적 조치). 밀려나는 1등이 차단 중일 때는 아래 교체 문장(D-049).
  - 교체 없음: 빈 자리(확정 수 < 재고)가 있을 때만 된다.
  - 교체(`replace` = 지금 1등 중 한 명, `replaceTo` = `WAITLIST` / `CANCEL`): 그 1등의 확정을 풀고(R-13) 그 자리에 확정한다. `WAITLIST`면 그 1등을 대기 1순위로 넣고, 대기가 `waitlist.max`를 넘으면 맨 끝 대기자부터 `REJECTED(SOLD_OUT)`. 단 그 1등이 차단 중이면 대기에 넣지 않고 `REJECTED(BLOCKED)`로 끝내며 대기 넘침 정리도 없다(아래 `blockBuyer`, D-049). `CANCEL`이면 `CANCELLED`. 빈 자리가 있어도 교체를 적었으면 교체한다.
  - 그 구매자에게 그 상품의 대기 찜이 있으면 그 찜이 대기에서 빠져 확정된다(새 찜 없음, 교체된 1등은 그다음에 1순위로 들어간다). 없으면 새 확정 찜을 만든다. 이미 확정이면, 또는 보류·충돌 찜이 있으면 아무 일도 없다(충돌은 `host.resolveConflict`로 정한다). 구매자는 지금의 구매자(합친 결과, R-11)로 본다.
  - 새로 만든 배정 찜의 순위는 그 조치의 순위다(R-6). R-7에서는 늘 잠금 후로 본다(R-7 3).
  - 그 밖(판매 중이 아님, 충돌 중, 모르는 구매자, 빈 자리가 없는데 교체 없음, `replace`가 지금 1등이 아님)은 아무 일도 없다.
- `host.promote(대기 찜)`: 자리가 비어 있을 때만 대기 찜을 확정한다. 아니면 아무 일도 없다.
- `host.confirm(찜)`: 잠금만 건다 (R-7.3). 확정 찜이 아니면 아무 일도 없다.
- `host.resolveConflict(상품, KEEP|SWITCH)`.
- `host.blockBuyer` / `unblockBuyer`: 차단은 구매자 하나(유튜브 채널 또는 문자 구매자)에 걸리고 합친 다른 구매자에게 번지지 않는다(R-11, D-057). 차단은 엔진 상태(엔진 범위 = 판매자·방송 날짜, R-0 6) 안에서 걸린다. 다음 날짜로 이어 가는 일은 서버가 한다: 새 범위를 시작할 때 바로 앞 날짜 범위에서 차단 중인 유튜브 채널마다 `host.blockBuyer`를 기록한다(D-069). 리허설 범위(R-0 6)는 이어받지도 넘겨주지도 않는다 — 실제 범위는 실제 범위에서만, 리허설 범위는 아무 데서도 이어받지 않는다(D-081). 차단 후 들어오는 찜은 R-4의 1번 줄로 거절한다. 차단하는 순간 그 구매자의 대기·보류·충돌 찜은 모두 `REJECTED(BLOCKED)`이고(대기 순번은 당겨지고, 충돌 표시는 사라진다), 확정 찜은 그대로 둔다(필요하면 방송자가 무효 처리). 차단을 풀어도 거절된 찜은 돌아오지 않는다 (D-040 — 이전 문구 "이미 있는 찜은 그대로 둔다"를 바꿨다. 차단한 사람이 대기에 남아 있다가 자동 승계로 1등이 되고 라벨·공개 감사 메시지를 받는 일을 막는다).
  - 차단 중인 구매자의 찜은 대기에 들어가지 않는다 (D-049): 차단 뒤에 그 사람의 확정 찜이 대기로 가야 하면(교체 `replaceTo=WAITLIST`, R-7 역전, 충돌 `SWITCH`) 대기에 넣지 않고 `REJECTED(BLOCKED)`로 끝낸다. 확정이 풀릴 때 규칙(R-13)은 그대로이고, 대기에 들어가지 않으므로 대기 넘침 정리도 없다. 그래서 차단 중인 구매자에게는 대기·보류·충돌 찜이 없고, 자동 승계·수동 승계가 차단한 사람을 확정하는 일이 없다.
- 맞지 않는 상태에 온 조치(대상 찜·상품 없음, 조건 안 맞음)는 아무것도 바꾸지 않는다 (D-039).
- 모든 조치는 사유·조치자·시각이 이력에 남는다.

## R-10. 상품 수정

`product.update`는 적힌 값(품종·가격·재고)을 한 번에 적용한다 (D-055). 하나라도 받을 수 없으면(재고를 확정 수보다 작게) 이벤트 전체가 아무 일도 없다. 없는 상품이면 아무 일도 없다. 상품 상태(`READY`·판매 중·`HOLD`·`CLOSED`)와 상관없이 고칠 수 있다. 지금 값과 같은 값은 바뀐 것이 아니다(이력 없음).

- **가격 변경**: 이력에 (이전 가격, 새 가격, 시각, 조치자)를 남긴다. 찜의 가격 스냅샷은 그대로 둔다. 단 `applyTo=UNPAID_CLAIMS`면 입금 전인 확정·대기 찜의 스냅샷도 새 가격으로 바꾸고 각각 이력을 남긴다.
  - 세부 (D-055): 입금 전 = 그 찜이 속한 정산 묶음(R-12)의 받은 금액이 0. 대기 찜은 아직 스냅샷이 없어 확정될 때의 상품 가격(새 가격)을 받는다 — `NEW_ONLY`여도 같다(스냅샷은 확정 시점 가격, R-4). `applyTo`는 가격이 바뀔 때만 뜻이 있다.
- **품종 변경**: 이력을 남기고, 이미 출력된 라벨에 "재출력 필요"를 표시한다.
  - **재출력 필요** (D-055): 지금 확정 찜 중 그 확정의 상품 라벨 출력 완료 보고가 있는 찜에, 품종이 바뀌거나 그 찜의 가격 스냅샷이 바뀌면 표시한다. 효과는 내지 않는다(재출력은 방송자가 고른다, I1). 화면의 "재출력 필요" 낱말은 서버가 LABEL_RULES L-10 내용 키로 정한다 — 이 표시는 다시 출력해도 지워지지 않으므로 화면 낱말로 쓰지 않는다(D-I1-04). 이미 나온 효과(아직 실행 전인 감사 문구 포함)의 내용은 바꾸지 않는다 — 효과 ID는 한 번만 실행하는 약속이라 같은 ID로 다른 내용을 낼 수 없다.
- **번호 변경**(`renumber a→b`): b가 이미 있으면 거부한다.
  - 세부 (D-056): a에 상품이 없거나, b에 상품 기록이 이미 있거나(`CLOSED` 포함), a = b이면 아무 일도 없다(거부).
  1. a에 붙어 있던 찜(확정·대기)은 전부 `REJECTED(RENUMBERED)`로 하고 방송자 확인 목록에 올린다. 그 사람들은 실제로 없는 번호를 쓴 것이기 때문이다.
     - 충돌 찜도 같다. 잠금·입금과 상관없다(입금된 찜은 정산에 환불 필요가 생긴다, R-12). 확정 찜은 확정이 풀릴 때 규칙(R-13)을 적용한다(출력된 라벨은 `VOID_LABEL`). 승계는 없다(그 번호의 찜이 모두 끝난다).
     - 번호 a의 보류 찜은 번호 a의 보류 찜으로 그대로 남는다.
  2. 상품은 b가 되고, 시각 = 변경 시각으로 R-5를 적용한다. b로 들어와 있던 보류 찜을 판정한다.
     - 상품은 품종·가격·재고·상태·가격 이력·확정버전(R-13)을 그대로 가지고 번호만 b가 된다. 번호 a에는 상품이 없다.
     - R-5는 상품이 판매 중(`OPEN`·`SOLD`)일 때만 적용한다. `READY`·`HOLD`·`CLOSED`면 b의 보류 찜은 그대로 보류이고 공개할 때 R-5를 적용한다.
- **재고 변경**: 늘리면 대기 1순위부터 확정한다. 줄이면 현재 확정 수보다 작게 할 수 없다.
  - 세부 (D-055): 늘린 수만큼(대기가 그보다 적으면 대기 전부) 대기 1순위부터 대기 순번 순서로 확정한다(확정버전도 이 순서, R-13, D-066) — 승계 결정 필요(ASK) 표시가 있어도 늘린 자리만 채우고, 원래 비어 있던 자리는 방송자 결정으로 남긴다(표시는 D-041대로 사라지거나 남는다). 충돌이 있으면 먼저 풀린다(R-7 7). 줄이는 것은 확정 수 이상이면 되고(같으면 `SOLD`), 확정 수보다 작으면 이벤트 전체가 아무 일도 없다.

## R-11. 구매자 식별

| 채널 | 식별 키 | 표시 이름 |
|---|---|---|
| 유튜브 | `channelId` | 최신 닉네임 (이력 보관) |
| 인스타그램 | `ig:<IGSID>` (서버가 붙인 접두어 — R-1 "인스타그램 댓글의 `chat`", D-N2-02) | 최신 username (이력 보관) |
| 문자 | 입력 시 지정한 기존 구매자 / 전화번호 키 `phoneKey`(있을 때 — 서버가 만든 불투명 키, R-1) / 없으면 새 문자 구매자 | "문자찜" 또는 "문자찜(메모)" |
| 수동 | 방송자가 고르거나 만든 구매자 | 입력한 이름 (구매자를 따로 만드는 이벤트는 두지 않는다 — 전화·현장 주문은 문자찜 입력으로 받고 메모에 이름을 적는다, D-051) |

- 닉네임이 같고 채널 ID가 다르면 다른 사람이다. 화면엔 구분 표시를 한다.
- 채팅 구매자(유튜브·인스타그램)는 엔진에서 한 종류다(구매자 종류 `youtube` = 채팅 구매자). 플랫폼은 키 접두어로 안다 — `ig:` 인스타그램, `tt:` 틱톡(예약), 그 밖 유튜브(D-N2-02). 닉네임이 같아도 키가 다르면(플랫폼이 달라도) 다른 사람이고, 같은 사람이면 판매자가 합친다(아래 "구매자 합치기", G-ENG-N2-03).
- 유튜브 구매자 기록 (D-045): 채팅 메시지가 오면(재수신·무시하는 방송자 메시지 제외, R-4 머리말) 그 채널을 구매자로 기록하고 닉네임을 갱신한다. 주문이 아닌 메시지도 같다(방송자가 그 사람에게 직접 배정할 수 있어야 한다, R-9). 표시 이름 = 가장 최근 닉네임, 닉네임 이력 = 바뀔 때마다 쌓은 목록(처음 것 포함, 연속 중복 없음).
  - 닉네임 정리 (Y1, D-Y05): 서버의 수집 경로(유튜브 수집기·리허설 생성기·시청자로 보내기)는 `chat`의 닉네임을 기록하기 전에 정리한다 — 공백 문자는 한 칸, 제어·서식·보이지 않는 글자(`Cc`·`Cf`·`Default_Ignorable_Code_Point`)와 `@`·`＠`·`﹫`는 지우고, 점(`.`·`。`·`．`·`｡`)은 `·`, 30자를 넘으면 앞 30자 + `…`, 비면 `시청자`. 엔진은 받은 닉네임을 그대로 쓴다(장부·라벨·감사 문구가 같은 이름이다).

**문자찜 구매자 정하기** (D-051): `sms` 이벤트마다 위에서부터 처음 맞는 것을 쓴다.
1. 지정 구매자(`buyer`)가 있으면 그 구매자(전화번호 키는 보지 않고 기록하지도 않는다). 엔진이 모르는 구매자면 찜·구매자·메모 반영이 모두 없다(D-039) — `ref`만 기록한다(아래, D-067).
2. 전화번호 키(`phoneKey`)가 있으면 그 키의 문자 구매자, 없으면 그 키로 새 문자 구매자를 만든다(그 구매자의 뒤 4자리 = 그 이벤트의 `phoneLast4`. 같은 키에 다른 뒤 4자리가 와도 구매자의 뒤 4자리는 바꾸지 않는다). 키는 서버가 휴대폰 번호 모양일 때만 만든다(R-1, D-061). 휴대폰 번호 모양 = 숫자만 남겨서(전각 숫자는 반각으로, 그 밖의 글자·공백·`-`·`+`·괄호는 지운다) `01`로 시작하는 10~11자리 — 코어 `normalizePhone`이 이 정규화를 하고 서버·화면·골든 러너가 함께 쓴다. 그 밖(`1234`처럼 일부만, `+82 10 …`처럼 국가 번호로 시작 등)은 전화번호가 없는 것과 같다 — 번호 일부만 같은 다른 사람이 한 구매자로 묶이지 않게. 형식이 달라도 숫자가 같으면 같은 번호(같은 키)다(`010-1234-5678` = `01012345678`).
3. 그 밖은 새 문자 구매자.
- `ref`는 처음 받을 때 기록한다. 이벤트가 찜·구매자를 만들지 않았어도(모르는 지정 구매자) 같다. 같은 `ref`가 다시 오면 내용이 달라도 아무 일도 없다(같은 입력의 재전송, INV-3·INV-12, D-067). 모르는 지정 구매자의 입력을 고쳐 다시 넣으려면 새 입력(새 `ref`)으로 한다.
- 표시 이름: 문자 구매자는 가장 최근에 받은 비어 있지 않은 메모(앞뒤 공백 제거)로 `문자찜(메모)`, 받은 메모가 없으면 `문자찜`. 닉네임 이력처럼 바뀔 때마다 쌓는다(처음 것 포함, 연속 중복 없음). 지정 구매자가 유튜브 구매자면 메모는 그 표시 이름을 바꾸지 않는다.
- 전화번호 키는 구매자를 잇는 데만 쓴다. 조회 결과에는 뒤 4자리만 보이고(ORD-08 AC4), 효과(감사 문구·라벨)·효과 ID·찜 ID·구매자 ID와 공개 메시지에는 어떤 경우에도 메모·전화번호 키·뒤 4자리를 넣지 않는다(YT-04 AC1, R-13). 엔진 상태와 이벤트 로그에는 전화번호 원문·정규화한 번호가 없다(D-061). 메모·닉네임·뒤 4자리는 남으므로 서버는 상태·이벤트 로그를 계속 개인정보로 다룬다(로그 출력 금지 — DAT-06, S04).

**구매자 합치기** (D-057)
- `buyer.merge(a→b)`: a의 모든 찜은 b의 것으로 계산된다. 원본 찜 기록은 바꾸지 않고 연결만 바꾸므로 `unmerge`로 되돌릴 수 있다.
  - 연결은 나무 모양이다. **지금의 구매자** = 연결을 끝까지 따라간 구매자. 합계·정산 묶음·R-4 4번 줄·INV-2·방송자 조치의 대상 찾기는 지금의 구매자로 한다. 표시 이름은 지금의 구매자 자신의 것이다.
  - 받는 경우: a·b 모두 엔진이 아는 구매자(채팅을 쓴 채널, 문자 구매자), a ≠ b, a가 지금 다른 구매자에 합쳐져 있지 않음(먼저 `unmerge`), b의 지금의 구매자가 a가 아님(고리 금지). 아니면 아무 일도 없다. a에 이미 합쳐 있던 구매자들은 a와 함께 따라간다.
- `buyer.unmerge(a)`: a의 연결만 끊는다(a에 합쳐 있던 구매자들은 a와 함께 떨어진다). a가 합쳐져 있지 않으면 아무 일도 없다. 떼어 낸 결과 어느 정산 묶음의 받은 금액(입금 합 − 환불 합)이 0보다 작아지면(합친 동안 적은 환불이 한쪽 입금만으로는 모자랄 때) 떼어 내기를 하지 않는다(아무 일도 없음, INV-6).
- 합친 결과로 한 상품에 같은 구매자의 활성 찜이 2개가 되면, 순위가 앞선 쪽을 남긴다. 나머지는 `DUPLICATE`로 바꾸고 방송자 확인 목록에 올린다.
  - "앞선 쪽" (D-057): 확정 > 충돌 > 대기(앞 순번) > 보류(판정 순위 R-6). `DUPLICATE`로 바뀐 대기 찜 뒤의 순번은 당겨지고, 충돌 찜이면 충돌 표시가, 취소 요청이 있었으면 요청이 사라진다. 효과는 없다.
  - 단 **확정 찜이 둘이 되는 상품이 하나라도 있으면 합치기 전체가 아무 일도 없다** — 장부 정리인 합치기가 확정을 풀어 승계·라벨·공개 감사로 번지지 않게, 방송자가 먼저 하나를 취소한다(화면이 알려 준다, S06).
  - `DUPLICATE`로 바뀐 찜은 `unmerge`해도 돌아오지 않는다(차단을 풀어도 거절된 찜이 돌아오지 않는 것과 같다).
- **미리 보기** (S06b, D-100): 코어 순수 조회 `previewMerge(state, from, into)`는 상태를 바꾸지 않고 위 규칙과 같은 답을 낸다 — 막힘 이유 하나(엔진이 모르는 구매자 → 같은 구매자 → `from`이 이미 합쳐져 있음 → 고리 → 확정 찜이 둘이 되는 상품, 위에서부터 처음 맞는 것), 확정이 둘이 되는 상품, 옮길 확정 찜(`from`과 그 아래 전부), 합친 뒤 지금의 구매자(`into`의 지금의 구매자)의 확정 찜·합계, `DUPLICATE`가 될 찜. 막히지 않으면 `buyer.merge`를 적용한 결과와 같다(골든 `mergePreviews`, G-ENG-174·175). 화면은 이 규칙을 다시 구현하지 않고 서버가 이 조회로 계산한 값을 보인다.
- 이벤트의 구매자: `buyer.merge`의 `from`·`into`와 `buyer.unmerge`의 `from`은 그 구매자 자신을 가리킨다. 그 밖의 이벤트(방송자 조치, 문자찜의 지정 구매자, 정산 기록)의 구매자는 그 구매자 자신에 기록하고, 판정·대상 찾기는 지금의 구매자로 한다. 정산 기록(배송비 예외·조정·입금·환불)은 적힌 구매자에 붙어 있다가 묶음 계산 때 합친 구매자들 것을 모두 더한다(R-12).
- 차단은 구매자 하나에만 걸린다(R-9). 감사 문구의 이름은 찜의 구매자 자신 기준이다(R-13).

## R-12. 정산 계산

- **정산 묶음** = (구매자, 기간). `DATE`면 같은 날짜(KST)의 모든 방송. `MANUAL`이면 방송자가 고른 방송 목록.
  - 방송의 날짜는 방송 회차에 정한 날짜다. 자정을 넘겨 끝난 방송도 그 방송의 날짜 하나로 묶는다. 찜 시각의 날짜로 나누지 않는다 (D-022, 한 방송이 두 묶음으로 쪼개져 배송비가 두 번 붙는 일 방지).
  - `MANUAL`은 묶음을 정하는 이벤트와 화면이 함께 필요해 아직 정하지 않았다. 엔진은 시작 때 미구현을 알리고, 설정 화면은 `MANUAL`을 보여 주지 않는다 (D-059).
  - 구매자 = 지금의 구매자(합친 결과, R-11). 정산 기록(배송비 예외·조정·입금·환불)은 이벤트에 적힌 (구매자, 날짜)에 붙고, 묶음은 합친 구매자들의 그 날짜 기록을 모두 더한다. 엔진이 모르는 구매자의 정산 기록은 아무 일도 없다 (D-058).
- **품목** = 기간 안 방송들에서 그 구매자(합친 구매자 포함)의 `CONFIRMED` 찜.
- **상품 합계** = 품목 가격 스냅샷의 합.
- **배송비**는 아래 순서로 정한다. 설정(`baseFee`·`freeThreshold`)은 그 날짜 첫 방송의 스냅샷이다(판매 규칙 설정표 아래 "설정 스냅샷", D-070).
  1. 품목이 없으면 0.
  2. 구매자 예외(직접 수령=0, 합배송=0, 금액 지정)가 있으면 그 값.
  3. `freeThreshold`가 있고 상품 합계 ≥ 기준이면 0.
  4. 그 외엔 `baseFee`.
  - 세부 (D-058): 예외는 그 묶음 기록 중 가장 나중 것 하나만 본다(`PICKUP` 직접 수령 / `COMBINED` 합배송 / `FIXED` 금액 지정). 가장 나중 것이 `DEFAULT`(예외 지우기)면 예외가 없다. 3의 기준은 상품 합계만 본다(조정은 보지 않는다). 도서산간 추가는 `FIXED` 금액이나 조정(+)으로 적는다.
- **조정** = 할인(−)·추가(+) 항목의 합. 항목마다 사유가 필수다.
- **최종 결제 금액** = 상품 합계 + 배송비 + 조정.
  - 세부 (D-058): 품목이 없으면 조정도 0으로 본다(기록은 남는다) → 최종 금액 0. 품목이 있어도 합이 0보다 작으면 최종 금액은 0이다 — 할인이 주문 금액을 넘었다고 돌려줄 돈이 생기지 않는다(INV-6).
- **입금 상태**: 받은 금액 = 입금 합 − 환불 합.
  - 세부 (D-058): 환불은 받은 금액을 넘을 수 없다 — 넘는 환불 기록은 아무 일도 없다(받은 금액은 0 아래로 내려가지 않는다). 품목이 없어도 받은 금액이 있으면 묶음이 있다(전부 취소된 뒤의 과입금: 최종 0, 환불 필요 = 받은 금액). 받은 금액이 0이면 최종 금액이 0이어도 `UNPAID`다(아래 표의 위에서부터).

  | 상태 | 조건 |
  |---|---|
  | `UNPAID` | 받은 금액 = 0 |
  | `PARTIAL` | 0 < 받은 금액 < 최종 금액 |
  | `PAID` | 받은 금액 = 최종 금액 |
  | `OVERPAID` | 받은 금액 > 최종 금액 → 환불 필요 = 차액 |

- 모든 값은 정수 원이다. 반올림할 일이 생기면 설계가 잘못된 것이다.

## R-13. 부수효과와 멱등성

- 엔진이 내는 효과: `PRINT_PRODUCT_LABEL`, `PRINT_PACKING_LABEL`(예약 — 지금은 내지 않는다. 포장 라벨은 판매자가 요청하면(정산 자세히, 포장 모드 D-I2-07) 서버 출력 대기열이 만든다, LABEL_RULES L-11 12, D-I1-02), `POST_THANKS(target=LIVE_CHAT|VIDEO_COMMENT)`, `VOID_LABEL`(취소·무효·승계·역전·교체로 이전 라벨 폐기 표시), `NOTIFY`(예약 — 지금은 내지 않는다, 아래).
- 효과 ID = `{찜ID}:{효과종류}:{대상}:{확정버전}`. 확정버전 = 그 상품에서 몇 번째 확정인지(1부터, 역전·승계마다 +1). outbox는 이 ID로 한 번만 실행한다.
  - 대상이 없는 효과(`PRINT_PRODUCT_LABEL`·`VOID_LABEL`)는 대상 자리에 `-`를 쓴다(`c1:PRINT_PRODUCT_LABEL:-:1`, D-060). 효과 ID는 엔진 상태 하나 안에서만 유일하므로 outbox는 (판매자, 엔진 범위, 효과 ID)로 중복을 막는다 — 엔진 범위 = 방송 날짜(R-0 6, D-069, S04·S11). 리허설 범위의 효과는 기록만 하고 실행하지 않는다 — 감사 메시지를 게시하지 않고 라벨을 자동 출력하지 않는다(D-081).
  - 확정버전 세부 (D-044): 상품마다, 찜이 `CONFIRMED`가 될 때마다(첫 판정·보류 공개·승계·수동 승계·직접 배정·역전·교체·충돌 바꾸기·메시지 변환·재고 늘림) 1씩 늘어난다. 번호를 바꿔도 상품의 확정버전은 이어서 센다(R-10). 재고가 2 이상이면 1등마다 따로 센다(A=1, B=2, A 취소 뒤 C=3). 한 이벤트에서 여럿이 확정되면 확정하는 순서대로 붙인다: 공개 순간의 보류 찜(R-5, 번호 변경 뒤 포함)은 판정 순위 순서, 재고 늘림(R-10)은 대기 순번 순서 (D-066 — 대기 1순위가 확정에서 밀려난 사람이라 순위로는 뒤여도 먼저 확정되고 먼저 붙는다). 찜ID는 같은 이벤트 로그면 항상 같게 정한다(NFR-02).
- **확정 때 내는 효과** (D-044): `print.autoOnConfirm`이면 `PRINT_PRODUCT_LABEL`, `thanks.liveChat`이면 `POST_THANKS(LIVE_CHAT)`, `thanks.videoComment=PER_SALE`이면 `POST_THANKS(VIDEO_COMMENT)`. `SUMMARY`는 판매마다 효과를 내지 않는다(방송 끝 요약 1건, S11). `batchWindowSec`은 엔진 효과를 바꾸지 않는다(묶음은 outbox가 한다). 자동 게시 동의(YT-04 AC2)는 실행하는 쪽이 본다.
- `NOTIFY`는 예약해 두고 지금은 내지 않는다. 충돌·보류·만료·취소 요청 같은 화면 알림은 상태에서 만든다 (D-044 — 실행 결과가 돌아오지 않는 효과가 실행 대상으로 계속 쌓이지 않게).
- **감사 문구** (D-044): `{번호}번 {품종} {가격} {구매자}님 구매 감사합니다`.
  - 가격 = 가격 스냅샷을 세 자리마다 쉼표로 끊고 `원`을 붙인다(`800원`, `10,000원`, `1,000,000원`).
  - 품종은 앞뒤 공백을 빼고 넣는다. 비어 있으면 품종과 그 뒤 공백을 뺀다(`15번 8,000원 홍길동님 구매 감사합니다`). 품종 안의 공백은 그대로다(`18번 방울복랑 금 15,000원 …`).
  - 구매자 = 확정되는 순간의 표시 이름(유튜브는 그때까지 받은 가장 최근 닉네임, 문자찜은 항상 "문자찜" — YT-04 AC1).
  - 세부 (D-057): 이름은 그 찜의 구매자 자신으로 정하고 합치기와 상관없다 — 유튜브 채널의 찜(채팅·메시지 변환·유튜브 구매자에게 배정)은 그 채널의 가장 최근 닉네임, 문자 구매자의 찜과 `sms`로 생긴 찜(지정 구매자가 유튜브 채널이어도)은 항상 `문자찜`. 합친 상대의 표시 이름(`문자찜(메모)`의 메모 등)이 공개 메시지에 나가지 않게 한다.
  - 두 대상(`LIVE_CHAT`·`VIDEO_COMMENT`)의 문구는 같다. 글자 수 제한은 게시하는 쪽(S11)이 다룬다.
- **확정이 풀릴 때**(취소·무효·역전·교체·충돌 바꾸기·번호 변경):
  - 그 찜의 미실행 효과는 취소(`SKIPPED`)한다. 엔진 상태에서는 "취소됨"으로 남긴다(골든 관찰 상태 `CANCELLED`). `SKIPPED`는 outbox가 실행 직전에 건너뛴 것이다.
  - 이미 출력된 라벨(`effect.labelPrinted` 기록)이 있으면 `VOID_LABEL`을 낸다. `VOID_LABEL`의 확정버전은 폐기할 라벨의 확정버전이다. 상품 키도 폐기할 라벨의 것이다 — 효과의 상품 키·문구는 효과가 나온 때의 것이고 번호를 바꿔도 바뀌지 않는다(D-056). `VOID_LABEL`에는 엔진 보고 이벤트가 없다 — 폐기 표시의 실행 기록은 서버 출력 대기열이 그 라벨 키(찜, 확정버전)에 남기고(LABEL_RULES L-11 5), 엔진에서는 실행 대상으로 계속 남는다(판정·잠금에 쓰이지 않는다, D-I1-02).
  - 이미 게시된 감사 메시지는 지우지 않는다.
  - 차단(R-9)은 확정을 풀지 않는다.
- **효과 보고** (`effect.labelPrinted`·`effect.thanksSent`, D-044): 효과 ID로 가리킨다.
  - 실행 대상인 효과는 실행 완료가 되고, 그 효과가 지금 확정(확정버전)의 것이면 잠금이 걸린다(R-7.3). 잠금은 확정 하나에 대한 것이라, 같은 찜이 나중에 다시 확정되면 새 효과의 보고나 `host.confirm`이 있어야 다시 잠긴다.
  - 이미 완료된 효과의 보고는 아무 일도 없다 (INV-11).
  - 취소된 효과의 늦은 보고(취소 직전에 이미 실행됨)는 실행 완료로 기록하되 잠금은 걸지 않고, 라벨이면 `VOID_LABEL`을 낸다(잘못된 구매자 이름의 라벨이 남지 않게).
  - 모르는 효과 ID는 아무 일도 없다.
- 실행 직전에 찜이 더 이상 확정이 아니면 효과는 `SKIPPED`.
- 게시 실패는 판매 상태를 바꾸지 않는다. 재시도는 지수 백오프로 최대 N회, 이후 수동 재전송.
  - 세부 (Y1, D-Y06): 2·4·8·16·32초 뒤 최대 5번. 자동 게시는 판매자의 게시 동의(대상마다, 효과가 나온 때 기준)가 있을 때만, 효과가 나온 뒤 실시간 채팅 10분·영상 댓글 24시간 안에만 한다. 게시 성공은 서버가 효과마다 `effect.thanksSent`로 보고한다(묶음이어도 효과마다).
- **응답 유실 대비**: 유튜브 게시 요청이 타임아웃되면 바로 재시도하지 않는다. 먼저 최근 채팅에서 우리 채널이 같은 문구를 이미 올렸는지 확인한다.
  - 세부 (Y1 후속, D-Y1-03·D-Y1-06): 다른 게시가 이미 자기 것으로 가진 메시지는 고르지 않고, 같은 문구가 여럿이면 효과 순서대로 짝짓는다. 재시도는 확인 시간(30초)이 끝난 뒤의 조회로도 그 문구를 못 찾았을 때만 한다. 조회가 실패해 끝내 확인하지 못하면 재시도하지 않고 실패(확인 필요)로 남겨 판매자가 수동 재전송을 고른다 — 이중 게시보다 누락이 안전하다. 게시 보고는 하지 않는다.
  - 세부 (I3, D-I3-17): "못 찾음"(재시도)은 그 시도 뒤에 올라온 우리 채널의 글을 **모두 본** 조회일 때만이다 — 다 보지 못한 조회(다음 쪽이 남음 등)는 확인하지 못한 조회로 센다. 게시·조회는 그 방송을 이은 채널의 연결로만 한다. 확인하지 못한 감사를 판매자가 유튜브에서 보고 "올라가 있어요"로 적으면 그때 효과마다 게시 보고(`effect.thanksSent`, 조치자는 그 판매자 계정)를 기록한다(D-I3-05).
- 묶음 감사(`batchWindowSec>0`)는 창 안의 효과를 모아 한 메시지로 보낸다. 묶음 안 효과들은 하나의 게시 결과를 공유한다.
  - 세부 (Y1, D-Y07): 각 효과 문구에서 끝의 ` 구매 감사합니다`를 뗀 것을 `, `로 잇고 끝에 ` 구매 감사합니다`. 메시지 하나는 200자까지, 넘으면 효과 경계에서 나눈다. 묶음을 보내기 직전에 확정이 풀린 효과는 뺀다. 방송 후 요약(`SUMMARY`)은 엔진 효과가 아니라 서버가 방송을 끝낸 뒤 만드는 댓글 하나다(D-Y08).
- **인스타그램 회차의 감사** (N2, D-N2-09·D-N2-10): 엔진 효과는 같다(`POST_THANKS(LIVE_CHAT)` — 찜마다 하나, 문구 같음). 실행하는 쪽이 공개 글 대신 **그 찜을 만든 댓글**(채팅 주문·메시지 변환 찜의 메시지)에 개인 답장(DM)을 보낸다. 댓글 하나에 DM 하나 — 같은 댓글의 기다리는 감사는 한 DM으로 모으고(같은 이벤트에서 나온 효과는 늘 함께), 그 댓글로 이미 DM을 보냈으면 뒤 감사는 보내지 않는다. 그 찜을 만든 댓글이 없으면(문자찜·직접 배정) 보내지 않는다(건너뜀). `VIDEO_COMMENT`·방송 후 요약·`batchWindowSec`은 인스타그램 회차에 쓰지 않는다. 보내면 효과마다 `effect.thanksSent`(잠금), 실패는 판매 상태를 바꾸지 않는다.

## R-14. 금액 해석 (빠른 입력·음성 공용, D-029)

애매한 금액은 추측하지 않고 실패(`null`)로 돌려 다시 묻는다. 잘못된 가격이 등록되는 것보다 한 번 더 입력하는 편이 안전하다. 사례: `tests/golden/parser/amount.yaml`.

1. **정규화**: R-3과 같다(앞뒤 공백 제거, 전각 숫자→반각, 연속 공백 1칸). 빈 문자열은 실패.
2. **`원`**: 맨 끝에 한 번만 올 수 있다(앞 공백 허용: `만 원`). 원 단위라는 표시일 뿐 값은 바꾸지 않는다.
3. **숫자 형식**: 숫자만(`10000`) 또는 천 단위 쉼표 묶음(`10,000`), 뒤에 소수점 아래 숫자 허용(`7.5`).
   - 쉼표 묶음이 틀리면 실패(`10,00`, `1,0000`). `0`이 아닌데 0으로 시작하면 실패(`0500`). 숫자 사이 공백은 잇지 않는다(`10 000` 실패).
   - 단위: `원`이 붙으면 원. 없으면 `price.unit`을 따른다. `WON`은 원, `THOUSAND`는 값이 1000 미만이면 ×1000(천원 단위), 1000 이상이면 원 그대로 (D-007).
4. **한글 단위 형식**: 단위는 `십`·`백`·`천`·`만`. 큰 단위부터 한 번씩: `[계수]만 [계수]천 [계수]백 [계수]십 [일의 자리]`.
   - 계수를 빼면 1이다(`만원` = 10,000, `천원` = 1,000).
   - 천·백·십의 계수: 숫자 `1`~`9` 또는 한글 `일`~`구`. 일의 자리는 한글 `일`~`구`만.
   - 만의 계수: 숫자 1~4자리(`12만`) 또는 만 미만의 한글 단위 표현(`십이만`, `백만`, `천만`, `1천2백만`). 만의 계수 안에는 공백이 없다.
   - 계수는 단위에 붙여 쓴다. 단위 묶음 사이 공백은 허용한다(`이만 오천 원`, `만 이천 오백 원`).
   - **숫자는 단위 바로 앞(계수)에만 쓴다.** 단위 뒤에 단위 없는 숫자가 오면 실패한다(`1만5`, `1만 500`, `2천500`) — `만오`(15,000) 같은 줄임말인지 글자 그대로(10,005)인지 애매하기 때문이다. 예외: 만 뒤의 정확히 네 자리 숫자(`1만 2500원`, `1만 2,500원` = 12,500).
   - **한글 일의 자리(`일`~`구`)는 앞에 단위가 없거나 바로 앞 단위가 `십`일 때만 쓴다** (D-032). 바로 앞이 `만`·`천`·`백`이면(공백을 사이에 두어도) 실패한다: `만오`, `만 오`, `이만오`, `천오`, `삼천오`, `오천오 원`, `백오`, `1천오`, `1만 오`, `만오천오`, `백만오`. 같은 이유다 — 현장에서 `만오`는 15,000, `삼천오`는 3,500을 뜻하는 일이 많아 글자 그대로(10,005·3,005) 읽으면 틀린 가격이 등록된다. 만의 계수 안에서도 같다(`백오만` 실패, `십오만` = 150,000, `오만` = 50,000). 받는 예: `오`(5), `십오`(15), `오십오`(55), `백오십`(150), `만십오`(10,015), `만오백`(10,500), `천오백`(1,500). 숫자 계수(`105만`)와 R-15 번호에는 적용하지 않는다.
   - 소수 계수는 단위가 하나뿐일 때만 쓴다(`1.5만`, `1.25만`, `1.5천`, `0.5만`). `1.5만5천`은 실패.
   - 순서가 거꾸로이거나 같은 단위가 두 번 나오면 실패(`5천 1만`, `1만 1만`). `억` 이상은 지원하지 않는다(실패).
   - 한글 단위가 있으면 `price.unit`을 무시한다.
5. 그 밖의 글자·부호(`-`, `+`, `공짜`, 금액 뒤 `이요`)가 있으면 실패.
6. 결과는 0 이상의 정수 원이다. 원 단위 소수가 남거나(`1.5`(WON), `1.23456만`) `Number.MAX_SAFE_INTEGER`를 넘으면 실패.
7. 이 함수는 해석만 한다. 가격 하한 같은 유효성은 쓰는 쪽(R-16)이 본다.

## R-15. 한글 수사 (음성 번호용, D-029)

상품 번호를 말로 한 것을 정수로 바꾼다. 결과는 1..9999 또는 `null`. 사례: `tests/golden/parser/amount.yaml`의 `korean-number`.

- 입력 전체가 수 하나여야 한다. 뒤에 `번`(앞 공백 허용)이 붙어도 된다.
- 숫자 1~4자리(선행 0 허용, `015번` → 15).
- 한자어 수사: `천`·`백`·`십` 단위와 `일`~`구`, 큰 단위부터 한 번씩(`백이십삼`, `구천구백구십구`). 단위 앞 `일`은 생략할 수 있다. 번호는 글자 그대로 읽는다: R-14 4의 "단위 바로 뒤 한글 일의 자리" 실패 규칙(D-032)은 여기에 적용하지 않는다(`백이` → 102, `백오` → 105, `천오번` → 1005). 방 번호·상품 번호는 `백오호`처럼 글자 그대로 부르는 것이 보통이기 때문이다.
- 고유어 수사 1~99: 십의 자리 `열` `스물` `서른` `마흔` `쉰` `예순` `일흔` `여든` `아흔`, 일의 자리 `하나/한` `둘/두` `셋/세` `넷/네` `다섯` `여섯` `일곱` `여덟` `아홉`의 조합(`열다섯`, `스물다섯`, `아흔아홉`). `스무`는 단독으로 20.
- 실패: 0(`영`, `0`), 9999 초과(`만`, `10000`), 숫자 하나씩 읽기(`일오`, `오오`), 같은 단위 반복(`십십`), 한자어·고유어 섞기(`백열다섯`), 다른 글자가 섞임.

## R-16. 빠른 입력 한 줄 (PRD-01, D-030)

애매하면 등록하지 않고 오류를 돌려준다. 화면은 오류에 담긴 번호·품종을 채운 채 고칠 칸으로 커서를 보낸다(PRD-01 AC3). 사례: `tests/golden/parser/quick-input.yaml`.

1. **정규화**: R-3과 같다. 공백뿐이면 `EMPTY`.
2. **나누기**: 공백으로 토큰을 나눈다. 번호 바로 뒤에 `/`가 오면(`15/핑크프릴/10`) 그 줄의 `/`를 모두 공백으로 본다. 그 밖에는 `/`도 품종 글자다(`15 핑크/블루 10`).
3. **번호**: 첫 토큰. 숫자 1~4자리(선행 0 허용)에 `번`을 붙여 쓰거나, 다음 토큰이 `번` 하나이면 번호에 붙는다(`15 번 핑크프릴 10`).
   - 첫 토큰이 숫자로 시작하지 않으면 `NUMBER_MISSING`.
   - 숫자로 시작하지만 번호 형식이 아니거나(`15.5`) `1..claim.maxNumber` 밖이면(`0`, `1000`) `NUMBER_INVALID`. 채팅으로 찜할 수 없는 번호(R-3)의 상품은 만들지 않는다.
4. **가격**: 번호 뒤 토큰 중, 끝에서부터 R-14로 해석되는 가장 긴 연속 토큰 묶음(`1만 5천` → 15,000). 그 앞 토큰들을 공백 하나로 이은 것이 품종이다(없으면 `""`).
   - 해석되는 묶음이 없으면 `PRICE_MISSING`. 품종 = 번호 뒤 전부(`15 핑크프릴 공짜` → 품종 "핑크프릴 공짜").
   - **금액 조각** (D-048): 가격 묶음 바로 앞 토큰이 띄어 쓴 한 금액의 앞부분일 수 있으면 어디서부터 가격인지 애매하므로 `PRICE_MISSING`이다(품종 = 번호 뒤 전부). 그 토큰이 금액 글자(숫자, 한글 숫자 `일`~`구`, 단위 `십`·`백`·`천`·`만`)와 쉼표·점으로만 되어 있고(금액 글자 하나 이상) 다음 중 하나일 때다.
     - 한글 숫자로 끝나지 않는다(단위·숫자·쉼표·점으로 끝난다): `15 핑크프릴 1만 500`(`500`만 가격으로 떼면 50만 원), `15 핑크프릴 5 만`, `15 핑크프릴 1 500`, `15 핑크프릴 1.5 만`, `15 핑크프릴 5천 1만`
     - 한글 숫자로 끝나고 가격 묶음이 단위 글자로 시작한다(계수와 단위를 띄어 씀): `15 핑크프릴 오 천`, `15 핑크프릴 이만오 천`
     - 한글 숫자로 끝나고 가격 묶음이 숫자·한글 숫자로 시작하면 한 금액으로 이을 수 없으니 애매하지 않다: `15 천사 5천` → 품종 "천사", 5,000원. `15 핑크 오 10` → 품종 "핑크 오", 10,000원.
   - 가격이 100원 미만이면(0원 포함, 단위 설정과 무관) `PRICE_TOO_LOW`.
5. **품종**: 공백 정리 말고는 바꾸지 않는다. 이스케이프는 화면이 한다(NFR-06).
6. **결과**: 성공은 정확히 `{ no, name, price }`. `EMPTY`·`NUMBER_MISSING`·`NUMBER_INVALID`는 `error`만. `PRICE_MISSING`·`PRICE_TOO_LOW`는 `error`·`no`·`name`.

## R-17. 음성 문장 추출 (VOC-02·VOC-03, P2, D-202·D-203, I4 보강 D-I4-01)

방송자가 말한 문장 하나(음성 인식의 최종 결과 하나)에서 번호·품종·가격을 뽑는다. 결과는 바로 등록하지 않고 제안 카드로 확인받는다(VOC-04, D-204). **애매하면 그 칸을 비운다(`null`)** — 틀린 값을 채우는 것보다 빈칸이 안전하다. 순수 함수이고 어떤 문자열에도 예외를 던지지 않는다. 사례: `tests/golden/parser/voice-extract.yaml`.

- 입력: 문장, `claim.maxNumber`, 품종 사전(이름 목록 — 아래 5). 결과: 정확히 `{ no, name, price, confidence }`. `no`·`name`·`price`는 값 또는 `null`, `confidence`는 `HIGH`/`LOW`.

1. **토큰**: R-3과 같이 정규화하고(앞뒤 공백 제거, 연속 공백 한 칸, 전각 숫자 → 반각) 공백으로 나눈다. 정규화한 문장이 300글자(코드 포인트)를 넘으면 아무것도 뽑지 않는다(전부 `null`, `LOW`) — 인식 결과 하나가 그렇게 길면 여러 상품 이야기가 섞였을 가능성이 크고 계산이 길어진다. 토큰 끝의 문장 부호 `.` `,` `?` `!` `~`는 모두 지우고, 지워서 빈 토큰은 버린다. 그 밖의 글자는 바꾸지 않는다.
2. **끝말**: `이에요` `예요` `에요` `입니다` `이요` `이고` `이랑` `하고` `짜리` `에는` `은` `는` `이` `가` `을` `를` `에` `엔` `도` `요` `랑`. 토큰의 **읽는 모양** = 토큰 그대로, 그다음 토큰이 끝말로 끝나면 그 끝말 하나를 뗀 모양(남는 글자가 있을 때만, 짧은 끝말부터). 끝말은 한 번만 뗀다.
3. **번호**: 번호 표시는 두 꼴이다 — 토큰의 읽는 모양 하나가 `X번`(붙여 씀), 또는 토큰 `X`(그대로) 바로 다음 토큰의 읽는 모양 하나가 `번`(띄어 씀, 두 토큰이 표시 하나).
   - `X` = 숫자 1~4자리, 또는 한자어 수사 글자(`일`~`구`·`십`·`백`·`천`)로만 된 글. 값은 R-15로 읽는다(R-15가 `null`이면 표시가 아니다). 고유어 수사(`한 번`·`두 번`·`열다섯 번`)는 횟수와 구별할 수 없어 받지 않는다. `X`가 `이` 한 글자이면 표시가 아니다(`이번`·`이번에` = '이번', `이 번`도 같다).
   - `번째`처럼 `번` 뒤에 끝말 밖의 글자가 붙으면 표시가 아니다.
   - **끊어 말한 번호** (I4, D-I4-01): 번호 표시의 `X` 바로 앞 토큰(붙여 쓴 꼴은 표시 토큰의 앞 토큰, 띄어 쓴 꼴은 `X` 토큰의 앞 토큰 — 둘 다 토큰 그대로)을 `X` 앞에 공백 없이 붙인 글이 R-15로 읽히면, 번호를 끊어 말했거나 인식이 번호를 갈랐을 수 있다(`1` `5번` → `15`, `십` `오번` → `십오`, `이` `십` `번` → `이십`, `백` `오번` → `백오`, `이` `십오번` → `이십오`). 그런 표시가 **하나라도** 있으면 그 문장의 `no`와 `price`를 모두 `null`로 둔다(그래서 `LOW`, 자동 확정 없음). 품종은 평소대로 고른다. 앞 토큰을 붙인 글이 R-15로 읽히지 않으면 해당 없다(`이 15번` → `이15`, `네 15번` → `네15`는 수가 아니므로 15번 그대로).
   - 문장의 번호 표시 값이 모두 같고(하나 이상) 그 값이 `1..claim.maxNumber` 안이고 끊어 말한 번호가 없으면 `no` = 그 값. 표시가 없거나, 서로 다른 값이 둘 이상이거나, 범위 밖이거나, 끊어 말한 번호가 있으면 `null`.
4. **가격**: R-14를 **원 단위**로 읽는다(`price.unit`과 상관없다 — 말로 하는 가격은 `천`·`만`·`원`을 붙이므로 천원 단위로 추측하지 않는다).
   - **가격 묶음**: 왼쪽 토큰부터, 번호 표시 토큰을 넣지 않고 이어진 토큰 1~6개를 본다. 마지막 토큰을 읽는 모양으로 차례로(그대로 먼저, 짧은 끝말부터) 바꿔 공백 하나로 이은 글을 R-14로 읽어 처음 읽히는 값이, 100원 이상이고 그 글에 `원`이나 한글 수·단위(`일`~`구`·`십`·`백`·`천`·`만`)가 있으면(숫자만 있는 `10000`·`10`은 아니다 — 개수·시각·번호일 수 있다) 묶음이 된다. 한 시작 토큰에서는 가장 긴 묶음 하나를 잡고 그 뒤 토큰부터 다시 본다. 없으면 다음 토큰부터 본다.
   - **금액 조각** (R-16의 D-048과 같은 취지): **금액 글자 토큰** = 숫자·`,`·`.`·`일`~`구`·`십`·`백`·`천`·`만`로만 된 토큰. 묶음의 읽은 글이 `십`·`백`·`천`·`만`으로 시작하고 바로 앞 토큰이 금액 글자 토큰이거나(`이 만원짜리` — 이만 원일 수도), 읽은 글이 `원`으로 끝나지 않고 바로 뒤 토큰이 금액 글자 토큰이면(`1만 500`) 애매하다. 이웃 토큰이 번호 표시나 다른 묶음에 속하면 보지 않는다.
   - 묶음 값이 모두 같고(하나 이상) 애매한 묶음이 없고 끊어 말한 번호(3)가 없으면 `price` = 그 값. 묶음이 없거나, 서로 다른 값이 둘 이상이거나(`만 원 하던 거 오천 원에`), 애매하거나, 끊어 말한 번호가 있으면 `null` — 번호 앞 조각이 가격으로 읽힐 수 있다(`백 오번 라울`의 `백` = 100원). 가격을 비워도 묶음 토큰은 품종 창에서 뺀다(5).
5. **품종**: 품종 사전에서 맞는 이름을 고른다. 사전에 없는 말은 품종으로 채우지 않는다(방송자의 말버릇·인사가 품종 칸에 들어가지 않게).
   - **사전**: 이름마다 R-3 정규화. 공백을 뺀 글자가 2글자 이상인 이름만 넣는다. 공백을 뺀 모양이 같은 이름은 앞에 적힌 하나만 둔다(판매 이력이 기본 사전보다 앞 — D-203).
   - **창**: 번호 표시 토큰과 가격 묶음 토큰을 뺀다. 남은 토큰이 이어진 덩어리(뺀 토큰에서 끊긴다) 안에서 이어진 토큰 1~4개 = 창. 창의 글 = 토큰을 공백 없이 이은 것이고, 마지막 토큰은 읽는 모양마다 따로 본다.
   - **유사도** = 1 − (자모 편집 거리 ÷ 긴 쪽 자모 수). 자모 = 공백을 지우고 유니코드 NFD로 푼 코드 포인트 하나(한글 음절은 초성·중성·종성 2~3개, 그 밖의 글자는 한 개). 편집 거리 = 넣기·지우기·바꾸기 각 1. 사전 이름은 공백을 뺀 모양으로 잰다. **유사도 0.8 이상**(= 거리 × 5 ≤ 긴 쪽 자모 수)만 후보다. 두 글이 모두 자모 4개 이하이면 정확히 같아야 맞는다(`로나` ≠ `로라`). 비교는 분수로 한다(부동소수점 오차 없이).
   - 모든 창·읽는 모양·이름 짝 가운데 유사도가 가장 높은 이름이 하나면 `name` = 그 이름(사전에 적힌 모양, R-3 정규화). 여럿이면 그중 하나가 나머지를 모두 품을 때(공백 뺀 글자로 부분 문자열 — `핑크프릴 금`은 `핑크프릴`을 품는다)만 그 이름, 아니면 `null`. 후보가 없으면 `null`.
6. **신뢰도**: `no`·`name`·`price`가 모두 있고 품종의 유사도가 1(사전 이름과 공백만 다름)이면 `HIGH`, 아니면 `LOW`. 자동 확정(설정, 기본 꺼짐)은 `HIGH`일 때만 한다(D-204).

## R-18. 상품 목록 가져오기 (PRD-05, I2, D-I2-09)

방송 전에 만든 상품 목록(번호·품종·가격)을 붙여 넣거나 파일로 올려 공개 전(`READY`) 상품으로 한꺼번에 등록한다. **애매한 줄은 등록하지 않고 그 줄의 문제로 알린다** — 빠진 줄은 한 번 더 넣으면 되지만, 틀린 번호·가격으로 등록된 상품은 판매 사고다(D-029·D-030과 같은 원칙). 해석은 순수 함수 하나가 하고 미리 보기와 등록이 같은 함수를 쓴다. 사례: `tests/golden/parser/product-import.yaml`.

- 입력: 글 하나(엑셀에서 복사한 표 = 탭으로 나뉜 줄, 또는 CSV 글), 그 방송의 설정 스냅샷 `price.unit`·`claim.maxNumber`, 그 방송에 이미 있는 상품 번호(판매 종료 포함 — R-2 `register`가 받지 않는 번호). 엑셀 파일(.xlsx)은 첫 시트의 행마다 칸 글 목록을 만들고(줄 번호 = 시트의 행 번호, 칸 글 만들기는 SPEC PRD-05 세부) 2의 정규화·빈 칸 지우기부터 같은 규칙을 쓴다.
- 결과: `{ header, rows }` — `header` = 머리글로 본 줄 번호 또는 `null`, `rows` = 상품 줄마다 줄 순서대로 등록할 값 `{ line, no, name, price }` 또는 문제 `{ line, error }`. 전체에 문제가 있으면 `{ error }` 하나.

1. **줄**: 글 맨 앞의 U+FEFF(BOM) 하나는 지운다. `\r\n`·`\n`·`\r`로 나눈다. 줄 번호는 1부터 빈 줄까지 센다. 빈 줄은 건너뛴다(문제 아님) — "빈 줄"은 2에서 칸을 나눌 수 있고 정규화한 칸이 모두 빈 줄이다(아무것도 없는 줄, 공백(R-3의 공백 — 탭 포함)만 있는 줄, 엑셀 빈 행을 CSV로 저장한 `,,` 줄, `"",,` 줄 — I2 마지막 감사, D-I2-21). 붙여 넣은 글·CSV·.xlsx 모두 같다(.xlsx의 칸이 모두 빈 행과 같은 결과). 건너뛴 줄은 머리글 판단(3)과 500줄(10)에 세지 않는다. 따옴표 문제로 칸을 나눌 수 없는 줄은 빈 줄이 아니다(`CELLS`).
2. **칸**: 줄에 탭이 있으면 탭으로, 없으면 쉼표로 나눈다.
   - 큰따옴표: 칸이 `"`로 시작하면 짝이 되는 `"`까지가 그 칸의 글이다 — 그 안의 `""`는 `"` 하나이고 탭·쉼표도 글자다. 닫는 `"` 바로 뒤에는 나누는 글자나 줄 끝만 온다. 닫히지 않거나 닫는 `"` 뒤에 다른 글자가 오면 그 줄은 `CELLS`. `"`로 시작하지 않는 칸의 `"`는 그냥 글자다(칸 앞에 공백이 있으면 따옴표가 아니다).
   - 칸마다 R-3과 같이 정규화한다(앞뒤 공백 제거, 연속 공백 한 칸 — 탭·줄바꿈도 공백, 전각 숫자 → 반각).
   - 넷째 칸부터 빈 칸은 지운다(엑셀에서 넓게 복사한 빈 열). 남은 칸이 정확히 셋(번호·품종·가격)이 아니면 `CELLS` — 둘이면 품종과 가격 중 무엇이 빠졌는지, 넷 이상이면 품종 안의 쉼표인지 알 수 없다.
3. **머리글**: 건너뛰지 않은 첫 줄의 첫 칸(정규화한 글)에 숫자 `0`~`9`가 하나도 없으면 그 줄은 머리글이다 — 등록하지 않고 `header`에 줄 번호를 적는다(칸 수는 보지 않는다 — 다만 따옴표 문제로 칸을 나눌 수 없는 줄은 머리글이 아니고 `CELLS`인 상품 줄이다). 머리글은 많아야 한 줄이고, 그 밖의 줄은 모두 상품 줄이다.
4. **번호** (첫 칸): 숫자 1~4자리(선행 0 허용)이고 `번`을 붙이거나 띄어 써도 된다(`15`, `015`, `15번`, `15 번`) — R-16 3과 같다. 그 밖의 모양(빈 칸·`15.5`·`십오`·5자리 이상)이거나 `1..claim.maxNumber` 밖이면 `NUMBER_INVALID`.
5. **같은 번호**: 칸 문제가 없고 번호가 읽힌 상품 줄끼리(그 줄의 품종·가격에 문제가 있어도) 같은 번호가 둘 이상이면 그 줄 모두 `DUPLICATE` — 어느 줄이 맞는지 알 수 없다. `015`와 `15번`은 같은 번호다.
6. **이미 있는 번호**: 그 방송에 그 번호의 상품이 있으면 `EXISTS`. 가져오기는 이미 있는 상품을 고치지 않는다(고치기는 한 개씩 묻는 화면 — PRD-01 AC4).
7. **품종** (둘째 칸): 정규화한 글 그대로. 비어도 된다(화면 "품종 미입력"). 정규화한 품종에 제어 글자(U+0000~U+001F·U+007F~U+009F — 탭·줄바꿈 같은 공백은 정규화로 이미 한 칸 공백이 되어 남지 않는다)가 있으면 `NAME_CONTROL`(I2 마지막 감사, D-I2-17 — 지우지 않고 그 줄을 등록하지 않는다. 라벨·확인서에 보이지 않는 글자가 찍히지 않게). 그다음 휴대폰 번호가 있으면(R-1 "판매자가 적는 칸의 휴대폰 번호"의 글 칸 판단 `containsPhoneRun`) `NAME_PHONE`.
8. **가격** (셋째 칸): 비면 `PRICE_MISSING`. R-14(`price.unit`)로 읽히지 않으면 `PRICE_INVALID`, 읽힌 값이 100원 미만이면(0원 포함) `PRICE_TOO_LOW` — R-16 4와 같다.
9. 한 줄의 문제는 위 순서(칸 → 번호 → 같은 번호 → 이미 있는 번호 → 품종(제어 글자 → 휴대폰 번호) → 가격)에서 처음 맞는 하나다. 문제가 없는 줄은 정확히 `{ line, no, name, price }`.
10. **전체**: 상품 줄이 하나도 없으면 `EMPTY`, 500줄(NFR-04 상품 500개)을 넘으면 `TOO_MANY` — 줄 결과를 내지 않는다.
11. **등록**: 판매자가 미리 보기에서 확인한 등록할 줄(문제가 없는 줄의 번호·품종·가격)만 줄 순서대로 `product.register`(`status: READY`, 재고 1)로 기록한다 — 한 요청, 한 트랜잭션. 등록하는 순간의 상태로 그 줄들을 4~8로 다시 검사해(그 사이 같은 번호가 등록됨 등) 하나라도 문제가 생겼으면 아무것도 기록하지 않는다(SPEC PRD-05 세부).

## R-19. 상품 옵션과 변형 (SPEC OPT-01~OPT-06, O0 초안 — 구현 O1·O2·O3, D-O-02~D-O-06·D-O-12·D-O-14)

> **구현 상태**: 엔진(코어)은 O1에서 이 절과 R-20을 구현한다. 골든은 `tests/golden/parser/comment-options.yaml`·`tests/golden/engine/23-o1-options.yaml`(O0 초안을 O1 시작 때 옮김 — D-O-01). 서버·화면은 O2, 라벨·문서는 O3이다.
> **다육 회귀 없음**: 판매 방식이 `STRICT`(기본)·`LOOSE`인 방송은 이 절과 R-20의 영향을 전혀 받지 않는다. 옵션 없는 상품의 수량 1 찜은 어느 방식에서도 지금 규칙 그대로 판정한다 — 옵션 방송에서 다른 것은 둘뿐이다: 판정 순위가 `ARRIVAL`만이고, 메시지 변환이 1등을 밀어내지 않는다(R-20 7). 기존 골든은 하나도 바뀌지 않는다.

**판매 방식** (D-O-02)
- `claim.parseMode=OPTIONS`(판매 규칙 설정표)인 방송을 **옵션 방송**이라 한다. 방송 시작 때 스냅샷으로 정하고 방송 중엔 바꾸지 않는다(설정 스냅샷 규칙 그대로).
- 옵션(`options`)·상품 별칭(`aliases`)·변형 재고(`stocks`)가 있는 `product.register`·`product.update`, 수량·옵션이 있는 `sms`·`host.assign`, `product.focus`·`host.resolveReview`·`host.dismissReview`는 옵션 방송에서만 받는다. 다른 방송이면 입력 오류다(서버가 기록하지 않는다 — 판매자에게 바로 알린다).
- 옵션 방송은 판정 순위 `ARRIVAL`만 쓴다. `claim.parseMode=OPTIONS`와 `contention.policy=RECEIVED_TIME`을 함께 적은 설정은 입력 오류다(설정값 범위). 그래서 옵션 방송에는 R-7의 자동 역전이 없다(메시지 변환은 아래 "1등을 밀어내지 않는다").

**옵션 모델** (D-O-04)
- 상품은 **옵션 항목**을 0~3개 가진다. 항목 = `{ name, choices }`. 항목 이름(예 `사이즈`·`색상`·`기종`·`무게`)은 1~10자, 한 상품 안에서 서로 다르다.
- **선택지** = `{ label, aliases?, price? }`. 한 항목에 1~20개.
  - `label`(표시 이름, 예 `M`·`흰색`·`아이폰 17 프로`·`500g`·`2호`)은 1~20자. `/`·`#`·제어 글자를 쓰지 않는다.
  - `aliases`(동의어·줄임말, 예 `엠`·`화이트`·`17프로`)는 선택지마다 0~10개, 각 1~20자, 같은 글자 제한.
  - `price`(가격 차이)는 정수 원, −1,000,000~1,000,000, 기본 0.
  - 숫자만으로 된 이름·별칭(`95`·`100`)도 된다 — 댓글에서 숫자를 옵션이 먼저 차지한다(R-20 4).
- **비교 글자**: 이름·별칭을 댓글과 비교할 때는 R-3 정규화 뒤 공백을 모두 빼고 영문을 소문자로 바꾼 글자로 본다(`17 Pro` = `17pro`). 한 상품 안에서 모든 선택지의 이름·별칭은 비교 글자로 서로 달라야 한다(다른 항목 사이도) — 같으면 그 등록·수정은 입력 오류다. 어느 항목의 어느 선택지인지 하나로 정해져야 하기 때문이다.
- **모든 항목은 필수**다. 선택하지 않아도 되는 항목은 두지 않는다 — 필요하면 판매자가 `없음` 같은 선택지를 만든다. 선택지가 하나뿐인 항목은 댓글에 없어도 그 선택지로 본다.
- **상품 별칭**(`aliases`, 0~10개): 상품 이름(`name`, 다육에선 품종) 외에 댓글에서 상품을 알아볼 말(예 `초코과자`·`초코`). 비교 글자 규칙은 위와 같다. 상품 이름·별칭·선택지 이름·별칭·항목 이름은 판매자가 적는 글 칸이다(R-1 휴대폰 번호 검사, 화면에선 늘 이스케이프).
- 상품 이름·별칭과 선택지 이름·별칭은 같은 글자여도 된다(댓글에선 상품 이름을 먼저 찾는다 — R-20 3).

**변형과 재고 단위** (D-O-03)
- **변형** = 상품 × (항목마다 선택지 하나)의 조합. 항목이 없는 상품은 변형이 하나(상품 자신)다. 한 상품의 변형은 100개까지(항목별 선택지 수의 곱).
- **변형 키** = `<방송>/<번호>#<선택지1>/<선택지2>…`(항목 순서, 이름 `label`). 예: `b1/21#M`, `b1/31#흰색/대형`. 항목이 없는 상품의 변형 키는 상품 키(`b1/11`)와 같다.
- **옵션 글** = 선택지 이름을 항목 순서대로 `/`로 이은 글(`흰색/대형`). 화면·감사 문구·라벨·확인서·판매대장이 이 글 하나를 쓴다.
- **재고는 변형마다 따로 센다.** `stocks`(변형 → 재고, 키는 옵션 글)에 적은 값, 적지 않은 변형은 `stock`(기본 1). 변형 재고는 0 이상 정수 — 0이면 그 변형은 처음부터 다 팔린 것과 같다(대기·품절, R-4). 옵션 없는 상품의 재고는 지금처럼 1 이상. `stock`은 옵션 상품에서도 1 이상이다(0은 `stocks`로만 적는다). `stocks`의 키는 그 상품(바꾼 뒤)의 변형 옵션 글이어야 하고, 옵션 없이 `stocks`를 쓰면 입력 오류다 (D-O1-03).
- **판정 단위는 변형이다.** R-4~R-10의 "상품 p"에 대한 확정·대기·승계 결정 필요 표시·대기 한도·충돌은 변형마다 따로다. 같은 상품의 다른 변형은 서로 영향을 주지 않는다(ORD-03 AC2와 같은 뜻). 상품 상태(`READY`·`HOLD`·`CLOSED`, 공개)와 번호 변경은 상품 전체에 걸린다.
- 판매 중인 상품의 상태: 모든 변형의 확정 수량이 재고와 같으면 `SOLD`, 아니면 `OPEN`. 변형마다도 `SOLD`/`OPEN`을 보인다. 상품이 판매 중이 아니면(`READY`·`HOLD`·`CLOSED`) 변형의 상태는 상품 상태와 같다 (D-O1-01).
- **찜의 키** (D-O1-02): 옵션을 가진 찜은 변형 키, 옵션이 없는 찜은 상품 키(옵션 없는 상품의 찜, 옵션 상품을 번호만으로 가리킨 보류 찜). 시청자 취소 요청(R-20 8)과 효과는 상품 키를 가진다(효과는 어느 찜의 효과인지 따로 안다).
- R-4 4번 줄(같은 구매자의 활성 찜)은 변형마다 본다 — 한 사람이 `M`과 `L`을 함께 살 수 있다. 같은 변형을 다시 쓰면 지금처럼 새 찜 없음(`DUPLICATE`)이다. 수량을 더하지 않는다.
- 확정버전(R-13)은 지금처럼 **상품마다** 센다(변형을 가리지 않는다).
- `close`(R-2)는 어느 변형에도 확정·대기 찜이 없을 때만 된다.

**가격** (D-O-05)
- 변형 단가 = 상품 가격 + 고른 선택지들의 가격 차이 합. 0 이상이어야 한다(아니면 그 등록·수정은 입력 오류).
- 찜의 가격 스냅샷은 **단가**(확정 시점의 변형 단가)이고, 찜에는 **수량**이 있다. 찜 금액 = 단가 × 수량. 정산 상품 합계(R-12)·INV-5는 찜 금액의 합이다. 모두 정수 곱과 합이라 소수가 생기지 않는다.
- 가격 변경(R-10)은 상품 가격이나 선택지 가격 차이를 바꾸는 것이다. `UNPAID_CLAIMS`면 입금 전 찜의 단가를 그 찜 변형의 새 단가로 바꾼다. 그 밖은 R-10 그대로.

**수량** (D-O-06)
- 찜마다 수량 q(1 이상 정수, 기본 1)가 있다. 수량은 옵션 방송에서만 1이 아닐 수 있다. 상한 `claim.maxQuantity`(기본 10, 1~99)는 댓글 인식(R-20)과 문자찜·직접 배정 입력 검사에 쓴다.
- **확정 수량** = 그 변형 확정 찜들의 수량 합. INV-1은 "확정 수량 ≤ 변형 재고"다. **남은 수량** = 재고 − 확정 수량.
- R-4 6번 줄은 "q ≤ 남은 수량이면 `CONFIRMED`"로 읽는다. 맞지 않을 때:
  - q = 1: 지금 규칙 그대로(7번 줄 대기, 8번 줄 품절).
  - q ≥ 2이고 0 < 남은 수량 < q: 찜을 만들지 않고 그 메시지(문자찜이면 그 입력)를 **확인 필요**(R-20 7, 사유 `STOCK_SHORT`)로 보낸다. 일부만 자동 확정하지 않는다 — "3개 주문했는데 2개만?"은 판매자가 구매자와 정할 일이다.
  - q ≥ 2이고 남은 수량 = 0: `REJECTED(SOLD_OUT)`. **수량 2 이상 찜은 대기하지 않는다** — 대기열에는 늘 수량 1 찜만 있어서, 자리가 비면 앞에서부터 한 명씩 채우는 지금 승계가 그대로 맞는다.
  - 승계 결정 필요 표시(R-4 5번 줄)가 있는 변형에 온 q ≥ 2 찜도 대기하지 않는다: 남은 수량이 0이면 품절, 아니면 확인 필요(`STOCK_SHORT`).
- **승계·재고 늘림**: 확정이 풀려 남은 수량이 k가 되면 R-8(`AUTO`)·R-10(재고 늘림)은 대기 1순위부터 순서대로 최대 k명을 확정한다(대기 찜은 모두 수량 1). `ASK`·`REOPEN`은 R-8 그대로다.
- **찜을 가리키는 방송자 조치**(`host.cancel`·`reject`·`promote`·`confirm`·`approveCancel`·`dismissCancel`·`reopen`, 효과 보고)는 옵션 상품이면 `options`로 변형을 고른다. 적지 않았는데 그 구매자의 그 상품 활성 찜이 하나뿐이면 그 찜이고, 둘 이상이거나 `reopen`이면 아무 일도 없다(맞지 않는 명령).
- 직접 배정(`host.assign`)에 수량·옵션을 적을 수 있다(옵션 방송, 옵션 상품이면 모든 항목 필수). "빈 자리" = 그 수량이 남은 수량 이하. 교체(`replace`)는 밀려나는 1등의 수량만큼 남은 수량에 더해 본다. 밀려나는 1등의 수량이 2 이상이면 `replaceTo=WAITLIST`는 아무 일도 없다(대기하지 않는다 — `CANCEL`을 쓴다). 교체 뒤에도 남은 수량이 있으면(밀려난 수량 > 배정 수량) 위 "승계·재고 늘림"을 그대로 적용한다 — 확정이 풀린 것과 같다 (D-O1-05).
- 문자찜(`sms`)에 `qty`·`options`를 적을 수 있다(옵션 방송). 상품이 있으면 옵션은 그 상품의 모든 항목이 맞아야 하고, 아니면 입력 오류다(판매자가 보낸 입력이므로 바로 알려 고치게 한다 — 조용히 버리지 않는다). 상품이 아직 없으면 번호·수량만 받아 보류(R-5)하고, 옵션을 함께 적었으면 입력 오류다("상품을 먼저 등록해 주세요").

**공개 전 찜** (R-5와 함께)
- 옵션 방송의 보류 찜은 수량과(있으면) 옵션을 가진 채 기다린다. 공개 순간 R-5를 변형마다 적용한다.
- 공개된 상품의 변형이 둘 이상인데 옵션이 없는 보류 찜(숫자만 쓴 댓글 `21`, 번호만 적은 문자찜)은 판정하지 않고 `REJECTED(OPTION_MISSING)`으로 끝내며 그 메시지·입력을 확인 필요(R-20 7, 사유 `OPTION_MISSING`)로 보낸다. 유효 시간(30초)을 넘긴 보류 찜은 지금처럼 만료다.

**옵션 바꾸기** (D-O-14)
- `product.update`의 `options`·`stocks`·`aliases`: 그 상품에 찜(어떤 상태든)이 하나도 없으면 옵션 전체를 바꿀 수 있다.
- 찜이 하나라도 있으면 옵션은 **선택지 더하기**(기존 항목 끝에, 새 변형은 `stocks` 또는 `stock`)와 **선택지 가격 차이 바꾸기**만 된다. 항목 더하기·빼기, 선택지 빼기·이름 바꾸기는 아무 일도 없다(판매자는 새 번호로 등록한다) — 찜이 가리키는 변형이 사라지거나 바뀌지 않게.
- 변형 재고 바꾸기는 R-10 재고 변경을 변형마다 적용한다(확정 수량보다 작게 하면 이벤트 전체가 아무 일도 없다).

**표시** (D-O-12 — 감사 문구는 O1, 라벨·문서는 O3)
- **감사 문구**(R-13): `{번호}번 {품종}[ {옵션 글}][ {수량}개] {찜 금액} {구매자}님 구매 감사합니다`. 옵션 글은 옵션이 있을 때만, 수량은 2 이상일 때만 넣는다. 예: `31번 수건 흰색/대형 2개 20,000원 홍길동님 구매 감사합니다`. 옵션 없는 수량 1 찜은 지금 문구와 글자까지 같다.
- **상품 라벨**(LABEL_RULES, O3): 찜 하나에 라벨 한 장(수량이 3이어도 한 장 — 묶음에 붙인다). 품종 자리에 `{품종} {옵션 글}`, 수량 2 이상이면 `{수량}개`, 가격 자리는 찜 금액. 긴 글은 L-5대로 줄이고 숫자 항목은 자르지 않는다.
- **확인서·영수증·공유 링크**(STL-04·RCP-02, O3): 품목 줄마다 번호·품종·옵션 글·수량·단가·금액(수량 1이면 지금 줄 모양 그대로).
- **판매대장**(STL-06, O3): 내보내는 기간에 옵션 방송이 하나라도 있으면 `옵션`·`수량`·`단가` 칸을 더한다(옵션 없는 찜은 빈칸·1·가격). 옵션 방송이 없으면 지금 칸 그대로.
- **포장**(STL-08·LBL-02, O3): 포장 모드 목록과 포장 라벨 항목은 `{번호}`[` {옵션 글}`][` ×{수량}`]. 같은 번호의 다른 변형은 다른 항목이다(무엇을 담을지 틀리지 않게).

## R-20. 댓글 옵션 인식 (SPEC CMT-01~CMT-07, O0 초안 — 구현 O1, D-O-07~D-O-11·D-O-13)

옵션 방송(R-19)에서 채팅(유튜브 채팅·인스타그램 댓글·틱톡 댓글) 한 줄을 **주문 / 취소 / 확인 필요 / 그 밖(언급)** 중 하나로 읽는다. **애매하면 주문이 아니다** — 자동 주문은 해석이 하나로 정해지고 모든 항목이 맞을 때만이다. 애매한 댓글 중 주문 같은 것은 확인 필요로 모아 판매자가 한 번에 고친다(D-006·D-036). 판정은 늘 규칙이 한다.

- 순수 함수 하나(코어 `parseOptionComment`): 입력 = 본문, 그 방송의 **상품 목록**(판매 종료가 아닌 상품마다 번호·이름·별칭·옵션 — 공개 전 상품 포함), **지금 상품**(아래 6)과 지금 상품이 정해진 뒤 지난 시간(그 채팅의 `at` − 지금 상품을 정한 이벤트의 `at`), 설정(`claim.maxNumber`·`claim.maxQuantity`). 시계·난수를 쓰지 않는다. 엔진은 R-4 4에서 `STRICT` 대신 이 함수를 부른다.
- 결과: `orders`(주문 — `{ no, options?, qty }` 목록), `cancels`(취소 번호), `review`(확인 필요 — `{ reason, no?, options?, qty? }` 하나), `mentions`(언급 번호). 많아야 하나만 비어 있지 않다.
- **방송자 본인 댓글·재수신·차단**은 R-4 그대로다.

**1. 정규화**: R-3과 같다(앞뒤 공백, 전각 → 반각, 연속 공백 한 칸). 이름 비교는 R-19 "비교 글자"(공백 빼기·영문 소문자).

**2. 번호 문법 먼저** (다육 방식과 같은 댓글은 같은 뜻): 메시지 전체가 R-3 `STRICT` 문법(주문·취소)이면 그 결과를 쓴다 — `claim.multiNumber`·번호 개수 상한·범위 규칙 포함.
- 주문 번호마다 수량 1, 옵션 없음. 그 번호의 상품이 변형 둘 이상이면 그 메시지 전체를 확인 필요(`OPTION_MISSING`, `no` = 그런 첫 번호)로 보낸다 — 다른 번호도 주문하지 않는다.
- 숫자만 있는 메시지(번호 하나)인데 그 숫자가 지금 상품(6)의 선택지 이름·별칭과 같으면(`100` — 사이즈 100) 확인 필요(`NUMBER_AMBIGUOUS`).
- 번호 상품이 아직 없으면 지금처럼 보류 찜(R-5). 공개 때 옵션이 필요하면 R-19 "공개 전 찜".
- 취소는 아래 8.

**3. 상품 찾기** (2에 맞지 않을 때): 한 메시지는 상품 하나만 주문한다. 해석 후보를 만든다.
- (가) **이름**: 메시지에서 상품 이름·별칭의 비교 글자와 같은 가장 긴 부분을 찾는다(겹치지 않게 왼쪽부터). 서로 다른 상품 둘 이상이 나오면 확인 필요(`MULTI_PRODUCT`). 가장 긴 부분이 서로 다른 두 상품의 이름·별칭이면 확인 필요(`PRODUCT_AMBIGUOUS`). 이름이 하나로 찾아지면 후보는 그것 하나다(맨 앞 숫자가 같은 상품의 번호면 함께 지운다. 다른 상품의 번호면 `MULTI_PRODUCT`).
- (나) **맨 앞 번호**: 이름이 없고 메시지가 `숫자{1,4}[번]` + 공백으로 시작하며 그 번호의 상품이 있으면 후보.
- (다) **지금 상품**: 이름이 없으면 지금 상품도 후보(그 앞 번호를 지우지 않은 채로).
- 아무 후보도 없으면 그 밖(언급).

**4. 후보마다 나머지 읽기** — 상품을 가리킨 부분을 지운 나머지에서 차례로:
1. **옵션 값**: 그 상품의 선택지 이름·별칭과 비교 글자가 같은 가장 긴 부분(겹치지 않게, 왼쪽부터). **옵션 사전이 숫자를 먼저 차지한다** — `17 프로`·`2호`·`500g`·`100`처럼 숫자가 든 선택지는 수량보다 먼저 옵션으로 읽는다. 단 숫자로 시작하거나 끝나는 부분은 정규화한 메시지(공백을 빼기 전)에서 앞뒤에 다른 숫자가 공백 없이 붙어 있으면 맞지 않는다(`1000` 안의 `100`은 아니다. `100 2`의 `100`은 맞다). 수량의 숫자도 앞뒤에 숫자가 붙지 않은 덩어리 전체여야 한다.
2. **수량**: 남은 것 중
   - 단위가 붙은 수: `숫자{1,2}` 또는 한글 `한`·`두`·`세`·`네`·`다섯`(1~5) 뒤에 단위 `개`·`봉`·`팩`·`병`·`통`·`장`·`벌`·`세트`·`박스`(띄어 써도 된다) — 메시지 어디에 있어도 된다.
   - 맨숫자 `숫자{1,2}`: **상품 이름이나 옵션 값 바로 뒤**(사이에 공백·구분자만)에 올 때만 수량이다(`초코 과자 3`, `흰색 대형 2`, `초코과자3`). 맨 앞의 맨숫자, 상품 번호 바로 뒤의 맨숫자는 수량이 아니다(`11 2`는 2의 번호 문법 — 11번·2번).
   - 수량은 하나만. 둘 이상이면 해석이 맞지 않는다.
3. **꼬리**: 맨 앞 `찜`, 끝의 R-3 꼬리말(`요`·`주세요`·`구매`…)과 꼬리 기호(허용 이모지 포함). 사이의 `,`·`/`·`·`는 구분자다.
4. 그 밖의 글자가 남으면 **남은 말**이다(공백으로 나눈 덩어리 수로 센다).

**5. 해석 고르기**
- 후보 해석이 **들어맞는다** = 남은 말이 없다(옵션이 빠졌거나 수량이 범위 밖이어도 들어맞을 수 있다). 지금 상품 후보는 옵션 값을 하나 이상 읽어야 들어맞는다(`3개`만으로는 지금 상품 주문이 아니다).
- 들어맞는 후보가 둘 이상이면 확인 필요(`NUMBER_AMBIGUOUS` — 예: 상품 100이 있고 지금 상품에 사이즈 `100`이 있을 때 `100 2개`).
- 하나면 그 해석을 검사한다(위에서 처음 맞는 것):
  1. 한 항목에 선택지 둘 이상(`흰색 검정`) → 확인 필요 `OPTION_CONFLICT`.
  2. 수량이 0 또는 `claim.maxQuantity` 초과 → 확인 필요 `QTY_INVALID`.
  3. 빠진 항목(선택지가 하나뿐인 항목은 빠진 것이 아니다) → 확인 필요 `OPTION_MISSING`.
  4. 지금 상품 후보이고 지금 상품이 정해진 지 **15초 미만** → 확인 필요 `FOCUS_CHANGED`(앞 상품을 보고 쓴 댓글이 늦게 왔을 수 있다).
  5. 통과 → 주문 `{ no, options, qty }`(수량을 안 썼으면 1).
- 들어맞는 후보가 없을 때: 이름(가)·맨 앞 번호(나)로 찾은 상품이 **옵션이 있는 상품**이고 남은 말이 **덩어리 하나**면 확인 필요 `UNKNOWN_WORD`(`반바지 XL` — 없는 사이즈). 그 밖(옵션 없는 상품, 남은 말 둘 이상, 지금 상품 후보뿐)은 그 밖(언급)이다.
- 확인 필요 결과에는 읽은 것(`no`, 읽은 옵션, 읽은 수량)을 담는다 — 판매자가 빈 칸만 고르면 되게.

**6. 지금 상품** (D-O-09): 방송마다 "지금 소개 중인 상품" 하나. 그 방송의 마지막 `product.register(OPEN)`·`product.open`·`product.focus`(R-1 새 이벤트 — 판매자가 콘솔에서 "지금 상품"을 누름)가 가리킨 상품이다. 그 상품이 판매 종료·일시 중지가 되면 지금 상품은 없다. 번호를 바꾸면 따라간다(정한 시각 그대로). 처음엔 없다. 세부 (D-O1-06): 이미 지금 상품인 상품을 다시 가리키면 아무것도 바뀌지 않는다(정한 시각 그대로 — 다시 눌렀다고 15초 유예가 다시 생기지 않는다). `product.focus`는 공개 전(`READY`) 상품도 가리킬 수 있다(그 상품의 옵션 댓글은 보류 찜이 된다). 없는 번호나 `HOLD`·`CLOSED` 상품을 가리킨 `product.focus`는 지금 상품을 없앤다(앞 상품으로 잘못 가지 않게).

**7. 확인 필요 대기열** (D-O-10)
- 확인 필요 결과·`STOCK_SHORT`(R-19)·공개 때 `OPTION_MISSING`(R-19)은 **찜을 만들지 않는다**(재고를 잡지 않고 효과도 없다). 엔진 상태에 항목으로 남는다: 항목 = (방송, 출처 = 메시지 ID 또는 `sms:<ref>`, 구매자, 사유, 읽은 것, 원래 순위 재료). 같은 출처는 하나만. 읽은 것 = 인식 결과의 번호·옵션·수량(못 읽은 것은 없음), 문자찜이면 판매자가 적은 번호·옵션·수량. `STOCK_SHORT`는 번호·옵션·수량을 모두 가진다. 항목의 순서는 원래 순위(출처 입력의 도착 순서)다 (D-O1-08·D-O1-10).
- 판매자 조치(R-1 새 이벤트, 사유 선택):
  - `host.resolveReview(출처, 번호, 옵션, 수량)`: 그 구매자의 찜을 만든다. 순위 재료와 `at`은 **원래 메시지(입력)의 것**이다. 번호의 상품이 그 방송에 없으면 입력 오류다. 상품이 판매 중(`OPEN`·`SOLD`)이 아니거나(`READY`·`HOLD`·`CLOSED` — 보류 찜을 만들지 않는다), 그 출처의 항목이 없거나, R-4 4번 줄(같은 변형에 그 구매자의 활성 찜)에 걸리면 아무 일도 없다(항목이 있으면 남는다, D-O1-04). 그 밖에는 R-4 1·5번 줄을 먼저 보고, 그다음 **1등을 밀어내지 않는다**: 수량 ≤ 남은 수량이고 그 변형에 순위가 앞선 대기자가 없으면 확정, 아니면 수량 1이면 대기 자리(R-4 "대기에 넣는 자리" — 넘치면 맨 끝 품절), 수량 2 이상이면 아무 일도 없다(항목이 남는다 — 화면이 남은 수량을 보인다). 찜이 생기면(대기·품절 포함) 항목이 사라진다. 옵션은 그 상품의 모든 항목이 맞아야 하고 아니면 입력 오류다.
  - `host.dismissReview(출처)`: 주문이 아닌 것으로 정하고 항목을 지운다.
  - 항목은 방송이 끝나도 남는다. 판매 종료된 상품을 가리킨 항목은 그대로 두고 판매자가 지운다.
- 옵션 방송의 `host.convertMessage`(언급 메시지를 찜으로 바꾸기)는 옵션 없는 상품에만, 수량 1로 되고(옵션 상품을 가리키거나, 그 메시지가 확인 필요 항목이면 아무 일도 없다 — 확인 필요는 바로잡기로 고친다, D-O1-07), 위와 같이 **1등을 밀어내지 않는다**(충돌을 만들지 않는다 — R-7 4 대신). 옵션·수량이 필요하면 판매자는 직접 배정(`host.assign`, R-19)을 쓴다.
- 확인 필요 항목 수는 상한이 없다. 화면은 오래된 순(원래 순위)으로 보이고, 읽은 상품·옵션을 먼저 채워 둔다(O2).

**8. 시청자 취소** (D-O-13): 옵션 방송의 취소 문법은 R-3 그대로(`15 취소` — 번호 하나). 대상은 그 채널 자신의 그 상품 활성 찜(모든 변형)이다. 하나면 R-8 그대로, 둘 이상이면 `cancel.buyerChat`이 `AUTO`여도 요청(`REQUEST`)으로 둔다(어느 변형인지 판매자가 고른다). `취소`가 들어 있는 다른 메시지는 주문도 확인 필요도 아니다(언급).

**9. 늘 주문이 아닌 것**: 질문 기호(`?`·`？`·❓·❔·⁉)가 어디에든 있는 메시지, 금액 덩어리(R-3 — `12,000`·`1.5`)가 있는 메시지는 주문도 확인 필요도 아니다(언급). 언급 번호는 R-3 "언급" 규칙 그대로다.

**10. 유사도·AI 자리** (D-O-11)
- 이름이 비슷한 말(오타 `반바치`)은 **자동으로 맞추지 않는다**. 비슷함(편집 거리 등 결정적 계산)은 확인 필요 화면의 후보 제안에만 쓴다.
- LLM 보조는 나중에 서버 어댑터(`CommentAssist`)로 둔다: 확인 필요 항목에 "이렇게 읽은 것 같아요" 제안(번호·옵션·수량)만 붙인다. 판매자가 고르기 전엔 아무 이벤트도 만들지 않고, 이벤트 로그에는 판매자의 `host.resolveReview`만 남는다. 기본 꺼짐, 켤 때 댓글 글이 바깥 서비스로 간다는 동의를 받는다. 엔진(`packages/core`)은 이 제안을 모른다.

**11. 업종 템플릿** (D-O-16): 의류(사이즈 S~XL·95~110, 색상), 휴대폰 케이스(기종 — 아이폰·갤럭시 모델과 줄임말), 식품(중량·용량·맛), 화분(1호~10호) 같은 묶음은 **상품 등록 화면이 채워 주는 기본 옵션·별칭**일 뿐이다. 판매자가 고치면 그 상품의 옵션이 된다. 엔진·인식 함수는 템플릿을 모른다(상품에 저장된 옵션만 본다) — 템플릿을 바꿔도 지난 판정이 바뀌지 않는다.

## 불변식 (속성 테스트로 검사)

| ID | 불변식 |
|---|---|
| INV-1 | 모든 상품에서 확정 찜 수 ≤ 재고 (중복 판매 없음) |
| INV-2 | 한 구매자(지금의 구매자, R-11)는 한 상품에 활성 찜(확정·대기·보류·충돌)을 최대 1개 가진다 |
| INV-3 | 같은 외부 메시지 ID(문자찜은 `ref`, 방송 시작은 방송 ID — D-070)를 다시 넣어도 상태가 바뀌지 않는다 |
| INV-4 | 이벤트 로그 재생 결과 = 저장된 현재 상태 |
| INV-5 | 구매자(지금의 구매자) 상품 합계 = 그 구매자 확정 찜 가격 스냅샷의 합 |
| INV-6 | 모든 금액은 0 이상의 정수 (조정 항목만 음수 가능) |
| INV-7 | 상품별 대기 순번은 1..n으로 빈틈없이 이어진다 |
| INV-8 | `ARRIVAL` 정책에서 확정 찜은 방송자 조치(취소·무효·교체·충돌 해결·번호 변경·시청자 취소 승인)나 방송자가 켠 시청자 자동 취소(`cancel.buyerChat=AUTO`, 잠금 전) 없이는 확정에서 풀리지 않는다 (D-047). 구매자 합치기·상품 수정·정산 기록은 확정을 풀지 않는다 (D-055, D-057) |
| INV-9 | 취소·거절·중복 찜은 어떤 합계에도 들어가지 않는다 |
| INV-10 | 잠긴 확정 찜은 방송자 조치(취소·무효·교체·충돌 해결·번호 변경·시청자 취소 승인) 없이 확정에서 풀리지 않는다 (D-047) |
| INV-11 | 효과 ID마다 실행 성공은 최대 1번 |
| INV-12 | 어떤 외부 메시지의 첫 수신 이후 위치에 그 메시지 사본을 몇 개 끼워 넣어도(재수신) 결과가 같다 |

- 옵션 방송(R-19, O1부터): INV-1·INV-2·INV-7의 "상품"은 **변형**이고, INV-1의 "확정 찜 수"는 **확정 수량**(확정 찜 수량의 합)이다. INV-5의 "가격 스냅샷의 합"은 **찜 금액(단가 × 수량)의 합**이다. 더해: INV-O1 대기 찜의 수량은 늘 1이다. INV-O2 확인 필요 항목은 재고·합계·효과에 들어가지 않는다. 옵션 없는 상품의 수량 1 찜에서는 모두 지금 문장과 같다.
